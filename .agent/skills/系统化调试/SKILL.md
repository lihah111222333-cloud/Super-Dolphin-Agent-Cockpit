# 系统化调试

## 概览

随意修复会浪费时间并制造新 bug。快速补丁会掩盖底层问题。

**核心原则：** 尝试修复前始终先找到根因。只修症状就是失败。

**违反这个流程的字面要求，就是违反调试精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你还没有完成阶段 1，就不能提出修复。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间压力下（紧急情况会诱使你猜测）
- “就快速修一下”看起来很明显
- 你已经尝试过多个修复
- 上一个修复没有奏效
- 你没有完全理解问题

**不要在以下情况跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你很赶时间（匆忙保证返工）
- 经理要求现在就修好（系统化比乱试更快）

## 四个阶段

进入下一阶段前，你必须完成当前阶段。

### 阶段 1：根因调查

**尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含精确解决方向
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 能否可靠触发？
   - 精确步骤是什么？
   - 是否每次都发生？
   - 如果不可复现 → 收集更多数据，不要猜

3. **检查最近变更**
   - 哪些变更可能导致这个问题？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件（CI → build → signing，API → service → database）时：**

   **提出修复前，添加诊断性仪表：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误位于很深的调用栈中：**

   查看本目录中的 `root-cause-tracing.md`，了解完整的向后追踪技术。

   **快速版本：**
   - 坏值从哪里产生？
   - 是谁用坏值调用了这里？
   - 继续向上追踪，直到找到来源
   - 在来源修复，而不是在症状处修复

### 阶段 2：模式分析

**修复前先找到模式：**

1. **寻找可工作的示例**
   - 在同一代码库中定位相似的可工作代码
   - 与坏掉部分相似的可工作内容是什么？

2. **对照参考实现**
   - 如果在实现某种模式，完整阅读参考实现
   - 不要略读：逐行阅读
   - 完全理解模式后再应用

3. **识别差异**
   - 可工作版本与损坏版本有什么不同？
   - 列出每个差异，无论多小
   - 不要假设“那不可能有影响”

4. **理解依赖**
   - 它还需要哪些组件？
   - 需要什么设置、配置、环境？
   - 它依赖哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚说明：“我认为根因是 X，因为 Y”
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做能测试假设的最小变更
   - 一次只改变一个变量
   - 不要一次修多件事

3. **继续前验证**
   - 成功了吗？是 → 阶段 4
   - 没成功？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 请求帮助
   - 继续研究

### 阶段 4：实现

**修根因，不修症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 能自动化就写自动测试
   - 没有框架就写一次性测试脚本
   - 修复前必须拥有
   - 使用 `superpowers:测试驱动开发` 技能编写合格的失败测试

2. **实现单一修复**
   - 解决已识别的根因
   - 一次只做一个变更
   - 不做“顺手”改进
   - 不夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 是否没有破坏其他测试？
   - 问题是否真的解决？

4. **如果修复无效**
   - 停止
   - 计数：你尝试了多少个修复？
   - 如果 < 3：回到阶段 1，带着新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 不要在没有架构讨论的情况下尝试第 4 个修复

5. **如果 3 个以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都在不同地方暴露新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每个修复都会在别处制造新症状

   **停下并质疑基本前提：**
   - 这个模式本质上是否可靠？
   - 我们是不是“纯靠惯性坚持它”？
   - 是应该重构架构，还是继续修症状？

   **尝试更多修复前，先与你的协作者讨论。**

   这不是失败的假设，而是错误的架构。

## 红旗：停止并遵循流程

如果你发现自己在想：
- “先快速修一下，以后再调查”
- “试着改 X 看看能不能行”
- “加多个变更，然后跑测试”
- “跳过测试，我会手动验证”
- “可能是 X，我来修它”
- “我不完全理解，但这也许能行”
- “模式说 X，但我换种方式适配”
- “主要问题如下：[列出没有调查支撑的修复]”
- 提出解决方案前没有追踪数据流
- **“再试一个修复” （已经尝试 2 个以上时）**
- **每个修复都在不同地方暴露新问题**

**这些都意味着：停止。回到阶段 1。**

**如果 3 个以上修复失败：** 质疑架构（见阶段 4.5）。

## 你的协作者发出的“你做错了”信号

**留意这些重定向：**
- “那没有发生吗？”：你在没有验证的情况下假设
- “它会让我们看到……吗？”：你本该添加证据收集
- “别猜了”：你在没有理解的情况下提出修复
- “Ultrathink this”：质疑基本前提，而不只是症状
- “我们卡住了吗？”（沮丧）：你的方法不起作用

**看到这些时：** 停止。回到阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题也有根因。流程对简单 bug 也很快。 |
| “紧急，没时间走流程” | 系统化调试比猜测-检查式乱试更快。 |
| “先试这个，再调查” | 第一个修复会定下模式。一开始就做对。 |
| “确认修复有效后再写测试” | 未测试的修复站不住。先写测试才能证明它。 |
| “一次做多个修复省时间” | 无法隔离哪个起作用，还会制造新 bug。 |
| “参考太长，我适配一下模式” | 部分理解必然产生 bug。完整阅读。 |
| “我看到问题了，我来修” | 看到症状 ≠ 理解根因。 |
| “再试一个修复”（2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 寻找可工作示例、比较 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或得到新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程揭示“没有根因”时

如果系统化调查表明问题确实是环境、计时相关或外部因素：

1. 你已经完成流程
2. 记录你调查过的内容
3. 实现合适处理（重试、超时、错误消息）
4. 添加监控/日志，便于未来调查

**但是：** 95% 的“没有根因”案例都是调查不完整。

## 支撑技术

这些技术属于系统化调试的一部分，并位于本目录：

- **`root-cause-tracing.md`**：通过调用栈向后追踪 bug，找到原始触发点
- **`defense-in-depth.md`**：找到根因后，在多层添加验证
- **`condition-based-waiting.md`**：用条件轮询替代任意超时

**相关技能：**
- **superpowers:测试驱动开发**：用于创建失败测试用例（阶段 4，第 1 步）
- **superpowers:完成前验证**：在声称成功前验证修复确实有效

## 真实影响

来自调试会话：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时乱试
- 首次修复成功率：95% vs 40%
- 引入新 bug：接近零 vs 常见
