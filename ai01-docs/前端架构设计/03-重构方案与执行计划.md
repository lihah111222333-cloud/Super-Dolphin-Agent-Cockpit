# 前端架构重构方案与执行计划

生成时间：2026-06-11

## 1. 总体目标

目标不是做表面目录调整，而是让前端形成长期可维护的工程边界：

- 页面负责组织页面级数据和布局。
- 展示组件只消费 props，不直接请求接口。
- Hooks 负责状态和副作用。
- Service 负责接口通信和请求语义。
- Adapter 负责 DTO 到 ViewModel 的转换。
- Store 只负责跨组件共享状态和全局业务动作，不承担所有页面业务细节。
- Utils 只放纯函数。
- 页面不直接依赖后端原始字段结构。

执行策略：

- 先落文档和守卫，再小步改代码。
- 优先处理 API 边界和低风险页面。
- 保持现有业务功能不变。
- 每个阶段都做 focused verification。
- 不修改 legacy `cmd/agent-terminal/frontend`。

## 3. API Service 设计

### 3.1 分层

目标调用链：

```txt
Page Component
  -> Page Hook
  -> Domain Service
  -> Domain Adapter
  -> shared/api/backendApi.js
  -> shared/api/wailsBridge.js
```

`backendApi.js` 继续保留为 RPC contract facade；新增 service 层提供 UI 语义。

### 3.2 `services/apiClient.js`

职责：

- 包装 service 层的统一请求入口。
- 归一化异常为 `ApiError`。
- 提供 `withRequestTimeout`、`toApiError`、`isAbortError` 等基础能力。
- 不直接调用 Wails runtime，只调用 `backendApi.js` 的具名 facade。

第一版保持简单，不引入新依赖。

建议接口：

```js
export class ApiError extends Error {
  constructor(message, options = {}) {
    super(message);
    this.name = 'ApiError';
    this.code = options.code || '';
    this.requestId = options.requestId || options.reqId || '';
    this.traceId = options.traceId || options.trace_id || '';
    this.cause = options.cause;
  }
}

export function toApiError(error, fallbackMessage = '请求失败') {
  if (error instanceof ApiError) return error;
  return new ApiError(error?.message || String(error || fallbackMessage), {
    code: error?.code,
    requestId: error?.requestId || error?.reqId,
    traceId: error?.traceId || error?.trace_id,
    cause: error,
  });
}

export async function runServiceRequest(fn, fallbackMessage) {
  try {
    return await fn();
  } catch (error) {
    throw toApiError(error, fallbackMessage);
  }
}
```

### 3.3 Domain Service

服务按领域拆分：

| Service | 职责 |
| --- | --- |
| `threadService.js` | thread list/state/messages/config/archive/delete/rename/start |
| `projectService.js` | project list/add/remove/set active/open new window |
| `memoryService.js` | memory snapshot、entry CRUD、similarity、consolidation |
| `promptService.js` | prompt assets、prompt CRUD、intent draft/commit/dry-run |
| `workflowService.js` | DAG list/detail/runs/start/terminate/delete/apply ops |
| `skillService.js` | skill list/read/write/create/import/resolution |
| `settingsService.js` | config、preferences、builtin tools、update、video key、logs |
| `fileService.js` | shared files、read/open/delete/export、clipboard |
| `observabilityService.js` | trace/recent/slow/errors/status |

首批迁移低风险页面：

1. `fileService.js`
2. `observabilityService.js`
3. `memoryService.js`

### 3.4 Adapter

Adapter 只做 DTO 到 ViewModel 的转换，不做接口请求。

示例职责：

| Adapter | 输出 |
| --- | --- |
| `memoryAdapter.js` | memory entry、overview、similar groups ViewModel |
| `workflowAdapter.js` | DAG item、run、node、diagnostic ViewModel |
| `skillAdapter.js` | skill card、resolution conflict ViewModel |
| `threadAdapter.js` | thread item、timeline item、runtime activity ViewModel |
| `apiErrorAdapter.js` | 用户可展示错误文本、trace/request id 提示 |

规则：

- 页面组件不得直接使用 snake_case 后端字段。
- adapter 输出字段使用前端稳定命名。
- adapter 应覆盖空数据，禁止 UI 自行猜 DTO 形状。

## 4. Hooks 设计

共享 hooks：

| Hook | 职责 |
| --- | --- |
| `useRequest` | 统一 loading/error/data/retry 状态，适合非 React Query 场景 |
| `useAsyncAction` | mutation pending、防重复提交、成功/失败 notice |
| `useDebounce` | 搜索输入、过滤条件 |

页面 hooks：

| 页面 | Hook |
| --- | --- |
| Chat | `useTimelineMaterialization`、`useThreadRailLayout`、`useComposerInteractions` |
| Files | `useSharedFilesDashboard`、`useSharedFileActions` |
| Memory | `useMemoryDashboard`、`useMemoryEditor`、`useMemorySimilarityActions` |
| Workflow | `useWorkflowPageController`、`useWorkflowActions` |
| Settings | `useProviderPreferences`、`usePromptSettings`、`useBuiltinToolsSettings` |
| Skills | `useSkillsDashboard`、`useSkillEditor`、`useSkillResolution` |

迁移原则：

- 先从页面同文件移到 page-local `hooks/`，不改变行为。
- 再把重复模式上提到共享 hooks。
- 每个 hook 拆分后必须有原页面测试或新增 hook/behavior 测试覆盖。

## 5. 组件拆分方案

### 5.1 App Shell

从 `App.jsx` 拆出：

- `app/providers/queryClient.js`
- `app/routes/pageRoutes.js`
- `app/shell/AppShell.jsx`
- `app/shell/Titlebar.jsx`
- `app/shell/NavRail.jsx`

同时引入页面级 lazy loading：

```js
const ChatPage = lazy(() => import('../../pages/chat/ChatPage.jsx'));
const WorkflowPage = lazy(() => import('../../pages/workflows/WorkflowPage.jsx'));
```

注意：

- fallback 必须使用稳定布局，避免页面跳动。
- route 映射保持现有语义：`chat -> /`、`prompts -> /prompts`、`workflows -> /dags`、`skills -> /skills`、`memory -> /memory`、`files -> /files`、`settings -> /settings`。
- `/` 不应覆盖已有显式页面初始化行为。

### 5.2 Chat

拆分顺序：

1. `chat/adapters/timelineAdapter.js`
   - timeline item normalize/sort/filter。
   - directive/markdown 纯解析 helper 后续独立。
2. `chat/hooks/useTimelineMaterialization.js`
   - `TIMELINE_INITIAL_MATERIALIZED_MESSAGES`、滚动加载、stick-to-bottom。
3. `chat/components/RuntimePanel.jsx`
   - runtime stats、warnings、results、diff summary。
4. `chat/components/ThreadRail.jsx`
   - active/archived threads、pin/archive/delete/rename 展示。
5. `chat/components/ComposerDock.jsx`
   - composer、附件、发送、中断、fork。
6. `chat/components/Conversation.jsx`
   - 只组合 timeline 和 composer，不直接做 API。

不在第一批拆：

- 不重写 markdown 渲染算法。
- 不替换 mermaid。
- 不引入虚拟滚动库。

### 5.3 Workflow

优先拆：

- `WorkflowFinalOutputPanel`
- diagnostics panel
- run history panel
- schedule editor
- workflow actions hook/service

### 5.4 Settings

优先拆：

- update panel
- provider preferences panel
- prompt settings panel
- builtin tools panel
- UI logs panel
- video API key panel

### 5.5 Skills / Prompt / Memory / Files / Observability

优先迁移 service 和 adapter，再拆 UI：

- Files 和 Observability 文件较小，适合作为 service/adapter 模板。
- Memory 有较完整状态矩阵，适合作为 hook 拆分模板。
- Skills 和 Prompt 涉及更多表单/导入/生成行为，放在第二批。

## 6. 状态管理优化方案

目标不是替换 Zustand，而是拆分 store 结构并收窄订阅。

目标结构：

```txt
store/client/
  useClientStore.js
  initialState.js
  projectSlice.js
  threadSlice.js
  runtimeSlice.js
  composerSlice.js
  forkSlice.js
  selectors.js
```

迁移规则：

- 第一阶段保持 `useClientStore` 对外 API 不变。
- 每个 slice 只接收 runtime dependencies 和 `set/get`。
- DTO normalization 迁到 adapter/helper 后，slice 只编排状态变化。
- 页面逐步从 `const store = useClientStore()` 改为 selector：

```js
const activePage = useClientStore((state) => state.activePage);
const setActivePage = useClientStore((state) => state.setActivePage);
```

优先拆分：

1. `forkSlice.js`：边界相对清晰。
2. `composerSlice.js`：附件、草稿、文件选择。
3. `projectSlice.js`：项目列表、切换、新窗口。
4. `threadSlice.js`：会话选择、归档、删除、重命名。
5. `runtimeSlice.js`：bridge/runtime/assistant event，风险最高，最后拆。

## 7. 性能优化方案

### 7.1 首屏

- 页面级 code splitting。
- QueryClient 和 route constants 从 `App.jsx` 移出。
- 保持 chat 默认页快速可用，非当前页面延迟加载。
- 构建后比较 chunk：目标是减少主入口 chunk，并降低 Vite >500 KB 警告影响。

### 7.2 Render

- `AppShell` 不再订阅整个 store。
- Titlebar 只订阅 titlebar 所需 action/status。
- NavRail 只订阅 activePage 和 memory badge。
- Chat 大组件先拆再 memo，避免在巨型文件里盲目 memo。

### 7.3 长列表

- Chat timeline 保留并测试增量 materialization。
- Thread rail 先按 active/archived 分组和必要过滤缓存。
- Workflow runs、Skill grid、Memory entries、Shared files 根据数据量引入分页/折叠/增量渲染。
- 暂不引入新虚拟滚动依赖。

### 7.4 大计算

- JSON pretty print、diff summary、markdown block parsing 放入 memo 或延迟渲染。
- Mermaid 继续动态 import。
- 大文件内容预览保留截断和显式展开策略。

### Phase 6：最终验收

验收标准：

- 页面功能保持正常。
- 页面组件不直接调用后端 RPC facade。
- 单个文件行数显著下降，核心页面拆出组件/hooks/service/adapter。
- 接口异常不会导致页面白屏。
- loading/error/empty/success/disabled 状态明确。
- 用户点击操作有即时反馈和重复提交防护。
- 无明显循环依赖。
- 无明显重复请求。
- 无明显无意义 re-render。
- `npm run lint` 通过。
- `npm test` 通过。
- `npm run build` 通过。
- UI 可见路径通过浏览器验证。

## 9. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 大范围重构引发回归 | 每阶段只处理一个边界，保持可回滚 |
| 移动文件导致测试 mock 失效 | 每次移动同步更新测试，先跑 focused tests |
| service/adapter 过度设计 | 只为已迁移页面创建必要接口，不预设复杂框架 |
| store 拆分破坏 runtime event | runtime slice 最后拆，先抽纯 helper 并保留测试 |
| lazy loading 改变路由体验 | stable fallback + App route tests |
| 样式拆分导致主题漂移 | 保持 `styles.test.js` token 合约，禁止散落 raw color |
| 后端 wire shape 不统一 | 前端 service 层先兼容，不在本轮推动后端大迁移 |

## 10. 第一轮执行边界

第一轮只落本文档组，不进入 Phase 1 代码重构。进入 Phase 1 前需要再次确认：

- 是否从 Files/Observability/Memory 三个低风险页面开始。
- 是否允许更新 `backendApiConsumer.surface.test.js` 收紧 guard。
- 是否把 `App.jsx` lazy loading 提前到 Phase 1，还是按计划保留在 Phase 4。
