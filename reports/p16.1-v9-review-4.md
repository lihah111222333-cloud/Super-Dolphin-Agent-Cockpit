# P16.1 v9 审查 R4

结论：不通过

## 验证结论

1. **`routeToolCall` 能消费 proxy 回填的 `agentId/threadId/callId`**
   - `ToolCallRequest` 已有 `AgentID/ThreadID/CallID` 字段：`internal/platform/toolbridge/types.go:20-26`
   - `routeToolCall()` 会把 `req.ThreadID` 写入 `mergeContext()`，并把 `req.AgentID/req.CallID` 传给 `aggregator.Merge()`：`internal/platform/toolbridge/handler.go:68-87,275-292`
   - 如果 proxy 用 `bindingStore.GetThreadByAgent()` 回填 `req.ThreadID`，当前 diff 链路可以把它一路带到事件总线：
     - `difftracker.WithToolCallContext()`：`internal/platform/difftracker/tool_context.go:24-34`
     - `buildHookMergeRequest/buildGitMergeRequest()`：`internal/platform/difftracker/tool_context.go:77-86,133-141`
     - `DiffAggregator.snapshot()`：`internal/platform/difftracker/aggregator.go:325-336`
     - `provideDiffEmitter()` → `event.Publish(...)`：`internal/platform/toolbridge/module.go:72-89`

2. **proxy 的 `tools/list` 按 family 分发可以复用现有实现**
   - `ListToolsForCodex()` 本身就是按 client kind 分别拉取 orch/lsp：`internal/platform/toolbridge/handler.go:99-110`
   - `listPeerTools(clientKind)` 已封装等待 peer + 回调 `tools/list`：`internal/platform/toolbridge/handler.go:116-152`
   - `mcp-lsp` / `mcp-orch` 当前都已注册 `tools/list` / `tools/call` 回调：
     - `cmd/mcp-lsp/fx.go:49-70`
     - `cmd/mcp-orch/fx.go:79-100`

3. **peer 查找机制已确认：按 `clientKind` 全局找活跃实例，不按 agent/thread 定位**
   - `FindActiveByKind()` 只读 `byClientKind` 索引并过滤 `StatusActive`：`internal/platform/mcpcontrol/resolution.go:79-94`
   - `ToolRegistry` 的确维护了 `byClientKind` 索引：`internal/platform/mcpcontrol/registry.go:56-65,97-115`
   - 索引写入发生在 `forEachInstanceBucket()`：`internal/platform/mcpcontrol/factory.go:153-172`
   - 这意味着 `/mcp/<family>/<agentId>` 里的 `agentId` **不会参与 peer 选择**；当前链路成立的前提仍然是“同一 family 只有一个活跃 peer”。

4. **proxy 若能查到 threadId，`ToolDiffUpdated.ThreadID` 可以正确传到总线**
   - thread 查询接口存在且 SQL 落点正确：
     - `internal/store/binding/contract.go:7-18`
     - `internal/store/binding/store.go:138-144`
     - `internal/store/sqlc/thread_binding.sql.go:61-72`
   - 但 UI 消费端会直接丢弃空 `ThreadID` 事件：`internal/module/uistate/diff_state.go:41-46`
   - 所以“查失败不阻断工具调用”是成立的，但其真实效果是：**工具能执行，diff UI 不会更新**。

5. **proxy 透传 `_agentId/_threadId/_callId` 给 peer 是兼容的**
   - `mcp-lsp` / `mcp-orch` 的 `OnToolsCall` 仅反序列化 `name/arguments`，未知顶层字段会被 `json.Unmarshal` 忽略：
     - `cmd/mcp-lsp/fx.go:56-69`
     - `cmd/mcp-orch/fx.go:86-99`

## 问题列表

### 1. `initialize` “直通”方案不闭环，当前链路里没有可供 proxy 转发的 peer `initialize` 回调

- v9 把 proxy 的 `initialize` 描述为“直通”：`docs/plans/迁移/p16.1-unified-diff-plan.md:93-95`
- 但当前注册到 mcpcontrol peer callback 的只有：
  - `tools/list`
  - `tools/call`
  见 `internal/mcpserver/common/bootstrap/lifecycle.go:98-109`
- 现有 MCP HTTP 握手是在 **HTTP server 本地**处理的，不是走 peer callback：
  - `initialize`：`internal/mcpserver/common/http_transport.go:105-148`
  - `notifications/initialized` / `exit`：`internal/mcpserver/common/http_transport.go:110-113`

**结论**：如果 proxy 设计成“`toolbridge.Handler` + `peer.Callback`”这条链，它不能把 `initialize` 再“直通”给 peer；proxy 必须自己实现一层与 `common.HTTPServer` 等价的 MCP 握手处理（至少覆盖 `initialize`、`notifications/initialized`、`exit` 的兼容语义）。

---

### 2. `tools/call` 的响应/错误语义没有做 MCP 适配，`routeToolCall` 不是 Claude MCP HTTP 的直接返回值

- `routeToolCall()` 当前返回的是 **Provider 侧** `ToolCallResult`：`internal/platform/toolbridge/handler.go:53-97`
- `adaptMCPResponse()` 会把 peer 的 MCP `content[]` 转成 `contentItems[]/inputText`：`internal/platform/toolbridge/handler.go:154-163`
- 同时，peer callback 出错时，`routeToolCall()` 不返回 Go error，而是返回 `Success:false` 的 `ToolCallResult`：`internal/platform/toolbridge/handler.go:71-82`
- 但 MCP HTTP 侧期望的是：
  - `ToolProvider.CallTool()` 返回**原始工具结果**：`internal/mcpserver/common/server.go:26-29`
  - 成功后由 HTTP transport 包一层 `{"content":[{"type":"text","text":"..."}]}`：`internal/mcpserver/common/http_transport.go:161-196`
  - 失败则走 JSON-RPC error：`internal/mcpserver/common/http_transport.go:176-180`

**结论**：proxy 如果只是“收到 `tools/call` → 直接调 `routeToolCall` → 原样回写”，返回体会变成 Codex 专用 `ToolCallResult` 语义，而不是 Claude/MCP 期望的 `tools/call` 结果语义；错误也会被错误地吞成 `Success:false`。

---

### 3. 1.5 的 diff tracking 方案与当前实现脱节，会重复造轮子并回归已有覆盖面

- v9 在 1.5 里写的是“`routeToolCall` 内 before/after 读文件 + `h.bus.Publish(ToolDiffUpdated)`”：`docs/plans/迁移/p16.1-unified-diff-plan.md:181-201`
- 但当前 `Handler` 结构里**没有 `bus` 字段**，只有 `registry/aggregator/resolver/logger`：`internal/platform/toolbridge/handler.go:21-26`
- 现在真实的 diff 发布链路已经存在：
  - `routeToolCall()` → `mergeContext()` → `aggregator.Merge()`：`internal/platform/toolbridge/handler.go:68-87,275-292`
  - `provideDiffEmitter()` → `event.Publish(ToolDiffUpdated)`：`internal/platform/toolbridge/module.go:72-89`
- 当前 snapshot 覆盖范围也比计划稿更大：
  - `code_run`
  - `code_run_test`
  - `lsp_edit(rename/format/code_action/replace_range)`
  见 `internal/platform/toolbridge/handler.go:294-305`

**结论**：Claude proxy 的 threadId 回填应该复用现有 aggregator/emitter 链路，只需要保证 `req.AgentID/ThreadID/CallID` 正确进入 `routeToolCall()`；不应该在 1.5 再手写一套 before/after diff + 直接发布事件，否则会：
1. 偏离当前实现；
2. 回归 `format/code_action/code_run/code_run_test` 的已有 diff 能力；
3. 产生两套 diff 语义并增加维护成本。

## 补充说明（非主阻塞）

- `waitForPeer()` / `listPeerTools()` 当前对同类 peer 的处理仍是“取第一个活跃 peer”：`internal/platform/toolbridge/handler.go:134-152`
- `routeToolCall()` 对同类 peer 则要求唯一，否则 `ErrAmbiguousPeer`：`internal/platform/toolbridge/handler.go:57-63`
- 因此，proxy 引入后，`/mcp/<family>/<agentId>` 这个 URL 里的 `agentId` 依旧**不会**解决“同 family 多活 peer”的歧义；它只会影响 diff/session 上下文。

---

建议：v10 至少补齐三点再审——
1. 明确 proxy 的本地 MCP initialize/initialized/exit 处理；
2. 明确 `tools/call` 的 MCP↔toolbridge 结果适配层；
3. 在 1.5 中改成“复用现有 aggregator/emitter，仅补 req.ThreadID 来源”，不要再重写 diff 主链路。
