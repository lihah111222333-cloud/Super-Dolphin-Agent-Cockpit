# P16.1 统一 Diff 计划 v9 审查报告 R1

- 审查日期：2026-04-12
- 审查对象：`docs/plans/迁移/p16.1-unified-diff-plan.md`
- 审查重点：P1 归一强制（Claude 是否被**强制**收敛到 proxy/toolbridge 链路）

## 结论

**不通过**

v9 的修正方向是对的：
- 当前 `internal/provider/claudecli/driver.go:61-100` 的 `StartSession` / `ResumeSession` 确实都把 `PeerHTTPAddrs: discoverPeerAddrs()` 传给了 `dto.BuildManifest(...)`。
- 当前 `internal/dto/provider/manifest.go:44-81` 确实会在 `ctx.PeerHTTPAddrs[fam]` 非空时生成 `http://<peer>/mcp`，这会让 Claude 直连 peer。
- 当前 `internal/module/turn/manifest.go:18-26` 仍然把 `PeerHTTPAddrs: discoverPeers()` 传给 `BuildManifest`，Codex 侧保留该逻辑不受 v9 影响。

但 v9 仍**没有把“Claude 必经 proxy”做成硬约束**。

## 关键核查结果

### 1. 当前 Claude driver 的确仍在传 `PeerHTTPAddrs`

- `internal/provider/claudecli/driver.go:62-70`
- `internal/provider/claudecli/driver.go:85-91`

两处都是：
- `dto.BuildManifest(dto.ManifestContext{ ... PeerHTTPAddrs: discoverPeerAddrs(), })`

这点与 v9 对现状的描述一致。

### 2. 当前 BuildManifest 的确会把 Claude 指到 peer HTTP 地址

`internal/dto/provider/manifest.go:60-69` 当前逻辑：
- 若 `ctx.PeerHTTPAddrs[fam]` 非空，则产出 `Type: "http"`
- URL 直接写成 `http://<addr>/mcp`

而 `internal/provider/claudecli/transport_config.go:207-269` 会把 manifest 里的 `bin.URL` 原样写进 Claude 的 `mcpServers` 配置；没有第二层重写。

因此，**当前代码里 Claude 的 peer 直连来源就是 BuildManifest 这条链**：

`driver.go -> dto.BuildManifest(...) -> bin.URL=http://<peer>/mcp -> writeManifestConfig() -> Claude 直连 peer`

### 3. Codex 侧仍在使用 `PeerHTTPAddrs`，不受该修正影响

- `internal/module/turn/manifest.go:18-26`：`manifestBuilder.Build()` 继续传 `PeerHTTPAddrs: discoverPeers()`
- `internal/module/turn/service.go:65-74`：`PrepareTurn()` 里继续通过 `s.manifest.Build(input)` 生成 turn MCP manifest

所以，**“只改 Claude driver，不改 Codex turn/manifest”** 这个方向本身没有问题。

## 问题列表

### 问题 1：v9 只消除了“peer HTTP 直连”，但没有消除“proxy 缺失时的 sidecar/stdio 绕过”

这是本次审查不通过的主因。

依据当前 `internal/dto/provider/manifest.go:44-81` 的结构，HTTP 分支命不中时，会继续落到：
- `binaryName := "mcp-" + string(fam)`
- `Command: []string{filepath.Join(ctx.BinaryDir, binaryName)}`

也就是 **stdio sidecar** 路径。

因此，v9 即使做到：
- Claude driver 不再传 `PeerHTTPAddrs`
- 只传 `ProxyHTTPAddr`

也只能推出：
- `PeerHTTPAddrs[fam]` 这条 **peer HTTP 直连** 分支不会再被 Claude driver 命中

**但不能推出：Claude 永远走 proxy。**

只要 `ProxyHTTPAddr` 在调用时为空（例如 proxy 尚未就绪、注入异常、生命周期异常），`BuildManifest()` 仍会退回 stdio sidecar；该路径同样绕过 proxy / toolbridge / diff tracking。

也就是说，v9 目前实现的是：
- **去掉 Claude → peer HTTP 直连** ✅
- **并未把 Claude → proxy 做成不可退化的强制约束** ❌

### 建议补强

至少补一个硬约束之一：

1. **Claude driver fail-fast**：`proxyAddrFn()` 为空时，`StartSession/ResumeSession` 直接报错，不允许继续构造 manifest；或
2. **BuildManifest 增加 Claude 严格模式**：Claude 模式下必须产出 proxy HTTP URL，禁止回落到 stdio command；或
3. 在计划里明确：**Claude 路径不允许 command fallback**，并补对应测试守卫。

## 关于“是否还有别的 Claude 直连路径”的结论

基于当前代码审查，除 manifest 生成链外：
- 未发现 `claudecli` 里还有第二条独立的 peer HTTP 直连路径；
- `internal/provider/claudecli/transport_config.go` 只是把 `dto.MCPManifest` 序列化到 `mcpServers`；
- 因此当前直连/绕过的关键入口仍然集中在 manifest 构造策略本身。

**但** 从“强制统一入口”的标准看，`proxyAddr` 为空时的 stdio sidecar fallback 仍然是遗漏的绕过路径。

## 最终判定

- 对“删除 Claude driver 中的 `PeerHTTPAddrs`”这一步：**认可**
- 对“v9 已彻底保证 Claude 永远走 proxy”这句话：**不认可**

当前 v9 方案 **方向正确，但约束还不闭环**，因此本轮判定：**不通过**。
