# ADR-004：F6.4 dispatcher 对无 assignee 节点的处理

> 状态：✅ Accepted（事后追认 / 2026-05-11） | 日期：2026-05-11 | 决策者：主线 | 相关：`docs/plans/dag改造实施计划.md` §3 F6.4 / §10 follow-up DAG 73、`docs/plans/dag改造现状与补丁v2.md` §4.1、commit `d068e04c` + `91057348`

## 1. 背景

DAG 节点的 `assigned_to` 字段指向负责执行该节点的 agent。原问题路径是：上游节点 done → `service.CompleteNodeAndScheduleDownstream` 自动调度下游 → dispatcher 立即 dispatch → 无 `assigned_to` 节点因 `agent id is required` 失败并耗尽重试。

**问题证据（DAG 73 实测）**：
- N1 (root) done → N2 自动 promote 到 ready
- dispatcher 立刻对 N2 dispatch → 因 N2 无 `assigned_to` → `error="agent id is required"` → retry policy 耗尽 → N2 自动 failed（terminal）
- 结果：DAG 在 M2 阶段**不能做"无 assignee 描述性任务编排"**

证据来源：DAG id=73, run audit-2026-05-11-route-n-runstore-review#run-001，N2 result.kind=exhausted_retries reason="agent id is required"。详见 `docs/plans/dag改造实施计划.md` §10 follow-up（line 461）。

**实施计划 §3 F6.4 行的描述与 §10 follow-up 矛盾**：F 表写"自动 spawn"，follow-up 写"应跳过"。本 ADR 拍板二选一。

## 2. 候选方案

### 方案 A：跳过自动 dispatch / wakeup enqueue
- flow store 检查 `node.assigned_to`，为空或 TrimSpace 后空白时**不 enqueue wakeup**
- 节点保持 pending；当依赖已满足时，该 pending 承担 ready 语义，等待外部 agent / 用户显式接管后再推进
- 优点：语义直观，描述型节点自然成为“等外部接管”的占位
- 缺点：节点可能长期滞留，需要后续 UI 提示或显式接管工具补齐

### 方案 B：`schedule.manual_dispatch=true` 标记
- DAG 节点 schedule 配置加 `manual_dispatch: bool` 字段
- dispatcher 检查 `schedule.manual_dispatch`，为 true 时跳过自动 dispatch
- `assigned_to` 不再作为"是否自动 dispatch"的判据（语义解耦）
- 优点：意图显式，不依赖 `assigned_to` 空值；可配合 `assigned_to` 预填"建议执行者"但仍由人/外部触发
- 缺点：node config schema 需加字段（破"骨架锁死"或走 ADR 修订）；F6.4 落地工作量略大

## 4. Open Questions

- Q1：方案 A 的"显式 dispatch"工具命名（`task_dispatch_node` / `task_advance_node` / `task_resume_node`）？
- Q2：方案 B 的 `manual_dispatch` 字段位放 `schedule` 还是 `exec`？schema 层级影响 typed config 解析路径。
- Q3：选定方案后，dispatcher 失败的 `"agent id is required"` 错误是否还要保留作 defense-in-depth？还是直接删（fail-fast 后不可达）？
- Q4：UI 端要不要给"等待外部 dispatch"的 ready 节点单独色 token？现 ready 色与"刚 promote 等 dispatch"无法区分。

## 5. 决策

✅ **选定方案 A：跳过自动 dispatch / wakeup enqueue**。

**实装证据**：
- commit `d068e04c` — `feat(orch/store): F6.4 — CompleteNodeAndScheduleDownstream 跳过无 assigned_to 节点的 wakeup enqueue`
- commit `91057348` — `test(orch/store): F6.4 补强 — TrimSpace 守护测试覆盖 assigned_to=空白`

**实装位**：
- `cmd/mcp-orch/orchestration/dag.go` `UpdateNodeStatus` 中 status=done 路由到 `CompleteNodeAndScheduleDownstream`
- `cmd/mcp-orch/store/taskdag/store_complete_downstream.go` `tryEnqueueDownstream` 内部对无 assigned_to / TrimSpace 后空白节点**不 enqueue wakeup**，节点保持 pending（依赖已满足时承担 ready 语义），等待外部 agent / 人工接管

**未选方案 B（manual_dispatch 标记）**：保留 §2 描述以备未来语义升级（例如某节点想“有 assigned_to 但仍人工触发”），但当前不实装。

**Open Questions 重审**：
- Q1（显式 dispatch 工具命名）：未来如需 UI 上“显式 dispatch ready 节点”再立项
- Q3（"agent id is required" 错误是否保留）：F6.4 已前置跳过，该错误路径不可达，保留作 defense-in-depth
- Q4（UI 色 token）：待 UI 一起设计时考虑
