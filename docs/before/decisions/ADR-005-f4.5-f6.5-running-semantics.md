# ADR-005：F4.5 与 F6.5 联动 —— 多 run 并发后 "running 受限" 的判定主体

> ⚠️ **历史快照**：本 ADR 2026-05-11 写于 F 阶段未开工时。2026-05-14 后 F4.5 / F6.5 已落地；2026-05-23 U2 质量封口把 running/active run 下的 `add_node` 从“受限允许”收敛为 fail-fast，直到 runtime append 真闭环。当前执行口径以 `docs/plans/dag改造实施计划.md` §3 F4.5 / F6.5 / U2 和本 ADR §5 决策为准。

## 1. 背景

本文初稿写于 F6.5 前，当时实施计划规定：

- **F4.5**：`ApplyOps` 在 `status=running` 时只允许 `add_node` 且 `depends_on` 指向 done 节点
- **F6.5**：T1.2-full —— 复制节点带 `run_id`，allow 同 DAG 多 run 并发；`StartDAG` 不再 reject 已有 running run

两者落地后会撞：多 run 并发模式下，run 状态已经下沉到 runtime `run_id` 维度，F4.5 初稿文字「`status=running`」的主体需要重新定义。

2026-05-14 后的实际实现保留 DAG 模板状态作为编辑 guard 的一部分，同时新增 active running run 查询；二者共同决定 ApplyOps 是否进入 running edit 限制。

## 2. 候选方案

### 方案 A：模板级聚合 —— 任一 run.status=running 时模板受限
- ApplyOps 内部对 dag_key 关联的所有 run 做存在性查询：若存在 status=running 的 run → 按 F4.5 限制
- 优点：保持 F4.5 原意（保护正在跑的 run 不被破坏性 ops 撞）
- 缺点：多 run 并发下模板可能几乎永远不可编辑（一个 run 没跑完另一个 run 又起）；ApplyOps 多一次 run 表扫描

### 方案 B：模板与 run 完全解耦
- 模板任意时刻可编辑（ApplyOps 不再看 run 状态），但 ApplyOps 写入 dag.version+1
- 正在跑的 run 用 snapshot 的 `dag.version`（F6.1 已留位），不受新 ops 影响
- 新 run 用新 version
- 优点：编辑体验流畅，符合 Temporal / Airflow 模板 vs 实例的标准模型
- 缺点：F4.5 原约束完全失效，需要明确"模板编辑期间已有 run 是否会看到旧 version 节点"——通常是看到（snapshot 隔离），但要测试覆盖

### 方案 C：混合 —— 仅守 add_node 不撞、update_node / remove_node 与 run 强一致
- ApplyOps 内 add_node 不看 run（无副作用）
- update_node / remove_node 仍按 F4.5 限制（影响正在跑的 run 行为）
- 优点：折中保护破坏性 ops 不撞 run
- 缺点：规则复杂，AI 设计师产 ops 时需要分类心智

## 4. Resolved Questions And Follow-Up Boundaries

- Q1 resolved：F6.5 没有采用“完整事件 replay snapshot”作为首版机制，而是在 `StartDAG` 时复制模板节点为带 `run_id` 的 runtime 节点。已启动 run 读取 runtime 节点；模板后续修改不回写旧 run。
- Q2 resolved：running edit guard 采用 active running run 查询来判断是否进入受限编辑，不再按旧“单 DAG 只能一个 running run”的唯一约束推导。
- Q3 resolved：U1 DAG Console 只负责 Start 与追踪；运行中编辑 UI 仍未开。后续 F8 若实现“改一处 prompt 再 Start”，必须遵循 §5：running/active run 期间所有模板改写先禁用或报错，等 runtime append 闭环后再恢复满足条件的 add_node。
- Follow-up：事件 replay、完整版本 diff、多人冲突提示仍属于后续 H/F8 设计，不是 ADR-005 已落地部分。

## 5. 决策

✅ **采纳方案 C 的 U2 fail-fast 变体**：

- 模板编辑与 run snapshot 仍保持隔离；已启动 run 使用自己的 runtime 节点，不回读模板节点状态。
- 当 DAG 模板自身为 `running`，或存在 active running run 时，`ApplyOps` 当前拒绝 `add_node` / `update_node` / `remove_node` / `update_dag`，避免只改模板却不进入当前 run 的 runtime nodes。
- 后续若补齐 runtime append 闭环，才能恢复 running 期间新增节点；届时新增节点的 `depends_on` 必须全部指向已 `done` 的现有 runtime 节点。
- F6.5 后的多 run 并发不再使用“单 DAG 只能一个 running run”的旧约束；保护点下沉到 runtime `run_id` fence 与上述 running edit guard。
