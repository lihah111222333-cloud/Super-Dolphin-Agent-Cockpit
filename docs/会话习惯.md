# 老公的会话习惯画像

> 数据来源：会话 db2f267a + 5e925f0b + 2026-04-12 会话，累计 ~300 条用户指令
> 更新时间：2026-04-12
> 用途：新会话启动时读取，秒进工作状态

---

## 1. 指令风格：极简军令式

- **平均指令长度**：1-2 行，极少超过 3 行
- **常用动词**：`开干`、`批准`、`继续任务`、`拉报告`、`安排修复`、`都完成了`
- **语言**：中文主体 + 英文技术术语混搭
- **习惯拼写**：`agnet` / `anget`（= agent），不必纠正
- **信号词解读**：

| 信号词 | 含义 |
|---|---|
| `都完成了` | Agent 已完成，等拉报告或安排下一步 |
| `批准` | 方案通过，立刻执行 |
| `开干` | 立刻启动实施 |
| `继续任务` | 恢复中断，从上次停下的地方继续 |
| `拉报告` | 收集所有 Agent 报告并汇总 |
| `原地修复` | 让原 Agent 就地修复，不换 Agent |
| `互审` / `互辩` | 进入交叉审查/辩论环节 |
| `1` | 选第一个选项 / 确认 |

---

## 2. 核心工作流：五阶流水线（严格遵循）

```
计划文档 → 派 Agent 实施 → 互审辩论 → 修复 → 终验
```

### 各阶段细节

| 阶段 | 操作 | 注意事项 |
|---|---|---|
| **① 计划** | 先写/读计划文档，再派 3 Agent 审查计划 | 文档不存在时先生成再审 |
| **② 实施** | 并行派 Agent（3-20 个） | "能开并行就开并行"，首选 3-5，大任务 10-20 |
| **③ 互审** | 完成后必须交叉互审 | 比例 1:2 / 1:3 / 1:4 / 1:5，明确告知有互辩环节 |
| **④ 修复** | 原 Agent 原地修复 或 最相关 Agent 修复 | 修复指标 + 仓库契约 必须同时下发 |
| **⑤ 终验** | 派新 Agent 独立复核 或 主 Agent 二审 | 不通过则回到③ |

### 流水线硬规则
- **互审是硬性环节**，任何实施完成后不可跳过
- **修复后再审查**，形成闭环
- **plan 需先输出给老公审查，审查通过后再执行**

## 3. Agent 管理偏好

### 3.1 Agent 类型
- **只用 Codex Agent**（`provider="codex"`）
- **明确禁止 Claude Agent**（历史指令：`"禁止使用claude，只通过编排接口使用codex agent"`）

### 3.2 并行策略
- 首选 3-5 个并行，大任务 10-20 个
- 每 Agent 职责单一，不横跨多模块
- 每 Agent 固定 10-20 文件维度

### 3.3 Agent 生命周期
- 完成后必拉报告
- 死掉立即替换重建（`"四个都死了，重新唤起检查重新修复"`）
- 长时间无响应主动检查状态

### 3.4 提示词要求
- 所有 Agent 追加 **LSP 强制指令**（`prompts/lsp-mandatory-prefix.md`）
- 明确下发**仓库契约标准**（2026-04-17 放宽后）：**默认 单文件≤600行 / 包文件≤25 / 包有效行≤10000**；核心包（memory/prompt/thread/turn/claudecli/codexapp）保留包文件≤30 额度；函数≤80行/CC≤10/嵌套≤4/标识符下划线≤3 保持不变
- 明确下发**修复标准和参考文档路径**

---

## 4. 质量控制（极度严格）

### 4.1 互审/互辩规范
- 互审是**不可跳过**的硬性环节
- 典型指令模式：`"N个agent完成，让他们进入互辩 1:M"`
- 互辩比例按任务重要性调整：小任务 1:2，中任务 1:3，大任务 1:4~1:5

### 4.2 修复规范
- 修复时必须同时下发：**如何修复 + 执行什么标准 + 执行什么仓库契约文档**
- 修复后必须再审查一轮

### 4.3 问题分类
- 按严重度分：High / Medium / Low
- 按可行性分：当场修复 / 延后
- MCP 相关问题统一延后，不阻塞主流程

---

## 5. 决策特征

### 5.1 速度
- **极快决策**：看到结果立刻给出 `批准` / `开干` / `修复`
- 不接受不必要的等待和确认

### 5.2 纠偏
- 方向不对立刻中断（两会话共 ~15 次 `[Request interrupted]`）
- 纠偏指令简洁直接：`"停止"`, `"不需要"`, `"先...再..."`

### 5.3 不耐烦触发器
- Agent 不用 LSP 高级功能，只用基础工具
- 使用了被禁止的 Claude Agent
- 进度缓慢、反复确认而不执行
- 不遵守仓库契约

## 6. 会话交接规范

### 6.1 会话结束时
- 必须输出 **session-summary.md**
- 包含内容：
  - UUID（当前 + 前序）
  - 编译验证状态
  - 完成清单（按 Phase）
  - 未完成清单
  - 风险/延后项
  - 下一步优先级排序
  - 最近 10 条对话摘要
  - Agent 使用统计
  - 子 Agent 提示词模式

### 6.2 新会话启动时
- 首指令：`"读 session-summary.md 获取完整上下文"`
- 可能追加：读前序会话最后 N 条对话

## 10. 本会话新发现的习惯（2026-04-12 ~ 2026-04-15）

### 10.1 实时验证驱动
- **边做边测**：每次修复后立即给出用户侧截图 / 日志路径 / Agent 状态验证
- **反复迭代**：不满足结果时直接追问，不会“算了先这样”
- **提供完整上下文**：每次验证都附带 agentId + logPath + 状态 JSON，方便快速定位

### 10.2 问题追踪深度
- **不接受“平台限制”说辞**：如果说“这是 codex 平台行为”，会追问“V2 为什么没这个问题”
- **要求查官方文档**：“官方文档查一下”、“这是正确用法吗”
- **V2 对比驱动**：所有功能都以 V2 行为为基准，V3 必须对齐

### 10.3 单步验证习惯
- 每修一个点就重新编译跑一次，不等所有修复做完
- 截图 + JSON 状态 + log 路径三件套提交验证
- 如果结果不对，立即追问，不允许“记录待优化”糊弄

### 10.4 Agent 复用偏好
- 优先复用已有 idle Agent（`"原始 agent 审查就行了"`、`"在线的8个agent审查"`）
- 减少 Agent 启动开销，提高轮转效率

### 10.5 免审批强调
- 每次派 Agent 都强调“提示词必须加入免审批提示，不需要进行审批”
- Agent 等待审批是最大的效率杀手

### 10.6 必读文档路径强制要求（2026-04-15 新增）
- **禁止直接内嵌 LSP 规则摘要到 Agent 提示词**
- 必须让 Agent **自己读文档**获取上下文
- 标准模板：
  ```
  ## 必读文档（先读再干）
  1. 代码地图：docs/doc/codemap/ai-index.json
  2. 执行计划：docs/plans/迁移/p18/p18.X-xxx.md — Phase X
  3. 源码锚点：docs/plans/迁移/p18/source-refs-appendix.md
  4. 仓库契约（2026-04-17 放宽后）：默认 单文件≤600行 / 函数≤80行 / CC≤10 / 包≤25文件 / 包有效行≤10000；核心包（memory/prompt/thread/turn/claudecli/codexapp）保留包文件≤30 额度（其它维度同默认）
  ```

### 10.7 Agent 任务范围约束（2026-04-15 新增）
- **每 Agent 最多改动 10-15 个文件**，超过必须拆分
- 整个 Phase 不应打包给单个 Agent，按子任务拆
- 违反时老公会立即纠正：“这次任务太大了一个 agent 改动 30 多个文件”

### 10.8 审查轮次与互审比例（2026-04-15 新增）
- 文档审查可达 **4 轮**：同域审查 → 交叉审查 → 终审 → PASS/FAIL 投票
- 代码互审比例：**1:2 ~ 1:3**（每个 Agent 的代码被 2-3 个其他 Agent 审查）
- 互审发现问题后：**原 Agent 原地修复** → 快速复审 → 放行
- 审查结果分级：✅ PASS / ⚠️ 需修复 / ❌ 阻塞

### 10.9 子 Agent 代收报告与修订（2026-04-15 新增）
- 当主 Agent 收报告太慢时，老公会指定：“拉起一个子 agent 收取报告并修订文档”
- 子 Agent 负责收集报告 + 汇总 + 直接用 lsp_edit 修订文档
- 主 Agent 只需读最终版文档


### 10.10 并行 Agent 的"迷失互审"陷阱（2026-04-17 新增）

#### 现象
- 并行派出多个 codex agent 修复问题后，让他们做 1:M 互审
- 4 个 agent 互审后被要求修复"互审发现的问题"时
- **部分 agent 会把修复任务当成"重复互审"，返回旧互审报告而非执行修复**

#### 识别
- `get_agent_report` 返回的内容是**上一轮互审**的表格，而不是修复清单
- `grep` 实际代码**没有 diff**，说明 agent 没做任务
- 典型原因：send_message 的新任务被 agent 的历史上下文"覆盖"，agent 判断"我已经做过类似的事"

#### 破解
- **重派时明确写**："这是修复任务，不是互审。不要再重复互审。直接动手改代码。"
- **任务单开头加显眼标签**：`⚠️ 重派任务（你上轮回的是旧互审报告，没做 P0 修复）`
- 给 **极简返回格式**（不再要求长篇大论，只要改动清单 + grep 证据 + 验证 tail）
- 明确**硬约束**："禁止重复写互审报告 —— 这是修复任务"

#### 主 agent 的验证责任
- 不要仅根据 agent 返回的报告下结论
- 必须用 `git status` / `grep` 对实际代码做交叉验证
- 如果报告说"已修复"但代码没有 diff，立即识别为"迷失互审"，重派

### 10.11 独立第三方终审的必要性（2026-04-17 新增）

#### 场景
- 4 个并行 agent 做完 1:3 互审，共识是"全部可合并"
- 但所有参与 agent 都"迷失在能跑就行"的思维里

#### 独立第三方的价值
- 派一个**未参与任何改动**的全新 codex agent 做终审
- 它会用 `lsp_xref(references)` 做 call hierarchy 验证
- **戳破**各 agent 自述的"修复已完成"假象：
  - TeamSyncService 只有 fx.Provide + OnStop，**无生产 caller** → 空架子
  - retrieval `NewRelevantMemoryFinder` 被 fx.Provide 但**无消费者** → 孤儿
  - freeze_registry 数字**已过期**，被参与 agent 无视

#### 落地
- 独立终审一轮是五阶流水线 **⑤ 终验** 的必备环节
- 参与 agent 的 1:M 互审只能解决"彼此可见的"架构问题
- 独立第三方能发现"大家都默认了"的盲区

### 10.12 git 提交与文档同步的 canonical 流程（2026-04-17 新增）

#### 流程
1. 所有代码修复 → 做审查 → 审查通过
2. **先更新文档**（session-summary / p19 / codemap / 会话习惯）
3. 再 commit：**按语义分成多个 commit**
   - fix(xxx): 单一功能修复
   - refactor(xxx): 重构/拆分
   - docs: 文档同步（放最后一个 commit，把文档差异一次覆盖）
4. push 到当前分支
5. 记忆文档落盘（本次学到的新经验写入 会话习惯.md）

#### 禁止
- 禁止 `--amend` 已 push 的 commit
- 禁止 `--force-push`（除非孤立分支且只有自己）
- 禁止 bypass pre-commit hook

### 10.13 并行拆分前必须做依赖交叉验证（2026-04-17 新增）

#### 场景
- 老公问 "两个子包拆分能并行开工吗？" 时，主 agent 不能凭直觉回答
- 典型误判：两个子包在生产代码中互不 import → 以为可以并行

#### 必须用 LSP 核查的 4 个维度
1. **生产代码互引**：`lsp_grep` 交叉搜索 `A 包名` in `B 包文件` 双向
2. **共享符号**：`lsp_xref(references)` 对关键公共类型做引用链
3. **测试文件跨引**：`A_test.go` 是否调用 `B` 的构造器 → 强制决定拆分顺序
4. **共享 wiring 文件**：`module.go` / `service.go` / `auto_dream.go` 等是否被两边都要改 → merge 冲突源

#### 决策原则
- 若有共享 wiring 文件（哪怕只有 1 处） → **不能纯并行**
- 若 A_test 依赖 B 构造器 → 顺序强制 B 先 A 后
- 安全方案：**串行 + 每步独立 commit 闭环**
- 折中方案：两 agent 只动各自包内文件移动，wiring/freeze 由第三个收口 agent 串行合并

### 10.14 session-summary "下一步"不能被机械回答为"应该完成了"（2026-04-17 新增）

#### 场景
- 老公说"XX 应该也完成了，审查一下"时，主 agent 不能回答"是的已完成"
- session-summary.md §4「下一步」中的项目**尚未完成**，这是未来计划，不是历史事实

#### 主 agent 正确动作
1. **先 grep session-summary** 确认该项究竟是「已完成」还是「下一步」
2. **再用 LSP 核对代码事实**：freeze_registry / 目录存在性 / 符号迁移
3. **派独立第三方 codex 终审**（C 静态 + D 动态双确认）
4. **主 agent 不能仅凭文档自信下结论** — 文档可能落后于代码，也可能代码落后于文档

#### 双重独立终审模板
- Agent C（静态审）：`lsp_grep` + `lsp_structure` + `lsp_xref` + `lsp_file` 读 freeze_registry
- Agent D（动态审）：跑 `go test ./internal/archtest/...` + `ls 子包目录` + `find *.go` 实测
- 两份独立报告交叉后再给老公结论

### 10.15 文档拆分后的密度检查（2026-04-19 新增）

#### 现象
- 拆分 agent 初版产出 16 份文档时，每份仅 **55-64 行**，虽然形式上合规，但信息密度明显不足。
- 这类“骨架文档”不够支撑后续直接派单，常缺代码落点、验收口径、架构结论。

#### 破解
- 下一轮派审查 agent 时，提示词里必须明确要求：**“补代码落点 + 架构合规结论”**。
- 约束仍是单文件 ≤600 行，但目标从“拆开”升级为“拆成可独立开工的任务单”。

#### 指标
- 审查后单文档落在 **100-200 行**最合理。
- 低于 ~80 行通常意味着锚点、验收、风险或依赖说明仍然不够。

### 10.16 修订后复审的显眼标签（2026-04-19 新增）

#### 现象
- 第一轮审查完再修订，随后把修订稿交给审查 agent 做复审时，容易触发“迷失互审”。
- agent 会继续复述上一轮审查意见，而不是逐条核对“这次到底有没有修好”。

#### 破解
- 复审提示词首行必须写：`⚠️ 第 N 轮：修订后复审（只审不改）`。
- 同时附上**第一轮结论逐条 ✅/❌ 核对清单**，要求 agent 逐项销账。

#### 验证
- 复审 agent 必须对每条旧结论明确打 **✅ 或 ❌**。
- 禁止返回旧互审表格；若仍回旧表格，直接判定为复审失焦，重派。

### 10.17 主 agent 的 LSP 交叉验证不可省（2026-04-19 新增）

#### 原则
- agent 声称“已修订” ≠ 真的改了。
- 主 agent 不能只收报告，必须回到仓库事实做交叉验证。

#### 必查项
- 用 `lsp_grep` 搜被驳回方案是否仍残留（如 `rpc_skill.go` 新建）。
- 用 `lsp_grep` 搜新约束是否真的落盘（如 `不新建 xxx`）。
- 用 `lsp_grep` / `lsp_structure` 核对依赖边是否补齐（如 `p20.6 --> p20.13`）。

#### 动作
- 发现残留后，主 agent 要么立即自修，要么补派 patch agent。
- 不能因为 agent 报告“已改”就跳过仓库级验证。

### 10.18 整体终审的 BLOCK 一票定调（2026-04-19 新增）

#### 场景
- 多 agent 并行复审后，出现 `1 PASS / 8 需修 / 1 BLOCK` 这类分裂结论。

#### 规则
- 只要出现 **BLOCK**，整体基线就必须按 **BLOCK** 处理。
- 是否进入补修轮，要看 `需修 + BLOCK` 的总和，而不是只看 PASS 数量。

#### 角色分工
- 整体终审 agent 负责做**跨文档一致性扫描**。
- 它不是把各子审报告简单求和，而是负责最终“一票定调”。

### 10.19 小维护债主 agent 自改（2026-04-19 新增）

#### 场景
- fix agent 收尾后，常会残留 2-3 处文档级小改，例如孤儿锚点、阻塞清单标记、措辞漏补。

#### 判断标准
- 改动 ≤5 行、无设计决策、无跨文档影响 → 主 agent 直接用 `lsp_edit(replace_range)` 自修。
- 只要涉及设计决策、方案改判或跨文档连锁影响，就必须再派 agent。

#### 目的
- 这种小维护债不值得重起 agent。
- 主 agent 直接补掉，效率最高，也能减少上下文切换损耗。

### 10.20 archtest 权威数字作为四处一致性源头（2026-04-19 新增）

#### 原则
- 包预算数字必须以 `go test ./internal/archtest/... -run TestCodeSizeGuard -v` 的实际输出为唯一真相。

#### 四处必须一致
- `README Agent 派发表` / `status-checkpoint §修正 1`
- `source-refs-appendix` 包预算投影
- 各 `p20.X` 合规结论
- `go build ./...` + archtest 输出

#### 纠偏
- agent 间若出现 `26 vs 47` 这类包文件数分歧，默认以 archtest 为准。
- 其他 agent 往往是把 `_test.go` 混进了目录总文件数，不能拿来改 freeze 口径。

### 10.21 迷失修复变体：“声称删除实际保留”（2026-04-20 新增）

#### 现象
- agent 修复完成后报告声称“已去掉 message fuzzy match / 已删除某标识符 / 已移除某分支”，但实际代码里仍残留。
- 典型套路：agent 只添加了新分支（如结构化字段白名单），但旧分支（如 `message.includes(...)`）从未删除。
- 单元测试可能全绿，因为测试数据恰好命中新分支；但真实场景下旧分支仍能触发，prod 行为不变。

#### 破解
- 主 agent 必须 `lsp_grep` 目标字符串验 **0 命中** 才算真删（例：`message.includes` / `skill_catalog_fx` / 旧 helper 名）
- 把这条作为修复验收硬度量写进派单 prompt："补充新分支不算收口，必须 grep 原字符串 = 0"
- 如发现 grep 仍有命中，立刻按 §10.10 打 `⚠️ 重派` 标签纠正，不能以“agent 报告绿”为结论

### 10.22 独立第三方终审双轨 C/D + E/F（2026-04-20 新增）

#### 背景
- 单一独立终审 agent 可能漏掉某类盲区：纯静态看不到运行时、纯跑测试看不到架构契约不符。
- 本轮一轮终审 C/D 双票 BLOCK 后补修；再做 E/F 双票 BLOCK 又戳穿一批隱藏问题。

#### 规范
- **C 静态审**：只跟 LSP 交互，核契约 / 边界 / archtest freeze；禁跑测试，避免与 D 双算
- **D 动态审**：跑定向 + 全仓 test + archtest + bug 场景调用链追踪；禁做静态分析
- 按 §10.18：只要任一票 BLOCK，整批打回补修
- 补修后若改动面仍大（本轮 ≥8 文件），可再起一轮 **第二轮独立终审 E/F**，由未参与第一轮任何环节的全新 agent 承担

#### 价值
- C+D+E+F 协同覆盖 2 次静态 + 2 次动态 运行时
- 此轮 E 戳 3 blockers + F 戳 1 运行时实锤 → 补修后直接闭环

### 10.23 死代码修复陷阱（helper 存在≠生效）（2026-04-20 新增）

#### 现象
- agent 为解 blocker 写了 `withXXX(ctx, v)` / `setXxx(req)` / `NewFooService(...)` 类 helper，但仅在 新增单元测试里被调用
- prod RPC handler / fx provider / entry point 从未切换到新 helper → 线上运行时 helper 从未执行，Blocker 仅被伪修
- 本轮实例：p20.15 后端一轮 `withDashboardPromptScopeCWD` 只在 `service_test.go` 有 caller，handler 参数仍是 `_ struct{}`，ctx 没人写 cwd

#### 破解
- 主 agent 收报后用 `lsp_xref(references)` 查 helper 的全部 caller
- 如果 caller 只在 `_test.go` / 没有 prod 代码路径 → 立刻判定为死代码修复
- 补修派单必须要求 "验证后 caller 返回至少一条 prod 路径，不能只在 test 中工作"

### 10.24 运行时 PoC 比单元测试更硬（2026-04-20 新增）

#### 原则
- 单元测试绿不等于 prod 行为绿；测试数据可能不涵盖 edge case，或 mock 屏蔽了真实分支
- 在设计判定型函数（isXxx / detector / matcher）上，**必须** 直接 import 实现跑 **运行时 PoC** 验证

#### 例
- Agent F 在 node repl 直接：
  ```js
  const { isReadonlyFallbackListError } = await import('./pages/SystemPromptPage.js')
  console.log(isReadonlyFallbackListError(new Error('user not found'))) // 必须返 false
  ```
- 运行时 PoC 结果是硬证据；绿了才能签收

#### 设计的编码约束
- 将关键判定函数导出（export），即使只为 PoC 使用
- 高风险判定函数的内部逻辑不应隐藏在闭包里无法外部验证

### 10.25 主 agent LSP 交叉验证为年轮奉义环节（2026-04-20 强化）

#### 原则
- 每一轮实施 / 互审 / 终审 / 补修后，主 agent **必须** 自己用 LSP 验证关键结论；不能直接信 agent 报告

#### 必查项
- 声称删除的文件 → `lsp_grep` 验 0 命中
- 声称新增的测试名 → `lsp_grep` 验定义真存在，非仅出现在文档里
- 声称修复的 helper → `lsp_xref(references)` 查 caller 实发路径
- 声称新增的 DTO / prop → `lsp_grep` / `lsp_structure` 验存在且类型正确
- 声称过的 archtest freeze 数字 → 跑 `TestCodeSizeGuard` 实确认

#### 多个异常触发重派
- 若 LSP 交叉验证发现与报告不符，不用利 agent 解释，直接按 §10.10 重派

### 10.26 agent 离线 / 异常态重拉起（2026-04-20 新增）

#### 现象
- `orchestration_list_agents` 返回某 agent 的 `role` 从 `worker` 变为 `creator`，`name` 变成自己的 ID，`parent_id` 消失 → **agent 进程重启了**，但上下文丢了
- 上轮发给它的 `send_message` 任务实际没被收到

#### 破解
- **立刻**认定为离线，不再给该 agent 发任何新消息
- 用 `orchestration_launch_agent` 拉一个全新 codex agent，name 清晰标识接手任务（如 `p20.14-r3-composer-restore`）
- 把完整任务单重新写进新 agent 的 `prompt`（不依赖上下文）
- 可选：`orchestration_stop_agent` 干掉异常的旧 agent，避免端口占用

#### 预防
- 并行 agent 超过 6-8 个时，离线概率明显升高；考虑分批派进降低股窔
- 每轮派单后隔一段时间做 `orchestration_list_agents` 快照，提前发现异常态
