# 老公的会话习惯画像

> 数据来源：会话 db2f267a + 5e925f0b + 2026-04-12 会话，累计 ~300 条用户指令
> 更新时间：2026-04-12
> 用途：新会话启动时读取，秒进工作状态

---

## 1. 指令风格：极简军令式

- **平均指令长度**：1-2 行，极少超过 3 行
- **常用动词**：`开干`、`批准`、`继续任务`、`拉报告`、`安排修复`、`都完成了`
- **语言**：中文主体 + 英文技术术语混搭
- **习惯拼写**：`agnet` / `anget`（= agent），不必纠正
- **信号词解读**：

| 信号词 | 含义 |
|---|---|
| `都完成了` | Agent 已完成，等拉报告或安排下一步 |
| `批准` | 方案通过，立刻执行 |
| `开干` | 立刻启动实施 |
| `继续任务` | 恢复中断，从上次停下的地方继续 |
| `拉报告` | 收集所有 Agent 报告并汇总 |
| `原地修复` | 让原 Agent 就地修复，不换 Agent |
| `互审` / `互辩` | 进入交叉审查/辩论环节 |
| `1` | 选第一个选项 / 确认 |

## 2. 核心工作流：五阶流水线（严格遵循）

```
计划文档 → 派 Agent 实施 → 互审辩论 → 修复 → 终验
```

### 各阶段细节

| 阶段 | 操作 | 注意事项 |
|---|---|---|
| **① 计划** | 先写/读计划文档，再派 3 Agent 审查计划 | 文档不存在时先生成再审 |
| **② 实施** | 并行派 Agent（3-20 个） | "能开并行就开并行"，首选 3-5，大任务 10-20 |
| **③ 互审** | 完成后必须交叉互审 | 比例 1:2 / 1:3 / 1:4 / 1:5，明确告知有互辩环节 |
| **④ 修复** | 原 Agent 原地修复 或 最相关 Agent 修复 | 修复指标 + 仓库契约 必须同时下发 |
| **⑤ 终验** | 派新 Agent 独立复核 或 主 Agent 二审 | 不通过则回到③ |

### 流水线硬规则
- **互审是硬性环节**，任何实施完成后不可跳过
- **修复后再审查**，形成闭环
- **plan 需先输出给老公审查，审查通过后再执行**

## 3. Agent 管理偏好

### 3.1 Agent 类型
- **只用 Codex Agent**（`provider="codex"`）
- **明确禁止 Claude Agent**（历史指令：`"禁止使用claude，只通过编排接口使用codex agent"`）

### 3.2 并行策略
- 首选 3-5 个并行，大任务 10-20 个
- 每 Agent 职责单一，不横跨多模块
- 每 Agent 固定 10-20 文件维度

### 3.3 Agent 生命周期
- 完成后必拉报告
- 死掉立即替换重建（`"四个都死了，重新唤起检查重新修复"`）
- 长时间无响应主动检查状态

### 3.4 提示词要求
- 所有 Agent 追加 **LSP 强制指令**（`prompts/lsp-mandatory-prefix.md`）
- 明确下发**仓库契约标准**：默认 文件≤400行/函数≤80行/CC≤10/包文件≤15；核心包（memory/prompt/thread/turn/claudecli/codexapp）放宽至 文件≤600行/包文件≤30/包总行≤10000
- 明确下发**修复标准和参考文档路径**

---

## 4. 质量控制（极度严格）

### 4.1 互审/互辩规范
- 互审是**不可跳过**的硬性环节
- 典型指令模式：`"N个agent完成，让他们进入互辩 1:M"`
- 互辩比例按任务重要性调整：小任务 1:2，中任务 1:3，大任务 1:4~1:5

### 4.2 修复规范
- 修复时必须同时下发：**如何修复 + 执行什么标准 + 执行什么仓库契约文档**
- 修复后必须再审查一轮

### 4.3 问题分类
- 按严重度分：High / Medium / Low
- 按可行性分：当场修复 / 延后
- MCP 相关问题统一延后，不阻塞主流程

---

## 5. 决策特征

### 5.1 速度
- **极快决策**：看到结果立刻给出 `批准` / `开干` / `修复`
- 不接受不必要的等待和确认

### 5.2 纠偏
- 方向不对立刻中断（两会话共 ~15 次 `[Request interrupted]`）
- 纠偏指令简洁直接：`"停止"`, `"不需要"`, `"先...再..."`

### 5.3 不耐烦触发器
- Agent 不用 LSP 高级功能，只用基础工具
- 使用了被禁止的 Claude Agent
- 进度缓慢、反复确认而不执行
- 不遵守仓库契约

## 6. 会话交接规范

### 6.1 会话结束时
- 必须输出 **session-summary.md**
- 包含内容：
  - UUID（当前 + 前序）
  - 编译验证状态
  - 完成清单（按 Phase）
  - 未完成清单
  - 风险/延后项
  - 下一步优先级排序
  - 最近 10 条对话摘要
  - Agent 使用统计
  - 子 Agent 提示词模式

### 6.2 新会话启动时
- 首指令：`"读 session-summary.md 获取完整上下文"`
- 可能追加：读前序会话最后 N 条对话

## 7. 特殊偏好

### 7.1 文档驱动
- 计划先写文档 → 审查文档 → 执行
- 重大决策写入对应的 execution-plan.md

### 7.2 分阶段推进
- 严格按 P0→P10 推进，不跳跃
- 每 Phase 有独立的 execution-plan.md

### 7.3 工具链要求
- LSP 工具链强制使用，禁止只用 lsp_grep + lsp_file
- 每个任务至少 4 种 LSP 工具
- 发现 Agent 偷懒会追加更严格的提示词

### 7.4 MCP 策略
- MCP 相关问题统一归档到 P8/P9 文档
- 不阻塞当前 Phase 进度
- 单独评估工作量后再安排

## 10. 本会话新发现的习惯（2026-04-12 ~ 2026-04-15）

### 10.1 实时验证驱动
- **边做边测**：每次修复后立即给出用户侧截图 / 日志路径 / Agent 状态验证
- **反复迭代**：不满足结果时直接追问，不会“算了先这样”
- **提供完整上下文**：每次验证都附带 agentId + logPath + 状态 JSON，方便快速定位

### 10.2 问题追踪深度
- **不接受“平台限制”说辞**：如果说“这是 codex 平台行为”，会追问“V2 为什么没这个问题”
- **要求查官方文档**：“官方文档查一下”、“这是正确用法吗”
- **V2 对比驱动**：所有功能都以 V2 行为为基准，V3 必须对齐

### 10.3 单步验证习惯
- 每修一个点就重新编译跑一次，不等所有修复做完
- 截图 + JSON 状态 + log 路径三件套提交验证
- 如果结果不对，立即追问，不允许“记录待优化”糊弄

### 10.4 Agent 复用偏好
- 优先复用已有 idle Agent（`"原始 agent 审查就行了"`、`"在线的8个agent审查"`）
- 减少 Agent 启动开销，提高轮转效率

### 10.5 免审批强调
- 每次派 Agent 都强调“提示词必须加入免审批提示，不需要进行审批”
- Agent 等待审批是最大的效率杀手

### 10.6 必读文档路径强制要求（2026-04-15 新增）
- **禁止直接内嵌 LSP 规则摘要到 Agent 提示词**
- 必须让 Agent **自己读文档**获取上下文
- 标准模板：
  ```
  ## 必读文档（先读再干）
  1. 代码地图：docs/doc/codemap/ai-index.json
  2. 执行计划：docs/plans/迁移/p18/p18.X-xxx.md — Phase X
  3. 源码锚点：docs/plans/迁移/p18/source-refs-appendix.md
  4. 仓库契约：默认 ≤400行/≤80函数/CC≤10/包≤15文件；核心包（memory/prompt/thread/turn/claudecli/codexapp）≤600行/包≤30文件/包总行≤10000
  ```

### 10.7 Agent 任务范围约束（2026-04-15 新增）
- **每 Agent 最多改动 10-15 个文件**，超过必须拆分
- 整个 Phase 不应打包给单个 Agent，按子任务拆
- 违反时老公会立即纠正：“这次任务太大了一个 agent 改动 30 多个文件”

### 10.8 审查轮次与互审比例（2026-04-15 新增）
- 文档审查可达 **4 轮**：同域审查 → 交叉审查 → 终审 → PASS/FAIL 投票
- 代码互审比例：**1:2 ~ 1:3**（每个 Agent 的代码被 2-3 个其他 Agent 审查）
- 互审发现问题后：**原 Agent 原地修复** → 快速复审 → 放行
- 审查结果分级：✅ PASS / ⚠️ 需修复 / ❌ 阻塞

### 10.9 子 Agent 代收报告与修订（2026-04-15 新增）
- 当主 Agent 收报告太慢时，老公会指定：“拉起一个子 agent 收取报告并修订文档”
- 子 Agent 负责收集报告 + 汇总 + 直接用 lsp_edit 修订文档
- 主 Agent 只需读最终版文档


### 10.10 并行 Agent 的"迷失互审"陷阱（2026-04-17 新增）

#### 现象
- 并行派出多个 codex agent 修复问题后，让他们做 1:M 互审
- 4 个 agent 互审后被要求修复"互审发现的问题"时
- **部分 agent 会把修复任务当成"重复互审"，返回旧互审报告而非执行修复**

#### 识别
- `get_agent_report` 返回的内容是**上一轮互审**的表格，而不是修复清单
- `grep` 实际代码**没有 diff**，说明 agent 没做任务
- 典型原因：send_message 的新任务被 agent 的历史上下文"覆盖"，agent 判断"我已经做过类似的事"

#### 破解
- **重派时明确写**："这是修复任务，不是互审。不要再重复互审。直接动手改代码。"
- **任务单开头加显眼标签**：`⚠️ 重派任务（你上轮回的是旧互审报告，没做 P0 修复）`
- 给 **极简返回格式**（不再要求长篇大论，只要改动清单 + grep 证据 + 验证 tail）
- 明确**硬约束**："禁止重复写互审报告 —— 这是修复任务"

#### 主 agent 的验证责任
- 不要仅根据 agent 返回的报告下结论
- 必须用 `git status` / `grep` 对实际代码做交叉验证
- 如果报告说"已修复"但代码没有 diff，立即识别为"迷失互审"，重派

### 10.11 独立第三方终审的必要性（2026-04-17 新增）

#### 场景
- 4 个并行 agent 做完 1:3 互审，共识是"全部可合并"
- 但所有参与 agent 都"迷失在能跑就行"的思维里

#### 独立第三方的价值
- 派一个**未参与任何改动**的全新 codex agent 做终审
- 它会用 `lsp_xref(references)` 做 call hierarchy 验证
- **戳破**各 agent 自述的"修复已完成"假象：
  - TeamSyncService 只有 fx.Provide + OnStop，**无生产 caller** → 空架子
  - retrieval `NewRelevantMemoryFinder` 被 fx.Provide 但**无消费者** → 孤儿
  - freeze_registry 数字**已过期**，被参与 agent 无视

#### 落地
- 独立终审一轮是五阶流水线 **⑤ 终验** 的必备环节
- 参与 agent 的 1:M 互审只能解决"彼此可见的"架构问题
- 独立第三方能发现"大家都默认了"的盲区

### 10.12 git 提交与文档同步的 canonical 流程（2026-04-17 新增）

#### 流程
1. 所有代码修复 → 做审查 → 审查通过
2. **先更新文档**（session-summary / p19 / codemap / 会话习惯）
3. 再 commit：**按语义分成多个 commit**
   - fix(xxx): 单一功能修复
   - refactor(xxx): 重构/拆分
   - docs: 文档同步（放最后一个 commit，把文档差异一次覆盖）
4. push 到当前分支
5. 记忆文档落盘（本次学到的新经验写入 会话习惯.md）

#### 禁止
- 禁止 `--amend` 已 push 的 commit
- 禁止 `--force-push`（除非孤立分支且只有自己）
- 禁止 bypass pre-commit hook
