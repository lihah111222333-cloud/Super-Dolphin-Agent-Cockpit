# 调研报告：Agent 上下文窗口（Context Window）大小的确定与展示

> 调研日期：2026-05-16
> 调研方式：5 个并行子代理分别调研 Anthropic Claude Code、OpenAI Codex / GitHub Copilot、Google Gemini CLI、Cursor / Windsurf、开源 Agent（Aider / Cline / Roo Code / OpenCode）
> 各厂商原始调研材料见同目录 `raw-*.md`
> 目的：评估本项目「context window 硬编码成模型名→数字表」的现状，给出去硬编码的演进方案

---

## 1. 背景：本项目现状与问题

### 1.1 用户观察到的现象

终端 UI 工具栏显示 `3% · 24.4k / 872.0k`，其中 `872.0k`（即 `872000`）是写死的。负责人观察到的具体场景是 **GPT-5.5 会话**：GPT-5.5 的有效上下文约 258k，但 UI 上限始终显示 872.0k。

### 1.2 代码事实

本项目有 **两条** provider 路径各自写死了一张「模型名 → 窗口」表。负责人在 GPT-5.5 会话看到的 `872000` 来自 **Codex 路径**，不是 Claude 路径。

**(A) Claude 后端（Go）— `internal/provider/claudecli/context_window.go`**

- `claudeModelContextWindow(model)`：一张硬编码的「模型名 → 数字」表，对小写化后的模型名用 `strings.Contains` / `strings.HasSuffix` 匹配（`best` 为精确匹配）：
  - `haiku` → `400_000 - 64_000`
  - `opus` 且后缀 `[1m]` → `1_000_000 - 128_000` = **872000**
  - `best` / `opus` → `400_000 - 128_000`
  - 后缀 `[1m]` → `1_000_000 - 64_000`
  - 其它 → `400_000 - 64_000`
- `claudeContextWindow(runtimeWindow, model, history)`：`runtimeWindow > 0` 时直接返回运行时值；否则调用 `claudeModelContextWindow`。其模型名来自运行时 `model`，为空时回退读 `settings.json` 的 `model` 字段——`settings.json` 不是「硬编码表之下的另一层窗口源」，只是同一张表的模型名输入兜底。
- Claude 路径优先级链：**`runtimeWindow` 运行时值 > 硬编码表**。

**(B) Codex 后端（Go）— `internal/provider/codexapp/support.go` + `session_dispatch.go`（负责人痛点所在）**

- `support.go:269-272` 有第二张硬编码表 `knownModelContextWindows`：
  - `gpt-5.5` → `872000`
  - `gpt-5.4` → `872000`
- `contextWindowForModel(model)`（`support.go:276-286`）：模型名命中表则返回表值；**模型名为空时直接 `return 872000`**（注释声称子代理应继承「872k capacity」）。
- `session.dispatch`（`session_dispatch.go:13-33`）对每个 provider 事件调用 `contextWindowForModel`，`cw > 0` 时用 `patchContextWindowInPayload`（`:57-77`）改写 payload。该函数对每个键带 `if _, ok := payload[key]; ok` 守卫——**只覆盖 payload 中已存在的 `contextWindowTokens` / `contextWindow` / `modelContextWindow` / `context_window` 键（含 `usage`、`tokenUsage` 嵌套），不注入新键**。
- 关键事实：Codex CLI 运行时事件本就携带这些键（否则 `872000` 不会显示到 UI），所以实际效果是**硬编码值覆盖了 Codex CLI 下发的值**。Codex 路径的实际优先级链是 **硬编码 override > Codex CLI 运行时值**，与 Claude 路径相反。
- `872000` 与 GPT-5.5 无关：它逐字节等于 Claude `opus[1m]` 的 `1_000_000 - 128_000`，是从 Claude 表跨 provider 复制来的常量，并非任何 GPT-5.5 来源给出的数值；再经「空模型 → 872000」分支扩散到所有未显式指定模型的子代理。GPT-5.5 真实窗口在各来源间口径不一（见 §5.2.0），但 `872000` 不在其中任何一个口径里。

**(C) Claude 路径的动态来源已存在但不完整**

- `internal/provider/claudecli/session_events.go:131-172` 的 `handleSystemInitRaw`：`system:init` 事件若带 `context_window` / `contextWindow` / `context_window_tokens` / `contextWindowTokens` 字段，会写入 `session.sessionContextWindow`。
- `internal/provider/claudecli/session_log_watcher_integration.go:149-163`：日志监听器据此发出 `tokens:log_watcher` 事件，带 `context_window`。
- 即 Claude 路径优先级链已是：**`system:init` 运行时值 > 硬编码表**。Codex 路径则相反（见 (B)）。

**(D) 前端（React）**

- `frontend-app/src/entities/client/model/useClientStore.js:2542-2551`：从 `thread/tokenusage/updated` 读取 payload，经过 `normalizeTokenUsage()` 后写入 `tokenUsageByThread`。
- `frontend-app/src/entities/client/model/threadActivityMetrics.js:168-180`：从 `contextWindowTokens` / `context_window_tokens` / `contextWindow` / `context_window` / `modelContextWindow` / `model_context_window` 归一化上下文窗口，并据此计算 `usedPercent`。
- `frontend-app/src/pages/chat/components/RuntimeActivityStats.jsx:27-29`：当前 UI 展示上下文使用百分比；旧 Vue 前端和旧的 `3% · 24.4k / 872.0k` 展示链路已删除。

### 1.3 问题本质

1. **两张硬编码表，且语义不一致**：Claude 路径的表是「运行时值缺失时的兜底」；Codex 路径的表会 override Codex CLI 已下发的窗口字段。后者更危险——它盖掉了 Codex CLI 给出的值。
2. **魔法数**：`872000` = 1M 扣掉 128k 输出预留，把「物理窗口」和「扣减策略」糅在一起写死；Codex 表把它复用到 GPT-5.5，而这个数与 GPT-5.5 毫无来源关系。
3. **靠模型名匹配**：Claude 表靠子串/后缀匹配，新模型/新别名上线可能匹配错或落到错误 default；Codex 表靠精确模型名，新模型不进表就拿不到值，或被「空模型 → 872000」分支误判。
4. **Claude 路径有被动动态源但没有主动查询；Codex 路径连已有的运行时动态源都被 override 盖掉**。

## 3. 各厂商关键发现

### 3.1 Anthropic Claude Code（详见 `raw-claude-code.md`）

- **`GET /v1/models` 直接返回 `max_input_tokens`** —— 这就是「无需硬编码」的权威动态源。`capabilities.context_management` 还描述压缩能力。
- **运行时信号是协议的一部分**：API 在对话中注入 `<budget:token_budget>1000000</budget:token_budget>` 和 `<system_warning>Token usage: 35000/1000000; 965000 remaining</system_warning>`。本项目「`system:init` 带 `context_window` 就用动态值」与此同思路。
- **1M 窗口取决于 beta header**：实际生效窗口 = 模型上限 × 是否启用 `context-1m-2025-08-07`。该 1M beta 计划 2026-04-30 退役，新模型默认即 1M。
- `/context` 命令把占用按 system prompt / tools / MCP / memory / messages 分类展示，并单独扣除「autocompact buffer」。
- 客户端 auto-compact 约 95% 触发；服务端 compaction（`compact-2026-01-12`）按绝对 input token 阈值（默认 150k）触发。

### 3.2 OpenAI Codex / GitHub Copilot（详见 `raw-openai-codex.md`）

- **OpenAI 官方 `GET /v1/models` 不返回 context window** —— 只有 `id`/`created`/`owned_by`。窗口数据只存在于文档页表格，无法程序化读取。这是 Codex 必须维护内置目录的根因。
- **Codex 的踩坑**：内置目录把 GPT-5.5 编码成 `272000`，再乘 95% 系数 → `258400`，即便用户 config 写了 `400000` 仍被压过。**硬编码目录与真实模型脱节的典型案例。**
- **Copilot 是纯动态**：CAPI `/models` 端点的 `capabilities.limits` 返回 `max_context_window_tokens` / `max_prompt_tokens` / `max_output_tokens` 多个字段，且**按账户档位实时变化**。
- 关键区分：`max_context_window_tokens`（总窗口）≠ `max_prompt_tokens`（可用输入预算）。压缩阈值应按可用输入预算算。

### 3.3 Google Gemini CLI（详见 `raw-gemini-cli.md`）

- **Gemini CLI 也是硬编码**：`packages/core/src/core/tokenLimits.ts` 一个 `switch`，`DEFAULT_TOKEN_LIMIT = 1_048_576`，Gemma 系列 256k，其余几乎全 1M。
- **Gemini API 提供动态源**：`models.get` 返回 `inputTokenLimit` / `outputTokenLimit`，但 Gemini CLI 没用它 —— 属可改进点。
- **硬编码的恶果**：写死 1M 跟不上 Gemini 3 Flash 实际只有 200K，产生「负数剩余 token」bug（issue #26188 等）。
- 自动压缩阈值 = `tokenLimit(model) × threshold`（默认 0.5），**上限不准会连锁影响压缩时机**。
- 已知 bug：剩余量计算只减 `promptTokenCount`，漏算 `candidatesTokenCount`（输出 token），导致剩余虚高。

### 3.4 Cursor / Windsurf（详见 `raw-cursor-windsurf.md`）

- **Cursor 是反面教材**：context 指示器（环形 token 计数器）在新版本被移除，社区大量要求恢复。
- **核心教训**：用户把 GPT-5.5 设 272k，但指示器「始终停在 1M」—— **display / enforcement / summarization 是三套不同步的系统**，UI 上限被写死是反复出问题的根因。
- 有效窗口由 `(模型, 模式 Normal/Max, 订阅档位)` 三者决定，单一标量无法表达。
- **Windsurf 做得更好**：footer 实时 context meter，按当前模型窗口归一化；prompt cache 计时器、response card token 明细。
- OpenRouter 被点名为「normalized model catalog」范式：`/models` API 返回 `context_length` 等结构化字段。

### 3.5 开源 Agent（详见 `raw-opensource-agents.md`）

- **几乎没有项目长期维护「模型名→数字」大表**，都依赖集中的模型元数据注册表：
  - **LiteLLM `model_prices_and_context_window.json`** —— 事实标准，社区 PR 维护，含 `max_input_tokens` / `max_output_tokens`。Aider 直接复用。
  - **models.dev** —— OpenCode 用的开放注册表。
  - **OpenRouter `/models` API** —— 运行时返回 `context_length`、`top_provider.context_length`。
- **三层结构是普遍范式**：静态注册表（常见模型）+ 动态 API（长尾/新模型）+ 保守兜底（未知模型）。
- **Aider 的关键理念**：`Aider never enforces token limits, it only reports token limit errors from the API provider` —— context window 仅用于提示/压缩决策，**不做硬拦截**，越界交给 provider 报错。
- **Cline 的工程实践**：`ModelInfo` 统一结构体；OpenRouter 模型动态拉取 + 内存 TTL 缓存（1h）+ 磁盘缓存 + 并发去重；选中模型时把完整元数据快照进 state 支持离线展示。
- **OpenCode 的缓冲实践**：可用上限 = context 上限 − 预留输出（32k）− 安全缓冲（20k）。

## 4. 跨厂商共性结论

1. **没有「官方统一」的动态接口** —— Anthropic / Copilot 有；OpenAI 官方 API 没有。所以「彻底去掉静态数据」不现实，现实目标是「静态数据可被动态值和配置覆盖」。
2. **硬编码表过期是公认痛点** —— Codex（258400）、Gemini CLI（1M 跟不上 200K）、Cursor（停在 1M）都因此出 bug。
3. **优先级链是共识**：`运行时事件/API 动态值` > `用户显式配置` > `静态注册表` > `保守默认兜底`。
4. **窗口不是单一数字** —— 要区分「物理总窗口 / 可用输入预算 / 输出上限」，且受 beta header、运行模式、订阅档位影响。
5. **静态数据应是「数据」而非「代码常量」** —— 用可同步/可配置的注册表 JSON，新模型不必改代码发版。
6. **窗口值用于展示与压缩决策，不做硬拦截** —— 真正越界让 provider 报错。
7. **预留输出缓冲** —— 不要把物理窗口直接当可用上限。

## 5. 对本项目的建议

### 5.1 直接问题：两张表里的 `872000` 魔法数

- Claude 路径 `872000` = `1_000_000 - 128_000`，把「物理窗口 1M」和「128k 输出预留」糅成一个写死的数。
- Codex 路径 `872000` 与 GPT-5.5 无关：它逐字节等于 Claude `opus[1m]` 的值，是跨 provider 复制来的常量，不是任何 GPT-5.5 来源给出的数值。
- 两张表都应**存物理窗口**，预留量由策略在运行时算（见 5.2 第三步）。Codex 路径的 `872000` 应直接删除。

### 5.2 演进方案

#### 5.2.0 先承认：GPT-5.5 的「真实窗口」本身口径不一

本调研的原始材料对 GPT-5.5 窗口给出互相冲突的口径，必须先消歧，否则「跟随真实窗口」无法验收：

| 来源 | 数值 | 说明 |
|---|---|---|
| `raw-openai-codex.md` issue #19319 | 400K（272K 输入 + 128K 输出） | 该处把 400K 称作「官方」窗口 |
| `raw-openai-codex.md` §3（OpenAI 文档页面） | 1M | 文档展示数据，不可程序化读取 |
| Codex CLI 内置目录 | 272000（输入侧）→ ×95% → 258400 | 删除 override 后用户将在 UI 看到的有效值 |
| 本项目当前硬编码 | 872000 | 从 Claude 复制的常量，应废弃 |

- **结论一**：这几个数没有一个能被本项目程序化、权威地拿到——OpenAI 官方 `/v1/models` 不返回窗口（§3.2）。这恰恰是「不能靠硬编码、必须有可配置/可覆盖来源」的根本理由。
- **结论二**：报告自身的原始材料就存在 400K 与 1M 的矛盾。定稿落地前需到 OpenAI 官方模型页核实 GPT-5.5 的 Context window，给出本项目采信的权威口径并标注核实日期；在此之前不把任何一个数署成「OpenAI 文档」既定值。
- 注意：用户**当前**在 UI 看到的是 override 后的 `872000`（见 §1.1）；Codex CLI 目录口径（约 258k）是删除 override（第一步）后才会显示的值。

#### 5.2 第一步（最高优先级）：删除 Codex 的 `872000` override

- 直接删除 `support.go` 的 `knownModelContextWindows`（`:269-272`）与 `contextWindowForModel` 的「空模型 → return 872000」分支（`:278-284`）。
- 删除后 `contextWindowForModel` 恒返回 0，`session_dispatch.go:27` 的 `cw > 0` 守卫恒为假，`patchContextWindowInPayload` 不再执行——**Codex CLI 自己下发的窗口值原样透传到 UI**，无需新增「填充」逻辑。
- 效果与边界：GPT-5.5 不再显示 `872000`，改为显示 Codex CLI 目录口径（约 258k）。**但这只解决了「不再写死那个错误常量」**：Codex CLI 下发的窗口值来自它自己的静态目录（`raw-openai-codex.md` §1.3：运行时事件只负责用量展示，窗口上限本身仍来自静态 catalog），并非 OpenAI API 动态值，issue #19319 表明该目录值本身也可能偏差。
- 因此「跟随真实窗口」还需配合第二步的可配置 / 可覆盖来源。

#### 5.2 第二步：建立「可配置 + 可覆盖」的窗口来源链

去硬编码的本质不是「换一个数据文件」，而是让窗口值能被更可信的来源覆盖。建议 Codex 路径优先级链：

1. **用户显式配置（最高）**：尊重 Codex config 的 `model_context_window`（Codex 自身最高优先级旋钮，见 `raw-openai-codex.md` §1.2）。这是「不写死、可配置」的核心出口。
2. **项目校正注册表（可覆盖 CLI 偏差值）**：一份仓库内 vendored 的模型元数据 JSON。与上一版方案不同——它**必须保留覆盖 CLI 值的能力**（CLI 事件恒带窗口字段，「仅 CLI 未下发时生效」是不可达分支），用于在「已确认 Codex 目录值偏差」时填入正确值。每条目须带 `provider`、`contextWindow`（物理窗口）、`maxOutputTokens`、`source`、核实日期。GPT-5.5 是否进此表、填什么值，取决于 5.2.0 的核实结论。
3. **Codex CLI 运行时值（默认）**：无上述覆盖时透传 CLI 目录值，并在日志中标注「值来源 = Codex CLI 目录，可能偏差」，便于发现脱节（参考 Aider warning）。
4. **保守默认（兜底）**：未知模型用偏小常量（按 provider 分别设，例如 200k）。

Claude 路径同样把 `claudeModelContextWindow` 子串表替换为同一份 JSON 注册表；对支持的 provider 可加主动查询：Anthropic `GET /v1/models` 读 `max_input_tokens`、OpenRouter `GET /models` 读 `context_length`（取 `min(context_length, top_provider.context_length)`）。OpenAI 官方 API 不返回窗口，Codex 路径不靠主动查询，依赖上面的「配置 + 校正注册表 + CLI 透传」。

**注册表维护与同步**：提供 vendoring 脚本从 LiteLLM/models.dev 拉取并 diff，纳入 CI 校验（过期 / 缺项告警）；LiteLLM 未必收录 OpenAI 内部新模型，这类条目手填并标 `source` 与日期。**主动查询缓存**：内存 TTL（1h）+ 磁盘兜底 + 并发去重，缓存 key 含 `(provider, model, 是否启用 1M beta)`，切换模型时失效对应条目，首次离线无缓存时降级到保守默认。

#### 5.2 第三步：保守兜底 + 输出缓冲

- 注册表存物理窗口，可用上限 = `物理窗口 − 预留输出 − 安全缓冲`，把扣减逻辑从硬编码数字里拆出来。
- 窗口值仅用于「展示 + 触发压缩」，不做硬拦截——越界交给 provider 报错（本项目已有 `permanent_context_length_exceeded` 分类，见 `useAutoContinue.js` / `ContextUsageBanner.js`）。

### 5.3 展示层建议

- `formatTokenInline` 等展示「已用 / 可用上限」时，可用上限应来自合并后的窗口值。
- 用兜底值（非 provider 真值）时，在日志/调试信息中可识别（参考 Aider 的 warning），便于发现「provider 没下发 `context_window`」。
- 可参考 Claude Code `/context`、Windsurf footer meter：把 autocompact buffer 单独标示。

### 5.4 注意点

- **`[1m]` 这种别名**应拆成「基础模型 + 是否启用 1M」，由 beta header 生效状态决定窗口，不要直接靠模型名映射最终数字。需明确本项目「1M 是否启用」的信号来源（beta header 在哪设）。Anthropic `context-1m-2025-08-07` beta 的退役时间需到 Anthropic 官方公告核实后再下结论，在此之前不据推测简化该机制——`claudecli/context_window.go` 的 `[1m]` 后缀匹配与 `872000` 目前仍在。
- **窗口 vs 可用预算**要分清，压缩阈值按可用预算算（避免 Copilot #298900 式过早压缩）。
- **保证 UI 与 enforcement 同源**（避免 Cursor 式「指示器停在 1M」脱节）。
- **Codex override 是优先级反转**：修复时确保 Codex 与 Claude 两条路径优先级链一致（用户配置 > 校正注册表 > 运行时值 > 默认）。
