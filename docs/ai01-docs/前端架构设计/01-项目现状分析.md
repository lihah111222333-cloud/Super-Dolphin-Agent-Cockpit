# 前端架构项目现状分析

生成时间：2026-06-11

## 1. 结论摘要

当前有效前端是 `frontend-app/` 下的 React/Vite 应用，桌面宿主仍由 `cmd/agent-terminal` 提供 Wails/HTTP/RPC 桥接。`cmd/agent-terminal/frontend` 是 legacy/package-embed Vue 路径，本轮架构扫描不把它作为当前产品 UI 的主要修改对象。

本轮只做静态扫描、架构分析和基线验证，未修改 `frontend-app` 源码。当前前端 lint、测试、构建均可通过；构建阶段存在 Vite 大 chunk 警告，说明首屏 JS 体积和页面级拆包是后续性能优化的高价值入口。

## 3. 当前接口调用方式

当前主链路：

```txt
Page / Store
  -> frontend-app/src/shared/api/backendApi.js
  -> frontend-app/src/shared/api/wailsBridge.js
  -> Wails runtime / Go RPC
```

关键事实：

- 页面中未发现散落的 `fetch(...)` 或 `axios(...)`。
- `backendApi.js` 是当前前端 RPC facade，集中声明 `RPC_METHODS`、参数校验、payload 标准化和具名导出。
- `wailsBridge.js` 是 Wails runtime adapter，负责 runtime 动态加载、`callAPI`、trace 注入、日志脱敏、RPC 成功/失败记录。
- 已有 `backendApi.surface.test.js` 和 `backendApiConsumer.surface.test.js`，用于阻止产品代码直接调用 raw `callAPI` / `callBackend`。

当前不足：

- 多个页面直接 import `shared/api/backendApi.js` 的具名 RPC facade。虽然不是裸 Wails 调用，但仍让页面直接消费后端接口形状。
- DTO 归一化分散在页面、`pageShared.js` 和 store 中，尚未形成领域 adapter 层。
- 统一错误结构、超时、取消、重复请求、loading 状态更多依赖页面自行处理，缺少统一 service/hook 语义。

## 4. 当前组件组织方式

当前应用壳位于 `App.jsx`，职责包括：

- QueryClient 创建。
- 页面路由和 `window.history` 同步。
- 主题读取与切换。
- 顶栏、导航栏、页面容器装配。
- 记忆中心 badge 查询。
- Chat 页部分工具栏动作。

主要页面基本按单文件组织：

- `ChatPage.jsx`：聊天主页面，包含 thread rail、conversation、composer、markdown 渲染、mermaid、runtime panel、diff/code preview、拖拽/粘贴等多个子系统。
- `WorkflowPage.jsx`：工作流列表、详情、运行、节点诊断、最终输出、计划配置混在一个文件。
- `SkillsPage.jsx`：技能列表、编辑、导入、简介生成、冲突处理混在一个文件。
- `SettingsPage.jsx`：运行时设置、更新、provider 偏好、prompt 注入、内置工具、日志、视频 API Key 混在一个文件。
- `MemoryPage.jsx`：记忆列表、编辑、删除、相似整合、自动沉淀混在一个文件。

现状说明：

- 部分页面已经抽出了本地 hooks，例如 `useMemoryDashboard`、`useSharedFilesDashboard`、`useWorkflowPageController`、`useSkillsPageModel`。
- 这些 hooks 仍保留在页面文件内，不能复用，也不能有效降低文件认知成本。
- 展示组件与业务动作虽然有一定分离，但很多展示组件仍直接接收 store 或 action runtime 对象，职责边界不稳定。

## 5. 当前状态管理方式

全局状态集中在 `entities/client/model/useClientStore.js`，使用 Zustand。

该 store 当前承担：

- bootstrap 和窗口状态恢复。
- 项目列表、当前项目、项目切换。
- 会话列表、当前会话、归档、删除、重命名、复制。
- composer 草稿、附件、文件选择、拖拽/粘贴附件保存。
- thread start / turn start / interrupt / force complete / recover。
- runtime event、bridge event、assistant delta 合并。
- timeline normalization、thread message pagination。
- fork thread 草稿、共享文件加载、继承对话创建。
- action notice、warning、runtime result entries。

优点：

- 关键行为集中，现有测试覆盖较多。
- 对 cwd/threadId 等关键字段有 fail-fast 思路。
- 运行时事件和 timeline 逻辑在一个位置便于追踪完整链路。

不足：

- 文件过大，单个 store 同时承担接口编排、DTO 转换、业务规则和 UI feedback。
- 页面通过 `useClientStore()` 订阅整个 store，容易引发宽范围 re-render。
- slice 边界缺失，新增行为很容易继续堆叠到同一个文件。

## 7. 性能现状

已确认风险：

- `App.jsx` 静态 import 所有页面，没有页面级 `React.lazy`/`Suspense`。
- `npm run build` 通过，但 Vite 提示大 chunk：
  - `dist/assets/index-*.js` 约 538 KB。
  - 另一个 chunk 约 594 KB。
- `ChatPage.jsx` 包含 markdown、mermaid、timeline、runtime panel 等大量逻辑；虽然 mermaid 已动态 import，但 Chat 主 chunk 仍偏重。
- `useClientStore()` 在 `AppShell` 里整体订阅 store，状态更新时容易扩大渲染影响面。
- 多个列表直接 `.map()` 渲染。Chat timeline 已有增量 materialization，其它页面的技能、工作流、记忆、文件列表尚无统一分页/虚拟滚动策略。

已有正向设计：

- Chat timeline 存在 `TIMELINE_INITIAL_MATERIALIZED_MESSAGES` 和增量加载策略。
- Markdown blocks 和 timeline message 已有部分 `React.memo`。
- Mermaid 使用动态 import。
- React Query 已用于多个 dashboard 页面，并有 focus invalidation 工具。

后续优化原则：

- 先以构建 chunk、React render 路径和用户可感知页面为依据定位瓶颈。
- 不为了“看起来高级”无差别加 `memo`。
- 优先页面级 lazy loading、store selector 收窄、长列表增量渲染和大计算缓存。

```bash
cd frontend-app

```

结果：

- `npm run lint`：通过。
- `npm test`：24 个测试文件通过，653 个测试通过，10 个跳过。
- `npm run build`：通过，Vite 报大 chunk 警告。

说明：

- 当前没有证据表明存在 P0 阻断性功能故障。
- 后续每个重构阶段必须重新运行匹配改动面的验证命令。
- 只要进入 UI 可见改动，还需要使用浏览器验证关键页面。
