# 前端架构问题清单与优先级

生成时间：2026-06-11

## 1. 优先级定义

| 优先级 | 定义 |
| --- | --- |
| P0 | 影响功能正确性、导致用户无法使用、可能造成数据丢失或白屏的已证实问题 |
| P1 | 明显影响性能、维护性、扩展性或架构边界的问题 |
| P2 | 代码质量、可读性、规范一致性问题，短期不阻断功能但会增加长期成本 |
| P3 | 可优化但不紧急的问题 |

当前基线 lint、测试、构建通过，因此本轮未提升任何问题到 P0。后续如果在执行阶段发现可复现功能故障，应以新证据重新定级。

## 2. 问题总表

| 优先级 | 问题 | 位置 | 原因 | 影响 | 建议 |
| --- | --- | --- | --- | --- | --- |
| P0 | 暂未确认阻断性功能故障 | 当前基线 | `npm run lint`、`npm test`、`npm run build` 均通过 | 无已证实 P0 | 文档中记录“未发现 P0”，后续每阶段继续验证 |
| P1 | 聊天页面超大且职责混杂 | `frontend-app/src/pages/chat/ChatPage.jsx`，6542 行 | 页面、布局、composer、thread rail、timeline、markdown、文件拖拽、runtime panel、代码预览混在一起 | 改动风险高，性能问题难定位，测试难聚焦 | 先拆纯函数/markdown/runtime panel，再拆 hooks 和展示组件 |
| P1 | 全局 store 过大 | `frontend-app/src/entities/client/model/useClientStore.js`，5716 行 | Store 同时做 RPC 编排、DTO 归一化、运行时事件合并、UI notice、草稿、项目管理 | re-render 影响面大，职责边界不清，新增行为容易继续堆叠 | 按 thread/project/runtime/composer/fork 分 slice，保留 `useClientStore` 门面 |
| P1 | API facade 单文件过大 | `frontend-app/src/shared/api/backendApi.js`，1322 行 | 所有 RPC 常量、payload 校验、业务 facade 都集中 | 新接口容易继续堆叠，缺少领域 service/adapters | 保留低层 facade，新增 `services/modules/*Service.js` 和 adapters |
| P1 | 页面直接 import backend facade | Settings、Skills、Workflow、Prompt、Memory、Files、Observability、Chat | 页面直接消费 RPC facade，缺少 service/adapter 中间层 | UI 容易被后端 DTO 污染，加载/错误语义不一致 | 页面改为依赖 hooks/services，DTO 只在 adapter 层出现 |
| P1 | 首屏静态导入过多页面 | `frontend-app/src/App.jsx` | 所有页面同步 import，未使用页面级 lazy loading | 首屏 JS 体积偏大；build 已报 >500 KB chunk 警告 | 引入 `React.lazy` / `Suspense` 页面级 code splitting |
| P1 | 直接触碰 Wails 全局对象 | `frontend-app/src/pages/chat/ChatPage.jsx` markdown link 打开逻辑 | `window.wails.Browser.OpenURL` 绕过 API 边界 | 平台差异、测试、错误处理和日志不可统一 | 增加 `openExternalUrl` facade/service，再替换页面直连 |
| P1 | 全局 CSS 超大 | `frontend-app/src/styles.css`，8533 行 | 所有页面样式集中在单文件 | 样式影响面不清，主题维护和回归定位成本高 | 保持 token 合约，按 app/pages/shared 分段迁移 |
| P1 | 应用壳职责偏多 | `frontend-app/src/App.jsx`，512 行 | 路由、主题、QueryClient、导航、Titlebar、memory badge、页面装配混在一起 | 首屏拆包和局部测试困难，Chat 专属动作泄露到壳层 | 拆到 `app/providers`、`app/routes`、`app/shell` |
| P2 | 超大函数/组件 | `Conversation`、`attachAssistantEventRuntime`、`createForkThreadActions` 等 | 单函数承载多个副作用和分支 | 难测试，容易引入回归 | 先抽纯函数和小 hooks，再迁移组件 |
| P2 | 请求状态模型不统一 | 多页面 | React Query、local state、`notice`、`busyKey`、`actioning` 混用 | 用户反馈风格不统一，重复提交防护分散 | 建立 `useRequest` / `useAsyncAction` / mutation pending 规范 |
| P2 | Adapter 分散在页面/store | `pageShared.js`、各 Page、`useClientStore.js` | DTO normalization 就地实现 | 重复逻辑和后端字段泄露 | 建立领域 adapters，service 输出 ViewModel |
| P2 | 长列表策略不统一 | Thread/timeline/skills/workflows/memory/files | Chat timeline 有增量 materialization，其它页面多为直接 map | 数据增大后可能卡顿 | 高风险列表先分页/折叠/增量渲染，暂不新增虚拟滚动依赖 |
| P2 | 测试文件超大 | `App.test.jsx`、`ChatPage.test.jsx`、`useClientStore.test.js` | 页面和 store 超大导致测试集中 | 修改定位慢，fixture 复用困难 | 跟随模块拆分同步拆测试 |
| P2 | 底层 bridge 单文件偏大 | `frontend-app/src/shared/api/wailsBridge.js`，1182 行 | runtime 加载、日志、trace、RPC、文件选择等集中 | 维护成本高，但职责仍集中在 bridge 层 | 暂不优先拆；先通过 apiClient/service 收口上层 |
| P2 | 页面内本地 hooks 不可复用 | 多个 `*Page.jsx` | hooks 定义在页面同文件 | 文件仍大，复用和单测困难 | 迁移到 page-local `hooks/` |
| P2 | 表单校验逻辑分散 | Settings、Prompt、Skills、Memory | 校验、提交、notice 分布在组件和 hooks 中 | 错误提示和 disabled 条件不一致 | 表单状态、校验、提交拆分成 hooks/utils |
| P3 | 当前目录层级命名不统一 | `features/prompts` 与 `pages/prompts` 并存 | 历史演进 | 新人理解成本高 | 保持兼容，逐步统一到 page-local modules 或 domain modules |
| P3 | 类型定义缺失 | 多数 JS 文件 | 当前项目未引入 TS，ViewModel 形状靠约定 | IDE 和重构辅助有限 | 先用 JSDoc/adapter contract 文档，暂不引入 TS 迁移 |
| P3 | 样式和组件边界同步不足 | `styles.css` 与各 Page | 样式全局选择器和页面结构紧耦合 | 拆组件时容易遗漏样式影响面 | 拆组件时同步迁移页面样式块或建立样式索引 |

## 3. P1 重点问题说明

### 3.1 `ChatPage.jsx` 职责过载

`ChatPage.jsx` 是最大风险文件。它同时处理：

- 页面布局和宽度拖拽。
- Thread rail 列表、置顶、归档、删除、重命名入口。
- Conversation、timeline、滚动保持、历史分页。
- Composer、附件、粘贴、拖拽、发送和中断。
- Markdown inline/block 渲染、图片预览、mermaid、表格、directive token。
- Runtime panel、activity stats、warning/result entries、diff preview。
- 代码定位、打开和保存。

风险：

- 任意小 UI 修改都可能触碰复杂行为。
- 页面级测试难以定位具体子系统回归。
- 性能优化必须先拆出可观察边界。

建议拆分顺序：

1. 抽纯函数：markdown/token/render helper、timeline sorting、file/path helper。
2. 抽展示组件：RuntimePanel、ThreadRail、ComposerDock、Conversation。
3. 抽 hooks：timeline materialization、layout resize、composer interactions。
4. 抽 service：chat page 里的 code/file/external URL 动作。

### 3.2 `useClientStore.js` 职责过载

`useClientStore.js` 是全局业务协调中心。它目前同时导入大量 RPC facade，并处理：

- 项目和会话 RPC。
- runtime event/bridge event。
- timeline DTO 标准化。
- assistant delta 缓冲和 flush。
- fork thread 创建和 kickoff。
- UI notice、warning、runtime logs。

风险：

- Store 变化很容易影响全应用。
- 页面订阅整个 store 时，局部状态也可能触发大范围 re-render。
- DTO adapter 和业务 action 难分层。

建议拆分顺序：

1. 先抽纯 adapter/helper，不改变对外 store API。
2. 再抽 action factory 到 slice 文件。
3. 最后收窄页面 selector，避免 `useClientStore()` 全量订阅。

### 3.3 接口层缺少领域 service

当前 `backendApi.js` 已经是重要边界，但它仍是 RPC facade，不是 UI service。页面直接 import facade 时，容易把后端字段、RPC 命名、参数校验细节带进 UI。

建议目标：

```txt
Page
  -> page hook
  -> services/modules/domainService.js
  -> adapters/domainAdapter.js
  -> shared/api/backendApi.js
  -> shared/api/wailsBridge.js
```

第一阶段不强行改后端 wire shape，不要求 Go 端统一 `{ code, message, data, requestId }`。前端先在 service 层归一化错误、空数据、ViewModel、重复提交和加载语义。

### 3.4 首屏性能和 code splitting

`App.jsx` 静态导入所有页面：

- Chat
- Files
- Memory
- Observability
- Prompt
- Settings
- Skills
- Workflow

构建已提示大 chunk。页面级 lazy loading 是低风险、高收益的第一步。注意 fallback 必须稳定，不改变当前 bootstrap/route 行为。

## 4. 暂不建议立即做的事项

| 事项 | 原因 |
| --- | --- |
| 一次性重写所有页面目录 | 风险过高，现有测试成本大，容易破坏功能 |
| 一次性把 JS 迁移到 TS | 当前任务目标是架构边界，不应叠加语言迁移风险 |
| 立即引入虚拟滚动依赖 | 需要先用真实数据量证明收益；当前可先分页/增量渲染 |
| 修改 Go 后端响应格式 | 影响范围大，当前可先用前端 service adapter 兼容 |
| 拆 `wailsBridge.js` | 底层职责相对集中，上层 service 边界更紧急 |
| 拆 legacy Vue 前端 | 不属于当前有效产品 UI 范围 |

## 5. 验收关注点

每个阶段完成后至少检查：

- 是否只改目标文件。
- 是否没有引入无关依赖。
- 页面是否仍只通过 service/hook 消费数据。
- 新 adapter 是否屏蔽后端原始 DTO。
- loading/error/empty/disabled/success 状态是否保持或增强。
- mutation 是否有 pending/disabled 防重复提交。
- `npm run lint` 是否通过。
- 相关测试是否通过。
- `npm run build` 是否通过。
- UI 可见改动是否经过浏览器验证。
