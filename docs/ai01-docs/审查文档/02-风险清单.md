# 风险清单

## 高风险问题

### H1. Provider 语义和实际装配不一致

证据：

- `frontend-app/src/entities/client/model/useClientStore.js:238`：`claude` 会被归一化为 `codex`。
- `frontend-app/src/entities/client/model/useClientStore.js:259`：后续又保留 `provider === 'codex' ? 'codex' : 'claude'` 的分支。
- `internal/app/modules.go:85`：`claudecli.Module` 被注释。
- `internal/app/modules.go:86`：只装入 `codexapp.Module`。

影响：

- 如果产品仍宣称 Claude 和 Codex 都可选，当前 UI 偏好会把 Claude 静默导向 Codex。
- 如果产品当前只支持 Codex，文档、provider 抽象和部分 UI 语义没有同步收窄。
- 这类问题会出现在 thread/start 之前，容易表现为“启动成功但 provider 不对”。

建议：

- 先做产品决策：当前桌面是否只支持 Codex。
- 只支持 Codex：删除或禁用 Claude UI 选项，并让错误文案明确。
- 支持 Claude：恢复 `claudecli.Module` 装配，并补完整 `settings.provider.active=claude` 到 `thread/start` 的前后端测试。

### H2. 新 UI 跨语言契约缺少编译期保护

证据：

- `frontend-app/tsconfig.json` 不存在。
- `frontend-app/jsconfig.json` 不存在。
- `frontend-app/src/shared/api/backendApi.js:1102-1114` 手写 `thread/start` payload。
- `frontend-app/src/shared/api/backendApi.js:1117-1135` 手写删除 UI-only keys。
- Go 侧 `internal/module/thread/rpc_types.go` 对 unknown field 有 strict rejection。

影响：

- 前端重命名字段或新增 nested `config` 时，只有测试覆盖到的路径会暴露问题。
- provider identity 这类字段同时经过 preference、store、API facade、Go decoder、provider adapter，多一层手写整形就多一处漂移点。

建议：

- 短期：给 `thread/start`、`turn/start` 的前端 payload builder 加表驱动测试，覆盖 unknown field、nested config、camel/snake 兼容、缺字段 fail-fast。
- 中期：引入 `jsconfig.json` + `checkJs` 或在 `shared/api`、`entities/client/model` 先迁移 TypeScript。
- 长期：从 Go RPC DTO 或 OpenAPI-like manifest 生成前端方法名和 payload 类型。

### H3. UI 状态、页面和 CSS 文件过大，重构回归面失控

证据：

- `frontend-app/src/styles.css`：10073 行。
- `frontend-app/src/entities/client/model/useClientStore.js`：4786 行。
- `frontend-app/src/pages/chat/ChatPage.jsx`：3641 行。
- `frontend-app/src/App.jsx:603-666` 的 app shell selector 一次性订阅大量 store 字段。

影响：

- UI refactor 的视觉改动、状态改动、RPC 改动容易落在同一批大文件里。
- 大 selector 和大 CSS 文件会让局部改动难以定位真实依赖。
- 测试文件也很大，`App.test.jsx` 超过 7k 行，回归测试可维护性下降。

建议：

- 先拆“已经有天然边界”的部分：provider preferences、thread lifecycle actions、timeline materialization、composer state、layout CSS。
- 拆分时只移动代码，不改行为；每个 slice 用当前测试锁住。
- 不建议一次性重构整个 store 或整个 CSS。

### H4. Windows/Unix 构建与启动链路不等价

证据：

- `Makefile:56` 使用 `rsync` 同步 `frontend-app/dist` 到 `cmd/agent-terminal/frontend/dist`。
- `run-new-ui-desktop.sh:1008` 先启动 Vite，`run-new-ui-desktop.sh:1012` 再启动 backend。
- `run-new-ui-desktop.ps1:777-785` 先启动 backend 并等待 `/metrics`。
- `run-new-ui-desktop.ps1:789-796` 再启动 Vite。
- `run-new-ui-desktop.sh:954` 默认 `SUPER_DOLPHIN_HOME` 在 `/tmp/...`。
- `run-new-ui-desktop.ps1:726` 默认 `SUPER_DOLPHIN_HOME` 在用户目录 `.super-dolphin`。

影响：

- CI Ubuntu 通过不代表 Windows 原生 PowerShell 可复现。
- 不同启动顺序可能影响 Wails dev proxy、metrics readiness、provider preference seed、端口占用恢复。
- `rsync` 在 Windows 原生环境通常不是默认可用工具。

建议：

- 用 PowerShell 原生同步命令或 Node 脚本替代 `rsync`，或者明确要求 Git Bash/WSL。
- 给 `.sh` 和 `.ps1` 建立最小等价性检查：端口、home、provider env、preflight、ready URL、cleanup。

## 中风险问题

### M1. 文档入口和版本口径漂移

证据：

- `README.md:31` 写 Go 1.23+。
- `go.mod:3` 和 `AGENTS.md:52` 是 Go `1.25.7`。
- `CLAUDE.md:79` 仍描述 `cmd/agent-terminal/frontend` 为 Vue/Vite 前端包。
- `AGENTS.md:67` 和 codemap 明确当前 UI 是 `frontend-app`。

影响：

- 新代理和新开发者容易误改 legacy UI。
- 版本不一致会导致本地环境排错成本增加。

建议：

- 统一 README、AGENTS、CLAUDE、codemap 中的 Go 版本和当前前端入口。
- legacy 文档保留，但必须明确“只在 package-embed/legacy 任务中编辑”。

### M2. UI action error 被吞掉

证据：

- `frontend-app/src/App.jsx:270-278` 的 `runUIAction` 对同步 error 和 Promise rejection 都 `void` 掉。

影响：

- 如果 action 本身没有写入 store error，UI 操作失败不会被用户或日志感知。
- 对 refactor 后的导航、弹窗、文件选择、provider 操作不利。

建议：

- 保持现有交互不被打断，但至少统一写入 `actionNotice` 或 frontend log。
- 对预期可失败的 action 增加明确 catch 和用户反馈。

### M3. Fail-fast 策略和现有 fallback 行为存在张力

证据：

- `AGENTS.md` 明确禁止隐式兜底。
- `internal/ui/wails/assets.go:47` 对非法 `VITE_DEV_URL` 记录错误后 fallback 到 embedded assets。
- `internal/app/modules.go:77-81` 注释里描述 cron/notify/insight optional dependency 缺失时 noop 降级。

影响：

- 启动配置错误可能被旧资源或 noop 行为掩盖。
- 桌面启动和测试环境的行为可能不一致。

建议：

- 对用户可配置项和开发入口使用 fail-fast。
- 如果某些 noop 是架构决策，写入 ADR 或注释说明其边界，不要让它看起来像普通错误兜底。

### M4. CI 策略和仓库 wrapper 策略不完全一致

证据：

- `.github/workflows/ci.yml:55` 使用 `go vet ./...`。
- `.github/workflows/ci.yml:57` 使用 `go build ./...`。
- `AGENTS.md` 和 Makefile 更强调 guard wrapper 与显式 package pattern。

影响：

- 本地和 CI 检查口径可能出现差异。
- 新增 script-only 或 generated package 时，`./...` 可能扩大或改变 CI 面。

建议：

- 要么把 CI 改为 Makefile 封装目标，要么在 CI 注释中说明为什么这里使用 raw `go vet/build ./...`。

### M5. 审查基准包含未提交改动

证据：

- `git status --short` 显示 3 个前端文件已修改。

影响：

- 当前报告审查的是 `29c46e57 + working tree`，不是纯 branch HEAD。
- 后续如果只看远端分支，会复现不了本报告中的 provider identity 测试状态。

建议：

- 在合并、PR 或二次审查前先决定这 3 个文件是提交、拆分还是丢弃。
- 报告、测试和 PR 描述都要明确审查基准。
