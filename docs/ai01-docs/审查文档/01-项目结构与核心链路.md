# 项目结构与核心链路

## 项目结构概览

| 区域 | 角色 |
|---|---|
| `cmd/agent-terminal` | 桌面宿主和 HTTP/Wails 入口。`main.go:36` 调用 `app.RunDesktop(frontendDistFS())`。 |
| `cmd/mcp-orch` | 独立 orchestration peer，承载 agent 生命周期、DAG、cron、tool registry 等能力。 |
| `cmd/mcp-lsp` | 多语言 LSP peer。 |
| `internal/app` | Fx 根装配层，负责组合 platform、store、module、provider、UI。 |
| `internal/contract` | 跨模块和跨 root package 的稳定接口/DTO。 |
| `internal/module` | 业务模块，包括 thread、turn、memory、prompt、skill、cron、dashboard、uistate 等。 |
| `internal/platform` | 基础设施，包括 rpc、toolbridge、mcpcontrol、hooks、config、db、event surface 等。 |
| `internal/provider` | Provider 适配层，当前装配 Codex App，保留统一 provider 抽象。 |
| `internal/store` | sqlc-backed store，按业务域拆分 adapter。 |
| `frontend-app` | 当前 React/Vite 新 UI。 |
| `cmd/agent-terminal/frontend` | legacy Vue/Vite embed 路径，只在 package-embed/legacy 任务中编辑。 |

## 前端入口链路

开发态：

1. `run-new-ui-desktop.sh` 或 `run-new-ui-desktop.ps1` 设置 `VITE_DEV_URL`、`SUPER_DOLPHIN_HTTP_ADDR`、provider dev preferences。
2. `frontend-app` 启动 Vite，默认 `127.0.0.1:5175`。
3. `cmd/agent-terminal` 启动 Go/Wails 宿主。
4. `internal/ui/wails/assets.go:36` 检测 `VITE_DEV_URL`，优先代理到 Vite。
5. `frontend-app/src/main.jsx` 挂载 React 应用。
6. `frontend-app/src/App.jsx` 组装 shell、路由、页面和全局状态选择器。

打包态：

1. `make frontend-app-build` 在 `frontend-app` 执行 `npm run build`。
2. `Makefile:56` 用 `rsync -a --delete frontend-app/dist/ cmd/agent-terminal/frontend/dist/` 同步到 legacy embed 目录。
3. `cmd/agent-terminal/frontend.go:15` 把 embed FS 交给桌面宿主。

## UI 到后端 RPC 链路

核心路径：

1. 页面或组件调用 Zustand store action。
2. `frontend-app/src/entities/client/model/useClientStore.js` 负责状态、偏好、thread/turn 生命周期编排。
3. `frontend-app/src/shared/api/backendApi.js` 负责 RPC 方法名和 payload 整形，例如 `thread/start`、`turn/start`。
4. `frontend-app/src/shared/api/wailsBridge.js:801` 调用 Wails runtime 或 RPC bridge。
5. `internal/ui/wails/binding.go:50` 的 `CallAPI` 接收方法名和 JSON 参数。
6. `internal/ui/wails/module.go:55` 把 `CallAPI` 转到 `contract.RPCDispatcher.Dispatch`。
7. `internal/platform/rpc` 分发到 module handlers。
8. 业务模块调用 store、provider、toolbridge、mcpcontrol。

对话首发路径：

1. `ChatPage` / composer 触发 `sendDraft()`。
2. `useClientStore` 读取 cwd、provider、model、prompt、agent、tool surface、Codex identity。
3. `backendApi.threadStartPayload()` 生成 `thread/start` 请求。
4. Go 侧 `internal/module/thread/rpc.go` 和 `rpc_types.go` 做 strict decode。
5. thread 创建或 pending launch 完成后，UI 继续调用 `turn/start`。
6. `internal/module/turn/service.go:202` 通过 provider session 发起 turn。

## Provider 链路

设计上：

- `internal/contract/provider.go` 定义 `Driver`、`Session`、`TurnHandle`。
- `internal/provider/unified` 聚合 provider drivers，并提供 `SessionResolver`。
- `internal/module/thread` 通过 provider session provider 启动或恢复 session。
- `internal/module/turn` 通过 `Session.StartTurn` 提交 turn。

当前装配上：

- `internal/app/modules.go:83` 装入 `unified.Module`。
- `internal/app/modules.go:85` 注释掉 `claudecli.Module`。
- `internal/app/modules.go:86` 装入 `codexapp.Module`。
- `internal/app/modules.go:87-89` 始终装入 toolbridge 及 Codex binding。

这说明当前桌面 app 的实际 provider 运行面偏 Codex。文档和部分 UI 仍保留 Claude 语义，需要在产品层明确。

## 工具系统链路

工具能力分成三层：

1. Provider-native mirror：skill 模块把 canonical skills 生成到 provider 可发现目录。
2. Host toolbridge：`internal/platform/toolbridge` 在桌面宿主内注册 host-direct 工具，例如 memory read/write。
3. MCP peer：`cmd/mcp-orch`、`cmd/mcp-lsp` 等作为独立工具 peer，通过 `mcpcontrol` 受控启动和连接。

架构优点是能力边界清楚，缺点是可用性判断跨越 provider mirror、toolbridge、mcpcontrol 和 peer runtime。审查时需要避免只看一个 registry 就断言工具可用。

## 状态管理链路

新 UI 当前状态结构：

- 全局 store：`frontend-app/src/entities/client/model/useClientStore.js`
- 局部 slices：`composerSlice.js`、`forkSlice.js`、`projectSlice.js`、`runtimeSlice.js`
- 页面级状态：`ChatPage.jsx`、`SettingsPage.jsx`、`SkillsPage.jsx`、`WorkflowPage.jsx`
- 服务 facade：`frontend-app/src/shared/api/backendApi.js`
- Wails adapter：`frontend-app/src/shared/api/wailsBridge.js`

主要问题不是 Zustand 本身，而是 `useClientStore.js` 同时承担 bootstrap、thread list、composer、preferences、provider config、events、warnings、runtime result 等多类职责。当前分支继续改动 provider preference 和 composer/UI 层，使 store 成为回归高发点。
