# 审查总览

## 结论

该仓库的后端架构边界总体清晰：`cmd/agent-terminal` 是桌面宿主入口，`internal/app` 负责 Fx 根装配，`internal/contract` 管跨模块端口，`internal/module` 承载业务能力，`internal/platform` 承载 RPC、事件、DB、toolbridge、mcpcontrol 等基础设施，`internal/provider` 承接 provider 适配，`internal/store` 以 sqlc 为主访问层。

当前分支的主要质量风险不在“后端分层是否存在”，而在“新 UI 集成面是否足够稳”：`frontend-app` 仍是 JS/JSX 项目，没有 `tsconfig.json`；状态、RPC facade、页面 controller 仍集中在几个大文件；CSS 已从沉重的 `styles.css` 拆成多文件，但入口仍依赖 `main.jsx` 的全局导入顺序。跨语言契约已有测试矩阵和 surface guard，比上一版更强，但编译期类型约束仍弱。

构建链路比旧审查时更合理：`Makefile` 已用 Node 同步脚本替代直接 `rsync`，并新增了同步脚本测试、runner 合同测试和 Wails asset fail-fast 测试。剩余风险集中在 Windows/Ubuntu/桌面宿主三条路径的真实端到端验证，以及 `cmd/agent-terminal/frontend` legacy embed 路径与 `frontend-app` 当前 UI 的长期共存。

## 高风险摘要

| 风险 | 当前证据 | 影响 |
|---|---|---|
| 新 UI 缺少编译期类型边界 | `frontend-app` 无 `tsconfig.json`，`package.json` 只有 `typecheck:contracts` 的 ESLint 窄检查 | RPC/provider/thread payload 仍主要靠运行时规范化和测试兜底 |
| UI 状态和页面 controller 过大 | `useClientStore.js` 4785 行，`ChatPage.jsx` 3645 行，`backendApi.js` 1252 行 | 小改动容易牵动大状态面，审查和回归定位成本高 |
| 当前桌面 provider 口径需要持续收窄 | `providerPreferences.js` 明确 runtime provider 为 `codex`，但仍保留 `KNOWN_PROVIDERS=['codex','claude']` | 文档、UI 设置、provider 抽象和运行态能力若不同步，容易再次出现“看似可选但不可运行” |
| 新 UI build/embed/desktop 三段链路仍需端到端验证 | `make frontend-app-build`、`sync-frontend-dist.mjs`、Wails dev proxy、legacy embed 同时存在 | 单跑 Vite 测试不能证明桌面打包和无 dev proxy 场景可用 |

## 中低风险摘要

- CSS 已明显拆分，`styles.css` 从旧审查的大文件降到 137 行，但全局 CSS 顺序依赖集中在 `main.jsx`，后续拆分仍要防止 import 顺序成为隐式契约。
- `frontend-app` 已有 RPC contract matrix、raw bridge surface gate、consumer guardrails，但这些 guard 本身也是 JS 静态扫描，不能替代类型生成或 schema 驱动。
- `cmd/agent-terminal/frontend` legacy Vue/Vite 包仍保留大量测试和依赖，和当前 `frontend-app` 并存，容易让新任务误改旧 UI。
- CI 主路径在 Ubuntu；Windows PowerShell runner 有合同测试，但仍需要真实桌面启动 smoke 和端口清理验证。
- 仓库文档存在中英文/编码显示风险：部分说明在 PowerShell 输出中呈现乱码，需要后续确认文件编码和渲染环境。

## 优先级建议

P0：

- 把 `thread/start`、`turn/start`、provider preference 这三块建立更强契约边界，至少覆盖前端 facade、Go strict decoder、provider runtime 三端。
- 对 `frontend-app` 引入最小 TypeScript/checkJs 迁移计划，优先落在 `shared/api`、`entities/client/model` 和 provider preferences。
- 做一次 Windows 原生 `run-new-ui-desktop.ps1` + in-app browser 手测 + `make frontend-app-build` 的完整记录。

P1：

- 继续拆 `useClientStore.js`：优先拆 thread lifecycle、bridge event patch、provider preference、runtime result buffer。
- 继续拆 `ChatPage.jsx`：优先拆 composer controller、timeline materialization、runtime panel wiring。
- 给 CSS import 顺序加一个轻量说明或测试，避免后续新增 CSS 文件破坏覆盖顺序。

P2：

- 清理 legacy UI 和当前 UI 的文档口径，让 README、AGENTS、CLAUDE、codemap 均明确 `frontend-app` 是当前主 UI。
- 把大型测试文件拆成按功能命名的小套件，降低维护成本。
