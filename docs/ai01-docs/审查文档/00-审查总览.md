# 审查总览

## 结论

这个仓库的后端主结构相对清晰：`internal/app` 负责 Fx 根装配，`internal/contract` 承接跨模块契约，业务能力放在 `internal/module`，可变基础设施放在 `internal/platform`，provider 适配在 `internal/provider`，持久化以 `sqlc` 生成层为中心。

当前分支的主要质量风险集中在新 UI 集成面，而不是 Go 后端主干：`frontend-app` 仍是纯 JS/JSX，状态、RPC payload、provider 启动配置和大块页面逻辑集中在少数巨型文件里。分支又在 provider identity / composer / shell / CSS 上叠加了较大变更，导致类型安全、回归测试粒度和跨平台启动链路都需要优先收敛。

## 高风险摘要

| 风险 | 证据 | 影响 |
|---|---|---|
| Provider 语义不一致 | `useClientStore.js:238` 把 `claude` 归一为 `codex`；`internal/app/modules.go:85` 注释掉 `claudecli.Module` | UI、文档、provider 架构同时暴露多 provider 语义，但运行链路实际偏向 Codex，后续功能可能误以为 Claude 已可用 |
| 新 UI 类型安全不足 | `frontend-app` 无 `tsconfig.json` 和 `jsconfig.json`，RPC payload 由 JS 手写整形 | provider config、thread/start、turn/start 这类跨语言契约容易靠测试兜底，缺少编译期约束 |
| UI 状态和样式过度集中 | `useClientStore.js` 约 4.8k 行，`ChatPage.jsx` 约 3.6k 行，`styles.css` 约 10k 行 | 小改动容易牵动大面积状态、样式和快照，降低重构可审查性 |
| Windows/Unix 构建与启动链路分叉 | `Makefile:56` 使用 `rsync`；`.sh` 与 `.ps1` 启动顺序和默认 home 不一致 | CI 在 Ubuntu 通过不等于 Windows 原生开发/打包可复现 |

## 中低风险摘要

- `README.md` 仍写 Go 1.23+，但 `go.mod` 和 `AGENTS.md` 是 Go `1.25.7`。
- `CLAUDE.md` 仍把 `cmd/agent-terminal/frontend` 描述为主前端，和 `README.md`、`AGENTS.md`、codemap 中的 `frontend-app` 当前口径不一致。
- `App.jsx:270-278` 的 `runUIAction` 会吞掉异步错误，可能削弱 UI 操作失败的可观测性。
- `internal/ui/wails/assets.go:47` 对非法 `VITE_DEV_URL` 继续 fallback 到 embedded assets，和仓库 fail-fast 策略存在张力。
- 审查基准包含 3 个未提交前端测试/状态文件改动，分支审查不是纯 HEAD 快照。

## 优先级建议

P0：

- 明确当前产品是否只支持 Codex。若是，只在 UI/文档暴露 Codex；若不是，恢复并验证 Claude 端到端链路。
- 给 `thread/start` provider identity payload 建立前后端契约测试，覆盖 scoped/global preference、tombstone、缺字段 fail-fast。
- 让 Windows 原生构建路径不依赖 `rsync`，或把 Git Bash/WSL 作为显式前提写进命令。

P1：

- 拆分 `useClientStore.js`、`ChatPage.jsx` 和 `styles.css` 中已经有明确边界的区域，优先拆 provider preferences、thread lifecycle、timeline materialization、composer。
- 给 `frontend-app` 增加至少 `jsconfig.json` + `checkJs` 迁移计划，或直接规划 TypeScript 边界文件。
- 对 `.sh` 和 `.ps1` 新 UI runner 建立等价性测试清单。

P2：

- 清理 `README.md`、`CLAUDE.md`、codemap 中的版本和前端入口口径漂移。
- 把 CI 中 raw `go vet ./...` / `go build ./...` 与仓库 wrapper/guard 策略对齐或明确解释。
