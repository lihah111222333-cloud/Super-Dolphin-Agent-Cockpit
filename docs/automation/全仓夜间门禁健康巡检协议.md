# 全仓夜间门禁健康巡检协议

## 1. 规范词

- **必须**：不可跳过的门禁；不满足即为 `FAIL` 或 `BLOCKED`。
- **应当**：不存在明确 blocker 时必须执行；例外必须记录原因。
- **可以**：在不突破本协议权限边界时由执行 Agent 选择。
- **禁止**：任何 Agent 均不得执行。

## 2. 目的与规范边界

本协议定义全仓夜间门禁健康巡检的主 Agent 编排、固定基线、领域 DAG、门禁拓扑检查、状态裁决及协议演进边界。其目标是以可复查的固定提交审视门禁是否仍可发现、路由和闭环仓库风险，而非把一次 Agent 输出当作仓库健康证明。

本协议是三份协议中的根协议，只通过稳定相对路径引用下列专项协议，不复制其完整规则：

- [门禁问题台账接管协议](门禁问题台账接管协议.md)：疑似 Bug 的唯一台账 steward、生命周期和 Git Evidence 规则。
- [授权问题修复与验证协议](授权问题修复与验证协议.md)：获授权 Issue 的隔离修复、独立验证与回写规则。

本协议不创建 SQLite、消息队列、额外服务、第四份 manifest 或新的长期事实源。`ISSUE.xlsx` 的受控结构仍是 Bug 的长期事实源；Git 仍是提交与协议变更的事实源。

## 3. 范围、节奏与轮次锁定

### 3.1 不可变 bootstrap 与协议来源锁

本协议期待外部信任根契约 `automation-5-immutable-bootstrap` 版本 `1.0.0`。automation-5 的 prompt **必须内建**该最小 immutable bootstrap；在三份协议 blob 尚未加载成功前，launcher 不得依赖本协议第 5 章或任何其他正文。本契约不是第四份协议、manifest 或持久化服务，而是 automation-5 的固定启动能力；它也绝不允许从用户工作区取得兜底内容。

该契约的唯一职责是按以下必要先后顺序生成 launcher receipt：

1. launcher 以 `fork_turns="none"` 派发 baseline Agent。baseline Agent 是唯一可执行 `git fetch origin main` 的 Agent：最多三次，第一次立即、失败后分别等待 15 秒和 45 秒；单次 fetch 最长 75 秒，整个 baseline 阶段最长 5 分钟。它只可在每次计划等待和 fetch 尚有“该次退避（如有）+75 秒”剩余预算时继续；不足即 `BLOCKED`。三次均失败即 `BLOCKED`。任一次成功后，它必须核验 `FETCH_HEAD` 与 `refs/remotes/origin/main` 的完整 SHA 一致，才锁定该精确 SHA；引用缺失、不一致或解析失败即 `BLOCKED`，禁止使用旧引用、当前 `HEAD` 或缓存 SHA。
2. 仅在 baseline Agent 成功回包后，launcher 以 `fork_turns="none"` 派发只读 protocol-reader Agent。protocol-reader 只能通过已锁定 SHA 的 Git object 读取三份 canonical 协议 blob：`docs/automation/全仓夜间门禁健康巡检协议.md`、`docs/automation/门禁问题台账接管协议.md` 与 `docs/automation/授权问题修复与验证协议.md`；不得读取、比较或采纳用户工作区副本。
3. protocol-reader 返回 bootstrap contract ID/版本、三份 blob 的精确路径、已解析版本、`canonical_file`、相对引用校验结果及每份 Git blob ID/内容哈希，并与 baseline 完整 SHA 一并构成 launcher receipt。

加载成功后，协议正文才接管：主 Agent 必须校验 launcher receipt 的 contract ID/版本为上述期望值，且 receipt 中的 SHA、三个路径、版本、`canonical_file`、相对引用和 blob ID/内容哈希完整且彼此一致；然后才把这些值写入本轮不可变协议锁。该锁是本轮编排内存/任务状态，不得回写 Git、工作区、`ISSUE.xlsx` 或另建持久化服务。

protocol-reader 在 receipt 前必须校验每个 blob 的 YAML Front Matter、`source.canonical_file`、`protocol.version`、`schema_version`、`status` 和所有三者之间的稳定相对 Markdown 引用。兼容性要求为 schema version `1`、协议主版本 `1`，且根协议声明的两条专项协议路径与其 canonical path 完全一致；更严格的版本兼容规则可以在后续经批准版本中追加，不能由 Agent 临时放宽。

任一协议在 baseline SHA 中不存在、Git object 无法读取、路径或 `canonical_file` 不匹配、相对引用目标不存在、版本/模式不兼容、blob ID 缺失、launcher receipt 的 contract ID/版本不匹配，或任何 Agent 将用户工作区副本与 baseline blob 混用，均为 `BLOCKED: immutable-protocol-source-invalid`。主 Agent 只能在 receipt 与该锁完整后执行协议锁定、DAG 拆解或任何领域派发。

本 bootstrap 不形成旧引用兜底：protocol-reader 只能消费同一轮 baseline Agent 刚刚成功锁定的 SHA，不能改用本地旧 `origin/main`、当前 `HEAD`、缓存 blob、用户工作区副本或历史协议提交。

bootstrap contract 的任何变更必须取得用户显式批准，完成与三份协议的兼容性审查，并对 automation-5 更新执行回读验证；不得由本协议的执行/演进双循环自行修改、激活或替代该外部契约。

### 3.2 daily-core

`daily-core` 在 `Asia/Shanghai` 每日 03:00 运行，且每个夜间轮次必须覆盖整个仓库的当前基线，至少包括：

1. 仓库、默认分支、远端基线、工作区与依赖工具可用性。
2. 全部门禁拓扑：入口、触发、依赖、路由、死目标、环和唯一 owner。
3. Go、前端、脚本、构建、测试、Git hooks、生成物校验、代码地图与能力契约门禁的实际可达性和失败语义。
4. 架构边界、静态/动态质量门禁、测试门禁、依赖与供应链、文档/配置/生成物一致性。
5. 已知失败、跳过、过期目标、失联 owner、无消费者门禁、重复执行路径及无法复现的健康结论。

“全仓”是覆盖边界，不等于一次性无差别读取所有文件。领域 Agent 必须使用最小且可复查的定位范围；涉及源码的判断仍须遵守仓库 `AGENTS.md` 的 LSP 证据链。

### 3.3 weekly-extended

`weekly-extended` 在 `Asia/Shanghai` 每周日 03:00 运行。当日轮次的 profile 是 `weekly-extended`，它必须先完整执行同日的 `daily-core`，再执行扩展检查；其他日期的 profile 是 `daily-core`。主 Agent 必须按此规则选择 profile，不得同时启动两条互相独立却共享同一轮次身份的流程。

`weekly-extended` 不是可选的“可扩展”集合。每个周日 profile 必须包含 `daily-core` 加上以下全部、非空的 mandatory extended lanes：

1. **deferred tests**：登记的延后/重型测试；当前已知 Make owner 是 `make test-deferred`。
2. **前后端/桌面 E2E**：登记的前端、桌面或跨进程 E2E；当前 `make test-e2e` 与 `make test-e2e-rpc-runtime` 是不同实际范围的候选，不得被泛化为覆盖完整类别的唯一 owner。若 gate-plan/Make/AI runner 未登记覆盖完整声明范围的唯一 owner，该类别是准入缺口并 `BLOCKED`。
3. **security/dependency audit**：登记的安全与依赖审计；本协议不宣称当前已有覆盖该完整类别的唯一命令，必须从现有登记事实解析，解析不到即为准入缺口并 `BLOCKED`。
4. **performance baseline**：登记的性能基线与回归判定；当前 AI runner 登记 `frontend:performance-verify`，其实际命令为 `npm run performance:verify`，且只覆盖该 runner 声明的前端范围。若该范围不能满足本轮声明的类别范围或没有唯一 owner，则 `BLOCKED`。
5. **release/update gate**：登记的发布/更新门禁；当前已知 Make owner 是 `make release-update-gate`。

每个类别在执行前必须由空上下文子 Agent 从当前 gate-plan、Make 目标或 AI runner 的登记事实解析为**一个且仅一个**存活 owner，并在任务包中记录 owner 文件、入口、实际命令、覆盖范围、前置条件和验收标准。优先使用这些现有事实源的唯一 owner；本协议不臆造命令、目标、runner lane 或把相邻类别的命令作为替代。某个类别目前没有登记 owner 时，这是该类别的准入缺口，不是允许跳过的理由。

类别为空、owner 未登记、目标/脚本/runner lane 已死亡或不可达、存在多个冲突 owner、前置条件或所需凭据缺失，均使该类别和整轮 `weekly-extended` 为 `BLOCKED`。主 Agent 必须披露准入缺口并路由后续治理，禁止静默跳过、以 daily-core 的成功替代该 lane，或把部分 extended lanes 汇总为 weekly PASS。非周日的 `daily-core` 不受 weekly lane blocker 影响。

### 3.4 轮次不可变输入

一轮在协议版本、基线 SHA、范围和授权快照锁定后开始。轮内产生的协议改进、基线变化或授权变化只可作为下一轮输入；不得追溯改变本轮判定。

## 4. 角色、权限与主工作区边界

### 4.1 主 Agent 的唯一职责

主 Agent 仅可执行以下编排动作：协议锁定、DAG 拆解、以 `fork_turns="none"` 派发最小任务包、等待、审查子 Agent 回包、状态路由、请求人工授权和总裁决。

主 Agent 禁止亲自执行任何仓库 shell、LSP、Git、构建、测试、编辑或 `ISSUE.xlsx` 操作；也禁止把这些操作包装为“快速确认”“只读检查”或“代为回读”。所有此类操作只能由空上下文、最小任务包的子 Agent 执行。

### 4.2 子 Agent 任务包

每个子 Agent 必须以 `fork_turns="none"` 启动，且只收到完成本任务所需的最小上下文。任务包必须包含：

```text
任务 ID、轮次 ID、角色、基线完整 SHA、允许工作目录、允许路径、允许操作、
禁止操作、输入证据、预期产物、完成条件、失败条件、回包格式、清理责任。
```

子 Agent 不得扩大路径、基线、Issue 或授权范围。缺少字段、路径无法验证、工具不可用、返回不完整或发现越权需求时必须停止并回报 `BLOCKED`。

### 4.3 工作区与 worktree

主工作区始终只读。每一个会写入文件、运行会产生仓库状态、或需要修复/验证隔离的 Agent，必须使用独立 Git worktree；同一 worktree 不得被两个写入型 Agent 共用。

创建、使用和清理 worktree 的子 Agent 必须核验：

1. worktree 绝对路径是本轮任务包指定的精确路径；不得用宽泛通配符或未解析变量。
2. worktree 的 `HEAD` 等于锁定的完整基线 SHA，除非任务包明确记录获授权的后续提交。
3. 预期 marker 文件和允许路径存在，且 marker 不指向主工作区或其他 Agent worktree。
4. 写入前、交接前和清理前均核验路径、marker、完整 SHA 与工作树状态。
5. 清理只针对该任务创建且已通过上述核验的 worktree；核验失败则不清理并上报 `BLOCKED`。

## 5. 基线获取与一致性门禁

### 5.1 baseline 子 Agent

主 Agent 必须先派发一个只读 baseline 子 Agent。它必须在运行时确认仓库身份、默认分支为 `origin/main` 的可用性、当前 `HEAD`、工作区状态和远端引用。

仅 baseline 子 Agent 具有执行 `git fetch origin main` 的窄权限例外。该命令会写入共享 Git common-dir 的 `FETCH_HEAD` 与远端跟踪引用；独立 worktree 不能隔离这些元数据。因此 baseline 子 Agent 是该共享元数据在整个 baseline 阶段的唯一 owner，其他 Agent 禁止并发 fetch、改写这些引用或把它们当作可隔离 worktree 状态。

该例外不授予主工作区写权限：主工作区文件、index、local branch 与 Git config 始终只读。baseline Agent 必须在 fetch 前后以 `git status --porcelain=v1 -z` 取得原始字节序列并核验完全一致；任一不一致即 `BLOCKED`，不得尝试恢复、暂存、checkout 或以其他方式修改主工作区。

baseline 阶段总预算严格为 5 分钟。`git fetch origin main` 最多尝试三次：第 1 次立即；第 2 次仅在第 1 次失败后等待 15 秒；第 3 次仅在第 2 次失败后等待 45 秒。每次 fetch 的超时上限为 75 秒。不得增加重试、延长时间、换远端、改用缓存或旧引用兜底。

在每次等待和启动 fetch 前，Agent 必须计算距 baseline 阶段截止的剩余预算。只有剩余预算不少于“本次所需退避（如有）+75 秒”时才可进入该次计划；若不足，立即停止 baseline 并报告 `BLOCKED: insufficient-baseline-budget`，不得缩短/部分执行 fetch 或省略后续校验。三次均失败才为 `BLOCKED: baseline-fetch-exhausted`；任一尝试成功后立即进入一致性核验，不再重试。成功 fetch 后必须核验 `FETCH_HEAD` 与 `refs/remotes/origin/main` 解析出的完整 SHA 完全一致；仅最终成功但引用缺失、SHA 不一致或解析异常为 `BLOCKED: baseline-ref-inconsistent`。旧的本地 `origin/main`、当前 `HEAD` 或任何历史 SHA 均禁止作为替代基线。

### 5.2 锁定与传播

主 Agent 仅在收到有效候选基线后锁定完整 SHA，并把它写入所有后续任务包。任何子 Agent 发现自身工作目录不是该完整 SHA，必须立即停止；不得自行 rebase、pull、checkout 到“最新”或继续使用近似提交。

## 6. 巡检 DAG 与领域任务

主 Agent 必须在基线锁定后建立显式 DAG，至少含以下依赖关系：

```text
baseline
  ├── inventory / gate-topology
  ├── architecture-and-static-gates
  ├── build-and-test-gates
  ├── frontend-and-generated-consistency
  ├── dependency-security-and-automation
  └── documentation-and-ownership
          ↓
    independent review / adversarial review
          ↓
   ledger steward (only suspected Bugs)
          ↓
 authorization routing / authorized repair / verification
          ↓
        main-agent final adjudication
```

每个领域任务都必须定义检查范围、排除范围、可运行命令、LSP 需求、最小证据、独立复核、对抗性复核、允许写入边界和完成条件。任务之间可并行，前提是无共享写入目标；`ISSUE.xlsx` 永远不得并行写入。

领域巡检结果必须区分：原始事实、推断、风险等级、反例/已有缓解、结论和 blocker。高风险或证据冲突结论必须经独立复核和对抗性复核后才能进入最终裁决。

## 7. 门禁拓扑健康规则

门禁拓扑子 Agent 必须以实际仓库事实构造并验证图，而非凭命名猜测。每个门禁节点至少要能回答：入口/触发者、依赖、被谁消费、失败如何路由、唯一 owner、执行上下文和适用范围。

下列均为问题候选，必须取得证据并判定：

- 无法从已声明入口到达的死目标；
- 没有有效消费者、永久跳过或重复执行的门禁；
- 缺失失败路由、错误被吞掉或结果无法到达责任方；
- 依赖环、不可满足依赖或次序冲突；
- 同一门禁/输出存在多个相互冲突 owner，或没有唯一 owner；
- 入口、脚本、Make 目标、Git hook、文档或生成物声明与实际实现脱节。

确认发现不能仅以扫描命中成立：必须提供定位、理解、影响面和必要的执行/配置证据；涉及源码时遵守 LSP 强制链。若结论指向产品缺陷，则按台账专项协议交给 ledger steward。

## 8. 统一状态、路由与完成条件

每项任务、每个领域和整轮仅使用以下状态：

- `PASS`：所有约定检查已完成，证据满足门禁，且没有未处理 blocker。
- `FAIL`：获得足够证据证明门禁、实现或已定义期望不成立；必须路由为已记录问题或明确的非 Bug 失败。
- `BLOCKED`：缺少强制输入、工具、权限、基线、一致性、独立验证或安全前提，无法合法得出 PASS/FAIL。

缺少证据、超时、等待人工授权、未回读台账、尚未运行验证、未清理/未核验 worktree，均不得标记 `PASS` 或“完成”。等待授权是等待状态，不是完成。

主 Agent 必须将 `FAIL` 和 `BLOCKED` 按原因路由：疑似产品 Bug 交由 ledger steward；授权缺口交由人工授权请求；工具/基线/隔离失败保留为运行 blocker；协议歧义交由下一轮演进提案。主 Agent 的最终裁决必须列出所有未覆盖范围，禁止将部分成功汇总为全仓 PASS。

## 9. 人工授权边界

主 Agent 只可请求授权，不能推定、扩大或替代人工授权。修复授权必须明确指向 Issue、仓库、范围、风险边界和授权人；任何范围扩大、旁支问题或风险上升都需要新的明确授权。授权后的执行完全遵循[授权问题修复与验证协议](授权问题修复与验证协议.md)。

## 10. 执行与演进双循环

执行循环使用本轮锁定版本完成 baseline、DAG、巡检、台账路由、授权路由和裁决。演进循环只收集执行中发现的协议提案，不得在同轮修改、激活或用新规则重判正在执行的轮次。

每项演进提案必须含触发事实、最小差异、行为/权限/安全影响、兼容性、回滚条件和验证计划。提案必须获得人工批准后方可实施；正式激活前**必须**完成连续 3 次 shadow 运行，证明新规则可执行且不会降低已知门禁覆盖。任一 shadow 失败、`BLOCKED`、范围不一致或证据不足都会使连续计数重置为零。提案 diff 在批准后发生任何语义、权限、范围或执行行为变化时，原批准失效，必须重新获得人工批准并重新开始 3 次 shadow。演进不得自动提交、推送、改写历史或绕过仓库门禁。
