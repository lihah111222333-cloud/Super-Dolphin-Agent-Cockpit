# 代码仓库腐化守卫巡检协议

## 1. 规范词

- **必须**：不可跳过的协议门禁。
- **应当**：不存在明确阻塞时必须执行。
- **可以**：由执行 Agent 根据可验证上下文选择执行。
- **禁止**：任何 Agent 均不得执行。

## 2. 协议目的

本协议用于周期性识别代码仓库中的腐化迹象，发现持续降低系统可维护性、可靠性、安全性和交付效率的问题，并通过多 Agent 调查、独立证据、交叉验证、对抗性验证及 Bug Issue 台账形成可追溯的治理闭环。

巡检不得只输出扫描工具结果，也不得把未经验证的推断包装为事实。

## 3. 适用范围与排除范围

### 3.1 适用范围

本协议固定适用于自动化任务运行时打开的当前 `Super-Dolphin` 仓库。运行时必须解析并验证当前 checkout 的绝对路径，但禁止将机器绝对路径、用户名或主机名持久化到 Bug 台账。

巡检至少覆盖：

1. 失效、废弃或长期未维护的代码。
2. 重复实现、职责漂移和架构边界侵蚀。
3. 高复杂度模块与持续扩张的技术债务。
4. 依赖老化、依赖冲突及供应链风险。
5. 测试缺失、测试失效、覆盖下降和脆弱测试。
6. 文档、配置、接口定义与实际代码不一致。
7. 长期未处理的 TODO、FIXME、临时补丁和兼容代码。
8. 无主模块、知识孤岛和关键代码单点维护风险。
9. 安全隐患、敏感信息暴露及不安全默认配置。
10. 构建、部署、脚本和自动化流程中的失效资产。

### 3.2 当前排除范围

本版本暂不规定：

- 巡检报告文件及其保存目录。
- 机器可读巡检结果文件。
- 仓库整体基线和腐化趋势算法。
- 自动发布规则。
- 整轮任务的结构化成功或失败状态模型。

上述事项由协议维护 Agent 在后续版本中按照第 15 章自治迭代。

## 4. 术语与角色

### 4.1 Agent 角色

- **主 Agent**：本轮巡检的编排者和最终责任主体。
- **领域 Agent**：对明确领域执行专项巡检的 Agent。
- **证据采集 Agent**：采集代码、测试、配置、Git 和工具输出等原始证据。
- **交叉验证 Agent**：使用独立方法验证同一候选结论。
- **对抗性验证 Agent**：主动寻找反例、合理替代解释和既有缓解机制。
- **协议维护 Agent**：识别协议缺陷，生成、审查、验证、激活或回滚协议版本。

### 4.2 治理对象

- **疑似 Bug**：存在可验证症状或风险信号、尚未完成分诊与验证的问题。
- **Issue**：Bug 台账中的当前快照。
- **Event**：Issue 的不可变、仅追加审计轨迹。
- **Evidence**：Issue 与经验证 Git 事实之间的映射，不是一般调查材料。
- **问题指纹**：用于辅助识别同一问题的动态稳定标识，不等于 Issue ID。
- **直接证据**：能够直接证明症状、缺陷或影响的原始事实。
- **独立旁证**：来源、方法或推理链与直接证据相互独立的支持材料。
- **Blocker**：阻止检查、验证或合法写回继续进行的明确条件。

## 5. 定时触发与运行上下文

任务每周一 03:00 按 `Asia/Tokyo` 时区触发，每周执行一次。

每轮运行必须：

1. 在当前仓库的本地执行环境中运行。
2. 记录巡检开始时间、当前提交、默认分支和工作区状态。
3. 默认以只读方式分析，不得擅自改变业务工作区。
4. 从本协议 YAML Front Matter 读取当前有效版本。
5. 从开始到结束固定使用同一协议版本。
6. 将本轮发现的协议修改应用于后续轮次，不得改变本轮判定依据。

## 6. 执行前置检查

主 Agent 必须按顺序完成以下检查：

1. 验证当前目录是可访问的 `Super-Dolphin` Git 仓库。
2. 读取仓库根目录 `AGENTS.md` 及其明确要求的当前任务上下文。
3. 获取默认分支、当前提交和未提交变更状态。
4. 识别主要语言、框架、模块、依赖管理、测试和构建方式。
5. 验证仓库要求的 LSP 工具链可用。
6. 完整读取 `.agents/skills/代码审查维度/SKILL.md`。
7. 完整读取 `.agents/skills/manage-bug-issues/SKILL.md`。
8. 验证 `ISSUE.xlsx` 存在且可访问。
9. 验证 `.agents/skills/manage-bug-issues/scripts/issue_ledger.py` 存在。
10. 使用当前环境可用的 Python 解释器运行台账脚本主命令 `--help`。
11. 在每种具体台账操作前运行目标子命令的 `--help`，以实际暴露的命令、必填参数、枚举和状态迁移为准。
12. 确认拟执行的分析命令不会修改业务代码、配置、依赖、生成物或 Git 状态。

相对资源路径必须以引用它的 `SKILL.md` 所在目录为基准解析。禁止默认把技能资源路径解释为仓库根目录下的同名路径。

强制依赖不可用时必须 Fail-Fast：停止受影响的操作，记录具体 blocker，不得猜测命令、字段、状态或结果。

## 7. 三层多 Agent 架构

### 7.1 第一层：主 Agent

主 Agent 的输入包括当前仓库、当前协议版本、仓库级指令、可用工具和台账资源。

主 Agent 必须：

1. 建立仓库画像。
2. 制定本轮巡检计划。
3. 将巡检拆分为相互独立、边界清晰的领域任务。
4. 动态创建或调用所需领域 Agent。
5. 汇总各领域证据、判断和风险评级。
6. 识别结论之间的冲突、重复、共同根因和因果关系。
7. 对高风险或证据冲突结论发起二次复核。
8. 确保疑似 Bug 按第 11 章登记和回读。
9. 识别本轮暴露的协议缺陷并交给协议维护流程。

主 Agent 禁止在缺少领域证据时直接下结论。

主 Agent 的完成条件是：已完成适用领域拆分；已处理各领域返回的证据、冲突和 blocker；疑似 Bug 已按台账流程处理；未覆盖范围已明确披露。

### 7.2 第二层：领域 Agent

主 Agent根据仓库实际情况动态创建领域 Agent。基础领域包括但不限于：

- 架构与模块边界。
- 代码质量与复杂度。
- 依赖与供应链。
- 测试质量。
- 安全风险。
- 文档与配置一致性。
- 构建、部署与自动化。
- 技术债务与失效资产。

本协议不限制 Agent 数量、并发数量、拆分层级或执行时长。每个领域 Agent 仍必须具有明确范围、排除范围、输入、证据目标和完成条件。

每个领域 Agent 必须：

1. 将领域任务拆分为证据采集子任务。
2. 使用多 Agent 能力调查，而不是依赖单次判断。
3. 区分事实、推断和建议。
4. 标注证据不足和不确定性。
5. 对疑似 Bug 触发第 11 章流程。
6. 输出结构化领域结论给主 Agent。

### 7.3 第三层：验证 Agent

每个领域 Agent 至少调用以下验证角色：

#### 证据采集 Agent

采集文件路径、行号或符号、提交信息、命令及输出摘要、配置项、复现步骤和证据有效时间。

#### 交叉验证 Agent

通过不同工具、不同事实来源或独立分析路径验证同一候选结论。对同一原始结果的重排、转述或二次格式化不构成独立证据。

#### 对抗性验证 Agent

主动回答：

- 结论是否可能是误报。
- 是否存在合理设计背景或历史约束。
- 是否有代码、测试或配置能够反驳当前判断。
- 风险是否仅存在于理论层面。
- 是否已有其他机制缓解。
- 修复建议是否可能引入更高风险。
- 是否需要额外事实才能定性。

## 8. 领域任务契约

主 Agent 派发的每个领域任务必须包含：

```text
任务标识
所属领域
巡检目标
检查范围
排除范围
输入上下文
允许使用的工具
必须取得的证据
交叉验证要求
对抗性验证要求
风险评级规则
安全边界
完成条件
阻塞写回要求
```

按照仓库 `AGENTS.md` 创建子 Agent 时，必须以空上下文启动，只传递完成子任务所需的最小信息。

## 9. 证据与验证门禁

### 9.1 原始证据

每条原始证据应尽可能包含：

- 稳定仓库身份或模块名称。
- 仓库相对文件路径。
- 行号、代码符号、配置键或其他定位信息。
- 提交记录或时间信息。
- 命令及输出摘要。
- 复现或验证步骤。
- 证据采集时间。
- 工具限制和已知缺口。

敏感信息只能记录类型、脱敏位置和必要摘要，禁止记录令牌、密码、私钥、完整连接串或其他秘密值。

### 9.2 LSP 证据链

涉及源码的路径判断、行为解释、审查或修复判断，必须遵守仓库 `AGENTS.md` 的 LSP 强制工作流，并至少保留：

1. 定位证据：`grep` 或 `structure`。
2. 理解证据：`inspect`。
3. 影响面证据：`xref`。
4. 精读证据：`file(read_file)`。
5. 诊断证据：`file(diagnostics)`。

LSP 超时、不可用或返回异常时，必须先收窄工作目录、路径、查询、语言或结果数后重试。仍失败时记录工具、动作、工作目录、目标文件或符号、错误和已尝试的收窄方式。

禁止将 `rg`、`go test`、`gopls check` 或其他单语言工具替代为 LSP 证据链。额外验证可以使用这些工具，但不能消除 LSP blocker。

所有 LSP `Error`、`Warning`、`Information` 和 `Hint` 都是待处理项。无法处理时必须记录文件、行号、规则和原因。

### 9.3 风险与置信度

- **P0 紧急**：已经或极有可能造成严重安全事故、数据损坏、生产中断或不可逆后果。
- **P1 高风险**：可能显著影响核心功能、安全、发布稳定性或关键维护能力。
- **P2 中风险**：持续影响可维护性、测试可靠性或交付效率，但短期内通常不会造成严重事故。
- **P3 低风险**：局部质量问题、轻度债务或优化事项。

置信度分为高、中、低。

证据门禁：

- P0/P1 原则上必须至少有两类相互独立的证据，并完成交叉验证和对抗性验证。
- P2 必须至少有直接证据和独立旁证。
- P3 可以基于单项直接证据，但禁止夸大为确定性系统风险。
- 低置信度问题禁止直接定为 P0/P1，除非明确记录预防性升级理由。
- 证据不足时必须降低置信度或标记无法验证。

## 10. 问题指纹

问题指纹由主 Agent 根据问题性质动态生成，默认参考：

- 所属领域。
- 检查规则或问题类型。
- 规范化仓库相对文件路径。
- 代码符号、配置键或模块标识。
- 必要时加入依赖名称、接口名称或构建阶段。

指纹必须：

1. 在同一轮巡检中保持稳定。
2. 记录生成依据和算法版本。
3. 算法变化时保留新旧映射。
4. 禁止仅依赖自然语言标题生成。
5. 无法生成稳定指纹时明确标记原因。

问题指纹不等于 Issue ID。只有台账脚本当前受控结构明确支持时，才可以把指纹写入工作簿；禁止为保存指纹而新增工作表、列、公式或绕过脚本。

## 11. Bug Issue 台账治理

### 11.1 唯一入口

Bug 台账的唯一操作入口是：

```text
.agents/skills/manage-bug-issues/scripts/issue_ledger.py
```

项目工作簿是：

```text
ISSUE.xlsx
```

禁止直接编辑 `.xlsx`，禁止使用电子表格库或其他脚本绕过台账。每次调用必须显式传入工作簿路径。Git 相关操作必须通过 `--repo-path <repo_id>=<运行时绝对路径>` 提供本次映射，映射不得持久化。

### 11.2 强制顺序

对每个疑似 Bug，必须：

1. **先报告**：创建或登记初始 Issue，并追加发现 Event。
2. **再检索**：检索相同症状、组件、错误签名、关联仓库和历史 Event。
3. **分诊写回**：判断同一问题、重复、回归或独立问题；更新 Issue 并追加分诊 Event。
4. **完成验证**：写入交叉验证和对抗性验证结论。
5. **请求并记录授权**：任何修复前取得明确授权并追加 Event。
6. **在授权范围内修复**：只处理被授权的 Issue、仓库和范围。
7. **无论结果都写回**：成功、失败、无法复现、撤销、部分修复或受阻均更新快照并追加 Event。
8. **回读校验**：重新读取 Issue、Event 和 Evidence，确认一致后才可宣称登记或更新完成。

自动巡检默认只拥有调查、登记、检索、分诊和验证权限。没有明确修复授权时，禁止进入 `READY_TO_FIX` 或 `FIXING`，禁止修改代码、配置、数据或部署。

### 11.3 记录职责

- Issue 保存身份、现状、责任、状态和结论的当前快照。
- Event 保存不可变审计轨迹，只能追加，禁止编辑、删除、重排或复用。
- Evidence 只保存 Issue 与 Git 事实的映射。
- Repository 保存稳定仓库身份，禁止保存 checkout 路径、用户名或主机信息。

Evidence 必须使用稳定 `repo_id`、canonical full commit hash，以及脚本允许的可选仓库相对路径和 locator。禁止写入分支、PR、比较范围、终端日志、截图、机器路径或推测。

### 11.4 状态与授权

只能使用脚本实际支持的状态和迁移，禁止自造中文状态、别名或捷径。状态迁移失败时立即停止，不得直接修改工作簿绕过约束。

巡检环境、临时权限、Agent 超时或工具暂时不可用不自动构成产品 Bug。只有证据确认异常源于仓库缺陷时，才可以创建 Issue。

## 12. 安全与权限边界

默认执行模式是只读巡检。

未经明确授权，所有 Agent 均禁止：

- 修改或删除业务代码。
- 修改配置、数据或依赖版本。
- 自动提交或推送代码。
- 自动创建或合并 Pull Request。
- 执行破坏性命令。
- 直接编辑 Bug 工作簿。
- 访问巡检目标和本协议明确依赖之外的目录。
- 上传源码或敏感信息到外部服务。
- 在任何持久化记录中写入秘密值。

可能改变仓库状态的测试、构建、生成或分析命令必须停止，或在明确隔离且不会回写业务工作区的环境中执行。

协议维护 Agent可以修改本协议及其协议历史记录；该权限不扩展到业务代码、Bug 台账结构或自动修复。

## 13. 异常、阻塞与证据不足

出现仓库不可访问、权限不足、默认分支无法确定、核心工具不可用、依赖无法安装、测试环境无法启动、Agent 超时、证据重大冲突、无法完成交叉验证或无法完成对抗性验证时：

1. 停止受影响的检查分支。
2. 保存已经获得的有效证据。
3. 明确未覆盖范围。
4. 记录失败阶段、工具、动作、目标、错误和已尝试措施。
5. 降低相关结论置信度。
6. 禁止伪造 PASS 或完整巡检结果。
7. 禁止将未验证推断包装为事实。
8. 禁止将临时执行异常自动登记为产品 Bug。

本版本暂不为整轮任务定义 `SUCCESS`、`PARTIAL`、`BLOCKED` 或 `FAILED` 等结构化状态。

## 14. 人工介入条件

以下情况必须请求人工介入：

- 对业务代码、配置、数据、依赖或部署进行任何修复。
- Bug 修复授权或授权范围扩大。
- 需要执行可能改变业务工作区的命令。
- 需要扩大仓库或数据访问范围。
- P0/P1 证据存在重大冲突且无法由独立验证解决。
- 发现可能暴露秘密值且继续调查会扩大泄露范围。
- 台账状态迁移失败或 Git Evidence 无法验证。

协议版本的提案、审查、激活和回滚不需要人工批准，按照第 15 章完全自治执行。

## 15. 协议自治维护

### 15.1 维护触发条件

满足以下任一条件时，主 Agent 必须发起协议维护：

- 协议存在歧义、冲突或不可执行规则。
- 路径、命令、工具契约或仓库事实已经变化。
- 协议导致重复误报、证据缺口或越权风险。
- 本协议的待定范围已具备可执行设计。
- 自动化配置与协议不一致。
- 新的仓库级强制规则影响巡检。

### 15.2 维护流程

协议维护 Agent 必须：

1. 记录触发事实和拟解决问题。
2. 生成最小充分修改提案和逐项差异。
3. 说明行为影响、安全影响、兼容性和回滚条件。
4. 分配语义化版本号。
5. 至少调用两个相互独立的审查 Agent。
6. 调用对抗性验证 Agent，尝试证明修改不必要、有害或存在替代方案。
7. 处理审查冲突；证据不足时禁止激活。
8. 验证 YAML、正文、路径、工具契约和自动化提示词的一致性。
9. 原子更新规范文件并激活新版本。
10. 仅提交本次协议变更涉及的协议文件，生成一个中文原子 Git 提交。
11. 回读新版本并检查该提交，确认 YAML 版本、正文和提交文件范围一致。
12. 在变更记录中追加审计条目。

### 15.3 完全自治激活

`MAJOR`、`MINOR` 和 `PATCH` 版本均由 Agent 自主激活，不设置人工激活门禁。

- `MAJOR`：权限、安全边界、Agent 权责、台账流程或核心门禁发生不兼容变化。
- `MINOR`：新增巡检领域、证据规则、异常处理或可执行能力。
- `PATCH`：修正文义、路径解析、格式或不改变核心行为的说明。

无论版本级别，均必须通过两个独立审查 Agent和一个对抗性验证 Agent。执行巡检的 Agent 禁止无痕修改本轮使用的协议。

### 15.4 Git 历史与原子提交

Git 是协议版本历史、差异审计和回滚的事实来源，不额外维护协议历史快照目录。

每次协议进化必须：

1. 在修改前记录当前协议版本和当前 `HEAD`。
2. 只修改本次提案明确覆盖的协议文件。
3. 更新 YAML 版本、正文和变更记录。
4. 验证协议语法、资源路径和自动化一致性。
5. 检查工作树和暂存区，识别用户已有变更。
6. 使用路径限定方式只提交协议文件，不得夹带业务代码、Bug 台账、生成物或用户已有改动。
7. 提交标题和正文使用中文，并遵守仓库提交门禁。
8. 禁止使用 `--no-verify`。
9. 提交后检查提交文件清单和差异，确认其为单一、完整、可回滚的协议变更。

一次协议进化只产生一个原子提交。协议维护 Agent 禁止为了整理历史而执行 rebase、amend、强制推送或其他历史改写操作。

激活后发现以下任一情况时必须自动回滚：

- 新版本无法解析或关键资源路径无效。
- 新版本导致安全边界放宽但缺少充分证据。
- 自动化提示词与协议发生不可调和冲突。
- 新版本无法完成前置检查。
- 审查证据被证明无效。

回滚必须使用 `git revert` 为目标协议提交生成新的中文原子提交，禁止使用 `git reset --hard`、检出覆盖或手工删除历史。回滚后必须检查协议内容、提交范围和自动化一致性。失败版本及其回滚提交都必须保留在 Git 历史中。

### 15.5 自动化同步

协议是执行规则的事实来源。自动化提示词只负责定位协议、要求严格执行并提供必要运行上下文，禁止复制整份协议形成第二事实源。

协议维护 Agent 修改调度时间、时区、任务状态或其他自动化配置字段时，必须同步更新自动化配置并回读验证。不能同步时不得激活相关协议变更。

## 16. 本轮完成门禁

在不定义整轮结构化状态的前提下，主 Agent 结束本轮前必须确认：

- 前置检查已经执行。
- 适用领域已经拆分并完成，或已披露 blocker。
- 源码结论具有可复查的 LSP 证据链，或已披露具体缺口。
- P0/P1 和 P2 结论满足对应证据门禁。
- 正式结论已经完成对抗性验证。
- 每个疑似 Bug 已先登记、再检索、分诊和写回。
- 所有台账写操作均已回读校验。
- 没有未经授权的业务写操作。
- 未覆盖范围和执行异常均已披露。
- 本轮发现的协议缺陷已进入自治维护流程。
