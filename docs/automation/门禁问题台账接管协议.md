# 门禁问题台账接管协议

## 1. 规范词

- **必须**：不可跳过的台账门禁。
- **应当**：不存在明确 blocker 时必须执行。
- **可以**：仅在脚本实际暴露的能力内执行。
- **禁止**：不得执行或不得以替代方式实现。

## 2. 目的与唯一事实源

本协议接管夜间门禁巡检发现的疑似 Bug，并把它们纳入受控、可审计且不越权的 Issue 生命周期。`ISSUE.xlsx` 是长期事实源；唯一操作入口是 `.agents/skills/manage-bug-issues/scripts/issue_ledger.py`。任何人或 Agent 禁止直接编辑工作簿、使用电子表格库、创建替代表格或绕过脚本。

本协议是根协议的专项子协议，根编排见[全仓夜间门禁健康巡检协议](全仓夜间门禁健康巡检协议.md)。获得授权后的修复和独立验证见[授权问题修复与验证协议](授权问题修复与验证协议.md)。

## 3. 唯一 ledger steward 与串行边界

每轮只能存在一个 ledger steward 子 Agent。它必须以 `fork_turns="none"` 启动，接收最小任务包，并且是本轮唯一可以对 `ISSUE.xlsx` 执行脚本写操作的 Agent。主 Agent、领域 Agent、fixer、verifier 与其他 Agent 均不得并行或直接写入台账。

single-writer 仅串行化**每一次** `ISSUE.xlsx` mutation 与该 mutation 的立即回读：steward 完成一个脚本写调用后，必须立即读取受影响的 Issue、Event 和 Evidence（如适用）并确认结果，再开始下一次 mutation。它不得在等待人工授权、fixer 修复、verifier 验证或外部 blocker 期间持有跨生命周期的“写锁”或阻塞其他已就绪的独立台账 mutation。每次后续写入仍须以刚回读的版本和状态为前提；发生冲突则 `BLOCKED`。

每个 steward 任务包必须限定候选 ID、基线完整 SHA、允许工作目录、允许脚本、是否只读或可写、工作簿路径、仓库稳定身份、回读要求和停止条件。路径、脚本、工作簿或任务边界缺失即 `BLOCKED`。

## 4. 前置检查与 fail-fast

steward 在本轮首次操作前必须完整读取 `manage-bug-issues` 技能，并在项目根目录确认 `ISSUE.xlsx` 与技能目录下脚本存在且可访问。每次脚本调用都必须显式使用 `--workbook ISSUE.xlsx`；相对资源以该技能 `SKILL.md` 所在目录解析。

在首次调用前必须运行脚本主命令 `--help`；在每种具体操作前必须运行目标子命令的 `--help`，以实际暴露的命令、必填参数、状态迁移和输出为准。不得臆造子命令、参数、字段、枚举、Issue ID、Event ID 或脚本行为。

脚本、工作簿、命令、校验、状态迁移、必填字段、repo 映射或回读任一失败、警告、冲突、缺字段或意外空结果时，立即停止当前台账分支并报告 `BLOCKED`。禁止默认值、手工改表、猜测、吞错或静默降级。

## 5. 接管门槛与严格生命周期

领域 Agent 只能提交“疑似 Bug 候选”给 steward；候选必须区分原始事实、推断、复现/症状、影响范围、风险、证据定位和已知反例。环境暂态、Agent 超时、工具不可用或授权未到位不自动构成产品 Bug。

对每个进入台账的疑似 Bug，steward 必须严格按以下顺序执行并在脚本实际支持范围内完成：

1. **先报告**：创建/登记初始 Issue，并追加发现 Event；未知信息明确为未知，不得编造。
2. **再检索**：检索相同症状、组件、错误签名、关联仓库和历史 Event；读取候选 Issue 当前快照与事件历史。
3. **分诊并写回**：判定同一问题、重复、回归或独立问题，写回分诊结论并追加分诊 Event；重复关系仅按脚本支持的方式记录。
4. **请求并记录授权**：任何代码、配置、数据或部署修复前，获得明确人工授权并写入 Event；仅在授权已记录且脚本允许时使 Issue 到达 `READY_TO_FIX`。
5. **授权范围内修复**：只由专项修复协议的独立 fixer 处理，不由 steward 擅自改动。
6. **无论结果都写回**：成功、失败、无法复现、撤销、部分修复和受阻均更新 Issue 快照并追加结果 Event。
7. **回读校验**：重新查询 Issue、相关 Events 和 Evidence，确认当前快照、追加轨迹、状态、授权和 Git 映射一致。

等待授权不是完成；无授权只能报告、检索、分诊和调查，禁止进入 `READY_TO_FIX` 或 `FIXING`，也禁止修改仓库内容。

## 6. 状态、授权与旁支问题

仅使用技能列出的状态及脚本允许的可达迁移：`REPORTED → TRIAGED → CONFIRMED → INVESTIGATING → READY_TO_FIX → FIXING → READY_TO_VERIFY → CLOSED`，以及脚本允许的终止/例外状态。每次迁移必须追加 Event，写明事实、操作者、时间和理由；迁移失败不得绕过。

授权必须明确记录授权人、目标 Issue、仓库、允许范围和时间。范围扩大、目标仓库改变、风险提高或修复中发现新问题时，既有授权不自动覆盖。

修复中发现的旁支 Bug 必须由 steward 新建独立 Issue 并追加其发现 Event；不得挤入当前 Issue、篡改当前症状以容纳它，或在未获该新 Issue 授权时顺手修复。新 Issue 必须从报告、检索、分诊和授权重新开始。

## 7. Git Evidence 的唯一规则

Evidence 仅是 Issue 与经脚本验证的 Git 事实映射，不是调查笔记、日志或修复结论。Git 相关调用必须以 `--repo-path <repo_id>=<本机绝对路径>` 提供本次运行时映射，由脚本验证仓库身份和 Git 对象；该绝对路径不得持久化。

每条 Evidence 必须关联 Issue、稳定 `repo_id` 和 canonical full commit hash；只有脚本支持时才可附带仓库相对路径与 locator。禁止写入分支、PR、比较范围、终端输出、截图、聊天摘录、机器路径、未推送猜测或人工复制的 Git 值。

`repo_id`、canonical URL、运行时映射、Git 对象或工作树前提不一致时必须停止。没有 Git 变更的结论必须如实写明原因，不能伪造 Evidence；有 Git 变更但未完成脚本验证和回读，也不得宣称已关闭。

当前脚本没有“无 Git 变更修复”的成功闭环：`issue complete-fix` 只在存在 active `FIX_COMMIT` Evidence 时才可进入 `READY_TO_VERIFY`，`issue record-verification` 只在存在 active `VERIFICATION` Evidence 时才可 `CLOSED`，而 `evidence register` 对每种 Evidence 都验证 canonical full Git commit。因此无 Git 变更时，steward 禁止臆造 Evidence、调用上述命令或声称 `READY_TO_VERIFY`/`CLOSED`。

此情形必须报告 `BLOCKED: no-script-supported-non-git-repair-closure` 并保持当前状态，或仅在事实真实且脚本迁移允许时使用 `revoke-fix-authorization` 返回 `INVESTIGATING`、或 `defer` 转为 `DEFERRED`；不得用这些命令伪装成功闭环。任何新的合法闭环必须先经脚本实现、技能和协议的人工批准后才能使用。

## 8. 与修复协议的交接

steward 只有在明确授权已记录、Issue 已达到 `READY_TO_FIX`、基线与范围可验证时，才可向独立 fixer 派发交接包。交接包必须含 Issue ID、授权 Event、允许路径、锁定 SHA、风险与验收条件；不得包含越权扩展。

fixer/verifier 的结果返回给 steward 后，只有 steward 可以使用脚本写回结果 Event、状态和已验证 Git Evidence，并立即回读。未完成回读时，Issue 不得被报告为已登记、已修复、已关闭或已更新。
