# 授权问题修复与验证协议

## 1. 规范词

- **必须**：不可跳过的修复或验证门禁。
- **应当**：不存在明确 blocker 时必须执行。
- **可以**：仅在明确授权和任务包范围内执行。
- **禁止**：任何 Agent 均不得执行。

## 2. 目的与适用条件

本协议只适用于已由单一 ledger steward 按[门禁问题台账接管协议](门禁问题台账接管协议.md)记录明确人工授权、并已处于 `READY_TO_FIX` 的 Issue。根编排、基线和主工作区边界由[全仓夜间门禁健康巡检协议](全仓夜间门禁健康巡检协议.md)定义。

不满足全部前提时，修复不得启动：目标 Issue 不在 `READY_TO_FIX`、授权 Event 不存在或不明确、授权范围与任务包不一致、锁定完整 SHA 缺失、隔离 worktree 无法核验、必要工具不可用，均为 `BLOCKED`。等待授权不是完成，也不得被标记为已修复。

## 3. 独立角色与最小权限

修复必须由独立 fixer 子 Agent 完成，验证必须由独立 verifier 子 Agent 完成；二者均以 `fork_turns="none"` 启动，且 verifier 不得参与同一 Issue 的修改。主 Agent 和 ledger steward 不得直接编辑业务文件或以验证名义替代 verifier。

fixer 和 verifier 的任务包必须至少含：Issue ID、授权 Event ID、授权人和明确范围、完整基线 SHA、隔离 worktree 路径与 marker、允许修改/读取路径、禁止路径、可运行命令、验收标准、台账回传格式及清理责任。任务包不得传递未授权的相邻问题、宽泛“顺手整理”目标或未证实假设。

所有 shell、LSP、Git、构建、测试和编辑操作只能由这些空上下文的任务 Agent 在指定 worktree 中执行。主工作区只读；不得在主工作区写入、生成、暂存、提交、清理或运行可能改变状态的命令。

## 4. 隔离 worktree 与 SHA 纪律

fixer 必须使用其专属 write worktree；verifier 必须使用独立 verifier worktree 或明确只读、不可回写的隔离副本。不得共享同一写入型 worktree，也不得在未核验的目录执行。

每个操作阶段前后均必须核验精确任务路径、marker、完整 SHA 与工作树状态。修复开始时 `HEAD` 必须与锁定 SHA 一致；修复提交后，verifier 必须获得任务包指定的完整候选提交 SHA，而不是分支名、短 SHA 或“最新”引用。路径、marker、SHA、提交对象或允许范围任一不一致，立即停止并报告 `BLOCKED`。

worktree 创建、交接和清理均须遵守根协议的精确路径/marker/SHA 核验。清理只可作用于本任务创建、并且经再次核验的 worktree；无法确认时不得删除。

## 5. 修复流程

1. **授权与台账回读前置**：fixer 通过 steward 提供的只读证据确认 Issue、授权 Event、当前状态、范围和验收条件；不得直接写 `ISSUE.xlsx`。
2. **定位与影响分析**：fixer 在授权范围内取得可复查证据。涉及源码时必须遵守仓库 `AGENTS.md` 的 LSP 定位、理解、影响面、精读和 diagnostics 链；LSP 无法取得时按仓库规则收窄并记录 blocker，不得用 shell 检查替代。
3. **最小修复**：仅修改解决该 Issue 所必需的文件。新增、删除、重命名或跨层字段变化必须遵循仓库相应字段守卫和契约要求；不得引入静默降级、默认兜底、吞错或超出授权的重构。
4. **本地验证**：fixer 运行任务包和受影响面要求的诊断、构建、测试、门禁及生成物检查。失败、警告、信息或 hint 均须处理或如实上报；不得声称验证通过。
5. **候选交接**：fixer 回报精确 diff、完整候选提交 SHA（若有）、命令结果、剩余风险和未覆盖范围给主 Agent/ledger steward；它不自行关闭 Issue 或写 Evidence。

修复产物是否提交由明确授权和任务包决定；本协议不授予自动提交、推送、创建 PR、合并或改写历史的权限。禁止 `--no-verify`、强制推送、rebase、amend、`git reset --hard` 及其他历史改写。

## 6. 独立验证流程

verifier 必须独立复现验收证据，不得仅阅读 fixer 的“通过”结论。它应在独立隔离环境中核验候选提交、授权范围、必要的 LSP diagnostics、相关测试/构建/门禁、回归风险和生成物一致性。

验证结果必须是下列之一：

- `PASS`：授权范围内的验收标准已被独立证据满足，且无未处理 blocker。
- `FAIL`：独立证据显示修复未满足验收标准、引入回归、越过授权边界或不能正确应用。
- `BLOCKED`：环境、基线、候选提交、工具、权限或必要证据缺失，不能合法给出 PASS/FAIL。

verifier 发现新问题时不得修复或扩展当前 Issue；必须把新候选交给 ledger steward，按报告、检索、分诊、授权、修复、回写、回读的独立生命周期处理。fixer 发现的旁支 Bug 同样如此。

## 7. 台账回写、Git Evidence 与关闭

fixer 和 verifier 都不得直接操作 `ISSUE.xlsx`。只有 ledger steward 可以通过技能指定脚本，将修复开始、结果、失败、受阻、验证结论、状态迁移和 Evidence 串行写回，并在每次写后立即回读。

若有 Git 变更，steward 只能依据脚本已验证的稳定 `repo_id`、canonical full commit hash，以及脚本允许的仓库相对路径/locator 写入 Evidence。不得把分支、PR、比较范围、终端日志、截图、本机路径或猜测写入 Evidence。

当前 `issue_ledger.py` 的合法成功路径要求 Git Evidence：`issue complete-fix` 需要 active `FIX_COMMIT` Evidence 才能从 `FIXING` 到 `READY_TO_VERIFY`，而 `issue record-verification` 需要 active `VERIFICATION` Evidence 才能到 `CLOSED`；`evidence register` 又对 Evidence 的 commit 执行 Git 验证。因此无 Git 变更的“修复”没有可用的脚本闭环。fixer 与 verifier 必须如实回报 `BLOCKED: no-script-supported-non-git-repair-closure`，不得调用这些命令、伪造 Evidence，或声称 `READY_TO_VERIFY`/`CLOSED`。steward 只能在事实真实且脚本允许时撤销授权并退回 `INVESTIGATING`，或延期为 `DEFERRED`；否则保持当前状态并请求人工处置。

Issue 仅在脚本允许的 `READY_TO_VERIFY` 后，取得独立 verifier 的明确验证结论、所需 Git Evidence 已验证（如适用），并由 steward 完成结果写回与回读后才可 `CLOSED`。任一项未完成则 Issue 仍未完成。

## 8. 失败、撤销与范围变化

修复失败、验证失败、无法复现、部分修复、撤销、工具故障或隔离失败都必须返回 ledger steward，由其按脚本允许的状态/事件写回并回读；不得删除历史、覆盖 Event 或把失败隐藏为完成。

授权范围扩大、风险等级上升、需要额外目录/依赖/数据操作或发现旁支 Bug 时，fixer 立即停止受影响部分并请求新的明确授权。已经获得的授权不能被解释为对未列明风险的默认许可。
