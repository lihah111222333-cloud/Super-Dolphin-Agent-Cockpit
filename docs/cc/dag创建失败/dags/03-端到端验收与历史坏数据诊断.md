# 修复点 3：端到端验收与历史坏数据诊断

## 目标

补齐上线前的产品级验收和历史数据处置，确认用户可以只用自然语言创建自动化任务，并且已有坏 DAG 不会被静默批量改成错误默认 prompt。

这个任务不替代前两个修复点。它验证：

- `prompt_list/prompt_get` 在空 DB 下能支撑 DAG designer 自动选 prompt。
- `task_create_dag` 不再保存缺执行者身份的坏节点。
- 已经落库的坏 DAG 能被只读诊断发现，并走显式重绑或重建。

## 修改范围

预计新增或修改：

- 端到端测试或验收脚本，优先放在 `cmd/mcp-orch/tools` 相关测试内。
- 历史坏 DAG 只读诊断测试或运维文档，具体位置由实现阶段根据现有工具入口决定。
- 如已有运维命令或诊断入口，优先扩展现有入口；不要新增长期维护成本很高的独立脚本。

不建议修改：

- 不要改运行时自动派发 guard 来“兼容”坏数据。
- 不要写迁移脚本自动填固定 prompt。
- 不要把端到端验收做成只检查工具 schema 的浅测试。

## 端到端验收路径

### 场景 1：空 DB 下自然语言创建每日简报 DAG

前置条件：

- `prompt_templates` DB 为空，或测试 store 返回空列表。
- builtin registry 可用，至少包含一个 runtime-visible 的自动化执行 prompt。
- 模型/provider/list_models 可返回可用 provider 和 model，或测试中用 stub 固定返回。

用户输入：

```text
每天早上 8 点生成热点新闻简报，输出到报告文件。
```

期望内部流程：

```text
聊天层识别为自动化任务
-> DAG designer 调 prompt_list/list_models/shared_file_list
-> prompt_list 返回 builtin prompt
-> DAG designer 自动选择 prompt_key
-> task_create_dag 保存完整 DAG
-> task_dag_apply_ops 写 scheduled cron
-> task_get_dag 能看到 final_node_key 和完整节点配置
```

验收断言：

- 用户不需要填写 `prompt_key/agent_key/provider/cwd/assigned_to`。
- 创建出的 agent 节点有 `config.exec.prompt_key` 或 `config.exec.agent_key`。
- agent 节点有 `config.exec.provider`。
- Codex provider 节点有 `codex_home/codex_instance_key/codex_model_provider`。
- 根 agent 节点有顶层 `assigned_to`。
- `final_node_key` 指向存在的节点。
- 定时任务的 `cron_expr` 通过 `task_dag_apply_ops update_dag` 写入，而不是只写 metadata。
- 创建和启动链路不再出现 `node.config.exec.agent_key or node.config.exec.prompt_key required`。

### 场景 2：坏 DAG 创建被拒绝且不落库

输入：

- agent 节点有 `config.exec.provider`，但没有 `prompt_key/agent_key`。
- hybrid verifier 有 provider，但没有 `prompt_key/agent_key`。

验收断言：

- `task_create_dag` 返回创建阶段 validation 错误。
- 错误包含字段路径，便于聊天层转译。
- store 中查不到该 DAG。
- 不产生 scheduled wakeup。

### 场景 3：聊天层错误转译

如果资源发现失败，例如 builtin registry 加载失败或 DB 查询失败：

工具层可以返回技术错误：

```text
prompt list failed: ...
```

聊天层面向用户应转译为：

```text
系统当前无法读取自动化执行模板，任务没有创建。请稍后重试或联系管理员恢复提示词资源。
```

验收断言：

- 不要求用户提供 `prompt_key` 或 `agent_key`。
- 不伪装创建成功。
- 不保存半成品 DAG。

## 历史坏 DAG 诊断

上线前需要只读列出已有坏配置。诊断范围：

### agent 节点

条件：

```text
node_type == "" 或 node_type == "agent"
config.exec 存在
config.exec.prompt_key 为空
config.exec.agent_key 为空
```

输出字段：

- `dag_key`
- `node_key`
- `node_type`
- `assigned_to`
- `run_count` 或最近 run 状态，如果查询成本可控
- 缺失字段摘要

### hybrid verifier

条件：

```text
node_type == "hybrid"
config.exec.verifier 存在
verifier.prompt_key 为空且 verifier.agent_key 为空
或 verifier.provider 为空
或 provider=codex 但缺 codex identity
```

输出字段：

- `dag_key`
- `node_key`
- `assigned_to`
- 缺失字段摘要

## 历史数据处置策略

### 不自动修复

禁止把所有坏节点静默改成某个默认 prompt。原因：

- 不同自动化任务需要不同执行模板。
- 默认 prompt 可能让任务看似成功但语义错误。
- 批量隐式修改会破坏审计和用户预期。

### 显式重绑

对仍需保留的 DAG：

1. 通过 `prompt_list/prompt_get` 选择明确 prompt。
2. 生成可审计的 `task_dag_apply_ops update_node` 或等价管理操作。
3. 更新后重新 `task_get_dag` 验证节点配置完整。
4. 必要时手动 `task_start_dag` 验证。

### 重建

如果 DAG 是聊天创建失败的半成品，优先建议用户重新用自然语言创建。新链路应能自动选择 prompt 并创建完整 DAG。

### 已失败 run

已失败 run 不做历史事件篡改：

- 保留原失败事件用于审计。
- 修复 DAG 模板后重新启动新 run。
- 用户侧说明“旧 run 失败原因已修复，请查看新 run 结果”。

## 风险与性能

- 诊断必须只读，避免误改生产 DAG。
- 诊断查询应分页或限量，避免一次扫描大量 run events。
- 如需统计最近 run 状态，优先只取每个 DAG 最近少量 run。
- 端到端测试应使用 stub 或临时 DB，不依赖开发者本机真实生产数据。
- 不把模型选择结果写死到测试里；只断言 DAG 节点内部字段完整。

## 回归测试建议

### 空 DB 用户路径测试

测试目标：

- 模拟空 prompt store + fake builtin registry。
- 调用 prompt discovery 和 DAG 创建相关 handler。
- 断言最终 DAG node config 包含 `prompt_key`。

建议名称：

```text
TestChatCreateAutomationDAGUsesBuiltinPromptWhenDBEmpty
```

### 坏 DAG 诊断测试

测试目标：

- 构造一个合法 DAG、一个缺 agent prompt 的 DAG、一个缺 hybrid verifier prompt 的 DAG。
- 运行只读诊断。
- 断言只返回两个坏 DAG。

建议名称：

```text
TestDiagnoseDAGPromptIdentityGapsReportsOnlyInvalidNodes
```

### 用户无感断言

测试目标：

- 测试输入不包含 `prompt_key`、`agent_key`、`provider` 等字段。
- 输出 DAG 包含完整内部配置。

建议名称：

```text
TestNaturalLanguageAutomationCreateDoesNotRequireInternalFields
```

## 验收标准

- 空 DB 下自然语言创建自动化任务成功，用户不需要填写内部参数。
- 创建出的 DAG 节点包含执行者身份、provider、cwd、assigned_to 和 final_node_key。
- 坏 DAG 在创建阶段失败，不落库、不产生 wakeup。
- 历史坏 DAG 能被只读诊断列出。
- 历史坏 DAG 处置路径要求显式绑定 prompt 或重建，不允许默认静默修复。
- 已失败 run 保留审计事件，通过新 run 验证修复。
