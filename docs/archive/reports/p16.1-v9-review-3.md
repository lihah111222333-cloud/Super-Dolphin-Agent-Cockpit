- **代码预算：通过**
- **Phase 0 清理完整性：不通过**

## 二、审查维度 A：Phase 0 清理完整性

### A1. `difftracker` 全量引用核对

repo 内对 `internal/platform/difftracker` 的外部 import 仅出现在 5 个 Go 文件：

1. `internal/platform/toolbridge/claude_diff.go:10`
2. `internal/platform/toolbridge/claude_diff_test.go:14`
3. `internal/platform/toolbridge/handler.go:15`
4. `internal/platform/toolbridge/handler_test.go:17`
5. `internal/platform/toolbridge/module.go:11`

这说明：
- **Phase 0 的影响面主要集中在 toolbridge 包内部**；
- 删除 `internal/platform/difftracker/` 后，只要上面 5 个文件同步清理到位，**不会在仓库其他包留下编译引用**；
- 但当前计划文本对 `handler.go` / `module.go` 的回退说明还不够细，存在漏删风险。

### A2. `toolbridge/module.go` 当前对 `difftracker` 的依赖列表

`internal/platform/toolbridge/module.go` 当前不是只依赖“aggregator 注入 + claude diff lifecycle”，而是整文件有一串 `difftracker` 绑定点：

- import：`module.go:11`
- `handlerIn` 字段：`Aggregator` / `Resolver`（`module.go:33-40`）
- `provideWorkDirResolver(...) difftracker.WorkDirResolver`（`module.go:56-70`）
- `provideDiffEmitter(...) difftracker.DiffEmitter`（`module.go:72-89`）
- `provideDiffAggregator(...) *difftracker.DiffAggregator`（`module.go:91-96`）
- `registerAggregatorLifecycle(...)`（`module.go:98-112`）
- `claudeDiffLifecycleIn`（`module.go:114-121`）
- `registerClaudeDiffLifecycle(...)`（`module.go:123-153`）
- `cleanupLifecycleIn`（`module.go:155-161`）
- `cleanupOnAgentError(...)`（`module.go:163-170`）
- `registerCleanupLifecycle(...)`（`module.go:172-205`）

#### 判定

计划里写“`module.go` 删除旧 aggregator 注入 + claude diff lifecycle”，**不够完整**。

至少还需要显式处理：

1. **cleanup lifecycle** 这条旧 diff session 清理链（`cleanupLifecycleIn / cleanupOnAgentError / registerCleanupLifecycle`）
2. **`difftracker.WorkDirResolver` 类型耦合**（`handlerIn.Resolver`、`provideWorkDirResolver` 返回类型）

> 否则如果 Phase 0 真按“先删 `difftracker/` 目录”执行，`module.go` 仍会因为类型引用残留而编译失败。

### A3. `claude_diff` 相关文件存在性

已确认以下文件/引用存在：

- 文件存在：`internal/platform/toolbridge/claude_diff.go`
- 文件存在：`internal/platform/toolbridge/claude_diff_test.go`
- `newClaudeRawDiffTracker(...)` 在 `module.go:127` 被调用
- `claudeRawDiffTracker` 相关实现集中在 `claude_diff.go:21-218`

#### 判定

v9 的“删除 `toolbridge/claude_diff.go` + test”这部分是**必要且正确**的。

### A4. `toolbridge/handler.go` 中需要删除/回退的位置

当前 `handler.go` 里与旧 difftracker 方案直接耦合的位置包括：

- `Handler` 字段：`aggregator` / `resolver`（`handler.go:21-26`）
- `routeToolCall()` 内：
  - `mergeCtx := h.mergeContext(...)`（`handler.go:68`）
  - `h.aggregator.Merge(...)`（`handler.go:86-94`）
- `mergeContext()`（`handler.go:275-277`）
- `beginSnapshot()`（`handler.go:279-292`）
- `shouldSnapshot()`（`handler.go:294-305`）
- `lspEditAction()`（`handler.go:307-318`，若 `shouldSnapshot` 删除则通常也应一并删除）

#### 判定

计划文本里写“删除旧 Merge/shouldSnapshot/aggregator”，**仍然少写了两段关键删除点**：

1. `mergeContext()`
2. `beginSnapshot()`

这两段仍直接引用 `difftracker.WithToolCallContext` / `difftracker.BeginSnapshot`；如果不显式纳入 Phase 0 清理，删掉 `difftracker/` 后仍会编译失败。

### A5. 测试侧残留

当前 toolbridge 包中和旧 diff 方案直接绑定的测试还有：

- `handler_test.go:304-350` `TestCleanupOnAgentError_RecoverablePreservesDiffSession`
- `handler_test.go:352-356` `TestShouldSnapshotReplaceRange`

#### 判定

计划里写“`handler_test.go` 删除旧 diff 测试”方向正确，但**建议在计划里明确点名至少上述 2 个 handler 测试**，避免 Phase 0 清理时漏删。

- **守卫本身没有问题，预算是安全的**；
- 但 `7 文件 / 800 行` 更像是**Phase 1 产物的粗估值**，不是当前基线；
- 建议在计划里标明“估算口径（是否含 test）”，避免后续互审时口径不一致。

## 四、问题列表

### 阻塞问题

1. **Phase 0 清理清单遗漏 `handler.go` 的 `mergeContext()` / `beginSnapshot()`**
   - 删除 `difftracker/` 后，这两段仍会直接引用 `difftracker`，导致编译失败。

2. **Phase 0 清理清单遗漏 `module.go` 的 cleanup lifecycle 与 resolver 类型迁移**
   - `cleanupLifecycleIn / cleanupOnAgentError / registerCleanupLifecycle` 仍依赖 `*difftracker.DiffAggregator`
   - `provideWorkDirResolver` / `handlerIn.Resolver` 仍依赖 `difftracker.WorkDirResolver`
   - 若不显式纳入 Phase 0，同样会留下编译残留。

### 非阻塞问题

3. **预算表述口径不清**
   - `7 文件 / 800 行` 不是当前实测基线，建议标注为“Phase 1 估算值”并说明是否包含测试文件。

## 五、最终判定

**不通过**。

原因：
- **预算守卫是安全的，代码预算这一项通过；**
- **但 Phase 0 清理说明仍有关键漏项，按当前文字执行存在删掉 `difftracker/` 后残留编译引用的风险。**

建议：
- 在计划里把 `handler.go` 的 `mergeContext/beginSnapshot` 明确列入 Phase 0 回退项；
- 在计划里把 `module.go` 的 `cleanup lifecycle` 与 `WorkDirResolver` 类型迁移明确列入 Phase 0；
- 将 `7 文件 / 800 行` 改成带口径说明的估算值。
