# P16.1 统一 Diff 计划 v9 审查（R2）

结论：**不通过**

## 维度 A：threadId 回填

结论：**通过**。

### 证据
- `internal/store/binding/contract.go:59-70` 的 `Binding` struct 字段只有 `AgentID / Provider / ProviderThreadID / CodexThreadID / RolloutPath / Cwd / Archived / CreatedAt / UpdatedAt / SessionUUID`，**没有 `ThreadID` 字段**。
- `internal/store/binding/contract.go:17` 定义接口：
  - `GetThreadByAgent(ctx context.Context, agentID string) (string, error)`
- `internal/store/binding/store.go:138-144` 的实现确实直接返回 `(string, error)`：
  - 先调用 `s.q.GetThreadByAgent(ctx, agentID)`
  - 成功时返回 `threadID, nil`
- `sql/queries/thread_binding.sql:39-42` 查询为：
  - `SELECT COALESCE(NULLIF(codex_thread_id, ''), provider_thread_id) AS thread_id`
  - 含义是：**优先 `codex_thread_id`，为空时回退 `provider_thread_id`**。

### 语义核对
这个 SQL 逻辑和现有线程语义是对齐的：
- `internal/module/thread/binding_registration.go:216-228` 会把 `registration.PublicThreadID` 持久化到 `CodexThreadID`
- `internal/module/thread/start_session.go:248-253` 回填运行态时，也优先把 `binding.CodexThreadID` 填到 `state.PublicThreadID`

所以，Claude proxy 要回填用于 UI/diff 展示的 threadId，**优先取 `codex_thread_id` 是正确的**。v9 把来源改成 `bindingStore.GetThreadByAgent(ctx, agentID)`，相对于 v8 的 `GetByAgentID(...).ThreadID`，这次修正是成立的。

## 维度 B：proxyAddr 延迟绑定

结论：**延迟绑定思路本身可行，但 v9 还没有把 P3 修到“可直接执行且满足强制归一”的程度。**

### B1. `func() string` 延迟绑定在 Go + fx 中可行

这部分思路本身没有问题。

### 代码侧依据
- `internal/provider/claudecli/module.go:13-25`
  - `claudecli.Module` 只是提供 Claude driver factory。
- `internal/platform/toolbridge/module.go:20-31,42-48`
  - `toolbridge.Module` 当前依赖的是 `codexapp.ServerManager` 和 `codexapp.DriverFactory`，用于绑定 Codex tool handler。
  - 它**没有**反向依赖 Claude driver factory/grouped drivers。
- `internal/app/modules.go:49-51`
  - 虽然模块列表里 `claudecli.Module` 写在 `toolbridge.Module` 前面，但这不会天然构成循环；依赖是否成环取决于构造图，不取决于书写顺序。

### 判定
如果由 `toolbridge` 提供一个 `func() string`，再让 `claudecli` 的 driver/factory 注入它，那么新增的是单向依赖：
- `claudecli -> toolbridge`

而当前仓库里没有 `toolbridge -> claudecli` 的对称依赖，因此**没有明显 fx 循环依赖风险**。

### 外部依据
- Fx 文档说明 `Provide` 接受普通构造函数，依赖解析不靠模块书写顺序：
  - https://pkg.go.dev/go.uber.org/fx
- Fx lifecycle 文档说明 `OnStart` 适合启动长生命周期 goroutine / server：
  - https://uber-go.github.io/fx/lifecycle.html

### B2. proxy 启动失败时，manifest 会怎样？

按 v9 当前文字和现有实现推导：**不会优先报错，而会静默降级为 sidecar**。

### 证据链
1. v9 明确写了：Claude driver **只传 `ProxyHTTPAddr`，不再传 `PeerHTTPAddrs`**
   - `docs/plans/迁移/p16.1-unified-diff-plan.md:78-80`
2. `internal/dto/provider/manifest.go:60-78` 的现有逻辑是：
   - 有 HTTP 地址 → 生成 `type:"http" + url`
   - 没有 HTTP 地址 → 回落到 `Command` 二进制配置
3. `internal/provider/claudecli/transport_config.go:253-297` 的现有逻辑是：
   - `type=http && url!=empty` → 写 HTTP MCP server
   - 否则只要 `Command` 合法 → 写 stdio MCP server
4. `internal/provider/unified/manifest_test.go:34-58` 也证明了：没有 HTTP 地址时，`BuildManifest` 默认就是产出本地 binary command。

### 结论
如果 `proxyAddrFn()` 返回空字符串：
- Claude manifest **不会报错**
- 而是会回落到 `mcp-lsp` / `mcp-orch` 的 **sidecar stdio 模式**

这和 v9 想要表达的“强制 Claude 走 proxy → 统一 diff tracking → 不可能绕过”是**冲突的**。只要 sidecar 还能被生成，Claude 就仍然存在绕过 proxy 的旁路。

## 问题列表

### 1. P3 文本里 `ServeProxy` 的接口与调用示例不一致
- `docs/plans/迁移/p16.1-unified-diff-plan.md:87-91` 写的是：
  - `func (h *Handler) ServeProxy(addr string) error`
- 但 `docs/plans/迁移/p16.1-unified-diff-plan.md:119-121` 示例却写：
  - `go h.ServeProxy(proxyListener)`

`proxyListener` 是 `net.Listener`，不是 `string`。这说明 v9 的 P3 片段**还没有收敛到可编译的实现级别**。

### 2. P3 的失败语义与“强制归一”目标冲突
- v9 一边说“只传 `ProxyHTTPAddr`，删除 `PeerHTTPAddrs`，强制 Claude 走 proxy”
- 另一边按现有 `BuildManifest + transport_config` 语义推导，只要 `ProxyHTTPAddr` 为空，就会**静默回落 sidecar**

这意味着：
- 时序问题虽然被“闭包延迟取值”修掉了
- 但**可用性失败路径**没有被修掉
- 最终仍然不能保证“Claude 不可能绕过 proxy”

### 3. P3 启动失败没有明确上抛路径
v9 的 OnStart 示例里：
- `proxyListener, _ := net.Listen(...)` 丢弃了 `error`
- `go h.ServeProxy(...)` 也没有把运行错误回传给 fx

因此即使 proxy 启动失败，也更像是“失败被吞掉后走旁路”，而不是“显式失败 / 显式降级”。这对审查结论是减分项。

---

## 总结判定
- **P2 threadId 回填：通过**
- **P3 proxyAddr 时序：思路通过，但方案文本仍有关键缺口，不足以判定为“正确修正”**

因此本轮审查总结果是：**不通过**。

## 建议
1. 如果目标真的是“Claude 必须经过 proxy 才能拿到统一 diff”，那么在 Claude driver / `BuildManifest` 路径上，`ProxyHTTPAddr == ""` 时应视为**硬错误**，而不是回落 sidecar。
2. 统一 `ServeProxy` 的 API：
   - 要么 `ServeProxy(addr string)`，内部自己 `ListenAndServe`
   - 要么 `ServeProxy(listener net.Listener)`，由 OnStart 先 `net.Listen`
   - 两种写法二选一，不要混用。
3. `OnStart` 必须对 `net.Listen` 失败、proxy serve 失败给出明确处理，不要吞错。
4. P2 部分可以保留，`GetThreadByAgent` 这次选型是对的，不需要再回退到 `GetByAgentID(...).ThreadID`。
