# 风险清单

## 高风险问题

### H1. 新 UI 缺少编译期类型边界

证据：

- `frontend-app` 没有 `tsconfig.json`。
- `frontend-app/package.json` 的 `typecheck:contracts` 实际是 `eslint src/shared/api/backendApi.js src/entities/client/model/providerPreferences.js`，不是类型检查器。
- `frontend-app/src/shared/api/backendApi.js` 手写 RPC 方法名、payload 规范化和字段过滤。
- `frontend-app/src/entities/client/model/useClientStore.js` 手写 provider、thread、turn、timeline、bridge event 状态编排。

影响：

- 跨语言契约仍主要靠 JS 测试和 Go strict decoder 兜底。
- 字段重命名、camel/snake 兼容、nested config 变更、provider preference tombstone 这类问题只有测试覆盖到才会暴露。
- 新页面如果绕过 facade 或遗漏 matrix，很难在编译期发现。

建议：

- P0：先在 `shared/api` 和 `entities/client/model` 引入 `jsconfig.json` + `checkJs` 约束，或直接迁移这些合同文件到 TypeScript。
- P0：把 `RPC_CONTRACT_REGISTRY` 与 Go RPC handler 清单建立自动对账，至少保证 P0 方法都有前端 facade、后端 handler、consumer 测试。
- P1：逐步从 Go DTO 或 manifest 生成前端 RPC 方法名和 payload 类型。

### H2. UI 状态和页面 controller 仍过大

证据：

- `frontend-app/src/entities/client/model/useClientStore.js`：4785 行。
- `frontend-app/src/pages/chat/ChatPage.jsx`：3645 行。
- `frontend-app/src/pages/workflows/WorkflowPage.jsx`：1856 行。
- `frontend-app/src/shared/api/backendApi.js`：1252 行。
- 对应测试也很大：`App.test.jsx` 7347 行，`useClientStore.test.js` 4853 行。

影响：

- 单个变更容易同时触碰状态、UI、RPC 和测试。
- 大文件让 review 难以判断“只是移动代码”还是“行为改变”。
- 局部回归定位成本高，尤其是 chat/workflow/files/skills/memory 等主页面。

建议：

- P0/P1：按行为边界继续拆，不做一次性大重构。
- 优先顺序：`useClientStore` 的 thread lifecycle、bridge event patch、provider preference、runtime result buffer；`ChatPage` 的 composer controller、timeline materialization、runtime panel wiring。
- 拆分时要求“只移动，不改语义”，每一步保留或补充同名测试。

### H3. Provider 产品口径和技术抽象仍容易漂移

证据：

- `frontend-app/src/entities/client/model/providerPreferences.js` 定义 `RUNTIME_PROVIDER = 'codex'`，非 Codex runtime provider 会 fail-fast。
- 同文件仍保留 `KNOWN_PROVIDERS = ['codex', 'claude']`，用于识别历史或配置值。
- `internal/app/modules.go` 当前加载 `codexapp.Module`，`claudecli.Module` 被注释。
- `README.md` 和 codemap 仍保留 Claude CLI 相关说明。

影响：

- 当前桌面产品若只支持 Codex，任何 UI 或文档里出现“Claude 可运行”都会造成误导。
- 后续有人看到 `internal/provider/claudecli` 存在，可能误判桌面链路已经支持 Claude。
- 这类误判会直接影响 thread/start provider identity、设置页、provider runtime 恢复链路。

建议：

- P0：明确文档口径：“当前桌面主链路只支持 Codex runtime；Claude provider 包是保留适配层，不等于已装配可用。”
- P1：设置页如果展示 Claude，必须清晰标记不可用或隐藏。
- 恢复 Claude 时必须补 Fx 装配、UI provider selection、thread/start、turn/start、恢复会话和端到端 smoke。

### H4. 新 UI build/embed/desktop 链路仍需真实端到端证明

证据：

- `frontend-app` 的 dev 路径走 Vite + Wails proxy。
- `make frontend-app-build` 先 build `frontend-app/dist`，再通过 `sync-frontend-dist.mjs` 同步到 legacy embed dist。
- `internal/ui/wails/assets.go` 同时支持 dev proxy 和 bundled asset server。
- `cmd/agent-terminal/frontend` legacy 包仍存在，且包含自身 Vite/Vitest/Playwright 配置。

影响：

- `npm test` 和 `npm run build` 不能证明桌面宿主、Wails bridge、嵌入资源、无 dev proxy 的路径都可用。
- CI 主要在 Ubuntu，Windows PowerShell runner 的端口清理、PATH、Postgres、Codex CLI 环境仍需单独验证。
- legacy embed 路径和当前 React UI 并存，容易在打包或文档中混用。

建议：

- P0：每次 UI 架构调整后跑 `frontend-app` lint/test/build，再跑一次桌面 smoke。
- P1：增加 Windows job 或至少保留可复现的 PowerShell smoke 记录。
- P1：给 embed dist 同步和 Wails asset handler 保持测试；当前已有测试，需要纳入固定验证清单。

## 中风险问题

### M1. CSS 拆分后仍依赖全局导入顺序

证据：

- `frontend-app/src/main.jsx` 直接按顺序 import 30 多个 CSS 文件。
- `styles.css` 已变轻，但 page/workbench/polish/shared 样式仍是全局级联。
- `PagePrimitivesLate.css`、`ThemePolish.css`、`PagePrimitivesPolish.css` 等文件名本身说明了顺序语义。

影响：

- 新增或移动 import 顺序可能改变覆盖结果。
- 页面级 CSS 可能影响其他页面，尤其是共享 class 或 token。

建议：

- 给 CSS 导入顺序增加注释分组，说明 base/page/component/polish/late 的覆盖规则。
- 对关键页面保留视觉或 DOM class regression 测试。
- 中期考虑按页面组件就近 import，减少全局覆盖面。

### M2. 合同测试矩阵有价值，但仍可能和后端 handler 漂移

证据：

- `backendApi.contractMatrix.js` 是手写 registry。
- `.github/workflows/ci.yml` 跑 frontend test 和 Go test，但未看到自动比对 `RPC_METHODS` 与 Go 注册 handler 的生成式检查。

影响：

- 新增 Go RPC handler 时可能忘记前端 matrix。
- 前端新增 facade 时可能没有后端 handler 或 P0 测试。

建议：

- 增加一个只读脚本：枚举 `RPC_METHODS`、contract matrix、Go RPC registration，输出缺口。
- 对 P0 方法强制 matrix entry + facade test + consumer test。

### M3. Legacy UI 仍占据大量仓库面积

证据：

- `cmd/agent-terminal/frontend` 仍有 `package.json`、`vite.config.js`、`vitest.config.js`、Vue app、Playwright e2e、快照。
- `README.md` 明确当前新 UI 是 `frontend-app`，legacy 路径只在 package-embed 或旧 UI 任务中编辑。

影响：

- 代理或新开发者容易误改 legacy Vue 路径。
- 打包 dist 仍位于 legacy frontend 目录，概念上容易混淆。

建议：

- 在 legacy 目录增加更醒目的 README/注释，说明“不是当前主 UI”。
- 长期将 embed dist 目录和 legacy source 目录拆开，降低误判。

### M4. 文档和终端编码显示存在可读性风险

证据：

- PowerShell 读取部分中文说明时出现乱码，例如 README/CLAUDE/Makefile 中的中文注释在终端输出不稳定。
- codemap 使用 `-Encoding UTF8` 后可正常读取中文正文。

影响：

- Windows 原生终端下审查和排错容易误读规则。
- 代理如果从乱码上下文推断命令，可能误判仓库约束。

建议：

- 统一文档 UTF-8，无 BOM 或有 BOM 的策略二选一。
- 增加简单编码检查脚本或在贡献说明中要求 PowerShell 使用 UTF-8 输出。

## 低风险问题

### L1. `styles.css` 已减重，但“样式治理”还未完成

当前 `styles.css` 只有 137 行，说明拆分方向正确。剩余工作不是继续机械拆文件，而是稳定命名、导入顺序和页面边界。

### L2. Vite watch 默认 polling 有性能成本

`frontend-app/vite.config.js` 默认 `watch.usePolling=true`，这对 Windows/VM 环境更稳，但在大仓库上可能更耗 CPU。已有 env fail-fast 测试，建议只在文档中说明如何显式关闭。

### L3. CI 没覆盖所有本地 smoke

CI 跑 frontend lint/test/build 和 Go build/test，但不会覆盖真实 Codex CLI 登录状态、Windows 桌面窗口、用户本机端口冲突。此类应作为 release/smoke 清单，而不是普通单测。
