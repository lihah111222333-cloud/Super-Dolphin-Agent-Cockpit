### 3.2 hash 语义与 p20.10 的关系
- `p20.10` 的 `skill/expand` 返回值里，`content_hash` 表示“**选中全文 / section / 资源内容在截断前**”的 SHA-256（`docs/plans/迁移/p20/p20.10-skill-rpc-expand-list.md:64-65`）。
- 只有 `section == ""` 时，这个 hash 才等于整份 `SKILL.md` 的全局 hash；section / resource 级 expand 的 hash 与 `(name,hash)` 全文缓存语义不一致。
- **本单明确选 A**：`ApprovalCache.Lookup/Approve(name, hash)` 只覆盖 `section == ""` 的整份 `SKILL.md`；section / resource 级审批只走 per-call，不读写 `(name,hash)` 持久缓存。若未来要做 artifact-level 缓存，另开后续单显式接 `LookupArtifact/ApproveArtifact`。

## 6. Approval 缓存接入链
1. `p20.10` 提供的 `skill/expand(name, section, max_bytes)` 进入 host skill service。
2. 先用 `validateSkillName()` + `resolveSkillRecordByName()` / expand 读路径拿到 `SkillInfo{Name, Trust}`、目标内容类别（整份 / section / resource）以及对应 `content_hash`。
3. 若 `Trust` 为 `user/signed`：直接放行，不走审批缓存。
4. 若 `Trust` 为 `project` 且 `section == ""`：先查 `approval.Lookup(name, hash)`；注意这表示 **content-global `(name,hash)`**，不是项目级批准。
5. 若 `Trust` 为 `project` 且 `section != ""`：**不查 `(name,hash)` 缓存**，直接走 per-call approval。请求 payload 至少包含：`name`、`section`、`content_hash`、`trust`、`approval_scope`、`skills_dir/project_root`、`threadId/sessionId`。
6. 审批通过后：
   - `scope=project` + `section == ""`：`approval.Approve(name, hash, trust, approvedBy)`
   - `scope=session` + `section == ""`：只写内存态，不落盘；绝不能写入 `ApprovalCache`
   - 任意 `section != ""`：只对本次调用生效，不写 `(name,hash)` 缓存
7. 返回 expand 结果；整份 `SKILL.md` hash 变化时因为 `Lookup(name,newHash)` miss，会自动强制重审；section / resource 的 hash 仅作为本次审批载荷，不参与持久缓存命中。
