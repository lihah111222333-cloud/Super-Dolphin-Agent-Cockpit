# rollout：用稳定 markers 替换 legacy trim 规则

> 创建时间：2026-04-19 | 状态：📝 审查后需拆成读/写两段 | 依赖：读端独立；写端改动并入 `p20.6 + p20.7`
> Agent 预算：1 个 codex agent，改动 ≤4 文件，≤350 行/文件

## 1. 目标（1-3 句）
本单**只做读端**：把 rollout trim reader 从 `摘要:` / `使用方式:` 这种自然语言 marker 升级成稳定机器可识别的 shared helper，并支持 legacy + v1 dual-read、fail-open。**写端切到 v1 marker 不在本单范围**，分别并入 `p20.6`（claude）与 `p20.7`（codex）。

## 2. 前置依赖
- **读端独立**：本单可以单独先发，只改 shared helper + provider reader。
- **写端不在本单**：切换写端 marker 的工作并入 `p20.6` / `p20.7`，且必须等本单 shared helper 合并后再开 gate。

## 3. 源码锚点（复用 `source-refs-appendix.md`）
- [SRC-A13](source-refs-appendix.md#src-a13) — codex rollout trim 仍是 legacy marker
- [SRC-A14](source-refs-appendix.md#src-a14) — claude rollout trim 仍是 legacy marker

## 3.1 审查补记（2026-04-19，LSP 已核）
- 真实读端入口：
  - `internal/provider/codexapp/history_rollout.go:152-155` — `normalizeRolloutUserContent()` 仅在 user message 上调用 `trimInjectedSkillBlock()`。
  - `internal/provider/codexapp/history_rollout.go:245-292` — codex 当前仍靠 `[skill:` + `摘要:` / `使用方式:` + 8 行 lookahead 的 legacy 启发式。
  - `internal/provider/claudecli/session_history.go:34-44` + `internal/provider/claudecli/factory.go:315-317` — claude 读端最终经 `trimClaudeHistory()` / `stripSystemNoise()` 进入 `trimInjectedClaudeSkillBlock()`。
  - `internal/provider/claudecli/history_trim.go:63-110` — claude 侧实现与 codex 基本重复，适合抽共享 helper。
- 真实写端现状（决定兼容策略）：
  - `internal/provider/codexapp/session_turn.go:77-80` + `internal/provider/codexapp/module.go:232-249` — 当前只写 `[skill:<name>]\n<body>`，未写 `摘要:` / `使用方式:`，也未写 `[/skill:...]`。
  - `internal/provider/claudecli/session_turn.go:315-352` — 当前写 `skills:` 列表 + `[skill:<name>]\n<body>`；与 codex 一样还没有 v1 close marker。
  - 仓内 `::full@v1` / `::summary@v1` / `[/skill:` 当前无命中（LSP grep）；说明本单必须坚持“读端双读先落地，写端后切”。
- 直接结论：
  - `internal/module/skill/rollout_markers.go` 应做成纯 helper（string in / string out），不要夹带 fx / store / provider 依赖。
  - 兼容期采用 **dual-read / single-write**；不要 dual-write，同一 skill 块同时输出 legacy+v1 会双倍耗 token 且加重 trim 歧义。
  - v1 trim 对 malformed / 未闭合 block 必须 fail-open（保留原文，不误删用户输入）；legacy 分支继续容忍旧历史。

## 6. 验收标准
- 单元/behavior 测试入口：`go test ./internal/provider/codexapp/... ./internal/provider/claudecli/... ./internal/module/skill/...`；`go build ./...`、`go test ./...` 全绿；archtest 不新增 provider duplicated trim util。
- 行为门槛：reader 端必须实现 **legacy + v1 dual-read**、fail-open；helper 只处理 marker block，不吞 Claude `skills:` prelude。

### 6.1 架构合规结论（审查补记）
- **分层**：shared helper 放 `internal/module/skill` 合规；provider → module 允许，反向不允许。不要放到具体 provider 包里继续复制，也不要让 helper 反向 import provider。
- **fx**：`internal/module/skill/module.go:15-18` 已负责 `fx.Provide(NewSkillHandlers)`；helper 文件本身必须保持无 fx import，符合 `internal/archtest/dependency_direction_test.go:54-67`。
- **freeze / 预算**：守卫默认值见 `internal/archtest/guardlib.go:17-33`；当前无 `freeze_registry.go` 对这几个路径的显式 freeze，说明本单无需额外 freeze 豁免。
- **循环依赖**：helper 最好只依赖 stdlib；若需要共用 mode/type 字面量，优先从 `internal/dto/provider` 读常量，禁止再回头 import `internal/provider/...`。
- **测试**：除新增 `rollout_markers_test.go` 外，至少补齐 codex / claude 两侧 reader golden。现有 provider tests 全绿只能证明 legacy case 未破，不能代表 v1 已覆盖。

## 7. 风险与回退
- 风险 1：若 shared helper 反向 import `internal/provider/...`，会把读端工具做成 provider-specific，破坏共享目标。回退：helper 保持纯函数，只收/返字符串。
- 风险 2：若写端与读端同单切换，会把“当前写端其实还没写 legacy/v1 marker”的事实掩盖掉。回退：坚持读写分离，writer 切换回 `p20.6` / `p20.7`。
- 风险 3：若新 marker 写端尚未合入，测试会只覆盖读端兼容。回退：保留 legacy 识别，读端先行不破坏旧 rollout。

## 8. 合规结论（修订后）
- **范围边界**：✅ 本单只做 reader + shared helper；writer 切换明确分流到 `p20.6` / `p20.7`。
- **当前真实写端**：✅ 文档已明确 `codexapp/module.go:232-249` / `claudecli/session_turn.go:315-352` 当前只写 `[skill:name]\n<body>`（Claude 另带 `skills:` prelude），既没写 legacy 摘要块，也没写 v1 close marker。
- **共享 helper**：✅ `internal/module/skill/rollout_markers.go` 保持纯函数，禁止反向 import `internal/provider/...`。
- **兼容策略**：✅ reader 采用 legacy + v1 dual-read、fail-open；Claude `skills:` prelude 继续由 provider 自己处理，不归 helper 吞噬。
