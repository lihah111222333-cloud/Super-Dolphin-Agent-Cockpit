# ~~MCP：把 `skill_list` / `skill_expand` 注册到 `cmd/mcp-orch`~~

> **状态：🚫 已废弃（2026-04-19）**
> 废弃决定人：项目负责人，经架构评审确认

## 废弃原因

### 1. 架构错位：Skill 是宿主独有能力，不属于编排层

`cmd/mcp-orch` 是独立二进制进程，与宿主主程序分离运行。Skill 的扫描、元数据解析、trust 校验、审批缓存、section 提取等全部实现位于宿主进程（`internal/module/skill/*`）。在 mcp-orch 中注册 `skill_list` / `skill_expand` 工具面临两个不可接受的选择：

- **重复实现**：在 mcp-orch 内重建 skill 扫描/expand 逻辑 → 双实现漂移
- **IPC 回调**：mcp-orch 通过某种 IPC 调用宿主 host RPC → 多一跳，架构复杂度无收益

### 2. 编排层拉起的子进程也在宿主中

mcp-orch 编排的子 agent 进程最终仍在宿主主程序中运行。只要宿主侧提示词包含 skill 清单（L1 manifest），模型即可通过提示词触发 skill 相关行为，无需额外的 MCP 工具入口。

### 3. 正确路径：宿主 Host RPC + Provider 暴露

`skill_expand` / `skill_list` 的正确实现路径：

```
模型 → provider (claudecli/codexapp) → 宿主 host RPC skill/expand → skill.Service
```

这与 `read_file`、`run_command` 等现有工具一致，由 provider 层将宿主 RPC 能力暴露给模型，不经过 mcp-orch。

### 4. mcp-orch 现有工具的数据归属验证

`internal/sidecar/orch/tools/` 中现有的所有工具（`prompt_list`、`command_get`、`orchestration_*`、`memory_*`、`shared_file_*`）读写的都是 **mcp-orch 自有数据**（SQLite/PG store）。Skill 数据来自文件系统（`.agent/skills/`），归宿主管理，不属于此范畴。
