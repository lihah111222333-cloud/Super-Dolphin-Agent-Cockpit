### 4.5 `StartAssembly` / `Snapshot` / `StartSessionRequest` 调用链结论
- `internal/module/thread/start_session_helpers.go:37-64,88-108` 是 `StartRequest -> StartInput -> StartAssembly / PromptAssemblySnapshot / StartSessionRequest` 的主映射落点。
- `internal/module/thread/prompt_snapshot.go:15-52,154-171,183-196,331-346` 是 runtime snapshot / stored snapshot 的统一入口；launch skill 一旦缺席这里，resume/fork/recover 就会丢失语义。

### 4.6 与 p20.7 的分工边界
- `p20.4` 负责 `StartRequest -> StartInput -> StartAssembly / Snapshot -> Store / Provider DTO` 的 DTO wire 与 durability 语义。
- `docs/plans/迁移/p20/p20.7-skill-inject-codexapp.md:21-28,42-46` 已定性：codex provider 侧由 `startAssemblyInstructions()` 单点调用 `InjectL1Manifest(baseInstructions, manifest)`，保证 runtime config 与 remote `thread/start` 同源。

## 8. critical-path 闭环检查
- **p20.2 -> p20.3**：`p20.2` 解决 turn 侧 `SkillRef` hydration；`p20.3` 只提供 launch name transport。两者还没有共享实体载荷，这是已知分层结果，不是 bug。
- **p20.3 -> p20.4**：本单必须把 `LaunchSkillNames/ForceLaunchSkills` 从 `StartRequest` 送到 `StartInput`，再进入 `StartAssembly/Snapshot`；如果任何一层遗漏，resume/fork/recover 都会丢 launch skill。
- **p20.4 -> p20.7**：本单产出的 `StartAssembly/Snapshot + StartSessionRequest` fallback 是 codex L1 manifest 注入的上游真相；`p20.7` 负责把它并入 `BaseInstructions`，本单不再创建 provider-side 平行 wire。
- **接口不对齐点 1**：若只改 `dto.StartSessionRequest` 顶层字段、不改 `StartAssembly/Snapshot`，resume/fork/recover 会丢 launch skill。
- **接口不对齐点 2**：若误在 `threadStartParams` 新增同名字段，会与 `StartAssembly/Snapshot` 形成 split-brain。
- **接口不对齐点 3**：`useThreadActions.js:103-125` 的“先 start 再 resolve skills”顺序仍限制首条聊天消息路径；这不是 p20.4 的 write set，但必须在文档中显式标注，避免误判为 launch 全链闭环已覆盖 UI 首发场景。

## 9. 风险与回退
- 风险：launch skill 变成 snapshot 语义后，若 hash 不包含新字段，会导致旧 snapshot 被错误复用。
- 风险：同时保留 top-level request 字段与 assembly/snapshot 字段，若未定义 precedence，会出现 split-brain。
- 风险：若在本单误改 codex `threadStartParams` / `startAssemblyInstructions()`，会与 `p20.7` 的单点注入方案冲突。
- 回退：字段全部保持 optional；若后续 `p20.5` / `p20.7` 尚未合入，provider 仍按旧 prompt 文本行为工作，但 snapshot / resume 语义先打通。

## 合规结论
- **仓库契约**：受影响生产包当前计数（排除 `_test.go`）为：`internal/module/thread=25/5790`、`internal/module/prompt=26/2858`、`internal/dto/provider=9/292`、`internal/contract=15/953`（格式：文件数/有效行）。`thread` 已触顶默认包文件预算 25，`prompt` 已依赖 freeze registry 26；因此本单 **必须 0 新文件**，测试只能复用现有文件；`internal/provider/codexapp` / `internal/provider/claudecli` 在本单只作 read-only 锚点。
- **分层合规**：`internal/contract` 只定义 provider-neutral `StartInput`；`internal/dto/provider` 承担 thread->provider DTO；`internal/module/thread` 负责 lifecycle + snapshot persistence；provider-specific manifest 注入显式交给 `p20.7`。禁止 provider 反向 import `internal/module/prompt`。
- **DTO 破坏性变更评估**：本单为 additive optional 字段。`threadstore.PromptSnapshot.UnmarshalJSON()` 已具备 legacy merge 机制；旧 snapshot 缺字段时回落到 `nil/false`。`StartSessionRequest` top-level 字段继续保留，但只作为 merge-skew / handoff fallback，不再与 provider wire 并行扩容。
- **rollout snapshot 兼容**：stored snapshot / runtime snapshot 都是 JSON additive；旧 rollout 不写新字段仍能加载。真正的兼容风险只在 hash 选择，不在字段解码。
- **fx wiring 变更清单**：无新增 fx provider / invoke。`internal/module/prompt/module.go` 已导出 `AsPromptAssemblyService`，`internal/module/thread/module.go` 已以 optional promptAssembly 注入；p20.4 只改 payload / snapshot，不改 DI 图。
- **freeze registry 预估调整**：无。若误新建 `start_skill_wire_test.go`，`thread` 会从 `25 -> 26`，需要新增 freeze 或拆包，均不符合本单范围。
- **循环依赖 sanity check**：新增字段沿 `thread -> dto/provider -> store/thread` 单向扩散；provider 端只读这些字段，不在本单新增写回路径；无新环。
- **测试入口锚定**：最小必改测试锚点为 `start_prompt_context_test.go`、`prompt_integration_test.go`、`phase45_regression_test.go`、`resume_test.go`、`fork_isolation_test.go`；`./internal/provider/unified/...` 与 prompt e2e 为回归锚点。
