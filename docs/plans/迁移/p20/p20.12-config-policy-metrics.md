## 8. 审查补遗（2026-04-19，LSP 核查）
### 8.1 config 设计结论
- `internal/platform/config/config.go:9-25` 当前只有 `DatabaseURL/RPCAddr/LogLevel/ProjectRoot` 四个字段；新增 `Config.Skill` 子结构是**增量兼容**的，不会反向要求 config 包依赖业务模块。
- 默认值与 fallback 必须双保险：
  - `Config.New()`：env 缺失时默认 `ProgressiveDisclosure=false`、`TokenBudget=3000`；
  - `SkillPolicy`：拿到 `nil config`、`0`、负数、解析失败时，仍回落到 `false/3000`。

### 8.2 Policy 接口结论
- 采用“**配置纯数据 + policy 代码接口**”混合方案，**不建议**做 policy-as-code DSL。
- 推荐最小接口保持在 `internal/module/skill` 内，例如：
  - `ProgressiveDisclosure() bool`
  - `TokenBudget() int`
  - `Mode(ctx, input) dto.SkillMode`
- `service.go:20-34` 已有 `approval` / `readConfigState` 预留字段，是新增 `policy` / `metrics` 的合适注入位；不要把决策逻辑塞回 `config` 包。

### 8.3 Metrics 结论
- 仓库内未发现统一 Prometheus / OTel / statsd 基础设施；现有“metrics”只见于 bootstrap heartbeat 的 `json.RawMessage`，字段名也是 `queued_reports` / `client_kind` 这种 snake_case。
- 因此本单先对齐 **backend-agnostic + snake_case**：
  - `skill_l1_tokens`
  - `skill_expand_total`
  - `skill_expand_error_total`
  - `skill_cache_hit_total`
  - `skill_cache_miss_total`
  - `skill_injection_decision_total`
  - `skill_context_tokens_saved_total`
- **不建议**直接落 `skill.expand_rate` / `skill.cache_hit` 这类“点号 + rate”命名：rate 应由面板/查询派生，代码里优先记原始 counter / histogram。

### 8.4 架构合规结论
- 当前草案“新增 3 文件”与仓库契约冲突，需修正后才可派单。
- `internal/module/skill` 现有 24 文件、约 4196 行；行数安全，**文件数是主约束**。
- 本单宜只落“配置 + policy/metrics 骨架 + 注入点”，不要顺手把 5 个消费者一起接完。
