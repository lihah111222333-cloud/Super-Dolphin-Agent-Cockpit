## 4. 关键决策点

### 4.1 codexapp 路径：toolbridge 加 host-direct 分支

新建 `internal/platform/toolbridge/host_tools.go`，提供：

- `HostToolRegistry` interface：`ListHostTools() []HostTool` / `CallHostTool(ctx, name, params) (any, error)`
- 一个 host-direct 实现：`SkillHostTools` 包装 `skill.Service`，把 `skills/expandBody` / `skills/readResource` 暴露成 `skill_expand_body` / `skill_read_resource`
- `Handler` 结构体新增 `hostTools HostToolRegistry` 字段（fx 注入，缺省 nil）
- `routeToolCall()` 加分支：peer 路由前先查 hostTools，命中则本进程直跑，不查 peer
- `ListToolsForCodex()` 加分支：聚合 hostTools 工具列表与 peer 列表

**实施细节明确（审查反馈补充）**：

- **fx 注入点**：`internal/platform/toolbridge/module.go` 通过 `provideHostToolRegistry(skill.Service)` 把 host skill service 包装成 `HostToolRegistry`。`Handler.HostTools` 是 optional 字段，便于测试 / 未来 no-provider 图 nil-safe fallback；但当前 provider 输入本身不是 optional。mcp-orch / mcp-lsp standalone 目前不加载 `toolbridge.Module`，若未来加载，需先改成 optional `fx.In` 或提供 noop registry。
- **hostTools 为 nil 的 fallback**：`routeToolCall` / `ListToolsForCodex` 都必须 nil-safe。`hostTools == nil` 等价于“no host-direct tools”，全部走现有 peer 路径，不报错不 panic——以保证测试 / 未来 no-host-tools 图不会因为可选字段为空崩溃。
- **dedup 优先级**：同名工具同时出现在 hostTools 和 peer 中时，**hostTools 优先**（宿主属于会调者，应能覆盖 peer）。dedup 在 `ListToolsForCodex` 聚合阶段按 `name` 判重，后加入的被忽略；`routeToolCall` 也遵守“hostTools 先查、命中即返回、不再查 peer”。需同步在实施时写到 routeToolCall 函数注释里。
- **调用路径**：codexapp/toolbridge 的 SkillHostTools.CallHostTool 不走 host RPC / event bus，直接 host-direct 同进程调用 `skill.Service.ExpandBody` / `ReadResource`；它只是跳过对应 DTO / 事件往返，仍会保留 tool-call JSON decode 与 tool result marshal，错误原样包装后返回给调用方。

### 4.2 claudecli 路径：独立二进制 / 复用 mcp-lsp / same-binary stdio MCP 子进程？

三个子选项，三选一：

- **B1：新增独立 mcp-skill 二进制** —— 复刻 mcp-orch 模板（cmd/mcp-skill/main.go），通过 bootstrap 与宿主交互。代价：新二进制 + 部署 + 反向 IPC 桥（mcp-skill → 宿主 skill RPC）。
- **B2：复用 mcp-lsp 进程暴露 skill 工具** —— mcp-lsp 已经存在且与宿主有 IPC，添加 skill 工具组到它的 registry。代价：mcp-lsp 责任边界扩张（lsp = 代码索引／skill = 宿主业务），不符合 P20.11 废弃文档“职责单一”原则。
- **B3：通过 mcp-config 注册 same-binary stdio MCP server 子进程** —— 与 mcp-orch / mcp-lsp 平级；Claude CLI 根据 `--mcp-config` 的 command/args spawn/own stdio child，Go provider 只生成 config/env/args 并清理临时文件。代价：进程数 +1，但无需新增独立二进制。

**推荐 B3**（审查反转后的结论）：

| 维度 | B1 | B3 |
|---|---|---|
| 代码量 | 新二进制 ~400 行 + cmd/ + fx + bootstrap | 主体在 `internal/provider/claudecli/`；另需 dto/provider manifest 标记、manifestbuilder 生成项、宿主二进制 child-mode 入口与 `pkg/skilltool` 共用 schema；无新增独立二进制 |
| Bootstrap / host RPC | 必须新增 bootstrap 反向 IPC（mcp-skill «» 宿主） | same-binary 子进程内置轻量 host RPC client 回调宿主 `skill.Service`，但不需要 bootstrap 协议全栈 |
| 跨 provider 一致性 | 与 codexapp 的 host-direct 同进程直调模型割裂 | 与 codexapp 概念上一致（都是宿主侧解决） |
| P20.11 废弃文档原则 | 满足 | 同样满足 |
| 部署 | 新增二进制 + 升级流程 | 无新二进制 |

B3 实际在进程边界上仍 spawn 一个 same-binary stdio 子进程，但 lifecycle owner 是 Claude CLI 的 `--mcp-config` stdio runner；Go provider 负责生成 mcp-config 与 host RPC client env/args，不持有 `exec.Cmd` 句柄。child 需通过 host RPC 回调宿主 `skill.Service`，只是不需要 B1 那套 bootstrap 协议全栈。B1 作为备选，如果未来某天需要 skill 服务在宿主之外独立运行（如跨机器部署），可从 B3 升级。B2 不推荐，与 mcp-lsp 现有职责不同质。

**B3 进程模型明确（审查反馈补充）**：

- **子进程 = 同二进制不同入口**。推荐复用宿主二进制（如 `agent-terminal`）加一个进程参数或子命令（如 `agent-terminal --mcp-skill-mode`），避免部署时多一个二进制。`cmd/agent-terminal` 必须在启动最早期解析该 flag，命中后进入 stdio MCP child runtime 并 return，**不得进入 `app.RunDesktop` / 完整 Fx / Wails app**。子进程启动后与宿主主进程靠上下文 RPC（复用现有 host RPC `skills/expandBody` / `skills/readResource`）交互，并监听 stdin EOF 自退出。
- **不选进程内 goroutine**：虽然资源占用更低，但 Claude CLI 的 `--mcp-config` 接受的是 stdio 子进程配置（`command: <path>` + `args: [...]`），不接受进程内 pipe。要走进程内 goroutine 需额外实现 stdin/stdout pipe 桥接，复杂度与子进程方案相近。
- **manifestServers 识别 same-binary stdio skill server 标记**：固定 DTO 合约为 `MCPLaunchKind`（JSON 字段建议 `launch_kind`）与常量 `LaunchKindSameBinarySkill = "same-binary-skill"`；`manifestbuilder` 生成 `Name:"skill"` + 该 launch kind 的 server 项；claudecli 侧 `manifestServers()` 识别后填 `command = <当前二进制路径>`、`args = ["--mcp-skill-mode"]`。

**B3 启动 / 延迟边界（必须写成测试）**：

- MCP `initialize` / `tools/list` 只能返回静态工具 schema：`skill_expand_body` / `skill_read_resource`。启动期不得扫描 skill roots、不得读取任何 `SKILL.md`、不得调用 `skills/expandBody` / `skills/readResource`、不得触发 approval / audit / candidateStore / `skill.Service`，也不得阻塞父进程 RPC。
- host RPC client 必须 lazy 使用：child 启动和 `tools/list` 阶段不连接 / 不探活父进程；第一次 `tools/call` 才按需调用父进程。普通首轮对话若模型没有调用 skill 工具，不得发生 expand/read RPC。
- 首轮延迟必须有 smoke / 指标约束：`--mcp-skill-mode` 进入 MCP runtime、Claude 侧 MCP initialize、`tools/list` 三段耗时需可观测；任一实现不得把全量 app/Fx/Wails、skill scan、approval 等重活放到启动路径。
- 该边界是 claudecli 与 codexapp 的实现差异：codexapp 用 `DynamicTools + parent host-direct`，claudecli 用 `--mcp-config + same-binary stdio child + host RPC`；两者只共享模型可见工具名、schema、结构化结果、approval/cwd 注入语义。

### 4.3 命名映射

- codexapp/toolbridge host-direct handler 中，工具 schema 使用 `name = "skill_expand_body"`，handler 同进程直调 `skill.Service.ExpandBody`（不发 host RPC、不经事件总线，避免对应 DTO / event-bus 往返；仍会 decode tool-call JSON 并 marshal tool result）。
- claudecli/B3 handler 不适用 codexapp 同进程直调路径；stdio 子进程必须只持有 host RPC client：模型 ⇄ Claude CLI ⇄ stdio MCP server 子进程 ⇄ host RPC `skills/expandBody` / `skills/readResource` ⇄ 宿主 `skill.Service`。
- 模型可见 `inputSchema` 仅包含 `name / anchor / max_bytes / path`；`cwd` 只存在于 runtime-internal params，由 toolbridge / claudecli skill_mcp_server 根据当前 thread context 注入，不能让模型填写。B3 child 端必须 decode 到 allowlist 参数或在 RPC 前强制 `params.CWD = runtimeCWD`，忽略模型 JSON 中伪造的 `cwd`。

## 8. 影响 / 风险 / 后置

- **解锁**：本任务完成后，codexapp 普通路径已有 Mode=Summary 的代码级能力，claudecli 也已有 same-binary skill MCP child 最小链路、内存 stdio smoke、真实 agent-terminal 二进制 framed smoke、Claude-like parent lifecycle 与真实二进制 latency budget 与 child outcome counters；harness 级端到端能力仍依赖真实 Claude/Codex 模型视角 E2E、host-direct 放量 metrics 与告警。
- **不破坏既有**：本任务不改 skill 服务层 / RPC 注册；codexapp 改 provider render 默认，claudecli 通过 `SkillMode.Effective()` 保持 Full/eager。
- **风险**：路 B1 需要新增二进制和部署流程；路 B3 需要 claudecli 端管理一个子进程 lifecycle，并会给首轮增加 MCP child spawn / initialize / tools-list 握手成本。Phase 2 必须用静态 `tools/list`、lazy host RPC、启动耗时 smoke / 指标把该成本锁在可接受范围；MCP smoke 放入 Phase 2 验收即可。
- **后置依赖**：解锁后，`docs/plans/迁移/p20.1-skill-progressive-disclosure-hardening.md` 中描述的 Summary 模式才能从"codexapp 代码级能力"继续推进到"harness 业务能力"。在 Phase 2/3 red gates 未完成前，不得删除 override 或把 provider default policy 推到全局 Summary。

## 10. 决策反转日志（B1 → B3）

初稿推荐 B1（新二进制 mcp-skill），理由是“贴合 P20.11 废弃文档拆出专属 server 的方向”。审查反馈后改推 B3，主要原因：

- **代码量：**B1 要复刻 mcp-orch 的 cmd/ 骨架 + fx + bootstrap 反向 IPC，实际代码量 ~400 行；B3 主体在 `internal/provider/claudecli/`，但还需要 dto/provider manifest 标记、manifestbuilder 生成项、same-binary child-mode 入口与测试，预计 ~600 行 ±150。
- **bootstrap 反向 IPC 代价：**B1 需 mcp-skill 进程反向调宿主 skill RPC，走 bootstrap.Client；B3 固定为 same-binary stdio MCP 子进程，因此必须内置 host RPC client，复用现有 host RPC 入口 (`skills/expandBody`)，不引入 bootstrap 协议全栈。
- **跨 provider 一致性：**codexapp 走 toolbridge host-direct 同进程直调，是宿主侧解决；B1 让 claudecli 变成 spawn-child + bootstrap 模型，与 codexapp 架构割裂，上下文说明成本高。选 B3 后两个 provider 在“宿主侧解决”这个维度上一致。
- **部署路径：**B1 需发布多一个二进制、起升级流程、使用方要多装一个包；B3 随宿主一起发。
- **未来升级路径：**如果未来某天需要 skill 服务运行在宿主进程之外（跨机器部署，或多实例共享），B3 可升级为 B1——代码形态上两者是连续迁移不是重写。

本节保留是为了让未来接手者看到“为什么选 B3”而不是判 plan 是错的。

## 11. 阶段 1.5：codexapp Mode override（Phase 1 后补上的临时折中）

### 11.1 背景

Phase 1 完成后，toolbridge 有了 host-direct 分支 + skill_expand_body / skill_read_resource 两个工具，理论上可走 progressive-disclosure。最初风险是：若上游默认把 skill 全部物化成 Full，system prompt 仍会 eager 注入完整 SKILL.md body，模型不会主动调工具。

本轮代码层已收敛普通 selected skill / name-only hydrate / cron skill 的默认物化点：这些路径保留 `Mode=Unspecified` 作为 provider-aware default marker。阶段 1.5 是 codexapp 的折中方案：只在 codexapp provider 入口映射时把该 marker 转换为 Summary；显式 Full / Summary / None 一律保留。

这让 codexapp 普通路径具备代码级 progressive-disclosure 能力，但仍不是 harness 级业务交付：claudecli Phase 2 same-binary skill MCP child 已有最小实现并暴露 `skill_expand_body` / `skill_read_resource`，但真实 Claude CLI E2E、stdio lifecycle 与 provider default policy 尚未闭环；Phase 3 前仍通过 `SkillMode.Effective()` 把 Unspecified 解释为 Full/eager 兼容。

### 11.2 实施文件清单（已落地）

- `internal/provider/codexapp/skill_mode_override.go`：`overrideSkillsToSummary([]dto.SkillRef) []dto.SkillRef` 辅助函数。仅 `Mode=Unspecified` 转换为 Summary；显式 Full / Summary / None 保留。不修改入参。
- `internal/provider/codexapp/session_turn.go`：`buildTurnStartParams` 和 `buildTurnSteerParams` 入口调 `overrideSkillsToSummary(req.Skills)` 后再传给 `turnInputsFromRequest`。注释写明 “P20.18 Phase 1.5 临时”。
- `internal/provider/codexapp/skill_mode_override_test.go`：8 个测试覆盖 Unspecified→Summary / 保留显式 Full / 保留 None / 幂等 / 不修改入参 / 空输入 / 集成到 buildTurnStartParams / `PrepareTurn→skill.Service hydrate→buildTurnStartParams` 普通路径。

### 11.3 预期删除时机

本函数 + 所有引用只有在以下条件全部满足后才能删除：

- provider-aware default policy 已有正式落点，codexapp 新入口无法绕过该 policy；
- Phase 2 (claudecli stdio MCP server) 最小实现 + 真实 smoke / lifecycle 验证完成，或 claudecli 保持 Full/eager 的兼容策略被明确写入 policy；
- 模型视角 E2E 通过：真实 DynamicTools 包含 skill tools，模型发 `skill_expand_body`，结果回到模型并可继续推理；
- host-direct observability / approval-or-error 结构化策略已闭环，默认放量可观测。

删除检查清单：

```bash
grep -R -n 'overrideSkillsToSummary' internal/provider/codexapp internal/module
grep -R -n 'Phase 1.5' internal/provider/codexapp/
```

期望：第一条零命中；第二条只剩迁移说明或零命中。

### 11.4 不选“加 env feature flag”的理由

考虑过 `SKILL_INJECT_MODE=progressive` flag：但只要 flag 开启，claudecli 路径仍会退化。flag 不能区分 provider。能区分的只有代码里叫不叫 override 函数。所以倒不如直接在 codexapp 包里加一个函数调用，语义明确、代码跟踪成本低。

## 12. owner / 触发条件

> 审查反馈强调：本文档如不带 owner / 明确触发条件，极易变成“永久 backlog”，导致 progressive-disclosure 架构上完成 90% 但用户感知 0% 的烂尾。

- **触发条件**：以下任一出现即应启动

  - skill 数量 / token 占用超过 system prompt 预算（实测 token 压力驱动）
