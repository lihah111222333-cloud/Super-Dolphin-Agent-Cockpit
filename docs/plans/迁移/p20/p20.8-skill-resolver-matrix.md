## 4. 决策矩阵（4×3，覆盖 12/12）
> 列定义：`Explicit` = 用户显式勾选 / 输入内显式选择；`Auto` = 运行时 matcher 输出；`Force-carry` = `expanded_state` 在 TTL 内对“同名同 hash”skill 的抑制 / 续留状态。为保证 12/12 覆盖，显式优先导致的“合并后退化为 explicit winner”也显式写出。

| 决策信号 \ 输入来源 | Explicit | Auto | Force-carry |
|---|---|---|---|
| Manual | `Full / manual`；不受 top-k / TTL 影响 | 合并后仍 `Full / manual`（显式赢） | 仍 `Full / manual`（显式赢，忽略 carry） |
| Force | 若同名同时显式，结论仍 `Full / manual` | `Full / force`；`top-k=5` | 同名同 hash 且 TTL 内 => `None`（不重复注入）；TTL 过期或 hash 变更后回到 Auto-Force |
| Trigger | 若同名同时显式，结论仍 `Full / manual` | `Summary / trigger`；`top-k=3` | 同名同 hash 且 TTL 内 => `None`；TTL 过期后回到 Auto-Trigger |
| Miss | 显式仍保留 `Full / manual` | `None`（只留 L1 可见，不进 turn） | `None` |

补充规则：
1. 去重键：`strings.ToLower(name)+"@"+version`；`version==""` 时退化到 name-only，保证旧 payload 仍能工作。
2. Mode 优先级：`Full > Summary > None`。
3. Source 优先级：`manual > force > trigger > unspecified`。
4. `SkillSourceExpand` 不由 resolver 直接产出；它属于 `skill_expand` 二次注入路径。
5. auto 排序：先 `force` 再 `trigger`，同层按 `matched_terms` 数量、最近 5 turn 未抑制优先、最后字典序稳定化。

## 5. `expanded_state.go` 数据结构与持久化结论
> 锁定语义：**per-thread 内存态**、**不持久化**、**TTL=5 turns**、去重 key=`strings.ToLower(name)+"@"+version`，有 `ContentHash` 时优先用 hash 判变更。

推荐数据结构（逻辑名，可落在 `internal/module/turn/expanded_state.go`）：

```go
type expandedStateStore struct {
    mu       sync.Mutex
    byThread map[string]*expandedThreadState
}

type expandedThreadState struct {
    TurnSeq uint64
    Entries map[string]expandedEntry // key = lower(name) + "@" + version
}

type expandedEntry struct {
    Version          string
    ContentHash      string
    LastExpandedTurn uint64
}
```

结论：
- **默认内存态，不持久化**：这是 5 turn 的去重优化，不是正确性边界；进程重启后最多多注一次，不会破坏协议。
- **不写 thread/history store**：否则会把 `turn` 模块拉向 thread/history 持久层，增加耦合且收益很低。
- **hash 优先于 version**：有 `ContentHash` 时用 hash 判定正文是否变化；没有时退化用 `Version`。
- **清理策略**：按 thread 维度懒删除；线程关闭时清空；必要时加固定上限（如 256 threads）防止常驻 map 增长。
