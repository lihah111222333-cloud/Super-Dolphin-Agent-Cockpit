# P8.5 执行计划 — MCP 生命周期控制面重写

> 生成时间：2026-03-22
> 前提：`cmd/mcp-*` 已经被明确为独立 binary，但核心层与各 binary 之间还缺统一的 lifecycle/control plane。
> 目标：一次性落地 v1 基线 9 个 `ctl/*` 方法 + v2 hook 扩展 5 个 `ctl/hook/*` 方法，并同步修订契约、包布局、lease 语义、bootstrap 流程、容错矩阵和验收标准。

---

## §0 目标

- 一次性实现基线 9 个生命周期方法 + hook 扩展 5 个方法，不再拆 Phase 1 / Phase 2。
- 生命周期协议统一从 `mcp/*` 改为 `ctl/*`，避免与 MCP 标准协议混淆。
- 明确双通道模型：
  - 工具执行通道：`stdio`，自包含闭环，只负责 MCP tool call。
  - 生命周期管理通道：`jrpc2` over TCP，只负责注册、lease、心跳、上下文、遥测、审批、hook 回调、hook resolve、配置推送、退出。
- 目标规模调整为 20-30 个活跃实例。
- 工具侧容错固定为 `live RPC > boot snapshot`；核心侧容错固定为 `live registry > internal DB rebuild`。
- 核心层只暴露 `ctl/*` RPC 接口；MCP binary 的启动方式、启动数量、执行位置与进程生命周期都由外部执行器决定，不属于核心职责。

当前基础与缺口：

- `internal/platform/rpc/server.go` 已有 TCP `jrpc2` server、active 连接集合和 `AllowPush`。
- `internal/platform/rpc/push.go` 已有单连接 `NotifyClient` / `CallbackClient`。
- `internal/platform/rpc/approval.go` 已有 `ApprovalManager`、pending snapshot、恢复和清理逻辑。
- `internal/contract/orchestration.go` 已暴露 `UpdateRuntime`、`SetReport`、`HandleReportEvent`、`RememberReportRequest` 等能力。
- `internal/dto/provider/manifest.go` 当前只注入有限 `GO_AGENT_MCP_*` env。
- `internal/mcpserver/common/server.go` 仍是骨架，尚未形成 “stdio serve + rpc bootstrap + reconnect + coordinated shutdown”。

范围边界：

- 不重写 `cmd/mcp-orch` 的业务工具定义。
- 不引入第二套 RPC 框架，继续使用 `jrpc2`。
- 不把 `ctl/context` 扩成万能 RPC 代理。
- 不引入通用操作级 cancel；只使用 deadline 和 `ctl/shutdown`。
- deprecation 目标是旧 lifecycle `mcp/*`，不是既有核心 UI RPC `agent.*` / `orchestration.*`。

## §1 通用协议（v1 基线 9 个方法 + v2 hook 扩展 5 个方法）

设计约束：

- 生命周期协议分两层：v1 基线 9 个方法 + v2 hook 扩展 5 个方法。
- 基线 9 个方法保持稳定，不按 tool family 分裂方法族。
- hook 扩展只在协商到 `ctl.hook` 能力后启用。
- family 差异只进入 `client_kind`、`capabilities`、`subscriptions`、`scope` 和 payload。
- `ctl/register` 之后的请求一律携带 `LeaseKey{instance_id, generation}`。
- `generation` 改为 server-issued lease generation。
- `ctl/event` 只做遥测 / 审计 fire-and-forget。
- `ctl/report` 只做 durable state migration，删除 `report_type=event`。

标准错误集合：

| 名称 | 代码 | 含义 |
| --- | ---: | --- |
| `INVALID_PARAMS` | `-32602` | DTO 字段缺失、类型不符、scope / report variant 不合法 |
| `ERR_LEASE_NOT_FOUND` | `4101` | lease 不存在 |
| `ERR_LEASE_STALE` | `4102` | generation 过旧 |
| `ERR_CAPABILITY_MISMATCH` | `4103` | required capability 不满足，或发送了未协商能力 |
| `ERR_SCOPE_NOT_ALLOWED` | `4104` | `ctl/context` 请求了白名单外 scope / key |
| `ERR_APPROVAL_UNAVAILABLE` | `4105` | 没有可用 UI peer 或审批系统不可达 |
| `ERR_PERSIST_FAILED` | `4106` | durable report 持久化失败 |
| `ERR_PEER_UNAVAILABLE` | `4107` | 找不到匹配 peer 或 peer 已断开 |
| `ERR_AUTH_FAILED` | `4108` | `session_token` / bootstrap session 校验失败 |
| `ERR_BUSY` | `4109` | 对端忙、限流、扇出队列满 |
| `ERR_TIMEOUT` | `4110` | 单 peer 发送超时或审批等待超时 |
| `ERR_HOOK_CALL_NOT_FOUND` | `4111` | `hook_call_id` 不存在、已完成或不属于当前 lease / subscriber |
| `ERR_HOOK_CALL_EXPIRED` | `4112` | pending hook review 已过 TTL，默认决策已生效 |
| `ERR_HOOK_NOT_SUBSCRIBED` | `4113` | 当前 peer 未订阅对应 hook topic 或无权处理该回调 |
| `ERR_HOOK_RESOLVE_CONFLICT` | `4114` | 同一 `hook_call_id` 收到互相冲突的 resolve 结果 |

### 1.1 MCP → 核心

上行方法矩阵：

| 方法 | 类型 | 请求 / 关键字段 | 响应 | 幂等键 | 重试 | degrade | 错误 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ctl/register` | request | `instance_id`, `binary_name`, `agent_id`, `thread_id`, `client_kind`, `peer_kind`, `pid`, `session_token`, `boot_id`, `capabilities_offered`, `capabilities_required`, `subscriptions`, `resume_from_generation?` | `instance_id`, `accepted_generation`, `peer_kind=tool`, `capabilities_negotiated`, `heartbeat_interval_ms`, `heartbeat_timeout_ms`, `send_timeout_ms`, `sweeper_interval_ms`, `config_version` | `instance_id + boot_id + client_kind` | 可重试；同幂等键超时重发 | 无本地替代；注册失败时只保留 `stdio` 工具执行面 | `INVALID_PARAMS`, `ERR_AUTH_FAILED`, `ERR_CAPABILITY_MISMATCH`, `ERR_BUSY` |
| `ctl/hook/subscribe` | request | `instance_id`, `generation`, `subscription_id`, `topics`, `scope`, `filters`, `mode` | `accepted`, `subscription_version`, `effective_topics`, `effective_scope` | `LeaseKey + subscription_id + request_hash(topics,scope,filters,mode)` | 可重试；相同 `subscription_id` 视为 upsert | 无本地替代；订阅失败则该 peer 不参与 hook fanout | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_CAPABILITY_MISMATCH`, `ERR_BUSY` |
| `ctl/heartbeat` | request | `instance_id`, `generation`, `heartbeat_seq`, `status`, `metrics`, `observed_config_version` | `ok`, `server_time`, `config_version`, `next_heartbeat_ms` | `LeaseKey + heartbeat_seq` | 可重试；连续 3 次失败触发重连 | 降级为 boot snapshot 只读，不再发送 durable report | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_BUSY`, `ERR_TIMEOUT` |
| `ctl/context` | request | `instance_id`, `generation`, `scope`, `keys` | `source`, `observed_at`, `scope`, `payload` | `LeaseKey + scope + request_hash(keys)` | 可重试 1 次 | 只允许对白名单 scope 回退 boot snapshot，且必须标记 `source=boot_snapshot` | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_SCOPE_NOT_ALLOWED`, `ERR_CAPABILITY_MISMATCH`, `ERR_TIMEOUT` |
| `ctl/event` | notify | `instance_id`, `generation`, `event_id`, `event_type`, `audit_class`, `payload` | 无 | `LeaseKey + event_id` | 默认不自动重试；仅 replayable 事件可本地缓冲后重发 | 失败时写本地 slog / stderr，不做 durable replay | 本地仅做 `INVALID_PARAMS` 校验；核心只记投递统计 |
| `ctl/log` | notify | `instance_id`, `generation`, `seq`, `level`, `message`, `fields`, `ts` | 无 | `LeaseKey + seq` | 默认不重试 | 失败时保留本地 stderr，不阻塞主路径 | 本地仅做 `INVALID_PARAMS` 校验；核心只记投递统计 |
| `ctl/approval/request` | request | `instance_id`, `generation`, `call_id`, `tool_name`, `kind`, `reason`, `payload`, `timeout_ms` | `approved`, `reason`, `detail`, `decision_source` | `LeaseKey + call_id` | 可重试；同 `call_id` 必须返回同一 pending / decision 语义 | 无 live RPC 且无静态 allowlist 时 fail closed | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_APPROVAL_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY` |
| `ctl/report` | request | `instance_id`, `generation`, `report_id`, `report` | `accepted`, `persisted_at`, `canonical_status`, `applied_variant` | `LeaseKey + report_id` | 可重试；服务端必须按 `report_id` 去重 | 进入有界内存重发队列，重连后补发 | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_CAPABILITY_MISMATCH`, `ERR_PERSIST_FAILED`, `ERR_TIMEOUT` |
| `ctl/hook/resolve` | request | `instance_id`, `generation`, `hook_call_id`, `decision`, `reason`, `idempotency_key` | `accepted`, `resolved_at`, `canonical_decision`, `pending_state` | `LeaseKey + hook_call_id + idempotency_key` | 可重试；同幂等键必须返回同一决策结果 | 无 live RPC 时保持 pending；TTL 到期默认 `reject` | `INVALID_PARAMS`, `ERR_LEASE_NOT_FOUND`, `ERR_LEASE_STALE`, `ERR_HOOK_CALL_NOT_FOUND`, `ERR_HOOK_CALL_EXPIRED`, `ERR_HOOK_RESOLVE_CONFLICT`, `ERR_TIMEOUT` |

`ctl/context.scope` 固定白名单：

- `agent.runtime`
- `thread.binding`
- `workspace.run`
- `config.snapshot`

`ctl/report.report` 使用判别联合：

```json
{ "type": "runtime", "runtime": { "port": 1234, "provider": "codex" } }
{ "type": "completion", "completion": { "status": "succeeded", "report": "done", "metadata": {} } }
```

预留但默认不启用的 variant：

- `progress`
- `diagnostic`

补充约束：

- `ctl/register` 不接受裸 `instance_id` 覆盖当前活跃实例。
- `ctl/heartbeat`、`ctl/context`、`ctl/approval/request`、`ctl/report` 都必须按 `LeaseKey` 查活体。
- `ctl/event` 不持久化状态，不得承载完成态、进度态、诊断态。
- `ctl/report` 不再接受 `event` variant。
- `ctl/log` 与 `ctl/event` 不合并：`ctl/log` 有 `level` / `seq` 语义并面向结构化 `slog` 消费者；`ctl/event` 有 `audit_class` 语义并面向审计消费者，消费路径不同。
- hooks 不扩展 `ctl/context` 的请求形状；turn / wakeup 恢复仍由本地 store 或 hook payload 处理。
- watcher-managed / wakeup dispatch 场景里，MCP 工具只能通过 hook 返回里的 `mutations.dispatch_intent` 表达 dispatch 意图；实际启动 turn 的 owner 仍然是核心层。

### 1.2 核心 → MCP

下行方法矩阵：

| 方法 | 类型 | 推送 / 关键字段 | 响应 | 幂等键 | 重试 | degrade | 错误 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ctl/shutdown` | callback 优先，notify 兜底 | `instance_id`, `generation`, `shutdown_id`, `reason`, `deadline_ms`, `final_report_expected` | `acknowledged`, `final_report_deadline_ms` | `LeaseKey + shutdown_id` | callback 失败可降级为 notify 1 次 | 若对端不支持 callback，则记录 `callback_unsupported` 后走 notify + process kill | `ERR_PEER_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY` |
| `ctl/config/changed` | notify | `selector`, `scope`, `config_version`, `payload` | 无 | `config_version + selector_hash + scope` | notify best-effort；单 peer 失败不回滚其他 peer | 不做历史重放；peer 通过后续 `ctl/context(config.snapshot)` 追平 | `ERR_PEER_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY` |
| `ctl/hook/before` | callback | `hook_call_id`, `topic`, `agent_id`, `thread_id`, `turn_id`, `session_context`, `task_context`, `tool_context`, `payload`, `deadline_ms` | `decision`, `reason`, `patch|mutations|dispatch_intent`, `allowed_tools`, `denied_tools`, `mode`, `retry_after_ms` | `hook_call_id + subscriber_lease` | 默认不自动跨 peer 重试；超时交给核心按 topic 默认策略处理 | `Before` 默认 fail-closed；工具列表先粗筛，再由 `agent.tool.before` 细筛 | `ERR_PEER_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY`, `ERR_HOOK_NOT_SUBSCRIBED` |
| `ctl/hook/check` | callback | `hook_call_id`, `topic`, `agent_id`, `thread_id`, `turn_id`, `state_snapshot`, `progress_snapshot`, `completed_tasks`, `tool_calls`, `artifacts`, `payload`, `deadline_ms` | `decision`, `reason`, `severity` | `hook_call_id + subscriber_lease` | 默认不自动跨 peer 重试 | 超时默认 `continue`，不阻塞 agent 主路径 | `ERR_PEER_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY`, `ERR_HOOK_NOT_SUBSCRIBED` |
| `ctl/hook/after` | callback | `hook_call_id`, `topic`, `agent_id`, `thread_id`, `turn_id`, `state_snapshot`, `artifacts`, `payload`, `deadline_ms` | `decision`, `reason`, `patch|mutations|dispatch_intent` | `hook_call_id + subscriber_lease` | 默认不自动跨 peer 重试 | 默认 fail-closed；若返回 `escalate`，核心写入 durable `pending_hook_review`，等待 `ctl/hook/resolve` | `ERR_PEER_UNAVAILABLE`, `ERR_TIMEOUT`, `ERR_BUSY`, `ERR_HOOK_NOT_SUBSCRIBED` |

selector 语义固定为：

`intersection(subscription, capability, scope)`

展开维度：

- `subscription`
- `capability`
- `scope.agent_id`
- `scope.thread_id`
- `scope.client_kind`
- `scope.instance_id`

解释规则：

- 每个维度都是交集，不是并集。
- 维度缺省表示 “在其它维度筛中的集合上不过滤”，不是 “无边界广播”。
- `ctl/shutdown` 不走 selector，只走单 lease 定向。

发送策略：

- 先复制目标 lease 列表，再做网络 I/O。
- `fanout_parallelism = 8`。
- `per_peer_send_timeout_ms = 2000`。
- 单 peer 连续 3 次发送失败会触发断连和 lease 清理。

取消语义：

- P8.5 不支持通用 `$/cancelRequest` 或操作级 cancel。
- 所有 request 依赖调用方 deadline。
- 只有 `ctl/shutdown` 可以作为显式中止信号。

`ctl/shutdown` 在 callback 成功时返回：

```text
ShutdownResponse {
    acknowledged: bool
    final_report_deadline_ms: int  // 工具有多少时间补发最终 report
}
```

### 1.3 版本协商与命名

命名约束：

- lifecycle 方法统一使用 `ctl/*`。
- `mcp/*` 只作为迁移期兼容别名，不再出现在新 DTO、接口和 handler 名里。
- env 主命名统一为 `GO_AGENT_CTL_*`。

能力协商取代精确版本命中：

- 客户端发送 `capabilities_offered` 与 `capabilities_required`。
- 服务端返回 `capabilities_negotiated` 与 `capabilities_rejected`。
- 只有 `required` 无法满足时才拒绝注册。
- 精确版本字符串仅用于日志、调试、指标。

建议 capability 命名：

- 工具侧：`tool.orch`、`tool.lsp`、`tool.ida`
- 生命周期侧：`ctl.context`、`ctl.event`、`ctl.log`、`ctl.approval`、`ctl.report.runtime`、`ctl.report.completion`、`ctl.report.progress`、`ctl.report.diagnostic`、`ctl.shutdown.callback`、`ctl.hook`

`client_kind` 与 `peer_kind` 必须分开：

- `client_kind`：工具类型，例如 `orch`、`lsp`、`ida`、`custom`
- `peer_kind`：连接类型，只允许 `ui` 或 `tool`

旧协议 deprecation 时间表：

| 日期 | 动作 |
| --- | --- |
| `2026-03-22` | 文档冻结，所有新代码只写 `ctl/*` |
| `2026-04-15` | 核心增加 `mcp/* -> ctl/*` alias，并对 alias 调用打 deprecation log |
| `2026-05-31` | `cmd/mcp-orch`、`cmd/mcp-lsp`、`cmd/mcp-ida` 全部切到 `ctl/*` 与 `GO_AGENT_CTL_*` |
| `2026-06-30` | 删除 `mcp/*` alias；旧 env 仅保留只读兼容 |

### 1.4 Hook 扩展分层

v1 基线 9 个方法：

- `ctl/register`
- `ctl/heartbeat`
- `ctl/context`
- `ctl/event`
- `ctl/log`
- `ctl/approval/request`
- `ctl/report`
- `ctl/shutdown`
- `ctl/config/changed`

v2 hook 扩展 5 个方法：

- `ctl/hook/subscribe`
- `ctl/hook/before`
- `ctl/hook/check`
- `ctl/hook/after`
- `ctl/hook/resolve`

协商规则固定为：

- 未协商到 `ctl.hook` 时，只有基线 9 个方法可用
- 协商到 `ctl.hook` 后，扩展 5 个方法一并启用
- 当前协议启用 hooks 时，`ctl/*` 方法总数为 14

### 1.5 Turn 事件入口与 SubmitTurn owner

turn 相关事件进入 MCP 的唯一路径必须写死为核心层主动发起的 hook callback：

- turn 开始前 -> `ctl/hook/before(topic=agent.turn.before)`
- turn 运行中 -> `ctl/hook/check(topic=agent.turn.progress|agent.state.change)`
- turn 完成 / 失败 / 进程退出 -> `ctl/hook/after(topic=agent.turn.after|agent.turn.failed|agent.process.exit)`

固定边界：

- `stdio` tool call 不是 turn 事件入口
- MCP binary 不能主动调用 `SubmitTurn`
- 若 hook 消费方希望触发下一次 turn，只能在 hook 返回的 `mutations.dispatch_intent` 中表达意图
- 核心层验证并持久化 `dispatch_intent` 后，才调用内部 `OrchestrationService.SubmitTurn`
- `ctl/report` 不承载 dispatch 命令

`dispatch_intent` 最小字段：

- `target_agent_id`
- `thread_id`
- `wakeup_id`
- `submission` 或 `prompt_payload`
- `idempotency_key`

### 1.6 DTO 迁移映射

`ctl/register` 的 DTO 不再使用旧的裸 `lease_id` 字符串；server-issued lease 统一抽象为 `LeaseKey{instance_id, generation}`。

```json
// 旧: {"lease_id": "xxx"}
// 新: {"lease": {"instance_id": "xxx", "generation": 123}}
```

补充约束：

- 所有 `ctl/register` 之后的方法统一使用 `LeaseKey` 嵌套对象形式 `{"lease":{"instance_id":"...","generation":N}}`，与代码 `json:"lease"` struct tag 保持一致。
- `RegisterResponse.accepted_generation` 就是 server-issued lease 的 `generation`；客户端据此重建本地 `LeaseKey`。
- `RegisterRequest` 新增字段固定为：

| 字段 | 含义 |
| --- | --- |
| `session_token` | manifest / bootstrap 注入的会话令牌，用于校验连接是否携带当前会话签发的合法 bootstrap 上下文 |
| `boot_id` | 单次进程启动标识，用于 register 幂等和 re-register 判定 |
| `capabilities_offered` | 客户端可提供的 lifecycle 能力集合 |
| `capabilities_required` | 注册必须满足的最小能力集合 |
| `resume_from_generation` | reconnect 时声明自己尝试承接的旧 generation |
| `peer_kind` | 连接类型；`cmd/mcp-*` 固定发送 `tool`，供 server 写入连接元数据 |

## §2 核心层注册表

核心侧新增 package 固定为：

- `internal/platform/mcpcontrol/tool_registry.go`
- `internal/platform/mcpcontrol/tool_callback.go`
- `internal/platform/mcpcontrol/router.go`
- `internal/platform/mcpcontrol/lease.go`
- `internal/platform/mcpcontrol/errors.go`

核心数据模型基线：

```go
type LeaseKey struct {
    InstanceID string
    Generation uint64
}

type PeerKind string // ui | tool

type ToolLease struct {
    LeaseKey
    BinaryName    string
    ClientKind    string
    AgentID       string
    ThreadID      string
    PID           int
    BootID        string
    Capabilities  []string
    Subscriptions []string
    Status        string
    LastHeartbeat time.Time
    PeerID        string
}
```

注册表职责：

- 维护 `leaseKey -> ToolLease`
- 维护 `instance_id -> current LeaseKey`
- 维护 `peer_id -> LeaseKey`
- 维护 `subscription`、`capability`、`agent_id`、`thread_id`、`client_kind` 到 `LeaseKey` 的索引
- 维护 `peer_kind -> set(peer_id)`，供 fanout 和 approval restore 使用

身份模型必须写死三层：

- `LeaseKey{instance_id, generation}` = binary 身份，也是 lifecycle 路由主键
- `agent_id` / `thread_id` / `turn_id` / `wakeup_id` = agent-scoped payload，只在 hook、event、report 等业务载荷里表达逻辑对象
- MCP 进程是共享服务；`agent_id` 只从 tool call 参数传入，不通过 env 或 boot snapshot 绑定

补充约束：

- lease 永远不等于 agent
- bootstrap env / boot snapshot 不得承担 agent 绑定职责
- runtime 路由、stale 校验和 peer 唯一性都必须以 `LeaseKey` 为准

为什么必须从裸 `instance_id` 升级为 `LeaseKey`：

- 同一进程重连时必须拿到新 generation。
- 迟到心跳、迟到 report、迟到 config ack 必须识别为 stale。
- 重注册时必须精确清理旧索引，而不是模糊覆盖。

生命周期固定流程（以下只描述 MCP binary 已被外部拉起后的 register/lease 演进；核心层不负责拉起 binary）：

1. tool binary 启动本地 `stdio` server。
2. bootstrap client 建立 TCP `jrpc2` 连接。
3. `internal/platform/rpc` 接受连接，但此时连接仍未分类。
4. tool 发送 `ctl/register`。
5. `mcpcontrol` 校验 `session_token`、能力协商、client metadata，并签发 `LeaseKey`。
6. 注册表把连接标记为 `peer_kind=tool`，并写入所有 lease 索引。
7. tool 周期性发送 `ctl/heartbeat`。
8. 连接中断或 3 次连续发送失败时，lease 先置 `disconnected`，等待重注册窗口。
9. sweeper 超时仍未重注册时最终 evict。

reconnect / 重注册语义：

- 重连时沿用同一 `instance_id` 和 `boot_id`，并带 `resume_from_generation`。
- 核心总是签发新的 `generation`。
- 旧 `LeaseKey` 立即标记为 `superseded`。
- 来自旧 `LeaseKey` 的心跳、context、approval、report 一律返回 `ERR_LEASE_STALE`。
- 旧连接后来断开时，不得把新 lease 清掉；清理逻辑必须比对 `LeaseKey`。

`peer_kind` 分类规则：

- `peer_kind=tool`：仅在 `ctl/register` 成功后赋值。
- `peer_kind=ui`：走既有 UI RPC 握手链路或连接来源分类。
- pending approval restore 只枚举 `peer_kind=ui` 连接。
- tool peer 只能发起审批请求，不能接收审批恢复 fanout。

心跳与扫尾参数：

- `heartbeat_interval_ms = 10000`
- `heartbeat_jitter_ratio = 0.20`
- `heartbeat_timeout_ms = 30000`
- `send_timeout_ms = 3000`
- `sweeper_interval_ms = 5000`
- `consecutive_send_failures = 3`
- `max_concurrent_dispatches = 8`

核心侧容错矩阵：

| 能力 | live 来源 | durable 来源 | degrade 规则 |
| --- | --- | --- | --- |
| 活体 liveness | registry lease | 无 | 核心重启后不从 DB 伪造 live lease，只等待重新注册 |
| runtime / completion report | 最新 `ctl/report` 结果 | orchestration store | 核心重启后可从 DB 重建 durable 状态，但不恢复 lease |
| config snapshot | 内存配置源 | 可选快照 store | peer 收不到 notify 时，可在后续 `ctl/context(config.snapshot)` 中追平 |
| pending approval | `ApprovalManager` 内存状态 | pending snapshot / 既有恢复逻辑 | 只向 `ui` peer 恢复，不向 `tool` peer 恢复 |

边界划分：

- `internal/platform/rpc` 继续做 transport，不继续接纳 lifecycle 业务文件。
- `cmd/mcp-orch/tools/registry.go` 仍然是进程内工具定义注册表，不是活体 lease 注册表。
- `internal/platform/mcpcontrol/tool_registry.go` 才是核心侧活体实例 owner。

## §3 工具侧 bootstrap client

共享位置固定为：

- `internal/mcpserver/common/bootstrap/client.go`
- `internal/mcpserver/common/bootstrap/reconnect.go`
- `internal/mcpserver/common/bootstrap/heartbeat.go`
- `internal/mcpserver/common/bootstrap/hooks.go`

不放在 `internal/platform/mcpcontrol/client/` 的原因：

- 它是工具侧共享运行库，不应该 import 核心侧 registry / handler 实现。
- 允许依赖只有 `jrpc2`、`internal/dto/mcp/*`、Go stdlib。

bootstrap env 基线：

- `GO_AGENT_CTL_RPC_ADDR`
- `GO_AGENT_CTL_INSTANCE_ID`
- `GO_AGENT_CTL_THREAD_ID`
- `GO_AGENT_CTL_BINARY_NAME`
- `GO_AGENT_CTL_CLIENT_KIND`
- `GO_AGENT_CTL_SESSION_TOKEN`
- `GO_AGENT_CTL_BOOTSTRAP_JSON`

迁移期兼容读取（deprecated）：

- `RPC_ADDR`
- `GO_AGENT_MCP_INSTANCE_ID`
- `GO_AGENT_MCP_THREAD_ID`
- `GO_AGENT_MCP_BINARY_NAME`
- `GO_AGENT_MCP_BOOT_CONTEXT`

`GO_AGENT_CTL_BOOTSTRAP_JSON` 最小字段：

- `instance_id`
- `boot_id`
- `thread_id`
- `cwd`
- `workspace_run_key`
- `config_version`
- `capabilities`
- `launched_at`

对单个 MCP binary 而言，在外部执行器已经拉起进程之后，内部 bootstrap 完整流程如下：

1. binary 先拉起本地 `stdio` MCP server。
2. bootstrap 读取 env，构建 boot snapshot。
3. 生成或恢复 `instance_id` 与 `boot_id`。
4. 建立到 `GO_AGENT_CTL_RPC_ADDR` 的 `jrpc2` 连接。
5. 创建 `jrpc2.Client`，注册 `OnCallback(ctl/shutdown)` 与 `OnNotify(ctl/config/changed)`。
6. 发送 `ctl/register`，保存 negotiated capabilities 和 `LeaseKey`。
7. 启动 heartbeat loop。
8. 运行期暴露 `Context` / `EmitEvent` / `Log` / `RequestApproval` / `Report`。
9. 连接中断后进入 reconnect loop，同时继续保留 `stdio` 执行面。
10. shutdown 时依次停止 heartbeat、补最终 completion report（`status=done`）、关闭 lifecycle client、关闭 `stdio` server。

reconnect 规则：

- 指数退避，上限 30 秒。
- 每次重连都重新发送 `ctl/register`，并带 `resume_from_generation`。
- 只有拿到新 lease 后，才允许恢复 `ctl/report` 重发队列。
- reconnect 成功后，旧 lease 相关缓存全部失效。

退出语义：

- 没有显式的 `ctl/unregister` 方法。
- 正常退出：停止 heartbeat，补最终 completion report，随后断开 lifecycle 连接；server 侧最终通过 sweeper 清理 lease。
- 异常退出：依赖 server 侧 sweeper 在 heartbeat 超时后清理。
- completion report 的 `status=done` 隐含“此 lease 已完成使命”语义，核心不再期待后续 completion 更新，只等待断连或超时回收。

工具侧 degrade 规则：

| 方法 | live RPC 正常 | live RPC 不可用时 |
| --- | --- | --- |
| `Context` | 走 `ctl/context` | 只允许回退 boot snapshot，并标记 `source=boot_snapshot` |
| `EmitEvent` | 走 `ctl/event` | 本地日志兜底，不做 durable replay |
| `Log` | 走 `ctl/log` | 输出本地 stderr / slog |
| `RequestApproval` | 走 `ctl/approval/request` | 若无静态 allowlist，则 fail closed |
| `Report` | 走 `ctl/report` | 进入有界内存重发队列，重连成功后补发 |

队列规则：

- 只缓存 durable 的 `ctl/report`。
- 默认容量 `128`。
- 队列满直接报错，不静默丢弃。
- `ctl/event` / `ctl/log` 不进入 durable 队列。

## §4 与现有基础设施的集成

### 4.1 基于现有 jrpc2 server 扩展，不另起炉灶

复用项：

- `internal/platform/rpc/server.go` 继续作为 lifecycle/control plane 的唯一 TCP `jrpc2` server。
- `prepareServerOptions()` 继续打开 `AllowPush`。
- `internal/platform/rpc/push.go` 继续提供单连接 `NotifyClient` / `CallbackClient`。

需要补的点：

- `rpc.Server` 增加连接元数据：`peer_id`、`peer_kind`、`OnDisconnect`。
- `rpc.Server` 只暴露 transport hook，不直接承载 lifecycle 业务。
- `mcpcontrol` 通过 `handler.Map` 注入 `ctl/*` handlers。

### 4.2 推送从广播改为定向

当前状态：

- `push.go` 已能做单连接 `NotifyClient` / `CallbackClient`。
- `subscribeCoreEventPushes()` 仍走 `server.NotifyAll(...)`。

P8.5 方案：

- 旧 UI 广播路径保留给既有事件桥接。
- 新建 `internal/platform/mcpcontrol/router.go` 作为 lifecycle 下行发送端的唯一 owner。
- tool lifecycle 下行一律走 `mcpcontrol.Router`。
- `selector = intersection(subscription, capability, scope)`，由 router 统一实现。
- `ctl/config/changed` 的发送端在 router 中实现，只发给 `peer_kind=tool` 且满足 selector 的 lease。
- `ctl/shutdown` 的发送端也在 router 中实现，只对单 lease 定向 callback / notify。
- fanout 使用有界 worker pool，`parallelism=8`，`per-peer timeout = 2s`。

### 4.3 approval 机制复用现有 ApprovalManager

复用点：

- `ApprovalManager.RequestApproval`
- `ApprovalManager.RequestUserInput`
- `RestorePending`
- `PendingSnapshot`
- `Cleanup`

P8.5 适配方式：

- `ctl/approval/request` handler 只做 DTO 转换和 lease 校验，然后进入现有 `ApprovalManager`。
- 继续使用 `WithApprovalDeadline`。
- 现有 callback method normalization 保留，避免破坏旧前端链路。
- 在 `rpc.Server` 的连接元数据上标注 `peer_kind`，tool 连接从 `ctl/register` 取得，UI 连接沿用既有握手链路标记。
- `mcpcontrol` 通过 `contract.ApprovalBroker` 接口调用审批能力，不直接 import `rpc` 包实现。
- `RestorePending` 改为只投递给 `peer_kind=ui` 的连接。
- 依赖方向固定为 `mcpcontrol -> contract.ApprovalBroker <- rpc.ApprovalManager`。

### 4.4 report 与 runtime 上报边界重写

P8.5 方案：

- `ctl/event` 成为唯一 telemetry / audit 入口。
- `ctl/report` 成为唯一 durable state migration 入口。
- `report_type=event` 删除，不再允许 “事件走 report”。
- `ctl/report` handler 按 `report_type` 分流：`runtime -> orchestration.UpdateRuntime`，`completion -> orchestration.SetReport`，`progress` / `diagnostic` 仅保留为能力协商后的扩展位。
- `report_id` 作为幂等键；server 维护最近 `N` 个 `report_id` 去重，防止重试写重。

variant 与核心映射：

| `ctl/report` variant | 核心映射 | 备注 |
| --- | --- | --- |
| `runtime` | `UpdateRuntime` | durable，覆盖端口 / provider 等运行时元信息 |
| `completion` | `SetReport`，必要时补 requester 通知 | durable，承载最终状态与文本报告 |
| `progress` | 预留 | 需要协商 `ctl.report.progress` 后再启用 |
| `diagnostic` | 预留 | 需要协商 `ctl.report.diagnostic` 后再启用 |

旧的 `HandleReportEvent`：

- 保留给既有内部调用方或兼容路径。
- 不再作为新的 lifecycle 协议入口。

### 4.5 manifest / provider 侧只做 env 透传

P8.5 需要扩展 `ManifestContext`、`BuildManifest(...)` 和 provider transport config，但职责仍保持最小：

- 注入 `GO_AGENT_CTL_RPC_ADDR`
- 注入 `GO_AGENT_CTL_INSTANCE_ID`
- 注入 `GO_AGENT_CTL_THREAD_ID`
- 注入 `GO_AGENT_CTL_BINARY_NAME`
- 注入 `GO_AGENT_CTL_CLIENT_KIND`
- 注入 `GO_AGENT_CTL_SESSION_TOKEN`
- 注入 `GO_AGENT_CTL_BOOTSTRAP_JSON`

manifest / provider 不负责 register、heartbeat、approval 或 lease 管理，也不负责托管 MCP binary 生命周期；它们只负责把统一 `GO_AGENT_CTL_*` bootstrap env 和启动描述透传给 Claude CLI 等外部执行器。MCP 进程是共享服务，`agent_id` 必须从 tool call 参数传入，而不是在 bootstrap 阶段绑定固定 agent。旧 `GO_AGENT_MCP_*` 仅由 bootstrap client 兼容读取，文档视为 deprecated。

## §5 设计原则

- 双通道优先：`stdio` 只做工具执行，`jrpc2` TCP 只做 lifecycle 控制。
- 一次性交付：全部基线 9 个方法 + hook 扩展 5 个方法同一轮落地。
- LeaseKey 优先：所有活体身份以 `LeaseKey{instance_id, generation}` 为准。
- 能力协商优先：accept/reject 依据 capabilities，不做精确版本命中。
- `ctl/context` 收窄：只允许 `agent.runtime`、`thread.binding`、`workspace.run`、`config.snapshot`。
- event / report 分离：遥测不持久化，durable 状态不走 fire-and-forget。
- selector 严格交集：`intersection(subscription, capability, scope)`。
- peer 分类强制：所有连接必须区分 `ui` / `tool`。
- approval fail closed：无 UI peer 且无静态 allowlist 时，不擅自放行。
- bootstrap 零核心依赖：共享 client 不依赖核心 registry / handler 实现。

## §9 成功标准

成功标准拆两层：

第一层，核心闭环：

- 任选 1 个 binary，例如 `cmd/mcp-orch`，完成完整闭环验收。
- `stdio` 执行面正常服务
- bootstrap 成功 `ctl/register`
- heartbeat 正常保活
- `ctl/context` 能返回 live 与 boot fallback 两种 source
- `ctl/approval/request` 能复用现有审批链路
- `ctl/event` / `ctl/log` 能进入统一审计 / 日志面
- `ctl/report(runtime|completion)` 能 durable 持久化
- `ctl/config/changed` 能按 selector 定向发送
- `ctl/shutdown` 能优雅退出并提交最终 report
- `ctl/hook/subscribe` 能注册 hook topic、scope 和过滤条件
- `ctl/hook/before` / `ctl/hook/check` / `ctl/hook/after` 能按 topic 定向回调，并遵守默认 timeout / degrade 语义
- `ctl/hook/after(escalate)` 能生成 durable `pending_hook_review`，随后由 `ctl/hook/resolve` 异步收敛为 `approve` / `reject`
- disconnect 后能 re-register 并拿到新 lease

第二层，多 binary adopter：

- `cmd/mcp-orch`、`cmd/mcp-lsp`、`cmd/mcp-ida` 全部使用同一套共享 bootstrap client。
- 不各自复制 register / heartbeat / reconnect 逻辑。
- 不 import 核心侧 `internal/platform/mcpcontrol/*`。
- 能在 20-30 实例规模下稳定运行。

关键验收项：

| 项 | 验收要求 |
| --- | --- |
| Lease 语义 | 旧 generation 心跳和 report 会返回 `ERR_LEASE_STALE` |
| Approval 路由 | pending approval restore 只发给 `ui` peer |
| Selector 语义 | `intersection(subscription, capability, scope)` 有回归测试 |
| Event / Report 边界 | `ctl/event` 不持久化状态，`ctl/report` 不接受 `event` variant |
| Hook 扩展 | `ctl/hook/subscribe` / `before` / `check` / `after` / `resolve` 全部可用；`After(escalate)` 必须 durable 挂起并可异步完结 |
| Reconnect | 同一 `instance_id` 重注册后旧 lease 不能再改状态 |
| 容错 | live RPC 断开时 `Context` 回退 boot snapshot，`Report` 入本地 durable 队列 |
| 守卫 | `rpc` 包不新增 lifecycle 业务文件；新 package 满足 package / file / function guard |

## §10 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 继续把 lifecycle 业务塞进 `internal/platform/rpc` | 直接触发 package guard 和职责混乱 | 新增 `internal/platform/mcpcontrol/*`，`rpc` 只保留 transport hook |
| heartbeat / re-register 竞态 | 旧 lease 覆盖新 lease，出现幽灵活体 | 全部索引升级为 `LeaseKey`，所有状态更新先校验 generation |
| `peer_kind` 分类不严 | pending approval 被误投给 tool peer | 连接元数据强制 `ui|tool` 二分，restore 逻辑只走 `ui` |
| reconnect 期间进程被 kill | 高 | 内存 report 队列丢失，核心不知道 agent 已完成 | 缓解：shutdown 时同步 flush；或本地 WAL 持久化 report 队列 |
| 认证 / 误连 | 非当前会话 bootstrap 上下文对应的进程误连核心控制面 | `ctl/register` 校验 `session_token` 和 manifest 注入的 bootstrap 上下文 |
| selector 语义做成并集或广播 | 配置推送过量或错发 | 明确规定 `intersection(subscription, capability, scope)`，并做回归测试 |
| `ctl/context` 变成万能代理 | 协议扩散、权限边界失控 | scope 固定 4 个 namespace，超出直接返回 `ERR_SCOPE_NOT_ALLOWED` |
| `ctl/report` 又承接 event | durable 边界再次混乱 | DTO 里删除 `event` variant，只保留 `runtime` / `completion`，其余仅预留标签 |
| boot snapshot 被误当成 live | 工具误判状态新鲜度 | `ctl/context` 响应强制带 `source` 和 `observed_at`，fallback 时明确标记 |
| deprecation 无限拖延 | 仓库长期同时维护 `ctl/*` 与 `mcp/*` | 写死 `2026-06-30` 删除日期，并给 alias 调用打日志 |

结论：

- P8.5 的核心不是再造新的 MCP 执行链，而是补齐一条独立于 `stdio` 的 lifecycle 管理通道。
- 通过 `ctl/*`、`LeaseKey`、`peer_kind`、bootstrap reconnect 和双层容错，可以把当前散落在 transport、approval、runtime reporting、manifest env 里的能力收束成一套清晰控制面。
- 这次必须一次性把基线 9 个方法、hook 扩展 5 个方法、包布局、契约、容错和验收口径都定死，否则后续 adopter 接入还会反复返工。
