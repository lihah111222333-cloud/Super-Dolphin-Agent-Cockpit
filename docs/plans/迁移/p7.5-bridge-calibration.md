# P7.5 执行计划 — 前后端桥接校准

> 生成时间：2026-03-21
> 前提：P0-P7 后端迁移收官，P8 前置任务进行中
> 目标：确保 V3 后端 RPC handler、Wails direct binding 与前端生产调用链路一致

---

## 1. 背景

P0-P7 全程聚焦后端迁移，前端仍沿用 V2 的 `cmd/agent-terminal/frontend/vue-app/` 代码。
V3 后端新增/重构了多个 RPC 模块（orchestration、dashboard、uistate），但前端未同步校准。

### 架构回路

```
前端 vue-app
  └─ callAPI(method, params)
       └─ window.__go_wails__.CallAPI(method, JSON)
            └─ wails/binding.go → server.Dispatch(method, params)
                 └─ jrpc2 本地调用 → handler.Map 路由
                      └─ module/*/rpc.go handler
```

## 4. 核心缺口分析

### 4.1 orchestration 当前只有只读展示，没有操作闭环

前端 agents 页面通过 `ui/dashboard/get` 获取 agent 列表（只读），但无任何 agent 操作入口：
- 无法从 UI 发起 `agent.launch`
- 无法从 UI 停止 `agent.stop`
- 无法查看 `agent.snapshot` 详情
- 无法管理 DAG（`task/dag/*`）

`agent.list` 虽然仍有 legacy `ListAgents` direct binding，但当前 Vue 主链路未使用它。

**影响**：用户无法通过 GUI 管理 agent，只能通过 CLI / MCP。

### 4.2 workspace 模块已落地，但前端仍零覆盖

后端已有 `workspace/run/create|get|list|merge|abort|files/list|file/get` 7 个 handler，前端无对应页面或 API 调用。

### 4.3 bridge 真实绑定不是“11 类 method”，而是“11 类 DTO 事件 + legacy fanout”

`internal/platform/eventsurface/bind.go` 实际只订阅 11 类 bus DTO 事件：
- `agentdto.StateChanged`
- `turndto.TurnStarted`
- `turndto.TurnCompleted`
- `threaddto.Started`
- `threaddto.Stopped`
- `threaddto.MessagesPage`
- `workspacedto.WorkspaceRunCreated`
- `workspacedto.WorkspaceRunMerged`
- `workspacedto.WorkspaceRunAborted`
- `agentdto.AgentLaunched`
- `agentdto.AgentStopped`

`internal/platform/eventsurface/legacy.go` 的 `ExpandNotifications(...)` 会在原始通知外，按条件追加：
- `ui/thread/changed`
- `ui/sidebar/changed`

当前前端主链路并不主要依赖那 11 个 DTO method 本身，而是严重依赖 legacy refresh：
- `thread-sync-helpers.js` 把 `ui/thread/changed` 作为线程同步主信号
- `thread-sync-helpers.js` 把 `ui/sidebar/changed` 作为侧栏同步主信号

### 4.4 命名约定、StrictHandler 与 JSON 迁移影响

| 风格 | 数量 | 说明 |
|---|---:|---|
| 斜杠 | 91 | `thread` / `turn` / `dashboard` / `uistate` / `skill` / `workspace` 全量 + `orchestration` 的 `task/*` 与 `orchestration/report` |
| 点号 | 11 | `orchestration` 的 `agent.*` + `orchestration.reportRuntime` |
| 模块级混合 | 1 | `orchestration` 同时使用 `agent.*` + `task/*` + `orchestration.*` |

| 层 | 现状 | 示例 |
|---|---|---|
| RPC method | 斜杠 / 点号混用 | `thread/start`、`agent.launch`、`dashboard/agentStatus` |
| Go 参数兼容 | middleware 兼容多种字段名 | `threadId` / `threadID` / `thread_id` |
| provider translator | 双读旧字段与新字段 | `oldState` / `old_state` |
| 前端 parser | 消费端兼容双读 | `threadId` / `thread_id` / `agent_id` |

`knownDiffRevision` 不是“静默漂移”问题，而是可能直接触发 strict 参数拒绝：
- `thread-diff-sync.js` 调 `ui/state/get` 时会发送 `knownDiffRevision`
- `uistate.scopeParams` 只声明了 `cwd`、`threadId`、`includeDiff`
- `rpc.StrictHandler(...)` 在 `internal/platform/rpc/strict.go` 中实际调用 `handler.Check(fn).AllowArray(false).SetStrict(true).Wrap()`

结论：未知字段不会被“悄悄忽略”，而是可能按 strict / `DisallowUnknownFields` 语义被 `StrictHandler` 直接拒绝并返回 `InvalidParams`。

bridge payload 命名不能简单概括为“全面混用”：
1. `bind.go` 中 helper 生成的 thread / workspace / agent lifecycle payload 以 camelCase 为主，例如 `threadId`、`agentId`、`runKey`、`sessionId`
2. `bind.go` 直传的 core DTO（`StateChanged`、`TurnStarted`、`TurnCompleted`）仍保留 DTO 自身的 snake_case tag，例如 `old_state`、`new_state`、`thread_id`、`agent_id`
3. 当前确认会在同一 payload 内同时混用 camel + snake 的范围，只出现在 legacy refresh path：`legacy.go` 的 `buildRefreshPayload(...)` 输出 `threadId` + `agent_id`
4. 前端 parser 双读 `threadId` / `thread_id` / `agent_id` 是消费端兼容层，覆盖 helper payload、DTO passthrough 与 legacy refresh，不代表所有 bridge 输出都混用

JSON 兼容层实际横跨三层，不是简单改一个 `json` tag：
1. Go middleware：`internal/platform/rpc/handler.go` 的 `ThreadScope(...)` 同时接受 `threadId` / `threadID` / `thread_id`
2. Provider translator：`internal/provider/codexapp/event_map.go` 双读 `oldState` / `old_state`
3. 前端 parser：`stores/bridge-event-parser.js` 同时读取 `threadId` / `thread_id` / `agent_id`，用于消费端兼容而非声明 bridge 输出统一混用

**结论**：这不是单点字段重命名，而是一次跨 Go middleware、provider translator、前端 parser 的协议迁移。

| 已发到 bus 但 `eventsurface.Bind(...)` 未订阅 | `AgentRecovering`、`AgentFailed`、`AgentRuntimeReported`、`TurnInterrupted`、`TurnInputReceived`、`TurnOutputDelta`、`ToolCallBegin`、`ToolCallEnd`、`ToolApprovalRequested`、`ToolApprovalResolved`、`WorkspaceRunStatusChanged`、`WorkspaceRunMergeError`、`UITokensUpdated` | 这些类型在 provider translator、workspace service 或审批事件里已有 publish / emit 证据，但 `bridge-event` 当前不会收到 |
| 已定义但无发布点 | `TurnStalled`、`TurnResumed`、`TaskDagCreated`、`TaskNodeStatusChanged` | 当前仓库中仅见 DTO 定义与 bus sink logging，未见真实 publish 调用 |

补充说明：
- `agent-event` 频道当前后端无 `EmitEvent("agent-event", ...)` 发射点，前端 `onAgentEvent(...)` 订阅实际是空频道
- `UITokensUpdated` 已经存在于 bus，但 bridge 既没有直推这个 DTO，也没有派生出前端实际等待的 `thread/tokenusage/updated`

## 5. Agent 拆分方案（3 审查 Agent）

### Agent 1: `bridge-audit` — 全量 1:1 接口审计

**范围：**
- 遍历前端所有 .js 文件中的 `callAPI` 调用，提取 method 名
- 遍历后端所有 `rpc.go` 中的 `handler.Map` 注册，提取 method 名
- 逐一交叉对比，输出 ✅ / ⚠️ / ❌
- 检查 request / response 的 JSON 字段名是否匹配（camelCase vs snake_case）

### Agent 2: `bridge-event` — 事件推送审计

**范围：**
- 检查后端 bus 事件 → Wails bridge 推送 → 前端 `onAgentEvent` / `onBridgeEvent` 订阅链路
- 确认 DTO 已发布但未进入 bridge 的事件名单
- 确认事件 payload 字段名与前端消费端匹配

### Agent 3: `bridge-naming` — 命名约定与兼容性审计

**范围：**
- 审计所有 RPC method 命名：斜杠 vs 点号 vs 混合
- 确认 jrpc2 dispatcher 是否支持点号 method
- 审计 JSON 字段命名兼容模式覆盖度

## 6. 验证标准

| 项 | 标准 |
|---|---|
| 接口对齐 | 前端每个生产 `callAPI` 都有后端 handler 响应，或已明确改走 direct binding（0 个无主调用） |
| 事件链路 | 后端每个前端可见事件都能到达 `bridge-event`，或有明确 legacy refresh 替代 |
| 命名统一 | 确定统一方案并全量执行，或双读 / 双写兼容全覆盖 |
| JSON 兼容 | 所有 RPC 参数 / 返回值字段名与兼容层约定一致，不触发 strict 拒绝 |
