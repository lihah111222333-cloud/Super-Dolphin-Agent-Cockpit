## 0. TL;DR

P20 的战略方向保持不变：仍然采用 **L1 元数据清单 → L2 按需展开正文 → L3 按需读取资源** 的 Progressive Disclosure 路线。

P20.1 的核心变化不是“推翻 P20”，而是对以下 7 个高风险点做加固：

1. **审批粒度升级**：不再只按 `(skill_name, SKILL.md hash)` 缓存，而是升级为 **artifact 级审批**（skill body / resource 分开）。
2. **未审批元数据降权**：`untrusted + unapproved` 的项目级 skill，**不得把作者提供的 description / summary 直接放进 system prompt**。
3. **L2/L3 API 拆分**：废弃 `skill_expand(name, section=...)` 的双语义设计，拆为 `skill_expand_body` 与 `skill_read_resource`。
4. **rollout trim 成对解析**：新格式不再“从首个 `[skill:` 头一路剪到 EOF”，改成 **header/footer 成对裁剪**；legacy 仅做兼容兜底。
5. **非法 Mode 保守降级**：`SkillMode` 仅 `""` 视为 legacy Full；**非法非空值 → None + 告警**，不再失败展开成 Full。
6. **expanded state 细粒度去重**：去重 key 从 `name` 升级为 `name + target(kind/section/path) + hash`。
7. **清单缓存带 revision**：`SkillCatalogProvider` 的缓存 key 纳入 `skillRevision + approvalRevision + trustRevision`，防止 manifest 陈旧。

**上线阻断项（P20.1 新定义）**：
- A. untrusted skill 元数据不得直接污染 system prompt
- B. 新格式 rollout trim 必须成对裁剪，不能再首块截断到 EOF
- C. L3 资源读取必须按 resource hash 审批，不能复用 SKILL.md 的旧批准
- D. invalid mode 不得默默回退为 full

## 3. 加固后的设计决策

### 3.1 L2 / L3 接口拆分：拒绝 `section` 双语义

P20 原方案把以下两种能力都塞进 `skill_expand(name, section?)`：

- `section="# Usage"`：读取 SKILL.md 某个锚点
- `section="references/api.md"`：读取 skill 目录内资源文件

P20.1 认为该设计**语义混杂、审批困难、缓存难做细**，因此拆分为：

```text
skill_expand_body(name, anchor?, max_bytes=20000)
skill_read_resource(name, path, max_bytes=20000)
```

语义划分：
- `skill_expand_body`：只负责 **SKILL.md 正文 / H2/H3 锚点切片**
- `skill_read_resource`：只负责 **skill 目录内资源文件**（`references/*`、`scripts/*`、`assets/*` 等）
- `skill_exec`：**不在 P20.1 实现范围**；如未来需要执行脚本，另立 P21/P22，不与“读取文本”共用入口

**直接收益**：
- 审批粒度可按 body / resource 分开缓存
- expanded state 可以按 API 类型去重
- 文案更清晰，模型误用率更低
- 便于后续对脚本类资源做单独沙箱化策略

---

### 3.2 审批模型升级：从 skill 级变成 artifact 级

P20 原审批缓存按 `(skill_name, content_hash)`，只适合 SKILL.md 全文场景；一旦 L3 资源参与，粒度不够。

P20.1 将审批 key 升级为：

```text
(repo_fingerprint, trust_scope, skill_name, artifact_kind, artifact_locator, content_hash)
```

字段定义：
- `repo_fingerprint`：项目根目录稳定指纹（建议：repo root absolute path hash；若在 git repo 内，可追加 remote/url/HEAD 作为增强）
- `trust_scope`：`user | project | signed`
- `skill_name`：规范化 skill name
- `artifact_kind`：`metadata | body | resource`
- `artifact_locator`：
  - body：`"SKILL.md"` 或 `"SKILL.md#Usage"`
  - resource：如 `"references/api.md"`、`"scripts/setup.sh"`
- `content_hash`：目标 artifact 的内容 hash；**不是整个 skill dir hash**

#### 审批规则

| 目标 | 审批策略 |
|---|---|
| trusted user skill metadata | 默认可见 |
| trusted user skill body/resource | 默认允许，无弹窗 |
| project skill metadata | **默认不可透传作者原文**；只暴露净化占位 |
| project skill body | 首次 `skill_expand_body` 前审批；hash 变化重审 |
| project skill resource | 首次 `skill_read_resource` 前审批；**resource hash 变化单独重审** |
| signed skill | P20.1 先视同 trusted；真正验签仍延后到 P21 |

#### 审批缓存文件模型修订

现有 `approval.go` 需从：

```go
ApprovalEntry { Name, ContentHash, Trust, ApprovedAt, ApprovedBy }
```

升级为至少：

```go
ApprovalEntry {
    RepoFingerprint string
    Name            string
    ArtifactKind    string // metadata|body|resource
    ArtifactLocator string // SKILL.md#Usage / references/api.md
    ContentHash     string
    Trust           TrustScope
    ApprovedAt      time.Time
    ApprovedBy      string
}
```

**注意**：
- 旧 key 只能做向后兼容读取，不能继续作为主 key
- `Approve/Revoke/Lookup` 都要切到 artifact 语义
- UI 文案必须能区分“批准正文”与“批准资源文件”

### 3.3 未审批元数据净化：L1 清单只放安全投影，不放作者原文

P20.1 明确：对于 `project + unapproved` 的 skill，**禁止把作者提供的 `description` / `summary` / 自动从 body 生成的 summary 直接放入 system prompt**。

#### 原因

当前 `parseSkillInfo` 会：
- 直接采纳 frontmatter 的 `description/summary`
- 若缺 summary，还会从 body 自动生成摘要

这意味着即使“不展开正文”，攻击者也能把注入载荷藏在摘要里。

#### P20.1 规则

| skill 状态 | L1 中可显示内容 |
|---|---|
| trusted / approved | `name + description + summary + when_to_use/SKIP` |
| project + unapproved | 仅 `name + trust badge + 固定模板提示` |
| disabled-model-invocation | 可列入索引，但必须标识“manual only” |

#### 固定模板示例

```markdown
- **rpc-tracing** — Untrusted project skill. Metadata hidden until approval.
  To inspect details, request approval and call `skill_expand_body("rpc-tracing")`.
```

#### 额外要求

- 对 untrusted skill，`summary` 自动生成逻辑仅供本地 UI 管理页预览，不得直接进入模型上下文
- L1 渲染时必须统一包一层系统前缀：
  - `Untrusted skill metadata is intentionally redacted until approved.`
- 若未来要做“预览审批”，也必须经 UI 明示批准，不允许后台静默喂给模型

### 3.4 rollout trim 改成“成对裁剪优先，legacy 兜底”

P20 共享 trim 虽已抽到 `rollout_markers.go`，但当前新格式逻辑仍然是：

- 一旦看到合法新 header：**直接从该行裁到 EOF**

P20.1 认为该行为对多块场景不安全，正式改成：

#### 新格式裁剪规则

```text
[skill:foo::summary@v1]
...
[/skill:foo::summary@v1]
```

- 必须按 **header/footer 成对匹配** 裁剪
- 同一个 payload 中允许出现多个 skill block
- block 后面的正常用户文本 / 系统文本必须保留
- 若 header 存在但 footer 缺失：
  - 记录 `skill_trim_corruption_fallback_count`
  - 再走“裁到 EOF”容错分支
  - 该分支只作为异常兜底，不作为正常语义

#### legacy 裁剪规则

legacy `[skill:name] + 摘要: + 使用方式:` 逻辑保持兼容，但仅用于旧 rollout 回放。新写端不得再产 legacy 格式。

#### 必补测试

1. 单块 full
2. 单块 summary
3. 单块 expanded
4. 多块顺序拼接
5. block 后还有普通文本
6. footer 缺失 / 损坏
7. legacy 与 new mixed
8. 同 skill 多次 expand

### 3.5 `SkillMode` 安全语义修订：空值兼容，非法值保守

P20 的 `Effective()` 语义是“空值或非法值都回退 Full”。P20.1 修改为：

| 原始值 | 语义 |
|---|---|
| `""` | **legacy payload**，按 Full 处理 |
| `full` / `summary` / `none` | 正常有效 |
| 其他非空非法值 | **按 None 处理**，并打告警日志/指标 |

建议实现：

```go
func (m SkillMode) Effective() SkillMode {
    switch m {
    case SkillModeUnspecified:
        return SkillModeFull
    case SkillModeFull, SkillModeSummary, SkillModeNone:
        return m
    default:
        return SkillModeNone
    }
}
```

同时新增：
- `skill_invalid_mode_total`
- warn log：包含 `thread_id / turn_idx / raw_mode / skill_name`

这样既保住 legacy 兼容，也避免错误 payload 触发“失败展开”。

### 3.6 Expanded state 去重键升级：从 `name` 到 `(kind,target,hash)`

P20 原状态：

```text
ExpandedSkills map[name]{Mode, TurnIdx, Hash}
```

P20.1 升级为：

```text
ExpandedArtifacts map[key]{Kind, Locator, Hash, LastTurnIdx, LastUsedAt}
key = lower(name) + "::" + kind + "::" + locator + "@" + short(hash)
```

说明：
- `kind`：`body` / `resource`
- `locator`：`SKILL.md#Usage` / `references/api.md`
- `hash`：目标内容 hash

#### 失效策略

- 不再单纯依赖“5 turn TTL”
- 改为双条件：
  1. **同 `(name, kind, locator, hash)` 近 5 turn 不重复注入**
  2. 一旦 `hash` 变化、thread resume、history compact、explicit re-request，则立即失效

这样可以解决：
- 同一 skill 不同 section 互相误伤
- `SKILL.md` 和 `references/api.md` 共用一个 name 时冲突
- 恢复会话后状态陈旧的问题

### 3.7 Manifest 缓存纳入 revision：防止 L1 清单陈旧

P20 的 `SkillCatalogProvider` 准备使用 `CacheByName`，但如果不把 skill 状态变化纳入 key，会导致：

- 新增/删除 skill 后清单不刷新
- 审批完成后仍显示“metadata hidden”
- trust 推断变化后清单不更新

P20.1 要求 cache key 至少包含：

```text
(session_id, skillRevision, approvalRevision, trustRevision, tokenBudget, progressiveDisclosureFlag)
```

#### revision 来源建议

- `skillRevision`：skills 目录文件变化、summary 改写、import/delete
- `approvalRevision`：审批缓存 approve/revoke 后递增
- `trustRevision`：trust 推断规则或 skill root 变化时递增

#### 补充修订

- L1 Summary 预算统一为 **≤160 字符**，文档与实现不得再出现 220/160 双口径
- `CacheByName` 可以保留，但 provider 自身必须把 revision 纳入 `Name()` 或内部缓存 key

#### 2026-04-27 修订

> 结论：§3.3 的 “project + unapproved metadata redaction” 保留为历史设计记录，不再作为当前 P20.1 实施基线。

- **上游基线**：Claude Code Skills 官方采用 `~/.claude/skills/<skill>/SKILL.md` 顶层扁平结构，`description` 常驻上下文、invoke 时注入完整 `SKILL.md`，官方文档零 trust / approval / redact 设计；OpenAI Codex Skills 官方采用 `~/.agents/skills`、`$CWD/.agents/skills` 等多层搜索与 progressive disclosure（catalog 先注入 metadata + path，约 2% context / 8000 chars hard limit），同样零 trust / approval / redact 设计；开放标准 `agentskills.io` 也不要求 catalog redact。
- **用户场景反馈**：`.agent/skills/` 下的 skill 是用户自己导入到项目的代码/文档，与 `src` 同信任度；在 catalog 上再套一层 redact + approval，会把“已选择导入”的明示信任重复询问，UX 多此一举。
- **新基线**：项目级 `TrustProject` 与系统/用户级 `TrustUser` skill **不再 redact**；L1 catalog 可直接展示 `name + description + summary`，并继续按 token 预算裁剪。
- **保守边界**：仅 `TrustUnknown` 或无法解析/无效 trust 值仍按 untrusted redacted 处理，防止异常来源、损坏 frontmatter 或未来外部来源静默注入 system prompt。
- **实施位置**：`internal/module/prompt/skill_catalog_provider.go:442` `isUntrustedScope`；当前判定为 `TrustUser` / `TrustProject` / `TrustSigned` 返回 `false`，其余返回 `true`，即只有 `TrustUnknown` / 非法 trust 视作 untrusted。
- **文档兼容**：上方 §3.3 的审批/redact 方案作为 2026-04-19 的历史硬化思路保留，后续实现与验收以本修订子节为准。

### Phase 6：工具设计修订（升级为 P0，2–3 天）

> 这是 P20.1 最大接口修订：**不用单一 `skill_expand`，直接拆成两个工具。**

P20 解决的是“技能太重、每 turn 全文注入不可扩展”的问题；

- **以 P20.1 作为后续施工和评审的唯一修订基线**
