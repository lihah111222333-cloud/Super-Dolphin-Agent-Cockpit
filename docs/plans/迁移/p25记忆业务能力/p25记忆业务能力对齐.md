## ✅ Phase 自有.1a：upsert 原子 CreateOrUpdate（slug: `dual-cli-write-coordination`）

**状态**：✅ 完成。Phase 自有.1 经调研拆分为 1a（upsert 原子化，本节）+ 1b（cross-CLI 协议，销账，详见下节）。

**触发**：Phase 4.0 spike 完成（CLI 不用 POSIX flock，走 proper-lockfile mkdir + mtime；详见 Phase 4.0a spike 子项 2）。

### 背景与真问题定位

- claude_code 模式下 `SuppressForOverlay=true` 仅注入让路（不注 prompt / 不 prefetch / 不更新索引），**写入仍跑**（extractMemories / autoDream 全开）
- 现有防护三层：进程内 mutex（`diskStoreLocks sync.Map`）+ 跨进程文件锁（`syscall.Flock LOCK_EX`）+ 写入原子性（`writeAtomicFile` = CreateTemp + Rename）
- 真问题位置：不是跨 CLI，是**单进程内 Create-then-Update 两段独立加锁窗口** —— 旧实现：(1) `CreateStructured` 持锁 → check exists → 释锁；(2) 返 `ErrMemoryAlreadyExists` 后走 `UpdateStructured` 重新持锁 → write → 释锁。两段锁中间 racing writer 可介入，第二个写入者的 Update 静默覆盖中间发生的写入。

### 实施清单

代码改动：
- `internal/module/memory/store.go`：`memoryStructuredStore` interface 加 `UpsertStructured(req, opts...)` method；`*diskStore` 加 `UpsertStructured` + `upsertWrite` 实现，单次 `withDiskStoreLock` 内 prepare → lock → `writePreparedMemoryFile` → `updateIndexAfterMutation` → release；跳过 `validateMutationMode`（upsert 总是写入）
- `internal/module/memory/service.go`：`upsertStructuredMemory` 简化为单次 `store.UpsertStructured` 调用，不再走 Create-then-Update 两段独立加锁

新增测试文件：`internal/module/memory/phase_self_1a_upsert_atomic_test.go`（+180 行 / 3 项 baseline）：
- **TestPhaseSelf1a_UpsertStructuredCreatesNewEntry**（正向）：空 store 调 Upsert，验证文件创建
- **TestPhaseSelf1a_UpsertStructuredOverwritesExistingEntry**（正向 + counter-baseline）：同名 entry 已存在，Upsert 必须覆盖不返 `ErrMemoryAlreadyExists`（旧实现 Create 路径会返）
- **TestPhaseSelf1a_UpsertStructuredConcurrentRaceFree**（核心 race scenario）：16 goroutine × 50 rounds = 800 次并发 upsert 同名 entry 不同 content，验证 0 `ErrMemoryAlreadyExists` 泄漏 + 0 race + 最终 on-disk content 含 race exercise marker（代表并发写入未丢失）

### 关闭的 race window

旧 `upsertStructuredMemory` 双段锁路径在并发 N goroutine 场景下会出现：
- Worker A: Create lock → exists=false → write A → 释锁。
- Worker B: Create lock → exists=true（A 已写）→ 释锁 → 返 `ErrMemoryAlreadyExists` → Update lock → exists=true → write B（覆盖 A）→ 释锁。

新实现把 check + write 合并到单次锁内，从根本上消除该 RMW 窗口。依然是 last-writer-wins 语义（跨 goroutine 的 last 是本身合理设计），但不会出现错误路径下静默覆盖。

**验证**：`go test -race -count=1 ./internal/module/memory/...` 全绿（含本表 3 项 + 现有 Phase 4 baseline 12 项 + 现有 13 项跨项覆盖）。
