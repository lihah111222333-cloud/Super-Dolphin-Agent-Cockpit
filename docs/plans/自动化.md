# 自动化（上下文继承与预警 · 自动续接）

> 分支：`上下文继承与预警`
> 范围：让 agent 派发的自动化任务在 token 满 / 状态出错时自我续命，保证任务流程不中断。
> 现状（写作时）：Phase 0 已 ship（commit `6765839` —— 修复进展段抽取）；Phase 1.1 待提交。

---

## 1. 背景与动机

### 1.1 问题
agent 派发的多轮自动化任务（child agent / typed agent / OwnerThreadID 关系下的 thread）跑着跑着会撞到两类天花板：

- **token 用量到 critical**：上下文窗口满，下一轮 turn 失败
- **status 转 error**：CLI 进程崩 / 网络断 / 内部异常

目前两种情况的处理都依赖**用户手动操作**（点 banner 上的"压缩 / 新建继承"或 thread 行的"恢复"按钮）。**对自动化任务而言这是不可接受的** —— 任务跑到一半要等人工介入，相当于没完成。

### 1.2 设计目标
让"task thread"（runtime config 含 `taskId`）在以下信号触发时**自动**完成续命动作，不打扰用户：

- token level 跨入 `critical`
- status 转 `error`

普通用户对话（无 `taskId`）**完全不在自动化范围内**，行为和今天一样（用户自己点 banner / 恢复按钮）。

### 1.3 边界（明确不做）
- 普通对话不自动触发任何动作（Phase 2.x 才会通过 promote-task RPC 让用户主动开关）
- 不引入新的"silent startThread"模式，焦点处理在调度器内部用 selectedThreadId 比较解决
- 不新增 toast / banner 组件，复用现有 `ContextUsageBanner`

## 2. 设计概览

### 2.1 整体架构
```
┌─ token level watcher ─┐    ┌─ status watcher ─┐
│  watch tokenUsageBy-  │    │  watch statuses   │
│  Thread (deep)        │    │  (deep)           │
└──────────┬────────────┘    └──────┬────────────┘
           │ critical 跨阈值         │ → error
           ▼                          ▼
   ┌──────────────────────────────────────┐
   │   useAutoContinue 调度器              │
   │  ── 过滤：仅 task thread (有 taskId) │
   │  ── 闸门：偏好 / 幂等 / 频率限制       │
   │  ── 决策优先级：                      │
   │       compact > continueTaskById      │
   │       recover > continueTaskById      │
   └──────────────────────────────────────┘
           │
           ▼
   ┌─ compactCurrent ─┐  ┌─ recoverThread ─┐  ┌─ continueTaskById ─┐
   │ 已存在            │  │ 已存在           │  │ 1.1 抽出           │
   └──────────────────┘  └─────────────────┘  └────────────────────┘
```

### 2.2 不重复造轮子
现有可复用：
- `compactCurrent`（`useThreadActions.js:282`）：上下文压缩，capability `context_compact` 的 thread 才支持
- `recoverThread`（`thread/recover` RPC）：进程恢复
- `useTaskHandoff.continueTaskById`（1.1 抽出）：task thread 续接，复用现有 handoff 文件链路
- `ContextUsageBanner`：警告 banner，已在 critical 时显示

### 2.3 触发范围（task-only）
判定条件：`threadStore.state.agentRuntimeById[threadId].taskId` 非空

来源（`task_handoff.go::shouldAutoTaskHandoff`）：
- `autoTaskHandoff: true` 显式 opt-in
- `ParentAgentID` 不空（agent 派发的子 thread）
- `OwnerThreadID` 不空
- `AgentType` 不空（typed agent）

**普通对话不在监听范围内**，不会被任何 watcher 关注。

## 3. 决策调度优先级

### 3.1 token level → critical
1. 如果 `canCompact`（capability 含 `context_compact`）→ 调 `compactCurrent`
   - 成功：done，不续接
   - 失败：转步骤 2
2. 调 `continueTaskById(threadId)` fork 续接

### 3.2 status → error
1. 调 `recoverThread(threadId)`
   - 成功：done，不续接
   - 失败：转步骤 2
2. 调 `continueTaskById(threadId)` fork 续接

### 3.3 焦点处理
- `continueTaskById` 内判断：如果 `selectedThreadId.value === sourceThreadId`，新 thread 走默认 saveActiveThread（焦点跟随）
- 否则**不抢焦点**（用户在别处工作时 task 静悄悄续接）

注：1.1 已实现 `continueTaskById` 接受任意 threadId 起续接 thread；焦点判断逻辑在 1.4 接通真实自动触发时加。

## 4. 频率限制（精简版 · 2 层闸）

> **2026-04-28 review 决策**：原计划 7 层闸（per-task 滑窗 / per-task 累计 / recover 冷却 / 用户静默期）属于过度设计 ——
> 真实失控防御 90% 已被 per-thread 1 次 + 全局保险丝覆盖；per-task 闸又被 §4.3 自己证明对多子 agent 场景无效。
> 按 YAGNI 精简：等真出现 corner case 再 case-by-case 加，不预先建仓库。

### 4.1 闸门设计

| 闸 | 维度 | 数值 | 触达后行为 |
|---|---|---|---|
| 偏好开关 | `taskHandoff.autoContinueOnAlert`（在 useAutoContinuePref，不在闸门模块） | bool | false 时整条链路跳过 |
| 单 thread 续接上限 | per source threadId | 1 次 | 静默 skip（reason `thread_already_continued`） |
| 全局保险丝 | 全应用 | 1min 内 20 次 | 静默 skip + `fuseBlown:true`，由 useAutoContinue 决定是否 alert / logError |

### 4.2 状态结构（在 `auto-continue-gating.js` 闭包内）
```js
const continuedSourceThreadIds = new Set();   // per-thread 1 次
const globalLog = [];                          // number[] 全局保险丝时间戳

const GLOBAL_WINDOW_MS = 60 * 1000;
const GLOBAL_WINDOW_MAX = 20;
```

### 4.3 多子 agent 场景与未来扩展
10 个子 agent × per-thread 1 次 = 10 次（每 thread 各自独立），全局保险丝 60s/20 兜底。
如未来出现"主任务反复 spawn 失败子 agent"的级联场景，再加 §3.x（rootTaskId 分组）。
已评估但未启用的 4 层闸（per-task 滑窗 / per-task 累计 / recover 冷却 / 用户静默期）作为扩展点，按需启用。
