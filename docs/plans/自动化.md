## 1. 背景与动机

### 1.1 问题
agent 派发的多轮自动化任务（child agent / typed agent / OwnerThreadID 关系下的 thread）跑着跑着会撞到两类天花板：

- **token 用量到 critical**：上下文窗口满，下一轮 turn 失败
- **status 转 error**：CLI 进程崩 / 网络断 / 内部异常

目前两种情况的处理都依赖**用户手动操作**（点 banner 上的"压缩 / 新建继承"或 thread 行的"恢复"按钮）。**对自动化任务而言这是不可接受的** —— 任务跑到一半要等人工介入，相当于没完成。

### 1.2 设计目标
让"task thread"（runtime config 含 `taskId`）在以下信号触发时**自动**完成续命动作，不打扰用户：

- token level 跨入 `critical`
- status 转 `error`

普通用户对话（无 `taskId`）**完全不在自动化范围内**，行为和今天一样（用户自己点 banner / 恢复按钮）。

### 1.3 边界（明确不做）
- 普通对话不自动触发任何动作；历史上的手动升级入口已移除，不再作为当前产品路径。
- 不引入新的"silent startThread"模式，焦点处理在调度器内部用 selectedThreadId 比较解决
- 不新增 toast / banner 组件，复用现有 `ContextUsageBanner`

## 2. 设计概览

### 2.1 整体架构
```
┌─ token level watcher ─┐    ┌─ status watcher ─┐
│  watch tokenUsageBy-  │    │  watch statuses   │
│  Thread (deep)        │    │  (deep)           │
└──────────┬────────────┘    └──────┬────────────┘
           │ critical 跨阈值         │ → error
           ▼                          ▼
   ┌──────────────────────────────────────┐
   │   useAutoContinue 调度器              │
   │  ── 过滤：仅 task thread (有 taskId) │
   │  ── 闸门：偏好 / 幂等 / 频率限制       │
   │  ── 决策优先级：                      │
   │       compact > continueTaskById      │
   │       recover > continueTaskById      │
   └──────────────────────────────────────┘
           │
           ▼
   ┌─ compactCurrent ─┐  ┌─ recoverThread ─┐  ┌─ continueTaskById ─┐
   │ 已存在            │  │ 已存在           │  │ 1.1 抽出           │
   └──────────────────┘  └─────────────────┘  └────────────────────┘
```

### 2.2 不重复造轮子
现有可复用：
- `compactCurrent`（`useThreadActions.js:282`）：上下文压缩，capability `context_compact` 的 thread 才支持
- `recoverThread`（`thread/recover` RPC）：进程恢复
- `useTaskHandoff.continueTaskById`（1.1 抽出）：task thread 续接，复用现有 handoff 文件链路
- `ContextUsageBanner`：警告 banner，已在 critical 时显示

### 2.3 触发范围（task-only）
判定条件：`threadStore.state.agentRuntimeById[threadId].taskId` 非空

来源（`task_handoff.go::shouldAutoTaskHandoff`）：
- `autoTaskHandoff: true` 显式 opt-in
- `ParentAgentID` 不空（agent 派发的子 thread）
- `OwnerThreadID` 不空
- `AgentType` 不空（typed agent）

**普通对话不在监听范围内**，不会被任何 watcher 关注。

### 2.4 另外两条同时在跑的自动续命路径（不在本计划范围）

本计划画的 useAutoContinue 调度器是"前端 thread 级"那一层（下记为 **F1/F2/F3**）。系统里同时还跑着两条**后端层面**的自动续命路径，与本计划独立，但梳理时容易遗漏：

- **B1 · mcp-orch agent launch retry** — `internal/sidecar/orch/orchestration/service_launcher_bridge.go` `launchWithRetry` + `isRetryableLaunchError`；`maxLaunchRetries=3`，退避 `attempt × 2s`（实际等待 0/2s/4s）；只识别 6 个关键字 + `errors.Is(context.DeadlineExceeded/Canceled)`，**不识别 429 / quota / context_length_exceeded**
- **B5 · codexapp peer 自动重启** — `internal/provider/codexapp/peer_supervisor.go` `superviseOne`；peer 进程 `Wait()` 返回后等 `restartBackoff` 调 `launcher.Launch` 重启；**首次重启失败即 degraded 直到整个进程 shutdown，不再尝试**

另外有 3 条**接口存在但没有 driver、不在跑**的，不要被代码骗：

- `store/taskdag/store_wakeup.go` 的 `RetryWakeup` —— 除 store 内部和 test 外**零业务调用** → **Phase 3 实施**
- `ReclaimStaleDispatchingWakeups` —— 同上，无 goroutine 调它 → **Phase 3 实施**
- DAG 节点完成自动 spawn 下一节点 —— `CompleteNode` 只更新 DB 不 enqueue；且整套 wakeup 派发（claim SQL 都没有）/ reclaim cron 都缺；要做不是补一行 enqueue，是**搭一整个 dispatcher** → **Phase 3 实施**（详见 [dag-auto-spawn-next-node](../../../../.multi-agent/memory/projects/users-mac-desktop-agnet-super-dolphin/memory/team/project_dag_auto_spawn_next_node.md)）

全图核对结论沉淀在 team memory `auto-continue-full-map`，再讨论"自动续命"前先看那条避免重核。

## 3. 决策调度优先级

> **2026-04-28 review 决策（保留原方案）**：曾考虑"自动化任务直接 fork 跳过 compact"，理由是 fork 是摘要继承设计的核心。
> 重新解耦"普通对话 vs 自动化任务"后回到原方案：**自动化任务无 timeline UX 担忧**（没人在 watch），且
> compact 是单点 RPC，活动部件比 fork 少（不开新进程 / 不重新初始化），失败模式更简单。fork 兜底链路已足够覆盖 compact 失败。
> 直接 fork 的理由（"compact 改 timeline 用户切回奇怪"）属普通对话 UX 视角，不适用本计划范围。
>
> **2026-04-29 审查补充（共识 3）**：上面 review 决策的"无 timeline UX 担忧"前提**只覆盖 fire-and-forget 类**（agent 派的 sub-agent，用户不在 watch）。
> Phase 2.x 曾设计的 user-attached 类（用户主动升级的对话）**有 timeline UX 担忧**（用户就在 watch）；当前产品已移除此入口。
> §3.1 / §3.3 / §3.5 决策按 `taskKind: 'auto' | 'attached'` 字段分流，详见各小节 attached 分支。taskKind 字段由 Phase 2.1 写入。

### 3.1 token level → critical（已落地于 1.4c；2026-04-29 审查加 taskKind 分流 → Phase 2.3）

**auto 类（agent 派的 sub-agent · 默认 · 已 ship）**：
1. 如果 `canCompact`（capability 含 `context_compact`）→ 调 `threadStore.compactThread(threadId)`（**底层 RPC，不复用 useThreadActions** —— 那一层是为前台用户写的）
   - 成功：done，不续接
   - 失败：healthcheck（thread 已自然恢复则 skip）→ 否则转步骤 2
2. `continueTaskById(threadId)` fork 续接（带 retry 1 次 + 1.5s 延迟 + retry 前 healthcheck）

**attached 类（user-attached · Phase 2.3 加 · 2026-04-29 审查共识 3-B）**：
1. **跳过 compact 直接 fork**（用户在 watch timeline，避免 compact 改 timeline 让用户 confused）
2. fork 同 auto 类（带 retry + healthcheck）；焦点处理见 §3.3 attached 分支

### 3.2 status → error（已落地于 1.4c）
1. 调 `threadStore.recoverThread(threadId)`
   - 成功：done，不续接
   - 失败：healthcheck → 否则转步骤 2
2. `continueTaskById(threadId)` fork 续接（同 §3.1 retry / healthcheck 链）

### 3.3 焦点处理（已落地于 1.4b；2026-04-29 审查加 taskKind 分流 → Phase 2.3）

**auto 类（已 ship）**：
- `continueTaskById` 内判断：如果 `selectedThreadId.value === sourceThreadId`（用户恰好在看这条 sub-agent），新 thread 走默认 saveActiveThread（焦点跟随）
- 否则传 `skipSaveActive: true`，新 thread **不抢焦点**（用户在别处工作时 task 静悄悄续接）
- `startThread(options.skipSaveActive)` 是 1.4b 在 thread-actions-helpers 加的小开关

**attached 类（Phase 2.3 加 · 2026-04-29 审查共识 3-C）**：
- **永远 `skipSaveActive: true`**：即使 selectedThread === sourceThread（用户就在跟 attached task 对话），也不强制切焦点
- 在原 thread 上渲染轻量提示："已 fork 到新 thread，[切过去]"，让用户主动选是否切换（避免对话突然切走 confused）

### 3.4 失败可见性（已落地于 1.4c + 1.4d；2026-04-29 审查补强 1.6 + 1.9）
- 单次自动续接失败 → `logWarn` + 写入 `failedAutoContinueByThread`（前端本地 ref<Map>）；UI 反馈靠现有 thread 卡片 status/token 视觉染色
- 全局保险丝触发 → `logError + window.alert(...)`（一次性，相同 reason 不重弹）
- 1.4d 在 `ContextUsageBanner` 渲染失败提示行 + "一键重试"按钮，调 `retryAutoContinue(threadId)`（绕过自动调度闸门，是用户主动入口）

**2026-04-29 审查补强**：banner 失败行只在 `selectedThreadId === failedThreadId` 时渲染，sub-agent 场景下用户没切过去就看不到，可达性低。外加两条补强路径：

- **修法 1（→ Phase 1.6）**：sidebar thread 卡片读 `failedAutoContinueByThread`，有记录时显红点 / 失败计数标记，让用户翻 rail 时一眼看到
- **修法 5（→ Phase 1.9）**：mcp-orch `launch_agent` 工具回执包含续命过程（自动续接次数 / 失败次数 / 最终 status），让主 agent 自己感知失败并决定后续（不依赖用户主动翻找）
- **修法 2/3/4 不做**：主 agent thread 顶部摘要（跨计划复杂）/ 失败实时弹 toast（撞 §1 设计约束）/ DAG 页面承接（属另份计划）

### 3.5 偏好开关（已落地于 1.5；2026-04-29 审查拆两组 → Phase 2.4）

**当前已 ship 状态**：单一开关 `taskHandoff.autoContinueOnAlert`（默认 true），所有 task thread 共享。

**Phase 2.4 拆两组（2026-04-29 审查共识 3-D）**：
- `taskHandoff.autoContinueAuto`（默认 **true**）：fire-and-forget 类（mcp-orch 派的 sub-agent）的自动续接开关
- `taskHandoff.autoContinueAttached`（默认 **false**）：user-attached 类（用户主动 promote 的对话）的自动续接开关
- 默认值反映两类 default 不同：auto 类用户期望"sub-agent 自动处理"；attached 类用户主动 promote 时再选要不要开

**通用原则（auto / attached 共享）**：
- watch 跨入 + taskId 过滤 + taskKind 路由后判对应 `prefRef.value`：false → 整条链路跳过（连 signal 日志都不打，避免"看似在做事"）
- prev level/status 仍正常更新，开关切换后下次跨入识别正确
- `retryAutoContinue` **不**受 pref 控制（用户主动点重试 = 已知情同意）
- UI 入口：`AutoContinuePrefCard` 挂在 `DagsPage` 顶部（侧边栏 DAG 一级页）；选位理由是 DAG 页面的核心用户 = 自动化任务用户，普通对话用户根本不打开此页，控件对其透明；卡片文案明确"不影响普通对话"消歧义
- Phase 2.4 后卡片同时显示两个 toggle，独立切换

### 3.6 代码层面识别的设计风险（含实施去向）

> **2026-04-29 复核纠正**：之前此节写的"4-28 fuse_blown 15 次 / 4-29 4 次"是 grep 误判（用户点击含 fuse_blown 字样文本触发的 `chat.fileRef.click.no_ref_node` 事件被误算）。实测 4-28 ~ 4-29 全部日志里前端 `auto_continue.*` 真实事件 = **0 条**——Phase 1.x 自动续命系统建好后**还没在生产里真跑过**。本节按 typical 标准筛选后分类到 Phase 1.7（已规划）/ Phase 1.8（待 1.7 ship 后启动）/ 仅登记（不在续命系统范畴）三档，详见末尾"实施去向汇总"。

**风险 1 · F2 → recover 假成功死循环（已证伪，不实施）**

- 假说：若 `recoverThread` 表面成功但底层 state 未持久化，F2 会反复触发→"假成功"→链路结束→下次 status 同步又 'error'→再次触发，最终 60s/20 跳闸
- 代码核实：`internal/module/thread/lifecycle.go::Resume` 确实有 swallow 模式（`persistThreadState` 失败仍 `publishThreadStarted` + return resumed），日志 "thread: resume persist failed, continuing with event emission" 在生产里出现 14 次属实
- **但**：`thread/recover` RPC 走的是 `internal/module/thread/lifecycle_fork.go::Recover`，**不是** lifecycle.go::Resume；`lifecycle_fork.go::Recover` 已正确返回 persist 错误（行 153-154），**没有 swallow**。所以 F2 路径上不会出现"假成功"
- 结论：bug 不存在于 F2 路径。Resume 的 swallow 是另一个独立设计选择（startThread/startup 流程），不影响自动续命。**不进 Phase 1.8，仅保留登记**

**风险 2 · 用户主动 stop 被 F2 覆盖（typical · 进入 1.8a）**

- 假说：`stopThread` 自身不写 status，由后端推回；若 interrupt 处理过程中 status 瞬间到 'error'，F2 会自动 fork 覆盖用户意图
- 当前无 `manualAbort` 抑制位区分"用户主动停"vs"真错误"
- 生产观察：F2 链路全程 0 触发（前端 `auto_continue.*` 事件不持久化，观察不到 ≠ 不发生）
- 结论：typical 必发场景（用户主动停的语义保护是消费侧基本诉求），**进入 Phase 1.8a 实施**（含共享文件持久化，刷新/多 tab 一致）

**风险 3 · 永久错误未识别 → 重试浪费配额（typical · 进入 1.8b）**

- 假说：401 / 403 / quota_exhausted / payment_required / **context_length_exceeded** 等永久错误，B1 重试 3 次浪费配额；F2 看到 status='error' 也会一直 fork 至 fuse_blown
- 当前 B1 `isRetryableLaunchError` 只识别 6 个 transient 关键字，未做 transient/permanent 分类
- 5 类永久错误：401（鉴权失败）/ 403（权限拒绝）/ quota_exhausted（配额耗尽）/ payment_required（订阅过期）/ context_length_exceeded（prompt 已超长）
- 生产观察：日志 grep 全 0；但 typical 必发——任何调外部 API 系统都得有错误分类，且 context_length_exceeded 会随用户阈值配置变化而出现
- 结论：**进入 Phase 1.8b 实施**

**风险 4 · 429 rate limit 短退避不够（typical · 进入 1.8c）**

- 假说：B1 退避是 `attempt × 2s`（最长 4s），429 通常需要 60s+
- 生产观察：日志 grep 0；但 429 是任何 LLM API 调用都会撞的限流，typical 必发
- 结论：**进入 Phase 1.8c 实施**

**风险 5 · handoff 文件预检防场景偏（typical · 修订 1.8d）**

- 原假说：fork 前不验证 `handoff/tasks/<taskId>.md` 存在性，缺失时 fork 失败但已消耗一次 per-thread 闸
- **2026-04-29 审查修订**：原假说防的是"文件不存在"，但消费侧概率分布反过来：
  - "文件不存在"概率低（任务一轮没跑就撞 critical / 文件被外部删 / worker 写盘失败积累）
  - "文件陈旧"概率中-高（worker 异步刷新 + last-write-wins，fork 时刻 worker 队列里可能还有 pending turn 没写完）
  - "陈旧"比"不存在"更危险：fork 表面成功 → 新 thread system prompt 缺最近上下文 → 重做 / 走错方向 / 不知任务进度 → **沉默失败比明确失败更难发现**，烧配额烧得更隐蔽
- 生产观察：F2 链路 0 触发；但 fork 前预检文件是基本工程实践，typical
- 结论：**进入 Phase 1.8d 实施（修法 4：保留预检 + 加 fork 前 flush worker）**

**风险 6 · thread 还活着但事件源断了（已实证，进入 Phase 1.7）**

- 假说：LLM stream 中断 / 工具回执丢失 / 网络抖动导致后端推送停止；thread 进程没崩，status 仍是 working 类（`thinking` / `responding` / `running` / `editing` / `syncing`）；token 用量不到 critical（F1 等不到），status 也不变 'error'（F2 等不到）→ **静默死锁**
- 代码核实：`stores/thread-sync-helpers.js::handleBridgeEvent` (line 335) 是后端事件唯一入口，所有 thread 相关事件（tokenusage/updated、turn/completed、item/started、item/completed、textdelta、outputdelta、thread patch 等）都过这里且带 `eventThreadId`。可在入口处统一记录 `lastEventTsByThread[tid] = now`，任何后端推送都会刷新；stream 真断时该时间戳停止更新
- 生产观察：用户实际遇到，普通对话 thread 工作中静默 1 分钟以上无反馈；用户手动发"继续"消息后 agent 立刻恢复；无 taskId 场景（§2.3 task-only 过滤导致 F1/F2 都不监控这个 thread）
- 结论：**已实证，进入 Phase 1.7**——独立于 useAutoContinue 链路（不受 §2.3 task-only 约束），监所有 thread

**风险 7 · agent 假完成（Phase 3.10 曾计划部分覆盖，当前已取消）**

- 现象：thread 回 idle，agent 输出"我做完了 X"但用户判断没真完成
- 历史方案曾计划通过 Phase 3.10 长任务进度协议部分覆盖；当前源码已移除 progress/done 文件协议和前端 watchdog。
- 当前处理方向：agent 假完成不再归入前端续命系统；应由 DAG node status / final output / 上层评估或 review 机制发现。

**风险 8 · agent 死循环 / 反复调同一工具（不在续命系统范畴 · 仅登记）**

- 现象：agent 反复调同一工具或在小范围打转
- 续命系统不覆盖：状态正常 + 事件源活跃，watchdog 也不会触发
- 出口：agent 行为监督层 / review 层，**不在本计划范围**

**风险 9 · fuse 自愈静默（typical 可观测性 · 进入 1.8e）**

- 现象：全局 fuse 跳闸时一次性 alert + logError，60s 滑窗自愈时**无任何提示**
- 运维 / 用户不知道当前是否还在保险丝里
- 修法：自愈时打一行 `auto_continue.fuse_recovered` info 日志，几行代码

### 3.6 代码层面识别的设计风险（生产未观察到，不立即处理）

> **2026-04-29 复核纠正**：之前此节写的"4-28 fuse_blown 15 次 / 4-29 4 次"是 grep 误判（用户点击含 fuse_blown 字样文本触发的 `chat.fileRef.click.no_ref_node` 事件被误算）。实测 4-28 ~ 4-29 全部日志里前端 `auto_continue.*` 真实事件 = **0 条**——Phase 1.x 自动续命系统建好后**还没在生产里真跑过**。本节保留以下风险条目供"未来真出现时启用"，但当前**不进 Phase 1.6 也不修代码**。

**风险 1 · F2 → recover 假成功死循环**

- 假说：若 `recoverThread` 表面成功但底层 state 未持久化，F2 会反复触发→"假成功"→链路结束→下次 status 同步又 'error'→再次触发，最终 60s/20 跳闸
- 代码核实：`internal/module/thread/lifecycle.go::Resume` 确实有 swallow 模式（`persistThreadState` 失败仍 `publishThreadStarted` + return resumed），日志 "thread: resume persist failed, continuing with event emission" 在生产里出现 14 次属实
- **但**：`thread/recover` RPC 走的是 `internal/module/thread/lifecycle_fork.go::Recover`，**不是** lifecycle.go::Resume；`lifecycle_fork.go::Recover` 已正确返回 persist 错误（行 153-154），**没有 swallow**。所以 F2 路径上不会出现"假成功"
- 结论：bug 不存在于 F2 路径。Resume 的 swallow 是另一个独立设计选择（startThread/startup 流程），不影响自动续命

**风险 2 · 用户主动 stop 被 F2 覆盖**

- 假说：`stopThread` 自身不写 status，由后端推回；若 interrupt 处理过程中 status 瞬间到 'error'，F2 会自动 fork 覆盖用户意图
- 当前无 `manualAbort` 抑制位区分"用户主动停"vs"真错误"
- 生产观察：F2 链路全程 0 触发，未观察到此场景；per-thread 1 次闸也限制了即便发生最多被续一次
- 结论：风险存在但未爆。等真观察到 `stopThread` 后立刻被 F2 续的日志再启动

**风险 3 · 永久错误未识别 → 重试浪费配额**

- 假说：401 / 403 / quota_exhausted / payment_required 等永久错误，B1 重试 3 次浪费配额；F2 看到 status='error' 也会一直 fork 至 fuse_blown
- 当前 B1 `isRetryableLaunchError` 只识别 6 个 transient 关键字，未做 transient/permanent 分类
- 生产观察：日志全文 grep `401`/`403`/`quota`/`payment` = 0；用户最近未遇到账号/配额问题
- 结论：风险存在但未爆。等真出现账号挂或配额耗尽再启动

**风险 4 · 429 rate limit 短退避不够**

- 假说：B1 退避是 `attempt × 2s`（最长 4s），429 通常需要 60s+
- 生产观察：日志 grep `429` / `rate limit` / `too many requests` = 0
- 结论：等真撞到再启动

**风险 5 · handoff 文件缺失时 fork 失败浪费一次配额**

- 假说：fork 前不验证 `handoff/tasks/<taskId>.md` 存在性，缺失时 fork 失败但已消耗一次 per-thread 闸
- 生产观察：F2 链路 0 触发，未观察到
- 结论：等真有人遇到再启动

**风险 6 · thread 还活着但事件源断了（已实证，进入 Phase 1.7）**

- 假说：LLM stream 中断 / 工具回执丢失 / 网络抖动导致后端推送停止；thread 进程没崩，status 仍是 working 类（`thinking` / `responding` / `running` / `editing` / `syncing`）；token 用量不到 critical（F1 等不到），status 也不变 'error'（F2 等不到）→ **静默死锁**
- 代码核实：`stores/thread-sync-helpers.js::handleBridgeEvent` (line 335) 是后端事件唯一入口，所有 thread 相关事件（tokenusage/updated、turn/completed、item/started、item/completed、textdelta、outputdelta、thread patch 等）都过这里且带 `eventThreadId`。可在入口处统一记录 `lastEventTsByThread[tid] = now`，任何后端推送都会刷新；stream 真断时该时间戳停止更新
- 生产观察：用户实际遇到，普通对话 thread 工作中静默 1 分钟以上无反馈；用户手动发"继续"消息后 agent 立刻恢复；无 taskId 场景（§2.3 task-only 过滤导致 F1/F2 都不监控这个 thread）
- 结论：**已实证，进入 Phase 1.7**——独立于 useAutoContinue 链路（不受 §2.3 task-only 约束），监所有 thread

## 4. 频率限制（精简版 · 2 层闸）

> **2026-04-28 review 决策**：原计划 7 层闸（per-task 滑窗 / per-task 累计 / recover 冷却 / 用户静默期）属于过度设计 ——

### 4.1 闸门设计

| 闸 | 维度 | 数值 | 触达后行为 |
|---|---|---|---|
| 偏好开关 | `taskHandoff.autoContinueAuto` / `autoContinueAttached`（Phase 2.4 拆两组，详 §3.5；在 useAutoContinuePref，不在闸门模块）| bool×2 | 对应 false 时整条链路跳过 |
| 单 thread 续接上限 | per source threadId | 1 次 | 静默 skip（reason `thread_already_continued`） |
| 族维度限频（c）| `rootTaskId` 或 `ParentAgentID` | 5min 内 5 次（数值落地敲定）| 静默 skip（reason `family_limit`），防链路递进 / 主 agent 反复派失败 sub-agent |
| 全局保险丝 | 全应用 | **5min 内 15 次**（原 60s/20 改，详 §4.3 慢失控数值算式）| 静默 skip + `fuseBlown:true`，由 useAutoContinue 决定是否 alert / logError |

### 4.2 状态结构（在 `auto-continue-gating.js` 闭包内）
```js
const continuedSourceThreadIds = new Set();        // per-thread 1 次
const familyCounters = new Map();                   // rootTaskId/ParentAgentID -> number[]（族维度滑窗，Phase 4 启用）
const globalLog = [];                               // number[] 全局保险丝时间戳

const GLOBAL_WINDOW_MS = 5 * 60 * 1000;             // 5 分钟（原 60s 改，匹配真实失控物理节奏）
const GLOBAL_WINDOW_MAX = 15;                       // 5min/15（原 60s/20 改）
const FAMILY_WINDOW_MS = 5 * 60 * 1000;             // Phase 4 启用
const FAMILY_WINDOW_MAX = 5;                        // Phase 4 启用，数值待落地敲定
```

### 4.3 多子 agent 场景与族维度闸

**慢失控数值算式（2026-04-29 审查发现）**：

- 触发全局保险丝所需事件密度 = `GLOBAL_WINDOW_MAX / GLOBAL_WINDOW_MS`
- 原设计 60s/20 → **0.33 次/秒**
- 真实失控自然节奏：launch + cli 启动 + 跑到 critical/error 至少 10-30 秒一次 → **0.05~0.1 次/秒**
- 0.05~0.1 远低于 0.33，**60s/20 挡不住慢失控**：失控持续多久都不会触发保险丝，配额持续被烧；连原 §4.3 自己举的"10 子 agent × 60s 内全撞"= 0.17 次/秒兜底场景也兜不住

**修法 a · 拉滑窗**：60s/20 → 5min/15。触发阈值降到 0.05 次/秒，覆盖真实失控物理节奏。

**修法 c · 加族维度闸（升 Phase 4 为必需）**：

- per-thread 1 次只锁源头 thread；fork 出新 thread 后新 thread 又是新源，**链路递进失控挡不住**
- 主 agent 反复派失败 sub-agent，每个 sub-agent 都是新 source thread，per-thread 锁不住
- 族维度闸：按 `rootTaskId / ParentAgentID` 分组限频，每族 5min 内自动续接 ≤ 5 次（数值待落地敲定）
- Phase 4 原标"按需"，按上述算式属于**必需**，纳入 Step 清单

**修法 b/d/e 不做**：累计无滑窗（违反自愈哲学）/ 成本维度（工程量大，留待真见事故）/ 让 1.8b 永久错误兜（覆盖不全，慢失控不只是永久错误）。

已评估但未启用的 4 层闸（per-task 滑窗 / per-task 累计 / recover 冷却 / 用户静默期）保留为扩展点，等真见到 corner case 再 case-by-case 加。

### Phase 3 —— DAG 自动化 + 协作文件层（合并版）

> 来源：消费侧反思的两个相关缺口——
> (1) thread 内自动续命（Phase 1.7+1.8）做完后节点之间仍 100% 手动启动 = 半自动；
> (2) sharedfile 当前只在 DB，agent 协作要走 MCP 工具，不能用通用 Read/Write/Edit/Glob。
> 合并解决两层。**Source of truth = 磁盘**，DB 退为查询索引（updated_by/时间戳/List 加速）。
> 工程量 10-15 天；技术栈：后端 Go + sqlc + goroutine + 文件系统。
> 详见 team memory [dag-auto-spawn-next-node](../../../../.multi-agent/memory/projects/users-mac-desktop-agnet-super-dolphin/memory/team/project_dag_auto_spawn_next_node.md)。

**架构**：
- CompleteNode → 同事务 enqueue 下游 wakeup → dispatcher goroutine 拾起 → launch_agent → 失败 RetryWakeup 退避；reclaim cron 兜底
- sharedfile write：直接落盘 `<cwd>/.agnet/shared/<path>` (atomic tmp + rename) → store 同步更新 DB 索引
- agent 用通用 Read/Write/Edit/Glob 操作 `.agnet/shared/`；MCP `shared_file_read/write` 走同样路径
- DAG 节点间数据传递走 sharedfile 约定路径（dispatcher 把 prev 节点产出路径塞进下一节点 prompt）
