## 一、背景与动机

在 V3 平台化迁移过程中，多个模块引入了大量 worker goroutine 模式（P22 P2 Finding 系列），但部分新增的 `go method()` 调用缺乏 panic 防护。Go 的 goroutine panic 会导致整个进程 crash，对长期运行的 agent 系统是致命风险。

同时，此前的 `framework_audit.md` 审计文档标注了多个维度的违规项，需要逐一验证并修复。

本次审查目标：
1. **全量扫描** 所有裸 goroutine，确保 panic recovery 覆盖率 100%
2. **验证** fx 生命周期配置、RPC 契约、数据层安全等架构约束
3. **修复** 所有可操作的违规项，并 **验证性关闭** 已实现但被错误标记的项

**结论**: 审计文档的标注是错误的，三层防护已完整实现。

#### 4.1.1 Panic Recovery 模式

对所有 17 处裸 goroutine 采用统一的 defer/recover 包装：

```go
// 标准模式 — worker goroutine
go func() {
    defer func() {
        if rec := recover(); rec != nil {
            logger.Error("module: recovered worker_name panic", "panic", rec)
        }
    }()
    w.runWorker()
}()
```

```go
// 特殊模式 — peer_supervisor (需要保持 wg 平衡)
go func() {
    defer func() {
        if rec := recover(); rec != nil {
            s.logger.Error("peer_supervisor: recovered superviseOne panic",
                "peer", name, "panic", rec)
            wg.Done()  // ← 确保 panic 后 wg 不死锁
        }
    }()
    s.superviseOne(ctx, name, h, &wg)
}()
```

```go
// 特殊模式 — approval dispatch (需要释放 pending)
go func() {
    defer func() {
        if rec := recover(); rec != nil {
            m.logger.Error("rpc: recovered approval dispatch panic",
                "call_id", pending.callID, "panic", rec)
            m.failPending(pending, errors.New("approval dispatch panicked"))
        }
    }()
    m.dispatchApproval(ctx, bridge, server, pending, method, params)
}()
```

```go
// session_runtime.go — 可复用 helper
func (r *SessionRuntime) recoverWorkerPanic(name string) {
    if rec := recover(); rec != nil {
        r.logger.Error("session: recovered worker panic",
            "worker", name,
            "session_id", r.sessionID,
            "panic", rec,
            "stack", string(debug.Stack()),
        )
    }
}
```
