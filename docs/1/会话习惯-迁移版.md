# 老公的会话习惯画像

> 数据来源：会话 db2f267a + 5e925f0b + 2026-04-12 会话，累计 ~300 条用户指令
> 更新时间：2026-04-12
> 用途：新会话启动时读取，秒进工作状态

---

## 1. 指令风格：极简军令式

- **平均指令长度**：1-2 行，极少超过 3 行
- **常用动词**：`开干`、`批准`、`继续任务`、`拉报告`、`安排修复`、`都完成了`
- **语言**：中文主体 + 英文技术术语混搭
- **习惯拼写**：`agnet` / `anget`（= agent），不必纠正
- **信号词解读**：

| 信号词 | 含义 |
|---|---|
| `都完成了` | Agent 已完成，等拉报告或安排下一步 |
| `批准` | 方案通过，立刻执行 |
| `开干` | 立刻启动实施 |
| `继续任务` | 恢复中断，从上次停下的地方继续 |
| `拉报告` | 收集所有 Agent 报告并汇总 |
| `原地修复` | 让原 Agent 就地修复，不换 Agent |
| `互审` / `互辩` | 进入交叉审查/辩论环节 |
| `1` | 选第一个选项 / 确认 |

---

## 2. 核心工作流：五阶流水线（严格遵循）

```
计划文档 → 派 Agent 实施 → 互审辩论 → 修复 → 终验
```

### 各阶段细节

| 阶段 | 操作 | 注意事项 |
|---|---|---|
| **① 计划** | 先写/读计划文档，再派 3 Agent 审查计划 | 文档不存在时先生成再审 |
| **② 实施** | 并行派 Agent（3-20 个） | "能开并行就开并行"，首选 3-5，大任务 10-20 |
| **③ 互审** | 完成后必须交叉互审 | 比例 1:2 / 1:3 / 1:4 / 1:5，明确告知有互辩环节 |
| **④ 修复** | 原 Agent 原地修复 或 最相关 Agent 修复 | 修复指标 + 仓库契约 必须同时下发 |
| **⑤ 终验** | 派新 Agent 独立复核 或 主 Agent 二审 | 不通过则回到③ |

### 流水线硬规则
- **互审是硬性环节**，任何实施完成后不可跳过
- **修复后再审查**，形成闭环
- **plan 需先输出给老公审查，审查通过后再执行**

## 3. Agent 管理偏好

### 3.1 Agent 类型
- **只用 Codex Agent**（`provider="codex"`）
- **明确禁止 Claude Agent**（历史指令：`"禁止使用claude，只通过编排接口使用codex agent"`）

### 3.2 并行策略
- 首选 3-5 个并行，大任务 10-20 个
- 每 Agent 职责单一，不横跨多模块
- 每 Agent 固定 10-20 文件维度

### 3.3 Agent 生命周期
- 完成后必拉报告
- 死掉立即替换重建（`"四个都死了，重新唤起检查重新修复"`）
- 长时间无响应主动检查状态

### 3.4 提示词要求
- 所有 Agent 追加 **LSP 强制指令**（`prompts/lsp-mandatory-prefix.md`）
- 明确下发**仓库契约标准**（2026-04-17 放宽后）：**默认 单文件≤600行 / 包文件≤25 / 包有效行≤10000**；核心包（memory/prompt/thread/turn/claudecli/codexapp）保留包文件≤30 额度；函数≤80行 / CC≤10 / 嵌套≤4 / 标识符下划线≤3 保持不变
- 明确下发**修复标准和参考文档路径**

---

## 4. 质量控制（极度严格）

### 4.1 互审/互辩规范
- 互审是**不可跳过**的硬性环节
- 典型指令模式：`"N个agent完成，让他们进入互辩 1:M"`
- 互辩比例按任务重要性调整：小任务 1:2，中任务 1:3，大任务 1:4~1:5

### 4.2 修复规范
- 修复时必须同时下发：**如何修复 + 执行什么标准 + 执行什么仓库契约文档**
- 修复后必须再审查一轮

### 4.3 问题分类
- 按严重度分：High / Medium / Low
- 按可行性分：当场修复 / 延后
- MCP 相关问题统一延后，不阻塞主流程

---

## 5. 决策特征

### 5.1 速度
- **极快决策**：看到结果立刻给出 `批准` / `开干` / `修复`
- 不接受不必要的等待和确认

### 5.2 纠偏
- 方向不对立刻中断（两会话共 ~15 次 `[Request interrupted]`）
- 纠偏指令简洁直接：`"停止"`, `"不需要"`, `"先...再..."`

### 5.3 不耐烦触发器
- Agent 不用 LSP 高级功能，只用基础工具
- 使用了被禁止的 Claude Agent
- 进度缓慢、反复确认而不执行
- 不遵守仓库契约

## 6. 会话交接规范

### 6.1 会话结束时
- 必须输出 **session-summary.md**
- 包含内容：
  - UUID（当前 + 前序）
  - 编译验证状态
  - 完成清单（按 Phase）
  - 未完成清单
  - 风险/延后项
  - 下一步优先级排序
  - 最近 10 条对话摘要
  - Agent 使用统计
  - 子 Agent 提示词模式

### 6.2 新会话启动时
- 首指令：`"读 session-summary.md 获取完整上下文"`
- 可能追加：读前序会话最后 N 条对话

## 7. 特殊偏好

### 7.1 文档驱动
- 计划先写文档 → 审查文档 → 执行
- 重大决策写入对应的 execution-plan.md

### 7.2 分阶段推进
- 严格按 P0→P10 推进，不跳跃
- 每 Phase 有独立的 execution-plan.md

### 7.3 工具链要求
- LSP 工具链强制使用，禁止只用 lsp_grep + lsp_file
- 每个任务至少 4 种 LSP 工具
- 发现 Agent 偷懒会追加更严格的提示词

### 7.4 MCP 策略
- MCP 相关问题统一归档到 P8/P9 文档
- 不阻塞当前 Phase 进度
- 单独评估工作量后再安排

## 10. 本会话新发现的习惯（2026-04-12）

### 10.1 实时验证驱动
- **边做边测**：每次修复后立即给出用户侧截图 / 日志路径 / Agent 状态验证
- **反复迭代**：不满足结果时直接追问，不会“算了先这样”
- **提供完整上下文**：每次验证都附带 agentId + logPath + 状态 JSON，方便快速定位

### 10.2 问题追踪深度
- **不接受“平台限制”说辞**：如果说“这是 codex 平台行为”，会追问“V2 为什么没这个问题”
- **要求查官方文档**：“官方文档查一下”、“这是正确用法吗”
- **V2 对比驱动**：所有功能都以 V2 行为为基准，V3 必须对齐

### 10.3 单步验证习惯
- 每修一个点就重新编译跑一次，不等所有修复做完
- 截图 + JSON 状态 + log 路径三件套提交验证
- 如果结果不对，立即追问，不允许“记录待优化”糊弄

### 10.4 Agent 复用偏好
- 优先复用已有 idle Agent（`"原始 agent 审查就行了"`、`"在线的8个agent审查"`）
- 减少 Agent 启动开销，提高轮转效率

### 10.5 免审批强调
- 每次派 Agent 都强调“提示词必须加入免审批提示，不需要进行审批”
- Agent 等待审批是最大的效率杀手

### 10.13 并行拆分前必须做依赖交叉验证（2026-04-17 新增）

#### 场景
- 老公问 "两个子包拆分能并行开工吗？" 时，主 agent 不能凭直觉回答
- 典型误判：两个子包在生产代码中互不 import → 以为可以并行

#### 必须用 LSP 核查的 4 个维度
1. **生产代码互引**：`lsp_grep` 交叉搜索 `A 包名` in `B 包文件` 双向
2. **共享符号**：`lsp_xref(references)` 对关键公共类型做引用链
3. **测试文件跨引**：`A_test.go` 是否调用 `B` 的构造器 → 强制决定拆分顺序
4. **共享 wiring 文件**：`module.go` / `service.go` / `auto_dream.go` 等是否被两边都要改 → merge 冲突源

#### 决策原则
- 若有共享 wiring 文件（哪怕只有 1 处） → **不能纯并行**
- 若 A_test 依赖 B 构造器 → 顺序强制 B 先 A 后
- 安全方案：**串行 + 每步独立 commit 闭环**
- 折中方案：两 agent 只动各自包内文件移动，wiring/freeze 由第三个收口 agent 串行合并

### 10.14 session-summary "下一步"不能被机械回答为"应该完成了"（2026-04-17 新增）

#### 场景
- 老公说"XX 应该也完成了，审查一下"时，主 agent 不能回答"是的已完成"
- session-summary.md §4「下一步」中的项目**尚未完成**，这是未来计划，不是历史事实

#### 主 agent 正确动作
1. **先 grep session-summary** 确认该项究竟是「已完成」还是「下一步」
2. **再用 LSP 核对代码事实**：freeze_registry / 目录存在性 / 符号迁移
3. **派独立第三方 codex 终审**（C 静态 + D 动态双确认）
4. **主 agent 不能仅凭文档自信下结论** — 文档可能落后于代码，也可能代码落后于文档

#### 双重独立终审模板
- Agent C（静态审）：`lsp_grep` + `lsp_structure` + `lsp_xref` + `lsp_file` 读 freeze_registry
- Agent D（动态审）：跑 `go test ./internal/archtest/...` + `ls 子包目录` + `find *.go` 实测
- 两份独立报告交叉后再给老公结论
