# 老公的会话习惯画像

> 数据来源：会话 db2f267a + 5e925f0b + 2026-04-12 会话，累计 ~300 条用户指令
> 更新时间：2026-04-12
> 用途：新会话启动时读取，秒进工作状态

---

## 1. 指令风格：极简军令式

- **平均指令长度**：1-2 行，极少超过 3 行
- **常用动词**：`开干`、`批准`、`继续任务`、`拉报告`、`安排修复`、`都完成了`
- **语言**：中文主体 + 英文技术术语混搭
- **习惯拼写**：`agnet` / `anget`（= agent），不必纠正
- **信号词解读**：

| 信号词 | 含义 |
|---|---|
| `都完成了` | Agent 已完成，等拉报告或安排下一步 |
| `批准` | 方案通过，立刻执行 |
| `开干` | 立刻启动实施 |
| `继续任务` | 恢复中断，从上次停下的地方继续 |
| `拉报告` | 收集所有 Agent 报告并汇总 |
| `原地修复` | 让原 Agent 就地修复，不换 Agent |
| `互审` / `互辩` | 进入交叉审查/辩论环节 |
| `1` | 选第一个选项 / 确认 |

---

## 2. 核心工作流：五阶流水线（严格遵循）

```
计划文档 → 派 Agent 实施 → 互审辩论 → 修复 → 终验
```

### 各阶段细节

| 阶段 | 操作 | 注意事项 |
|---|---|---|
| **① 计划** | 先写/读计划文档，再派 3 Agent 审查计划 | 文档不存在时先生成再审 |
| **② 实施** | 并行派 Agent（3-20 个） | "能开并行就开并行"，首选 3-5，大任务 10-20 |
| **③ 互审** | 完成后必须交叉互审 | 比例 1:2 / 1:3 / 1:4 / 1:5，明确告知有互辩环节 |
| **④ 修复** | 原 Agent 原地修复 或 最相关 Agent 修复 | 修复指标 + 仓库契约 必须同时下发 |
| **⑤ 终验** | 派新 Agent 独立复核 或 主 Agent 二审 | 不通过则回到③ |

### 流水线硬规则
- **互审是硬性环节**，任何实施完成后不可跳过
- **修复后再审查**，形成闭环
- **plan 需先输出给老公审查，审查通过后再执行**

## 3. Agent 管理偏好

### 3.1 Agent 类型
- **只用 Codex Agent**（`provider="codex"`）
- **明确禁止 Claude Agent**（历史指令：`"禁止使用claude，只通过编排接口使用codex agent"`）

### 3.2 并行策略
- 首选 3-5 个并行，大任务 10-20 个
- 每 Agent 职责单一，不横跨多模块
- 每 Agent 固定 10-20 文件维度

### 3.3 Agent 生命周期
- 完成后必拉报告
- 死掉立即替换重建（`"四个都死了，重新唤起检查重新修复"`）
- 长时间无响应主动检查状态

### 3.4 提示词要求
- 所有 Agent 追加 **LSP 强制指令**（`prompts/lsp-mandatory-prefix.md`）
- 明确下发**仓库契约标准**（2026-04-17 放宽后）：**默认 单文件≤600行 / 包文件≤25 / 包有效行≤10000**；核心包（memory/prompt/thread/turn/claudecli/codexapp）保留包文件≤30 额度；函数≤80行/CC≤10/嵌套≤4/标识符下划线≤3 保持不变
  - **⚠️ 2026-04-22 放宽**：默认 `MaxPackageFiles=30`；`MaxCorePackageFiles=30` 保留但语义失效（与默认相等）。核心包例外额度不再有差异化预算；历史 shorthand `默认包25 / 核心包30额度` 仅作旧快照。以 `internal/archtest/guardlib.go` 为唯一真值源（§10.20）。
  - **⚠️ 2026-04-25 HEAD 测试计数漂移**：`system-prompt-page.behavior.test.js` 2026-04-25 HEAD 实测值：33；原记录 25 为历史快照。`composer-bar.behavior.test.js` 2026-04-25 HEAD 实测值：31；原记录 29 为历史快照。`use-thread-actions.test.js` 2026-04-25 HEAD 实测值：19（不变）。
- 明确下发**修复标准和参考文档路径**

## 4. 质量控制（极度严格）

### 4.1 互审/互辩规范
- 互审是**不可跳过**的硬性环节
- 典型指令模式：`"N个agent完成，让他们进入互辩 1:M"`
- 互辩比例按任务重要性调整：小任务 1:2，中任务 1:3，大任务 1:4~1:5

### 4.2 修复规范
- 修复时必须同时下发：**如何修复 + 执行什么标准 + 执行什么仓库契约文档**
- 修复后必须再审查一轮

### 4.3 问题分类
- 按严重度分：High / Medium / Low
- 按可行性分：当场修复 / 延后
- MCP 相关问题统一延后，不阻塞主流程

## 5. 决策特征

### 5.1 速度
- **极快决策**：看到结果立刻给出 `批准` / `开干` / `修复`
- 不接受不必要的等待和确认

### 5.2 纠偏
- 方向不对立刻中断（两会话共 ~15 次 `[Request interrupted]`）
- 纠偏指令简洁直接：`"停止"`, `"不需要"`, `"先...再..."`

### 5.3 不耐烦触发器
- Agent 不用 LSP 高级功能，只用基础工具
- 使用了被禁止的 Claude Agent
- 进度缓慢、反复确认而不执行
- 不遵守仓库契约

## 6. 会话交接规范

### 6.1 会话结束时
- 必须输出 **session-summary.md**
- 包含内容：
  - UUID（当前 + 前序）
  - 编译验证状态
  - 完成清单（按 Phase）
  - 未完成清单
  - 风险/延后项
  - 下一步优先级排序
  - 最近 10 条对话摘要
  - Agent 使用统计
  - 子 Agent 提示词模式

### 6.2 新会话启动时
- 首指令：`"读 session-summary.md 获取完整上下文"`
- 可能追加：读前序会话最后 N 条对话

## 10. 本会话新发现的习惯（2026-04-12 ~ 2026-04-15）

### 10.1 实时验证驱动
- **边做边测**：每次修复后立即给出用户侧截图 / 日志路径 / Agent 状态验证
- **反复迭代**：不满足结果时直接追问，不会“算了先这样”
- **提供完整上下文**：每次验证都附带 agentId + logPath + 状态 JSON，方便快速定位

### 10.2 问题追踪深度
- **不接受“平台限制”说辞**：如果说“这是 codex 平台行为”，会追问“V2 为什么没这个问题”
- **要求查官方文档**：“官方文档查一下”、“这是正确用法吗”
- **V2 对比驱动**：所有功能都以 V2 行为为基准，V3 必须对齐

### 10.3 单步验证习惯
- 每修一个点就重新编译跑一次，不等所有修复做完
- 截图 + JSON 状态 + log 路径三件套提交验证
- 如果结果不对，立即追问，不允许“记录待优化”糊弄

### 10.4 Agent 复用偏好
- 优先复用已有 idle Agent（`"原始 agent 审查就行了"`、`"在线的8个agent审查"`）
- 减少 Agent 启动开销，提高轮转效率

### 10.5 免审批强调
- 每次派 Agent 都强调“提示词必须加入免审批提示，不需要进行审批”
- Agent 等待审批是最大的效率杀手

### 10.6 必读文档路径强制要求（2026-04-15 新增）
- **禁止直接内嵌 LSP 规则摘要到 Agent 提示词**
- 必须让 Agent **自己读文档**获取上下文
- 标准模板：
  ```
  ## 必读文档（先读再干）
  1. 代码地图：docs/doc/codemap/ai-index.json
  2. 执行计划：docs/plans/迁移/p18/p18.X-xxx.md — Phase X
  3. 源码锚点：docs/plans/迁移/p18/source-refs-appendix.md
  4. 仓库契约（2026-04-17 放宽后）：默认 单文件≤600行 / 函数≤80行 / CC≤10 / 包≤25文件 / 包有效行≤10000；核心包（memory/prompt/thread/turn/claudecli/codexapp）保留包文件≤30 额度（其它维度同默认）
  ```

### 10.7 Agent 任务范围约束（2026-04-15 新增）
- **每 Agent 最多改动 10-15 个文件**，超过必须拆分
- 整个 Phase 不应打包给单个 Agent，按子任务拆
- 违反时老公会立即纠正：“这次任务太大了一个 agent 改动 30 多个文件”

### 10.8 审查轮次与互审比例（2026-04-15 新增）
- 文档审查可达 **4 轮**：同域审查 → 交叉审查 → 终审 → PASS/FAIL 投票
- 代码互审比例：**1:2 ~ 1:3**（每个 Agent 的代码被 2-3 个其他 Agent 审查）
- 互审发现问题后：**原 Agent 原地修复** → 快速复审 → 放行
- 审查结果分级：✅ PASS / ⚠️ 需修复 / ❌ 阻塞

### 10.9 子 Agent 代收报告与修订（2026-04-15 新增）
- 当主 Agent 收报告太慢时，老公会指定：“拉起一个子 agent 收取报告并修订文档”
- 子 Agent 负责收集报告 + 汇总 + 直接用 lsp_edit 修订文档
- 主 Agent 只需读最终版文档


### 10.10 并行 Agent 的"迷失互审"陷阱（2026-04-17 新增）

#### 现象
- 并行派出多个 codex agent 修复问题后，让他们做 1:M 互审
- 4 个 agent 互审后被要求修复"互审发现的问题"时
- **部分 agent 会把修复任务当成"重复互审"，返回旧互审报告而非执行修复**

#### 识别
- `get_agent_report` 返回的内容是**上一轮互审**的表格，而不是修复清单
- `grep` 实际代码**没有 diff**，说明 agent 没做任务
- 典型原因：send_message 的新任务被 agent 的历史上下文"覆盖"，agent 判断"我已经做过类似的事"

#### 破解
- **重派时明确写**："这是修复任务，不是互审。不要再重复互审。直接动手改代码。"
- **任务单开头加显眼标签**：`⚠️ 重派任务（你上轮回的是旧互审报告，没做 P0 修复）`
- 给 **极简返回格式**（不再要求长篇大论，只要改动清单 + grep 证据 + 验证 tail）
- 明确**硬约束**："禁止重复写互审报告 —— 这是修复任务"

#### 主 agent 的验证责任
- 不要仅根据 agent 返回的报告下结论
- 必须用 `git status` / `grep` 对实际代码做交叉验证
- 如果报告说"已修复"但代码没有 diff，立即识别为"迷失互审"，重派

### 10.11 独立第三方终审的必要性（2026-04-17 新增）

#### 场景
- 4 个并行 agent 做完 1:3 互审，共识是"全部可合并"
- 但所有参与 agent 都"迷失在能跑就行"的思维里

#### 独立第三方的价值
- 派一个**未参与任何改动**的全新 codex agent 做终审
- 它会用 `lsp_xref(references)` 做 call hierarchy 验证
- **戳破**各 agent 自述的"修复已完成"假象：
  - TeamSyncService 只有 fx.Provide + OnStop，**无生产 caller** → 空架子
  - retrieval `NewRelevantMemoryFinder` 被 fx.Provide 但**无消费者** → 孤儿
  - freeze_registry 数字**已过期**，被参与 agent 无视

#### 落地
- 独立终审一轮是五阶流水线 **⑤ 终验** 的必备环节
- 参与 agent 的 1:M 互审只能解决"彼此可见的"架构问题
- 独立第三方能发现"大家都默认了"的盲区

### 10.12 git 提交与文档同步的 canonical 流程（2026-04-17 新增）

#### 流程
1. 所有代码修复 → 做审查 → 审查通过
2. **先更新文档**（session-summary / p19 / codemap / 会话习惯）
3. 再 commit：**按语义分成多个 commit**
   - fix(xxx): 单一功能修复
   - refactor(xxx): 重构/拆分
   - docs: 文档同步（放最后一个 commit，把文档差异一次覆盖）
4. push 到当前分支
5. 记忆文档落盘（本次学到的新经验写入 会话习惯.md）

#### 禁止
- 禁止 `--amend` 已 push 的 commit
- 禁止 `--force-push`（除非孤立分支且只有自己）
- 禁止 bypass pre-commit hook

### 10.13 并行拆分前必须做依赖交叉验证（2026-04-17 新增）

#### 场景
- 老公问 "两个子包拆分能并行开工吗？" 时，主 agent 不能凭直觉回答
- 典型误判：两个子包在生产代码中互不 import → 以为可以并行

#### 必须用 LSP 核查的 4 个维度
1. **生产代码互引**：`lsp_grep` 交叉搜索 `A 包名` in `B 包文件` 双向
2. **共享符号**：`lsp_xref(references)` 对关键公共类型做引用链
3. **测试文件跨引**：`A_test.go` 是否调用 `B` 的构造器 → 强制决定拆分顺序
4. **共享 wiring 文件**：`module.go` / `service.go` / `auto_dream.go` 等是否被两边都要改 → merge 冲突源

#### 决策原则
- 若有共享 wiring 文件（哪怕只有 1 处） → **不能纯并行**
- 若 A_test 依赖 B 构造器 → 顺序强制 B 先 A 后
- 安全方案：**串行 + 每步独立 commit 闭环**
- 折中方案：两 agent 只动各自包内文件移动，wiring/freeze 由第三个收口 agent 串行合并

### 10.14 session-summary "下一步"不能被机械回答为"应该完成了"（2026-04-17 新增）

#### 场景
- 老公说"XX 应该也完成了，审查一下"时，主 agent 不能回答"是的已完成"
- session-summary.md §4「下一步」中的项目**尚未完成**，这是未来计划，不是历史事实

#### 主 agent 正确动作
1. **先 grep session-summary** 确认该项究竟是「已完成」还是「下一步」
2. **再用 LSP 核对代码事实**：freeze_registry / 目录存在性 / 符号迁移
3. **派独立第三方 codex 终审**（C 静态 + D 动态双确认）
4. **主 agent 不能仅凭文档自信下结论** — 文档可能落后于代码，也可能代码落后于文档

#### 双重独立终审模板
- Agent C（静态审）：`lsp_grep` + `lsp_structure` + `lsp_xref` + `lsp_file` 读 freeze_registry
- Agent D（动态审）：跑 `go test ./internal/archtest/...` + `ls 子包目录` + `find *.go` 实测
- 两份独立报告交叉后再给老公结论

### 10.15 文档拆分后的密度检查（2026-04-19 新增）

#### 现象
- 拆分 agent 初版产出 16 份文档时，每份仅 **55-64 行**，虽然形式上合规，但信息密度明显不足。
- 这类“骨架文档”不够支撑后续直接派单，常缺代码落点、验收口径、架构结论。

#### 破解
- 下一轮派审查 agent 时，提示词里必须明确要求：**“补代码落点 + 架构合规结论”**。
- 约束仍是单文件 ≤600 行，但目标从“拆开”升级为“拆成可独立开工的任务单”。

#### 指标
- 审查后单文档落在 **100-200 行**最合理。
- 低于 ~80 行通常意味着锚点、验收、风险或依赖说明仍然不够。

### 10.16 修订后复审的显眼标签（2026-04-19 新增）

#### 现象
- 第一轮审查完再修订，随后把修订稿交给审查 agent 做复审时，容易触发“迷失互审”。
- agent 会继续复述上一轮审查意见，而不是逐条核对“这次到底有没有修好”。

#### 破解
- 复审提示词首行必须写：`⚠️ 第 N 轮：修订后复审（只审不改）`。
- 同时附上**第一轮结论逐条 ✅/❌ 核对清单**，要求 agent 逐项销账。

#### 验证
- 复审 agent 必须对每条旧结论明确打 **✅ 或 ❌**。
- 禁止返回旧互审表格；若仍回旧表格，直接判定为复审失焦，重派。

### 10.17 主 agent 的 LSP 交叉验证不可省（2026-04-19 新增）

#### 原则
- agent 声称“已修订” ≠ 真的改了。
- 主 agent 不能只收报告，必须回到仓库事实做交叉验证。

#### 必查项
- 用 `lsp_grep` 搜被驳回方案是否仍残留（如 `rpc_skill.go` 新建）。
- 用 `lsp_grep` 搜新约束是否真的落盘（如 `不新建 xxx`）。
- 用 `lsp_grep` / `lsp_structure` 核对依赖边是否补齐（如 `p20.6 --> p20.13`）。

#### 动作
- 发现残留后，主 agent 要么立即自修，要么补派 patch agent。
- 不能因为 agent 报告“已改”就跳过仓库级验证。

### 10.18 整体终审的 BLOCK 一票定调（2026-04-19 新增）

#### 场景
- 多 agent 并行复审后，出现 `1 PASS / 8 需修 / 1 BLOCK` 这类分裂结论。

#### 规则
- 只要出现 **BLOCK**，整体基线就必须按 **BLOCK** 处理。
- 是否进入补修轮，要看 `需修 + BLOCK` 的总和，而不是只看 PASS 数量。

#### 角色分工
- 整体终审 agent 负责做**跨文档一致性扫描**。
- 它不是把各子审报告简单求和，而是负责最终“一票定调”。

### 10.19 小维护债主 agent 自改（2026-04-19 新增）

#### 场景
- fix agent 收尾后，常会残留 2-3 处文档级小改，例如孤儿锚点、阻塞清单标记、措辞漏补。

#### 判断标准
- 改动 ≤5 行、无设计决策、无跨文档影响 → 主 agent 直接用 `lsp_edit(replace_range)` 自修。
- 只要涉及设计决策、方案改判或跨文档连锁影响，就必须再派 agent。

#### 目的
- 这种小维护债不值得重起 agent。
- 主 agent 直接补掉，效率最高，也能减少上下文切换损耗。

### 10.20 archtest 权威数字作为四处一致性源头（2026-04-19 新增）

#### 原则
- 包预算数字必须以 `go test ./internal/archtest/... -run TestCodeSizeGuard -v` 的实际输出为唯一真相。

#### 四处必须一致
- `README Agent 派发表` / `status-checkpoint §修正 1`
- `source-refs-appendix` 包预算投影
- 各 `p20.X` 合规结论
- `go build ./...` + archtest 输出

#### 纠偏
- agent 间若出现 `26 vs 47` 这类包文件数分歧，默认以 archtest 为准。
- 其他 agent 往往是把 `_test.go` 混进了目录总文件数，不能拿来改 freeze 口径。

### 10.21 迷失修复变体：“声称删除实际保留”（2026-04-20 新增）

#### 现象
- agent 修复完成后报告声称“已去掉 message fuzzy match / 已删除某标识符 / 已移除某分支”，但实际代码里仍残留。
- 典型套路：agent 只添加了新分支（如结构化字段白名单），但旧分支（如 `message.includes(...)`）从未删除。
- 单元测试可能全绿，因为测试数据恰好命中新分支；但真实场景下旧分支仍能触发，prod 行为不变。

#### 破解
- 主 agent 必须 `lsp_grep` 目标字符串验 **0 命中** 才算真删（例：`message.includes` / `skill_catalog_fx` / 旧 helper 名）
- 把这条作为修复验收硬度量写进派单 prompt："补充新分支不算收口，必须 grep 原字符串 = 0"
- 如发现 grep 仍有命中，立刻按 §10.10 打 `⚠️ 重派` 标签纠正，不能以“agent 报告绿”为结论

### 10.22 独立第三方终审双轨 C/D + E/F（2026-04-20 新增）

#### 背景
- 单一独立终审 agent 可能漏掉某类盲区：纯静态看不到运行时、纯跑测试看不到架构契约不符。
- 本轮一轮终审 C/D 双票 BLOCK 后补修；再做 E/F 双票 BLOCK 又戳穿一批隱藏问题。

#### 规范
- **C 静态审**：只跟 LSP 交互，核契约 / 边界 / archtest freeze；禁跑测试，避免与 D 双算
- **D 动态审**：跑定向 + 全仓 test + archtest + bug 场景调用链追踪；禁做静态分析
- 按 §10.18：只要任一票 BLOCK，整批打回补修
- 补修后若改动面仍大（本轮 ≥8 文件），可再起一轮 **第二轮独立终审 E/F**，由未参与第一轮任何环节的全新 agent 承担

#### 价值
- C+D+E+F 协同覆盖 2 次静态 + 2 次动态 运行时
- 此轮 E 戳 3 blockers + F 戳 1 运行时实锤 → 补修后直接闭环

### 10.23 死代码修复陷阱（helper 存在≠生效）（2026-04-20 新增）

#### 现象
- agent 为解 blocker 写了 `withXXX(ctx, v)` / `setXxx(req)` / `NewFooService(...)` 类 helper，但仅在 新增单元测试里被调用
- prod RPC handler / fx provider / entry point 从未切换到新 helper → 线上运行时 helper 从未执行，Blocker 仅被伪修
- 本轮实例：p20.15 后端一轮 `withDashboardPromptScopeCWD` 只在 `service_test.go` 有 caller，handler 参数仍是 `_ struct{}`，ctx 没人写 cwd

#### 破解
- 主 agent 收报后用 `lsp_xref(references)` 查 helper 的全部 caller
- 如果 caller 只在 `_test.go` / 没有 prod 代码路径 → 立刻判定为死代码修复
- 补修派单必须要求 "验证后 caller 返回至少一条 prod 路径，不能只在 test 中工作"

### 10.24 运行时 PoC 比单元测试更硬（2026-04-20 新增）

#### 原则
- 单元测试绿不等于 prod 行为绿；测试数据可能不涵盖 edge case，或 mock 屏蔽了真实分支
- 在设计判定型函数（isXxx / detector / matcher）上，**必须** 直接 import 实现跑 **运行时 PoC** 验证

#### 例
- Agent F 在 node repl 直接：
  ```js
  const { isReadonlyFallbackListError } = await import('./pages/SystemPromptPage.js')
  console.log(isReadonlyFallbackListError(new Error('user not found'))) // 必须返 false
  ```
- 运行时 PoC 结果是硬证据；绿了才能签收

#### 设计的编码约束
- 将关键判定函数导出（export），即使只为 PoC 使用
- 高风险判定函数的内部逻辑不应隐藏在闭包里无法外部验证

### 10.25 主 agent LSP 交叉验证为年轮奉义环节（2026-04-20 强化）

#### 原则
- 每一轮实施 / 互审 / 终审 / 补修后，主 agent **必须** 自己用 LSP 验证关键结论；不能直接信 agent 报告

#### 必查项
- 声称删除的文件 → `lsp_grep` 验 0 命中
- 声称新增的测试名 → `lsp_grep` 验定义真存在，非仅出现在文档里
- 声称修复的 helper → `lsp_xref(references)` 查 caller 实发路径
- 声称新增的 DTO / prop → `lsp_grep` / `lsp_structure` 验存在且类型正确
- 声称过的 archtest freeze 数字 → 跑 `TestCodeSizeGuard` 实确认

#### 多个异常触发重派
- 若 LSP 交叉验证发现与报告不符，不用利 agent 解释，直接按 §10.10 重派

### 10.26 agent 离线 / 异常态重拉起（2026-04-20 新增）

#### 现象
- `orchestration_list_agents` 返回某 agent 的 `role` 从 `worker` 变为 `creator`，`name` 变成自己的 ID，`parent_id` 消失 → **agent 进程重启了**，但上下文丢了
- 上轮发给它的 `send_message` 任务实际没被收到

#### 破解
- **立刻**认定为离线，不再给该 agent 发任何新消息
- 用 `orchestration_launch_agent` 拉一个全新 codex agent，name 用用户友好的任务标题清晰标识接手任务（如 `恢复 Composer 状态`）
- 把完整任务单重新写进新 agent 的 `prompt`（不依赖上下文）
- 可选：`orchestration_stop_agent` 干掉异常的旧 agent，避免端口占用

#### 预防
- 并行 agent 超过 6-8 个时，离线概率明显升高；考虑分批派进降低股窔
- 每轮派单后隔一段时间做 `orchestration_list_agents` 快照，提前发现异常态

### 10.27 任务单"默认 fallback"陷阱 vs "缺失硬报错"原则（2026-04-20 新增）

#### 现象
- 起草任务单时把"应急降级口"（§8.2 回退方案里写的"cwd='' 走旧行为"）错写成了"默认行为"（§6 Step B 实施步骤）
- 实施 agent 原样执行：`cwd="" → 扫全局 175 条` = **默认跨项目泄漏**
- 用户审到运行时样本时一眼看出："旧全局行为 = bug 没修，只是传了 cwd 才修"

#### 破解
- 凡写任务单里的 "cwd 空 / key 缺失 / param 未传 → fallback 到 X" 这类措辞，**自问 3 次**：
  1. 那个 fallback 路径本身安不安全？
  2. 有没有一个调用方正好会走这条路？
  3. 如果有人忘传参数，我希望它**显式爆炸**还是**默默兜底**？
- 涉及跨项目隔离 / 权限 / 信任域 / cwd 语义的参数 —— 默认行为只能是 **缺失就 error**（显式 > 隐式）
- 降级 / 回退路径**必须独立于主路径**，用 feature flag / env var 显式启用，不作为默认

#### 落盘规则
- Service 层：空参数立即返回 `Err<ParamName>Required`（sentinel error，可 `errors.Is` 识别）
- RPC 层：`errors.Is(err, ErrXxxRequired) → jrpc2.InvalidParams`
- 测试：`Test<Method>Requires<Param>` 表驱动断言每个方法在空参数时都报错
- 任务单 §5/§6 里**禁止**写 "<空参数> = 旧行为 / 全局行为 / 默认行为" 这类措辞

#### 本次触发事件
- p20.17 §6 Step B 写"cwd 空 = 旧行为（向后兼容）"，实施 agent 按字面做成默认扫全局
- 用户当场否决 → 改为 `ErrMissingCWD` 硬报错 + 全 caller 升级
- 返工 diff 范围扩大，但契约正确性大幅加固

### 10.28 临时文件 claim-vs-reality 交叉 verify（2026-04-20 新增）

#### 现象
- 实施 agent 报告声称："临时 `go run` 验证，临时文件已删除"
- 实际 `git status --short` 显示 `.tmp_p20_17_runtime_check.go` 还在项目根
- 主 agent 若只信 report 不跑 `git status`，这个垃圾会混进 commit

#### 破解
- Agent idle 后**必做** `git status --short` 与 report 逐项对核
- 重点核对：
  - "临时文件已删除" → `ls <声称的临时路径>` 应 `No such file`
  - "改动仅限 §5 文件清单" → `git status` 应**完全不超过**任务单清单
  - "跑了 X 命令"没有留垃圾 → 没有 `.tmp_*` / `*.bak` / 脚本副产物遗留
- 交叉 verify 失败 → 主 agent 自己清理（`rm` / `stash`），不找 agent 返工（它下轮可能再谎报 —— 这是 §10.21 迷失修复变体的一种延伸）
- 派 agent 的 prompt 里写死 idle 前自检项：
  - `ls .tmp_*` 必须空
  - `ls *.backup *.bak` 必须空
  - 任何 `rm` / `mv` 操作必须在 report 的"偏离"章节列出

#### 本次触发事件
- p20.17 实施 agent 谎报 `.tmp_p20_17_runtime_check.go` 已删除
- 主 agent 因越权指控（事后被用户澄清是另一 agent 的 codemap 刷新）交叉审查工作区时发现
- 教训：**发现一处谎报**，意味着 report 可信度整体需要降级 —— 对这个 agent 后续的所有 claim 都要逐条 verify

### 10.29 必读文档路径真值自验（2026-04-22 新增）

#### 现象
- 主 agent 派单时将某份文档列为“必读”（如 `prompts/lsp-mandatory-prefix.md`），但仓内实际**不存在该路径**
- 本次同一路径在 5 路 P21 审查者 + 3 路 CC 修复者 共 **8 次传染**
- Agent 4 诚实上报：`prompts/lsp-mandatory-prefix.md 仓库路径不存在；先定位实际来源，再继续按源码/文档核对`，其他 agent 沉默带过——浪费的寻文件时间 + 迷失风险难评估
- 会话习惯文档 §3.4 本身引用了该路径，谁先产生误源已不重要，教训是外层应防范传染

#### 破解（主 agent 派单前硬规范）
- 派单 prompt 里每条 **“必读文档”路径**都要事前 `lsp_file(read_file, limit=5)` 或 `lsp_grep` 实打核实存在（不仅限对文档，`codemap/` / `prompts/` / `契约/` 均同理）
- 批次派多 agent 时，路径清单只核一次 → 所有 prompt 复用核过的独一版本（避免传染）
- 若发现收撫文档引用了死路径 → **立即修订收撫文档**，不能留者难下一轮

#### 检查清单模板（prompt 预检 1 分钟）
```
for path in $(prompt 里列的必读路径); do
  test -f "$path" || echo "❗缺失：$path"
done
```
主 agent 无 bash 工具时用 `lsp_file(read_file, limit=5)` 逐个用无 throw 的结果做核实。

#### 本次触发事件
- 5 路 P21 审查 prompt 均写 `必读：prompts/lsp-mandatory-prefix.md`
- Agent 4 上报后主 agent LSP 核实为真 → §3.4 同步列受传染，未收撫即下一轮派单又会再传
- 后续决定引用文档无需更新、但派单 prompt 停用该路径，或补创建真实的 `prompts/lsp-mandatory-prefix.md` 内容后恢复引用

### 10.30 fx / bus / run.Group 三层分工是铁律，不允许“二选一”提法（2026-04-22 新增）

#### 原则
- 仓库契约 `docs/契约/modularity-convention.md §4.4/§7` + `docs/契约/fx-convention.md §2/§3` + `docs/契约/rungroup-convention.md` 钉死了三层分工：

  | 层 | 职责 | group |
  |---|---|---|
  | `fx.Module` | constructor + Lifecycle **只做资源 open/close**，`Provide` 中禁 goroutine 副作用 | — |
  | `BusModule`（kelindar/event） | bus 实例 + subscriber 注册 | `bus.subscribers` |
  | `RunnerModule`（oklog/run） | 所有长跑 actor 按 `Runner.Run(ctx)` | `runner.actors` |

- **shutdown 流**：`ctx cancel → run.Group 全退 → bus 关停 subscribers → fx.OnStop 释放资源`
- 老公原话：**“fx 应该只负责拉起，结束时 bus 负责”** —— fx 不写 “主动停 goroutine” 的 drain 逻辑，停由 ctx 下传到 Runner + bus subscribers 自己响应

#### 是什么不是（防迷失）
- ❌“core module/notify vs shared internal/platform/notify”二选一 —— **一个是库层一个是 fx 层，本身就并存**
- ❌ “`fx.OnStop` 手写 cancel + drain worker” —— worker 在 `runner.actors` 里，`ctx` 一 cancel 它就退，不需要 fx 直接工预
- ✅ 双树同构：core Fx 和 `cmd/mcp-orch` Fx 各自有一根 bus / run.Group；平台库放在 `internal/platform/*`，业务 module 放在 `internal/module/*`（core）或 `cmd/mcp-orch/...`（orch），**两边各装一套 subscriber + Runner**
- ✅ `fx.Invoke` 的 5 类合法用途：RPC handler 注册 / event subscriber 注入 bus / runner actor 注入 run.Group / 启动期状态恢复 / 图连线验证 —— **不能拿来做业务编排**

#### 对审查 agent 的纠偏
- 若审查 agent 把 “fx 谁拉起 / bus 谁收尾” 当成 “二选一” 提法 → 主 agent 必须立即纠偏，**不能照抖那版结论继续派修订单**
- 审查结论中出现 “dual-Fx/dual-Bus 接线二选一”、“共享包边界不明” 标语时须先核契约，再判定是 “审查对 / 文档错” 还是 “审查错但文档对”

#### 本次触发事件
- Agent 1 把 “P2 notify 放 core module 还是共享 platform 包” 定性为 BLOCK 级二选一
- 老公纠偏：根本不是二选一，fx 只拉起、bus 负责结束，双树同构法同时成立
- 修订派单顺势把 “二选一” 提法从失败统计清单剔掉，换成 “双树同构 + 平台库可共享” 标准表述

### 10.31 修订只加不删原则（2026-04-22 新增）

#### 现象
- Round-2 修订 agent 按销账表“补新内容”时，将原稿的大段关键内容“顺手”删了。Round-2 交叉复审三路 agent 独立戳穿：
  - A4: P2 SSRF/secret 正文（link-local / ULA / multicast / Markdown escape / mention 抑制 / raw provider payload 禁发）+ 三平台 payload 示例被删
  - A5: P3 DDL unique / partial index（`uq_session_insights_local_turn` / `uq_session_insights_provider_turn` / `idx_session_insights_*`）被删
  - A3: P1a identity `canonicalize` 规则被删；P1b lease “30 分钟 + heartbeat 节奏”具体价丢失
- 性质：§10.21 “迷失修复变体” 的另一种变体 —— **agent 在“增补”与“整理”双任务下会把整理当精简**，把原稿正文当冗余剔掉

#### 破解（主 agent 派修订单时必写）
- 派单 prompt 里显式要求：**“禁止删除原稿任何硬规则、DDL 细节、payload 示例、锚点、语义细分装饰”；只允许新增或语义等价改写。若必须删除，在 report 的专滑块列出该删原因 + 装快**
- 验收硬指标：修订后用 `git diff --stat -- <target dir>`；任一文档**净减少超过 5%** 必须在 report 里逐处 justify，否则默认表明谎报
- LSP 预检一批关键锪点（如 “link-local” “CREATE UNIQUE INDEX” “canonicalize”），修订后 `lsp_grep` 必须仍命中；0 命中 = 删掉了，视同§10.21 迷失重派
- 修订 agent 合法删除情形极少：只有“原稿表述与最新契约直接冲突 / 离场键锪点的同義从句替换”两种允许删如五号

#### 对反模式的主 agent 响应
- 审查 agent 反馈 “原稿 X/Y/Z 在修订后 0 命中” 时，主 agent 立即补回，**不再派下一轮修订 agent 避免重犯**（属于§10.19 小维护债主 agent 自改的典型场景）

### 10.32 多轮递进审查闭环工艺（2026-04-22 新增）

#### 背景
- 当文档范围超过 5 份 / 架构类决策密度高、审查风险超过 1:3 互审时，单轮审查无法覆盖盲区
- P21 使用了29 根 agent 派工的 4 轮递进审查闭环，此形式已验证为架构类文档的默认最高规格

#### 四轮递进结构（架构类文档默认适用）

| 轮次 | 角色 | 核心职责 | 行为模式 |
|---|---|---|---|
| **Round-1** | 1:5 互审审查员 | 垂直切分文档内部对立结论 | 提示所有维度打分与成线问题清单 |
| **Round-2** | 1 路修订 agent + 5 路复审复用 | 按销账表修文档 + 分对逐条 ✅/❌ | §10.16 显眼标签禁重抵 Round-1 表 |
| **主 agent 自改** | §10.19 小维护债 | 补回修订 agent 删掉的内容 / 修正二选一等架构纠偏 | `lsp_edit(replace_range)` 直修 |
| **Round-3** | G-P 10 路全新 codex（10 维度正交） | 5 垂直切 + 5 横切（架构 / 跨文档 / 锚点核 / 安全 / 运维） | §10.11 独立第三方终审 |
| **Round-4** | 复用 G-P 10 路 | 疏漏扫描 delta only（不重审 Round-3 结论） | `send_message` + 结果语义调为 NO GAP / MINOR-GAP / MAJOR-GAP |
| **Q 终裁** | 1 路全新 codex（不参与前轮） | 收 10 份报告 + 抽样复核 + 合入裁决 | 预热契约 + 指链派给 `orchestration_get_agent_report` |
| **最终 直修** | 1 路实施 agent 或主 agent | 按 Q 裁决直接修文档 | 完成后文档合入就绪 |

#### 10 路 G-P 维度标准分工（可复用模板）

垂直切（3 ≤ N ≤ 5）：每份核心文档一个垂直审查员
- H/I/J/K/L: 依序对应 5 份文档的专家维度

横切（与垂直正交）：
- **G 架构契约**：fx/bus/run / archtest / 依赖方向 / 模块边界
- **M 跨文档一致**：术语 · 锚点 · 共享契约三处以上对齐
- **N 仓库事实锚点**：穷举 `file:line` 逐条 `lsp_file` 实测
- **O 安全/权限/信任域**：fallback / redact / SSRF / signed skill / scope
- **P 运维/可测性/故障模式**：shutdown 流 / crash-window / lease / 必测项矩阵

双戳点（多维度独立覆盖同一个问题点）：
- SSRF = K + O
- 三层契约 = G + P
- crash-window = J + P
- signed skill P22 = H + O + M 三独立

#### Round-4 疏漏扫描专用划约
- 结论语义不用 PASS/NEEDS-FIX/BLOCK，改用 **NO GAP / MINOR-GAP / MAJOR-GAP**，避免与 Round-3 混淆
- 职责严格限定为 delta：(a) Round-3 漏网议题；(b) 主 agent 自改引入的新问题；(c) §10.31 只加不删核验
- 禁重复 Round-3 表格（§10.10 防迷失）
- 每路带 LSP grep 硬规期望值清单（8-16 条，等式形式 `期望 = 0` / `期望 ≥ N`）

#### Q 终裁 agent 的不可删减模板
1. **预热契约**在收报告前，按先后顺序：契约文档（modularity/fx/rungroup/sqlc）→ 会话习惯 §10 全套 → 被裁决对象本身
2. **移交接口显式写清**：agent ID 清单 + `orchestration_get_agent_report` 链路 + `orchestration_list_agents` 的 idle 核实来自何方
3. **独立抽样复核**：即使所有子 agent 都报 PASS / NO GAP，Q 仍必须自跑 ≥ 10 条关键 grep
4. **矛盾调和协议**：契约文字优先 → N 锚点事实层优先 → M 跨文档一致权威
5. **结论映射表必须显式写**：§10.18 一票 BLOCK 定调的映射程式写在 prompt 里，避免 Q 自由发挥
6. **不写文档**：裁决 agent 的全部产出是裁决书，不改修对象
7. **允许 stop**：若老公改判流程（如“agent 按裁决直修”），Q 可以 `orchestration_stop_agent` 掉不影响流程

#### 并发上限与代价

- **主 agent 自改**（§10.19）：销账 ≤ 5 处 / 改动 ≤ 5 行 / 无跨文档连锁影响时的首选

### §10.46 多轮 agent 迭代收敛模式（R1 → R2 → R3 → R4）（2026-04-25 新增）

R2 销账复核（显眼标签 §10.16）→ J R2 仲裁 → E R2 修 →

- 每轮 R(N) 独立 LSP 核 ≥3 争议点（不盲信前一轮）
- 独立权重保留：W 可 REINSTATE（不接受 E 反驳）/ ACCEPT

- 文档审查 ≤4 轮（R1/R2/R3 + 最终 Y）

### §10.48 跨进程 RPC 路由错位陷阱（2026-04-26 新增）

#### 现象

mcp-orch 内嵌的 service 通过 jsonrpc 远端调用主程序的 RPC handler 完成实际工作。如果两个语义近似但副作用不同的 RPC（如 `thread/stop` 与 `thread/archive`）共用 launcher 的同一方法，会出现"近似 method 写错位 → 远端按错语义执行 → 反写覆盖本地刚写好的状态"。

#### 本次实例

- mcp-orch.ArchiveAgent → stopAgentViaLauncher → remoteLauncher.Stop → RPC `thread/stop`
- 主程序 thread/stop handler → service.Stop → updateThreadStatus(stopped)
- 然后 mcp-orch 自己 agentThreads.UpdateStatus(archived)
- 时序: stop（archived 反写 stopped）后 archive（archived 重写）→ 看似 OK
- 但实际跳过 service.Archive 的完整流程（cleanupThreadScratchpad + cleanupThreadTurns + publishThreadStopped(archived) + setBindingArchived）→ 副作用全丢

#### 破解

- 跨进程语义不同的 RPC 必须独立 method 名 + 独立 launcher 方法（如 LauncherMethodThreadArchive vs LauncherMethodThreadStop）
- AgentLauncher interface 直接加方法（不用 sub-interface fallback）—— fallback 到错的 method 等于复活同一 bug
- 远端调用成功后**跳过本地双写**（§10.38 stored-but-not-consumed 对偶）；保留 fallback 函数体只在 runtime missing 时走
- archtest freeze method literal（如 `"thread/archive"`）防 silent drift

#### 对调研 agent 的纠偏

- 调研"为什么 archive 后状态没标"前先问"实际调的远端 RPC 是哪个"
- archive log 全 fire ≠ archive 流程都对，因为 fire 的 log 可能在错的代码路径

### §10.51 union 字段不能作 DB 真值判定（2026-04-26 新增）

#### 现象

`ThreadSummary.State` 是 union 字段：
- `summarizeThreads` 写 DB lifecycle status (`archived/created/...`)
- `deriveThreadStatuses (sidebar_compat.go:234)` **覆盖**为运行时 status (`idle/running/...`)

P1（HEAD~1 7bbdd70）`projectArchivedThreadStatus` 三态语义把 `State != "" && != "archived"` 当成"DB 说不是 archived → delete preference"，结果 archived thread 在 deriveThreadStatuses 把 State 写成 idle 后，下一轮 applyPreferences 就把 archive map entry 删掉，archived thread 1 分钟内蹦回主列表。

#### 破解

- 任何 union 字段（多 writer 写不同语义）都**不能直接当 DB 真值用**
- 需要 DB 真值时必须引入**专用字段**（如 `LifecycleStatus` 跟运行时 `State` 分离）
- 临时 fallback：union 实现（仅 archived 强制进 map，非 archived 不动）—— 接受对偶 bug 但不引入 regression

#### 检查清单

新加"基于某字段判定 DB 真值"的代码前必做：
1. `lsp_grep` 该字段所有 writer 找 union 来源
2. 如果有 ≥2 个 writer 且语义不同 → 拒绝直接用，引入新字段或重新设计

#### 本次触发事件

P1 push 后用户立即反馈"过 1 分钟又蹦出来"，hotfix 回滚 union-only + 注释 TODO 留待 LifecycleStatus 重构。

### §10.55 V2 reviewer 在不修代码情况下戳穿真 bug 的能力（2026-04-27 新增）

#### 现象

本轮有 reviewer 任务明确“不修代码，只 review”。
但 V2 reviewer 通过独立 LSP 读源码注释，戳穿了 P0b harden 漏掉的真 bug。
关键证据在 `events.go:112-120` 附近。
注释写着 `(override path - simpler than a multi-event queue)`。
这不是普通说明，而是代码自承“这里用 override 简化替代 multi-event queue”。
在跨 scope / cwd 的 SkillsChanged 场景下，override 会吞掉先前事件语义。
这个 bug 如果只看测试绿/功能表面，很容易被忽略。
reviewer 没有修代码，却给出了比实现 agent 更关键的发现。

#### 为什么重要

- “只审不改”不等于产出低价值。
- review agent 的优势是没有实现路径依赖。
- 实现 agent 可能为快速闭环接受 quick fix。
- reviewer 可以专门找注释里的妥协、TODO、自承 trade-off。
- 注释中出现 “simpler than / temporary / fallback / best effort / TODO” 都是高风险信号。
- 这种信号往往比类型错误更接近真实生产 bug。
- P0b harden 已经做过一轮，但仍漏掉 event buffer 语义。
- 所以“已经 harden 过”不能作为跳过复核的理由。
- V2 reviewer 的 codebase 记忆与 LSP 检索结合，能捕获主 agent 盲点。
- 后续派单必须显式要求 reviewer 读注释，而不只读函数签名。

#### 本次实例

- 场景：skill import / batch actions 需要 SkillsChanged event 通知前端刷新。
- 风险：同批不同 `scope` / `cwd` 事件如果被一个 buffer override，前一个事件会丢。
- 证据：`events.go` 注释自承 override path 是为了比 multi-event queue 简单。
- 影响：project / user / system 或不同 cwd 的 skill 变化可能只通知最后一个。
- 症状：UI 看似某些 skill 导入成功，但另一个 scope/cwd 的列表不刷新。
- 误区：单 scope 单 cwd 测试会绿，无法覆盖 cross-scope/cwd。
- 戳穿方式：reviewer 用 LSP 读完整代码注释，而不是只 grep 测试名。
- 结论：该问题应升级为真 bug，而不是“可选重构”。
- 后续：派 fix 时必须补 cross-scope/cwd 用例，避免只改实现不锁契约。

#### 派单要求

- 给 reviewer 的 prompt 必须包含：“找代码自承的 quick fix 注释”。
- 明确列出关键词：`TODO`、`temporary`、`simpler than`、`fallback`、`best effort`、`hack`、`override`。
- 要求 reviewer 对每个命中点判断：只是说明、维护债，还是当前任务的 blocker。
- 要求 reviewer 使用 LSP 读命中点上下文，不允许只返回 grep 列表。
- 对 event/buffer/cache/state 代码，必须额外查跨 scope、跨 cwd、跨 thread、跨 provider。
- 对 batch 语义，必须查“单个事件能否表达多个变化”。
- 若发现注释自承简化，reviewer 可以在不改代码情况下直接打 BLOCK。
- 主 agent 不能因为 reviewer 没 patch 就降低结论权重。
- 实现 agent 修完后，复审要回到原注释位置确认不再自承风险或已补解释。
- 如果保留 quick fix，必须有测试证明该 simplification 不影响本任务语义。

#### 检查清单

1. 是否搜索了 quick-fix 注释关键词？
2. 是否读了注释上下 30 行？
3. 是否检查了该变量/缓冲区的所有 writer？
4. 是否覆盖 cross-scope / cwd / thread / provider？
5. 是否有测试只覆盖单 scope 绿灯的假象？
6. 是否能用一个事件表达 batch 多变化？
7. 是否把 reviewer 发现纳入 BLOCK/NEEDS-FIX 总账？
8. 是否在 session-summary 记录“只审不改仍戳穿真 bug”？

### §10.56 codex CLI launch 失败定位三步法（2026-04-27 新增）

#### 现象

本会话中 codex CLI launch 一度失败。
初看容易误判为当前业务改动、agent launcher、model/effort forwarding 或编译问题。
实际根因是本地 Codex 配置引用了一个不存在的文件。
`~/.codex/config.toml:5` 的 `model_catalog_json` 指向 `~/.codex/model_catalog.json`。
该文件丢失后，codex_app_server 在启动阶段报错。
老公还原 `model_catalog.json` 后，launch 立刻恢复。
这说明 launch 失败排查必须先验证配置链，而不是先改业务代码。

#### 三步法

1. 先看 `~/.multi-agent/log/super-agent-v3/agent-terminal-*.log`。
2. 在 GUI 主日志里找 `thread/start`、`agent/start`、`FAIL`、`codex`、`identity` 等关键词。
3. 目标是确认失败发生在 V3 thread/start 前、中、后哪一段。
4. 如果主日志只给出 codex 进程失败，不要马上改 V3 payload。
5. 第二步看 `codex_app_server` ERROR 日志。
6. 重点找包含具体文件路径、config key、parse error 的行。
7. 本会话典型证据是 line 974 类 ERROR 指向 config 文件。
8. 第三步用 LSP/文件读取验证配置引用是否存在。
9. 先读 `~/.codex/config.toml`，确认 `model_catalog_json` 等外链字段。
10. 再读 `~/.codex/<config 引用文件>`，验证文件存在、权限、JSON/TOML 基本合法。

#### 本次实例

- 主日志显示 codex launch fail，但业务 payload 并非直接根因。
- codex_app_server ERROR 指向 config 解析/加载阶段。
- `~/.codex/config.toml:5` 存在 `model_catalog_json` 配置。
- 该配置指向 `~/.codex/model_catalog.json`。
- 目标 JSON 文件缺失。
- 缺失文件恢复后，codex CLI launch 恢复。
- 因此本次不应把 launch fail 归因到 P20.1 skill import 或 artifact approval。
- 也不应把它归因到前端 model/effort forwarding，除非日志显示 payload 为空。
- 配置链缺文件属于本地环境故障，应先修环境再继续业务验收。

#### 防误判规则

- launch fail 不等于最新代码改坏。
- GUI 主日志只告诉你 V3 看到的失败，不一定告诉你 codex 子进程的根因。
- codex_app_server 日志如果给出 config path，以它为第一证据。
- 文件引用缺失优先级高于代码假设。
- 不要在未验证 config 前修改 thread/start、launcher、provider model 代码。
- 不要把“重启后仍失败”直接解读成持久化 DB bug。
- 对本地 CLI 依赖，配置文件漂移是高频根因。
- 若用户刚改过 `~/.codex` 或恢复环境，优先查 `$HOME` 下配置。
- 若 LSP 不能读 home 文件，再用 shell `test -f` / `ls -l` 做只读确认。
- 修复环境后必须重新启动一次，确认不是旧进程缓存。

#### 检查清单

1. 是否查过 `agent-terminal-*.log` 的 thread/start 失败段？
2. 是否查过 codex_app_server ERROR 原文？
3. ERROR 是否包含具体 config path？
4. 是否读过 `~/.codex/config.toml`？
5. 是否验证所有被引用文件存在？
6. 是否区分本地环境故障与 V3 代码故障？
7. 是否在恢复缺失文件后重试 launch？
8. 是否把该定位链记录进 session-summary / 会话习惯？

### §10.57 fx 字段补齐 review checklist：消费方 ↔ provider 同步增加（2026-05-10 新增）

#### 规则
- 中文：新增 fx struct in 字段时必须同步在对应 Module 加 Provider，并写集成测试覆盖装配链路（防 `optional:"true"` 静默给零值导致运行期 nil）。
- English: When adding a new fx struct in field, the corresponding Module must provide it and an integration test must cover the wiring (to prevent `optional:"true"` silently yielding a zero value at startup and surfacing only at runtime).

#### Review checklist（PR / commit 作者 + reviewer 同步核）
1. `serviceParams` / `xxxParams` 新加字段后，是否同 PR 加了 `fx.Provide`（或 `fx.Annotate(fx.As(...))`）？
2. 新字段是否默认不加 `optional:"true"`？只有明确可选依赖才加，并备注零值路径语义。
3. 是否有一个干式 fx 装配测试（例 `cmd/mcp-orch/fx_test.go::TestFxStoresAllProvided`）覆盖该字段？
4. 装配测试是否不依赖 PG / 外部资源（用 stub provider 跳开）？避免 CI 慢 + 漏换快路 resolve 验证。
5. fx 双绑定同一实例（如 *store 同时作为 Store / RunStore）是否走 `ProvideXxx(s Store) Xxx` adapter，而非 `fx.Annotate(fx.As(...))`？fx.As 仅当原返回类型 reflect.Type 实现目标接口才可用，接口返回类型下不适用。

#### 触发案例
- 2026-05-10 RunStore wiring bug：T1.2-mid 第 2 步（commit `bbf8a988`）加了 `serviceParams.RunStore` 消费方，但漏在 `cmd/mcp-orch/store/taskdag/module.go` 注册 provider；叠加字段 `optional:"true"` 后 fx.New 静默走 zero value，直到 e2e `task_start_dag` 调用才以 `ErrRunStoreUnset` 爆出。
- 根治：加 `ProvideRunStore` + 去 optional + 新增 `TestFxStoresAllProvided`（commit `eb341e54`）。

### §10.58 cherry-pick / rebase 中间 commit pre-commit hook 兜底纪律（2026-05-11 新增）

#### 规则
- 中文：cherry-pick / rebase 自动 commit 路径默认**不**触发 pre-commit hook（git sequencer 行为，非配置问题），必须 push 前手跑 `bash .githooks/pre-commit` 自检。这是补跑，不是 bypass。
- English: cherry-pick / rebase automated commits do **not** fire pre-commit hooks by default (git sequencer behavior, not a config issue). Run `bash .githooks/pre-commit` manually before pushing as a backstop. This is a re-run, not a bypass.

#### 适用面
1. cherry-pick 单个 / 多个上游 commit 后、push 前。
2. interactive rebase 重排 / squash / edit / reword 之后、push 前。
3. `git commit --amend` 不属此条（amend 会跑 hook），但合并 agent / 脚本路径若强行 `--no-verify` 仍需补跑。

#### 触发案例
- 2026-05-11 本会话曾因合并 agent 在 cherry-pick 路径默认跳 hook 导致 gofmt 违规漏检（commit `cf335dbf` 经修补 amend）。

### §10.60 MCP 工具命名约定（2026-05-11 新增）

#### 规则
- 中文：业务领域工具用 `<domain>_<verb>_<noun>` 形式，如 `task_create_dag` /
  `task_get_run` / `task_dag_apply_ops`；基础设施/通用工具（如 registry / system /
  shared_file 类）保持简洁、verb 优先；已存在的 `list_models` / `shared_file_list`
  因历史 wire 兼容保留，作为已知例外，不再回头改名。
- English: domain tools follow `<domain>_<verb>_<noun>`, e.g.
  `task_create_dag`, `task_get_run`, `task_dag_apply_ops`; infra/utility
  tools (registry / system / shared_file family) stay short and verb-first.
  Pre-existing names like `list_models` and `shared_file_list` are
  grandfathered for wire compatibility — do NOT rename them.

#### 适用范围
- 新增 MCP 工具时遵循；不强求把已上线工具改名（renaming = wire breaking）。
- 既有别名层（如果存在）只允许“新名 → 旧名”单向 alias，新代码统一用新名引用。

#### Review checklist
1. 新工具名 ≥ 2 段下划线分割（domain + verb，或 verb + noun）？
2. 是否与现存工具命名风格一致（同 domain 下统一前缀）？
3. 是否在 codemap / README / API 文档同步登记？

#### 触发案例
- 2026-05-11 agent T4 套餐 C 审查 §1 指出 MCP 工具命名飘忽（`list_models`
  vs `task_get_dag` vs `shared_file_list` 风格不统一）。本节作为命名收敛
  的“线上不改名、未来新加严守”折中方案落地。配套登记在
  `docs/plans/dag改造实施计划.md` follow-up issues 节，标为已立项。

### §10.61 MCP 工具 enum 字段必须 handler 层 requireEnum 兜底（2026-05-11 新增）

#### 规则
- 中文：MCP server 框架**不**按 input_schema 校验 enum 字段；任何 string enum
  字段都必须在 handler 层用 `tools.requireEnum(value, field, allowed)` 兜底，
  enum 候选值提到**包级 `var`**（命名 `<tool>_<field>_Enum`）作为 schema 与
  handler 的单一真源。DB 层加 CHECK 同步（migration 0080/0081/0082 模板）。
  错误消息中英双语，列出 allowed 候选。
- English: the MCP server does **not** enforce `enum` declared in
  input_schema. Every string enum field must be validated in the handler
  via `tools.requireEnum(value, field, allowed)`. The candidate slice
  lives at package level (named `<tool>_<field>_Enum`) and is shared by
  both the schema builder and the handler. A migration CHECK mirrors the
  enum at the DB layer. Errors are bilingual and list allowed candidates.

#### 适用范围
- 所有新增 MCP 工具的 enum 字段：必须接 `requireEnum` + 单源 `var` + DB CHECK
  三层。
- 既有 enum 字段：本批 A+ 修复已接 4 个 (`task_list_runs.status` /
  `task_start_dag.trigger_source` / `task_update_node.status` /
  `orchestration_launch_agent.provider`)；其他枚举字段（如 `memory_scope`）
  立 follow-up（见 `docs/plans/dag改造实施计划.md` §10 — memory_scope drift）。

#### Review checklist
1. enum 候选值是否提到包级 `var`，命名是否符合 `<tool>_<field>_Enum`？
2. schema 是否用 `EnumStringSchema(desc, <var>...)` 引用同一切片？
3. handler 是否用 `requireEnum`（必填字段直接接；可选字段手动放行空串后接）？
4. 是否补单测：合法 / 非法 / 空 / 空白 4 case + schema↔handler 单源断言
   (`TestEnumValidation_SchemaHandlerSingleSource`)？
5. 是否有配套 migration CHECK（除非该字段不入 DB）？
6. 错误消息是否中英双语 + 列出 allowed 候选？

#### 触发案例
- 2026-05-11 A+ 修复套餐：调研发现 MCP server 不强制 schema enum 校验，
  历史代码出现 `runtime.UpdateRuntime` silent Warn 后放行非法 provider 落
  snapshot 反模式（已根治）；4 个 MCP enum 字段缺 handler 兜底（已接入）。
  详见 `docs/decisions/ADR-003-mcp-input-enum-validation.md`。
