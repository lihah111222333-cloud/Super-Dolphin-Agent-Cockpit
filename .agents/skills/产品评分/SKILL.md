# super-agent-v3 产品评分

本技能只评估 `super-agent-v3`。目标不是给出好听的分数，而是用当前仓库事实回答：产品现在处于什么水平、为什么、哪些硬门禁尚未满足、下一轮怎样以最小改动获得最大真实收益。

## 适用请求

- 给当前项目、某一版本、提交、PR、工作树或指定产品面评分。
- 做发布评估、版本对比、提分建议或修复后的复评。
- 判断桌面体验、编排、后端、前端、MCP/LSP 工具或 AI 可维护性是否达到目标等级。

不把旧计划、旧报告、文档中的示例分数或目标值当作当前事实。`7.0 -> 9.3` 只能是目标或历史主张；除非当前证据独立重现，否则不得写成已实现。

## 评分纪律

1. **当前证据优先**：当前 `HEAD`、工作树、源码、测试、守卫和可复现产品路径优先于计划、记忆、代理自报或历史 PASS。
2. **事实与判断分离**：每个分数都要同时给出证据、扣分理由和置信度；没有证据时写“未验证”，不能补成乐观推断。
3. **Fail-Fast**：构建失败、关键测试失败、协议/字段漂移、数据安全风险、静默兜底、成功误报或发布产物过期会触发硬门禁；不能用其他维度高分抵消。
4. **禁止谄媚**：不使用“非常优秀”“行业领先”等无基准修饰语。只陈述可复核事实、明确推断和证据缺口。
5. **禁止虚假精度**：没有测量就不写毫秒、成功率、吞吐、资源下降比例或“100%”。定性证据最多支撑区间分和中低置信度。
6. **最小提分闭环**：建议必须指向明确 owner、文件或产品路径、验收指标和复评命令；不得用大重写掩盖局部问题。

## 先锁定评测快照

评分前记录：

- 评测对象与范围：全仓、某产品面、版本、提交、diff 或工作树。
- `HEAD`、分支、`git status --short`，以及已有 dirty 文件；不得把用户未提交改动误算成基线版本能力。
- 当前日期、平台、构建模式和未覆盖范围。
- 对比评分时，两个版本必须使用同一维度、权重、命令、场景和门禁；无法同基准复测时，明确标为“非同基准对比”。

路径和行为取证遵循仓库 `AGENTS.md`：README -> codemap -> AI index/精确目录 -> LSP -> 源码与同包测试。涉及源码行为时，保留定位、理解、影响面、精读和 diagnostics 五类 LSP 证据；工具不可用时按仓库规则记录 blocker，不得用纯 shell 结果冒充完整 LSP 证据。

## 唯一的 100 分评分模型

先按每个子项 `0.0-10.0` 打分，再按权重折算。总分是所有加权分之和，保留一位小数。

| 维度 | 权重 | 本产品评分重点 |
|---|---:|---|
| P1 产品定位与任务价值 | 10 | 生产级多 Agent 编排与 AI-native 工程治理定位是否由真实能力支撑；核心用户任务是否清楚；功能是否形成可交付闭环，而非只展示工程组件 |
| P2 桌面前端与交互体验 | 12 | 核心任务可发现性；开始/运行/审批/取消/失败/恢复/完成状态；流式渲染一致性；错误可行动性；可访问性、布局和 Wails bridge 真实体验 |
| P3 编排运行时 | 16 | session/turn/agent 生命周期；并发隔离；取消和超时；恢复与幂等；DAG/cron/wakeup 在适用时的状态一致性；成功误报和 orphan 资源 |
| P4 MCP/LSP 与工具效能 | 12 | MCP schema/envelope；stdio 纯净；短名工具契约；多语言 LSP 定位/编辑/diagnostics；参数抽象；大目录排除；原子编辑；审批与资源释放 |
| P5 后端契约、数据与安全 | 14 | Go 边界与 Fx 组装；`internal/contract`/DTO 约束；显式类型安全；SQLite/sqlc/migration/事务；错误传播；权限、路径、命令和 secret |
| P6 Provider、Skill 与集成面 | 10 | provider adapter/home、toolbridge、skill canonical/mirror、prompt snapshot、线程恢复、凭据边界和不同 provider 语义的一致性 |
| P7 可靠性与可观测性 | 12 | fail-fast；错误分类；取消/恢复/重试；资源上限；结构化日志、状态和关联 id；故障注入、E2E 与成功误报防线 |
| P8 AI 可维护性与发布准备 | 14 | codemap/AI index；archtest/guard；字段守卫；生成物与 SSOT；测试可复现性；embed/manifest/安装；发布产物与已验证源码一致性 |

八个维度是一张评分卡，不得再并列输出另一套“通用评分”或“工程评分”。工程成熟度由 P1-P8 的加权分表达；公开发布就绪度是独立门禁结论，不是第二个分数，也不能因总分高而自动通过。

### 统一分档锚点

| 子项分 | 判定 |
|---:|---|
| 9.0-10.0 | 有当前自动化门禁和真实产品路径证据；关键失败路径已覆盖；无已知高风险缺口 |
| 7.0-8.9 | 主路径可靠且多数门禁存在，但仍有明确的边界、交互、测试或发布缺口 |
| 5.0-6.9 | 能工作，但证据不完整或关键路径依赖人工约束；存在中高风险缺口 |
| 3.0-4.9 | 关键体验或工程能力不稳定，回归防线弱，不能据此宣称生产就绪 |
| 0.1-2.9 | 大部分能力缺失、不可复现或被硬风险主导 |
| 0.0 | 该能力不存在，或在评测快照中完全不可用；不能仅因出现一个普通 warning 就机械归零 |

“未验证”不是 0 分。对未验证子项给保守区间，并降低置信度；如果它属于发布硬门禁，则发布结论保持阻断。

## 硬门禁与封顶规则

先评分，再应用门禁。必须同时展示“原始加权分”和“门禁后结论”，避免门禁掩盖真实结构性水平。

### G0 无法评估

以下任一情况成立时，不给确定总分，只给区间和缺口：

- 评测对象、版本或工作树基线无法确定。
- 关键源码行为需要 LSP 证据，但按仓库规则重试后仍不可用。
- 用户要求当前发布结论，但无法取得任何当前构建、测试或产物证据。

### G1 发布阻断

任一项成立时，`发布门禁 = BLOCKED`，总分最高显示为 `79.9`：

- 与范围匹配的编译、构建、关键测试或强制 guard 失败。
- 前端当前变更未通过 `lint + test + build`。
- 协议、DTO、schema、字段、sqlc、migration 或 provider mirror 存在已确认漂移。
- 发布/embed 产物与源码不一致，安装或启动主路径不可复现。

### G2 生产安全阻断

任一项成立时，`生产门禁 = BLOCKED`，总分最高显示为 `59.9`：

- 高危命令注入、路径穿越、secret 泄露、权限绕过或不安全写入。
- 数据事务/迁移可造成不可接受的半写入、破坏或不可恢复状态。
- 已确认的静默降级、吞错成功、失败状态被完成状态覆盖。
- 取消、超时或生命周期缺陷造成稳定可复现的资源泄漏或跨会话污染。

### G3 证据门禁

- 只引用旧报告、代理结论、空日志或单次 PASS：置信度不得高于“低”。
- 产品定位只有 README/文案、没有真实用户任务证据：P1 不得高于 `7.0`。
- 没有真实用户路径/E2E/手工复现证据：P2 不得高于 `8.0`。
- 没有并发、取消、恢复或故障注入证据：P3 不得高于 `8.0`，P7 不得高于 `8.0`。
- 没有发布包或安装验证：P8 的发布准备子项不得高于 `7.0`，公开发布结论必须为 `NOT VERIFIED`。

## 证据采集矩阵

按评测范围选择最小充分证据，不为全仓评分机械读取全仓。

| 维度 | 首选入口 | 高价值证据 |
|---|---|---|
| P1 | `README.md`、产品入口、真实用户工作流和当前 UI | 定位主张与可运行能力的映射、核心任务完成证据、产品边界和目标用户证据 |
| P2 | `frontend-app`、Wails bridge、相关 UI 状态/组件测试 | 真实任务路径、截图或手工 QA、错误/取消/恢复状态、`npm run lint && npm test && npm run build` |
| P3 | session/thread/turn/runtime、适用时 `cmd/mcp-orch` | 状态机与调用链、并发/取消/恢复测试、幂等/租约/资源释放证据 |
| P4 | `cmd/mcp-lsp`、MCP peers、`internal/mcpserver/common` | schema/协议测试、LSP definition/references/call hierarchy/diagnostics、超时和大目录测试 |
| P5 | `internal/app`、`internal/contract`、`internal/module`、`internal/platform`、`internal/store` | backend boundary registry、archtest、事务/migration/sqlc、安全边界和错误传播证据 |
| P6 | `internal/provider`、skill/runtime/thread/prompt、toolbridge | provider 生命周期、canonical/mirror、snapshot、resume/fork、凭据和集成测试 |
| P7 | 错误、事件、日志、E2E、资源与恢复路径 | 故障注入、状态一致性、关联 id、取消/重试、泄漏检查和成功误报防线 |
| P8 | `docs/doc/codemap`、`internal/archtest`、`.agents/skills`、Makefile、CI、package/embed/install | guard、地图/字段/contract/生成漂移门禁、构建产物、manifest、安装/启动和平台证据 |

全仓或发布评分优先尝试当前适用的验证集合：

```bash
make guard
make codemap-check
make project-map-check
make capcontract-check
make sqlc-verify
make build-plain
python3 scripts/validate_super_agent_skills.py
cd frontend-app && npm run lint && npm test && npm run build
```

命令不存在、超时或因环境失败时，原样记录命令、错误和影响的维度；禁止改写成 PASS。不要为了评分擅自刷新 baseline、生成物或快照，因为那会改变被评对象。

## 评测执行闭环

### Phase 1：独立评分

对每个适用维度分别输出：分数、最多 5 条关键证据、主要扣分、证据缺口、置信度，以及一项最高 ROI 的改进。不适用的维度必须说明理由，并重新归一化权重或同时给出“局部评分”，不得默默按满分处理。

### Phase 2：交叉裁决

检查以下冲突：

- 文档主张与源码/测试冲突。
- 单元测试通过但真实产品路径失败。
- 本地源码通过但 embed、sidecar 或安装产物过期。
- 平均分较高但存在 G1/G2 门禁。
- 改进建议引入新层、双写、第三方重依赖或跨层耦合，却没有量化收益。

只有存在真实架构分歧且用户要求设计落盘时，才建议 ADR；不要为普通局部修复制造 ADR。

### Phase 3：提分计划

按 `收益 / 风险 / 工作量` 排序，最多给 5 项：

- P0：解除安全或发布硬门禁。
- P1：修复主用户路径、成功误报、状态一致性或高频性能问题。
- P2：补足治理、可观测性、体验细节或低频风险。

每项必须包含：问题、证据、最小改动面、预计影响维度、验收场景、验证命令。预计提分只能写区间，不承诺目标分。

### Phase 4：同基准复评

修复后复用相同快照定义、场景、命令、权重和门禁；展示前后证据差异。只有验证结果和用户路径都改善时才提高对应分数。测试数量增加、代码量增加或文档更新本身不等于产品提分。

## 多代理使用边界

评分本身不要求固定数量的 Agent，也不强制绑定 DAG。只有用户明确要求子代理、并行评审或当前编排规则明确允许时，才可按互不重叠的 P1-P8 维度分派独立取证；主代理负责统一快照、同基准校准、裁决重复/冲突证据并给出最终分数。不得把多个 Agent 的平均意见当成客观证据。

- 门禁后结论：x.x/100 或区间
- 产品成熟度：优秀 / 良好 / 有条件可用 / 不成熟
- 公开发布结论：PASS / CONDITIONAL / BLOCKED / NOT VERIFIED
- 发布门禁：PASS / BLOCKED / NOT VERIFIED
- 生产门禁：PASS / BLOCKED / NOT VERIFIED

- 评测快照：分支、HEAD、工作树、日期、范围

## 分项评分
| 维度 | 权重 | 分数 | 加权分 | 置信度 | 核心证据 | 主要扣分 |

## 硬门禁
| 门禁 | 状态 | 证据 | 解除条件 |

## Top 扣分项

## 最小提分闭环

## 完成判定

只有以下条件同时满足，才能称本轮评分完成：

- 快照、范围和 dirty-worktree caveat 已记录。
- 每个分数都有当前证据或明确的未验证标记。
- 原始分、门禁后结论、置信度和发布状态没有混写。
- 已确认问题与证据缺口分开陈述。
- 提分项可执行、可验收、可按同基准复评。
- 没有把目标值、历史案例、代理共识或空 PASS 当作当前产品事实。
