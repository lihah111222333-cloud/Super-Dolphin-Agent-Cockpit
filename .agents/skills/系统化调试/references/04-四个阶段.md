进入下一阶段前，你必须完成当前阶段。

### 阶段 1：根因调查

**尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含精确解决方向
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 能否可靠触发？
   - 精确步骤是什么？
   - 是否每次都发生？
   - 如果不可复现 → 收集更多数据，不要猜

3. **检查最近变更**
   - 哪些变更可能导致这个问题？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件（CI → build → signing，API → service → database）时：**

   **提出修复前，添加诊断性仪表：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误位于很深的调用栈中：**

   查看本目录中的 `root-cause-tracing.md`，了解完整的向后追踪技术。

   **快速版本：**
   - 坏值从哪里产生？
   - 是谁用坏值调用了这里？
   - 继续向上追踪，直到找到来源
   - 在来源修复，而不是在症状处修复

### 阶段 2：模式分析

**修复前先找到模式：**

1. **寻找可工作的示例**
   - 在同一代码库中定位相似的可工作代码
   - 与坏掉部分相似的可工作内容是什么？

2. **对照参考实现**
   - 如果在实现某种模式，完整阅读参考实现
   - 不要略读：逐行阅读
   - 完全理解模式后再应用

3. **识别差异**
   - 可工作版本与损坏版本有什么不同？
   - 列出每个差异，无论多小
   - 不要假设“那不可能有影响”

4. **理解依赖**
   - 它还需要哪些组件？
   - 需要什么设置、配置、环境？
   - 它依赖哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚说明：“我认为根因是 X，因为 Y”
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做能测试假设的最小变更
   - 一次只改变一个变量
   - 不要一次修多件事

3. **继续前验证**
   - 成功了吗？是 → 阶段 4
   - 没成功？形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 请求帮助
   - 继续研究

### 阶段 4：实现

**修根因，不修症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 能自动化就写自动测试
   - 没有框架就写一次性测试脚本
   - 修复前必须拥有
   - 使用 `superpowers:测试驱动开发` 技能编写合格的失败测试

2. **实现单一修复**
   - 解决已识别的根因
   - 一次只做一个变更
   - 不做“顺手”改进
   - 不夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 是否没有破坏其他测试？
   - 问题是否真的解决？

4. **如果修复无效**
   - 停止
   - 计数：你尝试了多少个修复？
   - 如果 < 3：回到阶段 1，带着新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 不要在没有架构讨论的情况下尝试第 4 个修复

5. **如果 3 个以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都在不同地方暴露新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每个修复都会在别处制造新症状

   **停下并质疑基本前提：**
   - 这个模式本质上是否可靠？
   - 我们是不是“纯靠惯性坚持它”？
   - 是应该重构架构，还是继续修症状？

   **尝试更多修复前，先与你的协作者讨论。**

   这不是失败的假设，而是错误的架构。
